0导读与大事记：性能仿真是什么、为什么现在

这份报告回答四个问题：性能仿真在估什么、账怎么记、框架与硬件要摸清哪些参数、以及怎么自己搭一个。全文沿一条主线展开——性能仿真 = 算子级账本（FLOPs/字节） × 硬件屋顶模型（算力/带宽） × 系统动力学（排队/批处理/缓存）。前两者决定"一步多快"，后者决定"用户等多久"。

为什么是现在？三个变化叠加：（1）模型结构进入"为推理设计"的时代——DeepSeek-V4.1-Flash 用 CED 结构让 prefill 只激活 8B 参数、KV 每 token 仅 890 字节[DSV41FLASH26]，账本从"两个矩阵乘"变成"三种注意力模式 × 跨层共享 × 四种精度"；（2）部署形态爆炸——TP/EP/PP/USP、P/D 与 E-P-D 分离、投机解码、KV 卸载，组合空间靠实测试错已经试不过来；（3）仿真器本身成熟了——从 Vidur（MLSys 2024）到 KernelSight-LM（2026），预测误差从 ~9% 进入 3-6% 区间，且不再需要对每对(模型, GPU)做画像[VIDUR24][KERNELSIGHT26]。注意 ~9% 是 Vidur 原论文在自家画像场景的口径——KernelSight-LM 同场对比实测，在 graphed vLLM 上 Vidur 的 decode 中位误差达 436%：预测精度强依赖"被测引擎与场景是否对齐"，跨场景引用误差数字必须注明口径[KERNELSIGHT26]。

[KERNELSIGHT26] Yao, Kim, Pei, et al. (AWS + Boston University). 1预备知识：一次推理到底在算什么

写给第一次接触推理性能的读者：只需要线性代数里"矩阵乘"的概念就能读完本节。

1.1 三种"钱"：FLOPs、字节、显存

GPU 干活花三种钱，所有性能问题都是这三种钱的分配问题：

资源单位由谁决定类比
计算量 FLOPs浮点运算次数（1 GFLOP = 10⁹）模型结构 × 序列长度 × batch厨师要炒多少勺
访存量 Bytes从 HBM 搬运的字节数权重/激活/KV 的字节数 × 读写次数从冷库搬多少食材
显存 GB驻留容量权重 + KV Cache + 激活峰值冷库有多大

GPU 每秒能花掉的计算钱有上限（如 H100 BF16 约 989 TFLOP/s），每秒能搬运的字节也有上限（约 3.35 TB/s）。谁先到上限谁就是瓶颈——这就是第 9 节 Roofline 的全部思想。

1.2 矩阵乘的记账公式：一切从 2MNK 开始

Transformer 里 95% 以上的 FLOPs 是矩阵乘。Y[m×n] = X[m×k] · W[k×n] 的计算量是 2·m·n·k（每个输出元素 k 次乘加），要读的字节是 m·k + n·k + m·n 个元素 × 精度字节数（权重 n·k 是大头）。于是每个 GEMM 的算术强度（每搬 1 字节做多少次浮点运算，AI = FLOPs/Bytes）≈ 2m（当 m 远大于 n,k 时，权重读取被 m 次计算摊薄）。

食堂炒菜：一筐菜（权重 W）不管炒几份都要先搬进厨房。炒 1 份（m=1）时搬运占满时间；一次炒 500 份（m=500）时搬运被摊薄、灶台（算力）成为瓶颈。batch size 就是"一次炒几份"——这就是为什么 decode 加 batch 能白赚吞吐。

由此得到后面反复用的三条基准公式（详见第 4 节逐算子展开）：

prefill 总 FLOPs      ≈ 2 × 激活参数量 × N + 注意力 O(N²) 项

1.4 KV Cache：第三种显存居民

自回归生成需要缓存每层的 Key/Value。经典 MHA 的公式是 2 × L × h_kv × d_head × s × B × 字节数；DeepSeek-V2 起的 MLA 把每层压成一个 latent 向量（V3 为 512+64 维）[DSV324]；V4.1-Flash 再叠三层压缩——序列维（每 m 个 token 合成 1 个 entry）、层维（跨层共享）、精度维（FP4）——最终 890 字节/token，比初代 DeepSeek 缩小 437 倍[DSV41FLASH26]。第 4 节给出完整分解。

本章小结（记住三句话）

  1. GEMM 记账 = 2MNK；算术强度 ≈ 2m，batch 就是摊薄权重搬运的手段。
  2. Prefill 计算受限、Decode 访存受限——同一个模型在 roofline 图上落在两个角落。
  3. 显存 = 权重 + KV + 激活峰值；三者都由 config 决定，所以仿真器天然应该 config 驱动。

2案例一：DeepSeek-V4.1-Flash 结构拆解

2026-09-10 发布、9-17 挂出技术报告的 DeepSeek-V4.1-Flash 是"为推理设计"的典型：总参数 552B（骨干）+ 196B（Engram 记忆），但 prefill 每 token 只激活 8B、decode 激活 16B，上下文 100 万 token，全局 KV 常驻 HBM 仅 890 B/token[DSV41FLASH26][DSAPI26]。它的 config（HuggingFace deepseek-ai/DeepSeek-V4.1-Flash）本身就是一份仿真输入表。

2.1 整体骨架：CED（因果编码器-解码器）

40 层切成两半：前 20 层是因果编码器，后 20 层是解码器。灵感来自 YOCO（You Only Cache Once）[YOCO24]：解码器各层的全局 KV 不从自己的隐状态算，而是直接从第 20 层（编码器末层）的隐状态投影出来：

C_l = H_{L/2} · W_KV_l ,   Z_l = H_{L/2} · W_Z_l ,   l > L/2

式 2-1 CED 的解码器 KV 投影（报告式 (1)）：prefill 时只需跑前 20 层 + 一组轻量投影，就拿到了全部 40 层的 KV。

于是 prefill 复杂度从 O(N·L) 降到 O(N·L/2 + n_win·L/2) ≈ O(N·L/2)——计算近乎减半，这就是"prefill 只激活 8B"的来源。代价是解码器每层自己的滑窗注意力（SWA，窗口 128）仍需逐层计算：为此引入 SWA Bounded Replay——恢复解码器 SWA 状态时只重放最后 n_win=128 个 token（而非精确重建所需的 L/2×128），实测质量几乎无损，持久 KV 需求降到上代的 1/8[DSV41FLASH26]。

2.2 CSA2：三种模式的稀疏注意力

每层都有"全局注意力 + 滑窗注意力"双通道，全局通道分三种静态分配的模式：

模式全局 KV索引（Top-512）每层成本
Full（L2/L8/L14/L20）自己生成（写缓存）自己打分选择KV 投影 + 索引 GEMM + 稀疏注意力
Reindex（L24/28/32/36）复用前层用自己的 Q 对共享 K 重新打分索引 GEMM + 稀疏注意力
Reuse（其余）复用前层复用前层选择结果只剩稀疏注意力（部署时仅 11 个 kernel）

解码器还有层级稀疏索引器：第一个 Full 层选出的 Top-512 构成共享候选池（最多 2048 块×8 位置 = 16384 候选），后续 Reindex 层只在池内打分——每查询成本从"正比于上下文"降为"正比于池大小"。配合这三项，单 token decode FLOPs 在 4K→1M 上下文间只涨 1/4[DSV41FLASH26]。

2.3 其余部件：MoE、mHC、Engram、DSpark、FP4-KV

  • MoE：每层 1 个共享专家 + 384 个路由专家、top-6、专家中间维 2304（SwiGLU，clamp=10）；路由打分用 sqrtsoftplus + noaux_tc 无辅助损失负载均衡。这决定了"每 token 激活 ≈ 7×35.3M ≈ 247M/层"。
  • Single-Pass mHC + Mega-mHC：残差流混合改为单遍 kernel，激活读写从 (3n+2)d 降到 (2n+2)d，激活访存减半。
  • Engram 条件记忆：2 个模块（插在 L1/L14），N-gram{2,3,4} × 8 头哈希索引一张 ~384M 条目的表（素数尺寸），每条 256 维 FP8——2×384M×256 ≈ 196B 参数。推理时按输入序列确定性寻址，可从主机内存 RDMA 预取——196B 不占 HBM。
  • DSpark 投机解码：3 个 Transformer 块（SWA 128）一次并行给出 5 个 draft 位置的 logits，Markov 头（rank 256）建模 draft 内依赖，置信头预估接受率；调度器结合实测引擎吞吐曲线动态选验证长度——生产系统里内置了一个迷你性能模型。
  • FP4 主 KV：E2M1 + 每 16 通道一个 E4M3 scale（NVFP4 去掉二级全局 scale），RoPE 之后量化；SWA KV 保持 FP8；索引 Q/K 自 V4 起就是 FP4 QAT。

本章小结（记住三句话）

  1. CED 让 prefill 只跑一半层（8B 激活）、CSA2 让 KV 与注意力近似常数——结构本身就是性能优化。
  2. 每层三种模式（Full/Reindex/Reuse）成本差一个量级，仿真必须逐层建模而不是"40 层同构"。
  3. Engram（196B 在主机）与 SWA KV（分钟级 TTL 内存池）说明：显存账本要分 HBM / 主机 / SSD 三层。

  • TP 把 decode 的 GEMM 进一步推向带宽瓶颈：每卡权重变 1/tp，但通信仍是 2·T·d·b 量级——batch 小时通信占比飙升。这就是 MoE decode 更爱"DP + 小 TP/EP"组合的原因（SGLang 用 96 卡 H100 复现 DeepSeek 生产配置用的正是大 DP+EP[LMSYSEP]）。

9Roofline：分层瓶颈图示分析

Roofline 只需要一个公式：t = max(FLOPs/峰值算力, 字节数/峰值带宽)。KernelSight-LM 在此基础上加了两个修正：效率系数 η（≥1，衡量离屋顶多远）与波量化 u（blocks 不是 SM 整数倍时的空转），再加 kernel 启动下限 t₀[KERNELSIGHT26]：

t = max( t_roof · η ,  t₀ ),   t_roof = max( F_comp / (P_peak · u) ,  F_mem / BW_peak )

式 9-1 KernelSight-LM 式 (2)。η = 实测时延 / 屋顶时延——唯一需要从真实硬件学的量；这就是"数据手册 + 一次微基准"两档精度的全部秘密。

图 9-1 DeepSeek-V4.1-Flash 关键算子的 roofline（H100，TP8/EP8 单卡视角）。prefill chunk 深处计算区；decode 整步卡在屋脊附近；TP/EP 切分后的 MoE 与 q/o GEMM 回到带宽区（AI≈64-128 vs 屋脊 295）。

9.1 逐层账本：每层的计算量/访存量由什么组成

把公式写成一行（对每层 l）：

AI_l = [ 2·act_params_l + 4·(topk·1 + W_sw·1)·H·(d_h+d_r) ] / [ act_params_l·bytes_l + (topk·320B + 128·320B) ]

式 9-2 decode 每层算术强度。分子是 FLOPs（GEMM 2×激活参数 + 注意力），分母是访存（权重 + KV 读取）。B 个请求共批时分母的权重项不变、分子 ×B——AI 近似 ×B，这就是 batch 沿 roofline 斜线向右滑的机制。

本章小结（记住三句话）

  1. 每个算子两个数（FLOPs、字节）决定 roofline 位置；η 是唯一要从真实硬件学的量。
  2. decode 靠 batch 沿斜线右滑、prefill 天生在平顶、H3 去噪整步都在平顶——三种负载三个角落。
  3. 逐层记账的意义：Full/Reindex/Reuse 三种层成本差一个量级，平均掉就看不见索引器这个长上下文隐形炸弹。

10请求级仿真：从 QPS 到 TTFT/TPOT 曲线

算子级模型回答"一步多快"，请求级仿真回答"用户等多久"。做法是离散事件仿真：请求按泊松流到达，调度器逐事件推进——这就是 Vidur 与 KernelSight-LM 的骨架，后者干脆"逐行复刻 vLLM v1 调度器"[KERNELSIGHT26]。llsim 的 serving.py 实现了同样的核心循环：

每步：
  1) 到达事件入等待队列
  2) 组批：先保 RUNNING 解码（≤ max_num_seqs），剩余 token budget
     （max_batched_tokens）从等待队列补 prefill chunk   ← chunked prefill
  3) 前缀命中部分直接跳过                                  ← prefix cache
  4) 调用算子级模型得本步 GPU 时间 t(组成) ；投机解码放大产出 ← spec decoding
  5) 推进时钟，记录 TTFT/TPOT/队列/KV 显存 → 时间序列

代码 10-1 调度循环伪代码（llsim/serving.py:simulate）。P/D 分离把 2-3 步放到 P 副本、第 4 步 decode 放 D 副本，中间插 KV 迁移事件。

图 10-1 QPS=8（接近饱和）：8-16K prompt、500-1200 输出。排队短暂堆积后被消化——queue 长度是饱和预警信号。
图 10-2 QPS=12（过载）：等待队列线性增长，TTFT 尾部爆炸——goodput 由"满足 SLO 的请求速率"决定而非裸吞吐。
图 10-3 KV Cache 占用随时间波动（TP8 全局，890 B/token × 在途上下文）。它是准入控制的资源上限：满了就抢占/拒绝。

10.1 DiT 的请求级仿真是另一套形状

H3 请求是"编码 2.8 s → 50 步去噪（每步 1-2 s）→ VAE 解码 4-6 s"的三段流水，每段占用资源不同（文本编码器只在第一段用、VAE 只在最后用）。vLLM-Omni 的 --step-execution 允许在去噪步之间收发请求（准入门限 ≈1.3 s 而非整条 45 s），但实测 co-batching 对吞吐无益（计算受限）——DiT 的请求级仿真重点是段间排布与显存峰值，而非批摊薄[H3RECIPE]。

10.2 交互：到达率×服务率的排队演示

图 10-4（交互）泊松到达 × 指数服务的单队列动画：每个横条是一个请求（绿=服务中，黄=排队）。λ→µ 时队列爆炸——TTFT 尾延迟正是从这里来的。真实引擎把 µ 换成第 9 节的算子级模型即可。

本章小结（记住三句话）

  1. 请求级仿真 = 离散事件调度器 + 算子级时间模型；调度策略逐行对齐引擎才有意义。
  2. 输出的是时间序列：TTFT/TPOT 分布、队列、KV 显存——容量规划与 SLO 验收的原料。
  3. DiT 仿真的关键是三段流水排布而非批摊薄；LLM 与 DiT 的服务仿真模型必须分开建。

11.3 与生产级仿真器的差距（诚实清单）

  • η 是常数默认值而非按 shape 插值的表（KernelSight Tier B 的做法：一次微基准扫出 η(shape) 网格）。
  • 没有 host 开销通道（CPU 调度、launch、TP 同步尾），小 batch decode 会偏乐观。
  • 通信只算了时间近似，没有重叠调度与 NCCL 拓扑；MoE all2all 未按专家分布展开。
  • 投机解码用期望接受长度而非逐 token 接受链模拟；P/D 的迁移只进了 TTFT 未建独立副本池。

每一项都是 KernelSight-LM 论文里对应的一节——把这份清单当 roadmap，就得到了一个mini-Vidur 的进化路径。

12未来方向

  1. 跨代预测的注意力效率迁移：KernelSight-LM 自认的最大开放问题——attention 的 η 在新 GPU 代上漂移，需要按架构做一次校准[KERNELSIGHT26]。
  2. 结构-系统联合设计回路：V4.1-Flash 证明了"为推理设计结构"（CED/CSA2/FP4-KV）收益超过任何单一系统优化；下一代仿真器应当能在结构空间里搜索（改 config 里的 compress_ratios 扫一遍 KV-质量-带宽曲面）。
  3. 异构与全模态：GPU+NPU 混布（vLLM-Omni 已上昇腾 950）、AR+DiT 混合负载的统一仿真；Engram/持久 KV 这类"主机/SSD 资源"要进同一张账本。
  4. SLO 反向求解：从"TTFT p99<2s、TPOT<50ms、QPS=50"反解最小硬件配置——Vidur-Search 的思路加上 KernelSight 的精度。
  5. 生产闭环：Dynamo 1.0 的调度器已用实测吞吐曲线做决策[DYNAMO26]；下一步是"仿真器在线校准"——影子流量持续回归 η 表。
