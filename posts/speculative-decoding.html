1为什么大模型推理"慢"？[2,3]

现代大语言模型（LLM）生成文本的方式是自回归（autoregressive）的：每生成一个 token，都要把"之前所有 token"喂给模型做一次前向计算，得到下一个 token 的概率分布，采样出下一个 token，如此循环。

第 t 步：  xt  ∼  p( · | x1, x2, …, xt−1)   ⇒   生成 K 个 token 要 K 次串行前向

关键洞察是：在 batch size 较小（比如单用户对话）时，推理瓶颈不是算力（FLOPs），而是显存带宽（memory bandwidth）。每一步都要把整个模型的几百亿参数从显存（HBM）搬运到计算芯片，却只算出 1 个 token——算力被严重浪费了。[7]

"each forward pass requires transferring the complete model parameters from High-Bandwidth Memory (HBM) to the accelerator's cache. This process, which generates only a single token, underutilizes the arithmetic computation potential of modern accelerators, leading to inefficiency." — Medusa, Cai et al., ICML 2024 (arXiv:2401.10774) 每一次前向计算都要把完整的模型参数从高带宽显存（HBM）搬运到加速器缓存。这个过程只生成一个 token，却严重浪费了现代加速器的算术计算能力，导致效率低下。

打个比方：你（计算芯片）有一支超快的笔，但每次写字前，都要等别人把整本字典（模型参数）从书架（显存）搬到你面前，你才能写一个字。瓶颈在"搬字典"而不是"写字"。

于是有了一个朴素的想法：既然搬一次字典只写一个字太亏了，那能不能一次搬运，多写几个字？——这就是投机解码的出发点：用并行的多余算力，换更少的"搬字典"次数。

2核心思想：用"草稿+验证"换并发

投机解码（Speculative Decoding）的核心范式是 "草稿（draft）+ 验证（verify）"：

① 草稿模型 Md又小又快，自己"猜"接下来 γ 个 token（比如 4 个）。
→
② 目标模型 Mp（那个大模型）把这些猜测 一次性并行算出每个位置的概率。
→
③ 接受/拒绝从左到右逐个判断：草稿和目标一致就接受；第一个不一致的位置，用目标模型的分布重新采样一个"修正 token"。后面全丢弃。

如此一来，目标模型每跑一次（搬一次字典），最少产出 1 个 token，最多产出 γ+1 个 token。如果草稿猜得准，整个生成过程就被大幅加速了。

2.1 为什么能做到"无损"（不改变输出分布）？

这是投机解码最巧妙、也最重要的性质。它依赖一种叫 投机采样（speculative sampling）/ 改进版拒绝采样 的接受规则。对于草稿在第 k 位猜的 token x̂k，目标模型在该位给了概率 p(x̂k)，草稿模型给了概率 q(x̂k)，则：

接受概率 = min( 1 ,   p(x̂k) / q(x̂k) )
  • 若 p ≥ q（目标模型也认为这个 token 很可能）：以概率 1 接受；
  • 若 p < q（草稿过度自信，目标模型没那么看好）：以 p/q 的概率接受，否则拒绝，并从"残差分布" norm(max(0, p − q)) 重新采样一个修正 token。

可以看到：唯一被"打折"的"爱"少掉的概率（0.60→0.50），恰好通过残差重采样补给了唯一被低估的"是"（0.20→0.30）——此消彼长，总量守恒，这就是无损的全部秘密。同时可算出这一步的理论接受率 α = Σ min(p,q) = 0.900。

"We present speculative sampling, an algorithm for accelerating transformer decoding by enabling the generation of multiple tokens from each transformer call… combined with a novel modified rejection sampling scheme which preserves the distribution of the target model within hardware numerics." — Chen et al. (DeepMind), "Accelerating Large Language Model Decoding with Speculative Sampling", 2023-02 (arXiv:2302.01318) 我们提出投机采样，这是一种通过让每次 transformer 调用生成多个 token 来加速解码的算法……它结合了一种新颖的改进版拒绝采样方案，能在硬件精度范围内保持目标模型的（输出）分布不变。

可以证明（见下方 DeepMind 的定理），这套"接受+残差重采样"的最终结果，在数学上与直接从大模型逐 token 采样的分布完全相同。也就是说：投机解码是"无损"的——输出质量不会下降，只是变快了。[2,3]

🧮 想知道"无损"是怎么证明的？（点开看一段极简推导）

设草稿采样得到 x̂，最终输出 X。要证 P(X=x) = p(x)（即等于目标分布）。事件 X=x 分两种情况：①草稿恰好采到 x 且被接受；②草稿采到别的并被拒绝、残差重采样到 x。

# Chen et al. 2023, Theorem 1 的核心两步
P(X=x) = P(x̂=x)·P(接受|x̂=x)   +   P(被拒绝)·P(X=x | 被拒绝)
       = q(x)·min(1, p(x)/q(x)) +  (1-Σ min(p,q)) · [ max(0,p(x)-q(x)) / Σmax(0,p-q) ]
       = min(p(x), q(x))        +  max(0, p(x)-q(x))
       = p(x)   ✅  # 与目标分布完全一致

（其中用到了 1 − Σmin(p,q) = Σmax(0,p−q)，因为 Σp = Σq = 1。）

2.2 加速从何而来？——一个简洁的公式

设每个解码周期里：草稿耗时 Tdraft，验证耗时 Tverify，平均接受 token 数 τ。那么每个 token 的平均延迟是[11]：

L = ( Tdraft + Tverify ) / τ ，  加速比 η = L目标自回归 / L

也就是说，加速只有三条路可走：① 让草稿更快（降低 Tdraft）；② 让草稿更准（提高 τ）；③ 让验证更聪明（减少 Tverify 的浪费）。后面你会看到，整个投机解码的发展史，就是围绕这三条杠杆的军备竞赛。

📏 草稿该猜多长？——期望产出公式的直觉

Leviathan 等证明了：若每步接受率恒为 α、每轮猜 γ 个，则每轮目标模型前向的期望产出 token 数为 (1−αγ+1)/(1−α)。[2] 用上面例子里的 α=0.9 代入：

草稿长度 γ12468∞（上限 1/(1−α)）
期望产出（含 bonus）1.902.714.105.226.1310.0

规律很清楚：边际收益递减——γ 从 1 加到 4，期望产出翻了一倍多；从 8 加到无穷也只再多不到 4 个。而草稿成本（自回归时）却在线性上涨。这说明"猜多长"存在一个甜点，且随 α 变化——这正是后来"动态长度/置信度调度"（如 DSpark、SpecDec++等）的理论根源。

⚠️ 一句话记住全部： 草稿要"快"，目标要"准"，验证要"无损且省"。 任何方法都在权衡这三者。

2.3 · 动手实验：50 行代码亲眼验证"无损"

光看公式不过瘾？下面这段代码不依赖任何深度学习框架（纯 Python 标准库），把上面的接受规则原样实现一遍，然后重复 20 万次，统计投机采样产出的每个 token 的频率——如果"无损"成立，频率应当收敛到目标分布 p。

demo_speculative_sampling.py（与本页同目录，可直接 python 运行；已实测通过）

import random
from collections import Counter

VOCAB = ["爱", "是", "在", "了", "有"]

# 某个解码位置上，目标模型 p 与草稿模型 q 给出的两个分布（与 §2.1 手算例子相同）
p = {"爱": 0.50, "是": 0.30, "在": 0.10, "了": 0.05, "有": 0.05}
q = {"爱": 0.60, "是": 0.20, "在": 0.10, "了": 0.05, "有": 0.05}

def sample(dist):                          # 从离散分布采一个样本
    r, acc = random.random(), 0.0
    for k, v in dist.items():
        acc += v
        if r < acc: return k

def residual(p, q):                       # 残差分布 norm(max(0, p − q))
    diff = {k: max(0.0, p[k] - q[k]) for k in p}
    s = sum(diff.values())
    return {k: v / s for k, v in diff.items()}

def speculative_sample(p, q):
    x = sample(q)                                   # ① 草稿先猜一个
    if random.random() < min(1.0, p[x] / q[x]):    # ② 以 min(1, p/q) 概率接受
        return x
    return sample(residual(p, q))               # ③ 拒绝 → 从残差分布重采样

alpha = sum(min(p[k], q[k]) for k in VOCAB)     # 理论接受率 α = Σ min(p,q)
print(f"理论接受率 alpha = Σ min(p,q) = {alpha:.3f}")

random.seed(0)
N = 200_000
count = Counter(speculative_sample(p, q) for _ in range(N))
for k in VOCAB:
    print(f"{k}:  目标 p={p[k]:.3f}  采样频率={count[k]/N:.4f}")

2.4 · 四个常见误区（最容易踩的坑）

❌ 误区一："投机解码会降低输出质量。"

不会。改进拒绝采样在数学上保证每个 token 的边缘分布与目标模型完全相同（贪心解码时输出甚至逐 token 一致）。"投机"投的是时间，不是质量。

❌ 误区二："草稿被拒就白干了。"

即使第一个草稿就被拒，目标模型也会在拒绝位重采样出 1 个"修正 token"——最坏情况也只是退回基线速度，额外代价只是草稿那点时间。每轮保底 1 个、上限 γ+1 个。

❌ 误区三："并发/batch 越大越划算。"

恰恰相反。batch 大了以后 GPU 已经吃满（compute-bound），验证不再"免费"，甚至会挤占别的请求——这正是 DSpark 要做负载感知调度的原因。[12]

❌ 误区四："草稿猜的 token 必须和目标一样。"

不需要"猜中"，只需要分布覆盖得好：q 给了概率而 p 给得更高的 token 永远会被接受。所以即使草稿"口味"略有不同，仍能高速通过验证。

4阶段一（2022–2023）：奠基 —— 经典投机采样

2022 年底到 2023 年初，Google 与 DeepMind 两支团队几乎同时、各自独立地提出了我们今天所说的"投机解码"。[2,3]

"the work in this manuscript was undertaken concurrently and independently of the work on speculative decoding from Leviathan et al. (2022)… the core underlying idea is the same." — Chen et al. (DeepMind), arXiv:2302.01318, 2023-02 本工作与 Leviathan 等人（2022）关于投机解码的工作是同期、独立进行的……其核心思想是一致的。

4.1 Google 版（Leviathan, Kalman, Matias）

核心贡献是把"投机执行"（CPU 里早就有的分支预测思想）推广到了随机场景。关键观察有两条：

"(1) hard language-modeling tasks often include easier subtasks that can be approximated well by more efficient models, and (2) using speculative execution and a novel sampling method, we can make exact decoding from the large models faster, by running them in parallel on the outputs of the approximation models, potentially generating several tokens concurrently, and without changing the distribution." — Leviathan et al., "Fast Inference from Transformers via Speculative Decoding", ICML 2023 (arXiv:2211.17192, 2022-11) （1）困难的语言建模任务里，常常包含能被更高效模型很好近似的"简单子任务"；（2）借助投机执行和一种新颖的采样方法，我们可以让从大模型解码变得更快——把大模型对近似模型输出并行计算，从而可能一次生成多个 token，并且不改变输出分布。

实验：用更小的近似模型（Mq）给目标模型（Mp）当草稿，在 T5-XXL（110 亿参数）上取得 2–3 倍加速，且输出完全一致。[2]

经典投机解码一周期（γ=4 个草稿 token，本例接受 3 个）： 草稿模型 Mq 自回归猜： [tok1]→[tok2]→[tok3]→[tok4] （串行，慢但小） ↓ 一次性喂给大模型 目标模型 Mp 并行打分： Mp(·|prefix+tok1..tok4) ← 只算 1 次大前向 ↓ 验证（左→右）： tok1 ✓ tok2 ✓ tok3 ✓ tok4 ✗ ↓ 第一个被拒处重采样 本周期产出： tok1 tok2 tok3 + [修正token] = 4 个 token （最多 γ+1 个，最少 1 个）

4.2 DeepMind 版（Chen et al.）—— 为什么"并行打分"几乎不增加耗时？

DeepMind 在 Chinchilla 70B 上验证了 2–2.5× 加速。他们额外解释了一个工程上的关键点：对大模型而言，"给 K 个 token 打分"和"生成 1 个 token"耗时几乎一样，因为瓶颈在搬运参数/通信，而非计算本身——这正是投机解码能"免费"加速的根源。[3]

"computing the logits of a short continuation of K tokens in parallel has a very similar latency to that of sampling a single token." — Chen et al., arXiv:2302.01318, 2023-02 并行计算一段长度为 K 的续写的 logits，其延迟与采样单个 token 非常接近。
阶段一的小结：这一代方法的草稿模型是一个独立的小模型（比如同系列的更小版本）。它的局限是——(a) 还得训练/维护一个额外小模型；(b) 草稿本身仍是自回归的，要串行跑 γ 次；(c) 接受率受小模型能力限制。这些痛点，直接催生了阶段二。

5阶段二（2024）：自投机与特征级草稿

2024 年的工作，核心思路是："别再用外面的小模型了——大模型自己就藏着未来的线索，让它的某些部件直接当草稿。"这样既省了独立草稿，又让草稿质量大幅提升。这一阶段有三个里程碑：Medusa、EAGLE、MTP。

5.1 Medusa：给大模型装上多个"预测头"

自投机树注意力无需独立草稿 Medusa 在大模型最后一层 hidden state 上，额外加 K 个轻量"预测头"：第 k 个头用来预测"往后第 k+1 个 token"。[7]

"MEDUSA, an efficient method that augments LLM inference by adding extra decoding heads to predict multiple subsequent tokens in parallel. Using a tree-based attention mechanism, MEDUSA constructs multiple candidate continuations and verifies them simultaneously in each decoding step." — Cai et al., "Medusa", ICML 2024 (arXiv:2401.10774) Medusa 通过给 LLM 推理增加额外的解码头来并行预测后续多个 token。借助基于树的注意力机制，Medusa 在每个解码步同时构造多条候选续写并一并验证。

它的"树注意力"很巧妙：每个头给出 top-s 个候选，做笛卡尔积展开成一棵候选树，用一张特殊的注意力 mask 让"每条路径只看自己的祖先"，从而一次前向并行验证整棵树。结果：Medusa-1（冻结主干）无损 2.2×；Medusa-2（联合训练）2.3–2.8×。[7]

Medusa 树注意力（头1 取 top-2、头2 取 top-3 → 2×3 = 6 条候选路径） [t] ← 原始 LM 头预测的下一 token（第 0 层，独立采样） / \ [A1] [A2] ← Medusa 头1 的 top-2（预测 t+2 位置） /|\ /|\ [B1 B2 B3] [B1 B2 B3] ← Medusa 头2 的 top-3（预测 t+3 位置） 树注意力 mask（每条路径只能"看见"自己的祖先，其余全遮住）： t A1 A2 B1 B2 B3 t ✓ · · · · · A1 ✓ ✓ · · · · A1 只看 t A2 ✓ · ✓ · · · B1 ✓ ✓ · ✓ · · B1（挂在 A1 下）只看 t, A1 B2 ✓ ✓ · · ✓ · B3 ✓ ✓ · · · ✓ ... 位置编码也按树深度重排 → 目标模型一次前向算出 6 条路径所有位置的概率，取"最长被接受前缀"那条

Medusa 第 k 个头：单层 FFN + 残差（按论文公式实现，w1 零初始化 / w2 拷贝原 LM 头，保证训练起步时与原模型行为对齐）

class MedusaHead(nn.Module):
    # p_t^(k) = softmax( W2 · SiLU(W1 · h_t) + h_t )   ← 残差连接
    def __init__(self, d, V):                    # d=hidden 维, V=词表大小
        self.w1 = nn.Linear(d, d, bias=False)   # 初始化为全零
        self.w2 = nn.Linear(d, V, bias=False)   # 拷贝原模型 LM head 权重
    def forward(self, h):                        # h: 主干最后一层 hidden state
        return F.softmax(self.w2(F.silu(self.w1(h)) + h), dim=-1)

# 第 k 个头负责预测 "往后第 k+1 个 token"；训练只需冻结主干 + 交叉熵：
#   L = Σ_k −λ_k · log p^(k)_t ( y_{t+k+1} )，λ_k = 0.8^k（越远的头越难，权重递减）

局限：各头之间是"独立预测"，位置越往后越不准（后缀衰减的雏形）；且这些浅层 MLP 头能力有限，接受率约 0.6。

5.2 EAGLE：在"特征空间"做自回归，让草稿又准又快

特征级自回归树草稿"目标最懂未来" EAGLE 给出了两个关键洞察[8]：

  1. 在特征（feature）层做自回归，比在 token 层更简单。这里的"特征"指大模型倒数第二层的 hidden state。特征序列比 token 序列更"规律"，所以预测下一特征再过 LM Head 得到 token，比直接预测 token 准。
  2. 采样的随机性会破坏特征预测。比如 "I" 后面可能接 "am" 也可能接 "always"，下一个特征取决于实际采样了哪个，存在不确定性。

解法：把"往后移一位的 token 序列"也喂给草稿模型（它包含了真实采样结果），从而消解不确定性。这个改动让加速比从 1.9× 跃升到 2.8×。

EAGLE 的两个洞察，一图看懂 (1) 特征层比 token 层"更好预测"： token 级（经典做法）： t1 t2 t3 ──draft──> t4 token 是语言的直接编码，"跳跃大" 特征级（EAGLE）： f1 f2 f3 ──draft──> f4 ──LM Head──> t4 └ 特征（倒数第二层 hidden）更平滑、更规律 (2) 采样随机性让"下一个特征"不确定（多分支）： ┌── 采样得 "am" (p=0.6) ──> f_am f_I ────────┤ └── 采样得 "always" (p=0.4) ──> f_always → 光看 f_I 无法确定下一个特征是谁（Medusa 头也受此困扰） EAGLE 解法：输入 (f_I, t="am") → 预测 f_am ；输入 (f_I, t="always") → 预测 f_always 把"提前一步的真实 token"拼进输入，分支被"钉死"，不确定性消除 ✓

5.3 MTP（多 Token 预测）：一个训练目标，顺带做推理加速

训练目标自投机DeepSeek-V3 落地

MTP 严格说是一个训练阶段的技术，但它天然能用于推理加速，因此常被归入投机解码生态。Meta 的 Gloeckle 等（2024）最早系统地提出它。[6]

"we suggest that training language models to predict multiple future tokens at once results in higher sample efficiency. More specifically, at each position in the training corpus, we ask the model to predict the following n tokens using n independent output heads, operating on top of a shared model trunk." — Gloeckle et al. (FAIR/Meta), "Better & Faster LLMs via Multi-token Prediction", ICML 2024 (arXiv:2404.19737, 2024-04) 我们提出，训练语言模型一次性预测多个未来 token，能带来更高的样本效率。具体而言，在训练语料的每个位置，我们让模型用一个共享主干之上的 n 个独立输出头来预测接下来的 n 个 token。

关键点：MTP 在训练时就让模型"预看"多个未来 token。这样做有两个好处：① 更强的训练信号、更好的样本效率（13B 模型在 HumanEval 上多解 12%）；② 训练好的多个头可以直接拿来自投机解码，推理快 3×。[6]

DeepSeek-V3 如何落地 MTP（2024.12）[4]

DeepSeek-V3 借鉴了 Meta 的 MTP 思想，但做了一个关键改造：Meta 是"并行独立头"，而 DeepSeek-V3 改成 "顺序预测、保留完整因果链"（和 EAGLE 的精神类似，但目标不同——DeepSeek 主要为提升主模型质量）。

"Different from Gloeckle et al. (2024), which parallelly predicts D additional tokens using independent output heads, we sequentially predict additional tokens and keep the complete causal chain at each prediction depth." — DeepSeek-AI, "DeepSeek-V3 Technical Report", 2024-12 (arXiv:2412.19437) 不同于 Gloeckle 等（2024）使用独立输出头并行预测 D 个额外 token，我们顺序地预测额外 token，并在每个预测深度上保持完整的因果链。

结构上，第 k 个 MTP 模块 = 共享嵌入层 + 共享输出头 + 一个 Transformer block + 一个投影矩阵 Mk∈ℝd×2d。它把"上一深度的特征"和"下一个真实 token 的嵌入"拼起来，预测再下一个 token。DeepSeek-V3 取深度 D=1（即额外预测 1 个 token）。

5.4 顺带提一句：Lookahead Decoding（2023.11）[10]

思路完全不同：不训练任何草稿模型，而是用 Jacobi 迭代把"自回归解码"看作一组非线性方程来并行解，过程中自然产生很多 n-gram，缓存成一个"n-gram 池"，边生成边用目标模型验证池里的候选。代码（HumanEval）这种重复结构多的场景特别吃香，提速 1.5–2.3×。

6阶段三（2025–2026）：并行 / 块草稿 —— DFlash 与 DSpark

前面所有方法的草稿（除 Medusa/Lookahead 外）都是自回归的——要串行生成 γ 个 token，草稿耗时 Tdraft = γ · tstep 线性增长。这逼着草稿只能做得很浅（EAGLE-3 只有 1 层），草稿质量被压住，整体加速卡在 2–3×。

自回归草稿：Tdraft = γ · tstep　　→　　并行草稿：Tdraft = tparallel（与 γ 几乎无关）

6.1 DFlash（2026.02）：用"块扩散模型"做并行草稿 [11]

扩散模型草稿一次前向出整块KV 注入

DFlash 的作者注意到一个"鱼与熊掌"的机会：扩散语言模型（dLLM）能并行去噪一整块 token，但单独用质量不如自回归模型；而自回归模型质量好却慢。于是——让扩散模型只当草稿（够快），让自回归模型负责验证（够准），各取所长。

"we introduce DFlash, a speculative decoding framework that employs a lightweight block diffusion model for parallel drafting… By generating draft tokens in a single forward pass, DFlash enables efficient drafting, and by conditioning the draft model on context features extracted from the target model, it achieves high-quality drafts with higher acceptance rates." — Chen et al., "DFlash: Block Diffusion for Flash Speculative Decoding", ICML 2026 (arXiv:2602.06036, 2026-02) 我们提出 DFlash，一个采用轻量块扩散模型做并行草稿的投机解码框架……通过一次前向生成草稿 token，DFlash 实现了高效的草稿；通过用从目标模型提取的上下文特征来条件化草稿模型，它获得了高质量、高接受率的草稿。

它的两个关键设计：

  1. "目标最懂未来"（the target knows best）—— KV 注入。把大模型若干层的 hidden feature 拼起来、投影，作为持久上下文，注入到草稿模型每一层的 K/V 里（而非只在输入层融合一次）。这样即使草稿模型变深，目标模型的信息也不会被稀释，接受长度能随层数有效提升。
  2. 并行块草稿。草稿模型一次前向就把整块（比如 16 个）token 全部去噪出来，Tdraft 几乎不随块长增长——于是可以放心地用更深的草稿模型（5 层）。

① 半自回归生成（治"后缀衰减"）

把草稿拆成两段：

并行阶段（重）

用 DFlash 那样的并行骨干（实质就是 DFlash），一次前向出整块的 base logits U1..γ。Tdraft 几乎不随 γ 增长。

串行阶段（轻）

在 base logits 上叠加一个"前缀相关的转移偏置" Bk，让每个位置能看到块内前面已经采样的 token。最终：
pk(v) = softmax( Uk(v) + Bk(x0, x<k, v) )

串行模块很轻，分两种实例：Markov 头（只看上一个 token，低秩大表 B = W1W2）和 RNN 头（用一个门控循环状态累积整段前缀）。因为采样要逐位进行，它必须计算极轻（Tseq ≪ Tparallel），整体草稿延迟仍由并行阶段主导。

    next_token_ids = sample_tokens(logits.unsqueeze(1), temperature=temperature)
    sampled_tokens.append(next_token_ids)

对应公式：低秩分解 B ≈ W1W2，其中 W1∈ℝV×r 是嵌入查表（r=256），W2∈ℝr×V 是 logit 投影——避免存下 V×V 的完整转移矩阵。回到前文的例子：一旦第 1 位采样了 "of"，Markov 头就会在第 2 位抬升 "course"、压低 "problem"，把"串味"组合扼杀在采样阶段。

"A parallel drafter produces all γ draft logits in one forward pass, so each prediction cannot condition on tokens sampled elsewhere in the block. When the context admits multiple plausible continuations… a parallel drafter may produce incoherent combinations such as 'of problem' or 'no course'… We therefore adopt a semi-autoregressive structure that splits draft generation into two stages." — DSpark, arXiv:2607.05147, 2026-07 并行草稿器一次前向产生全部 γ 个草稿 logits，因此每个预测都无法以块内别处采样的 token 为条件。当上下文存在多种合理续写时……并行草稿器可能产生 "of problem" 或 "no course" 这种不连贯的组合……因此我们采用一种半自回归结构，把草稿生成分成两个阶段。

② 置信度调度验证（治"验证浪费"）

这是 DSpark 的系统级创新。在生产高并发场景下，无脑验证整块草稿会浪费宝贵的 batch 容量（很多尾部 token 本来就会被拒）。DSpark 用两件套解决：

  • 置信度头（confidence head）：给每个草稿位置预测一个 ck∈(0,1)，表示"在前缀都被接受的前提下，本位 token 能存活"的条件概率。监督信号用草稿/目标分布的总变差距离 c*k = 1 − ½‖pd−pt‖1。
  • 硬件感知前缀调度器：用 Πci 估计期望接受长度，结合实时引擎吞吐画像，动态决定每个请求验证多长——负载轻就验长一点、多赚 token；负载重就截短，把 batch 容量让给别的请求。
置信度调度怎么随"系统负载"伸缩（论文图 8 所述行为，示意） 每请求验证预算（token） 6 ┤ ●●●● 5 ┤ ●● ●● ← 轻载：算力有富余，验长一点多赚 token 4 ┤ ●● ●● （MTP-1 时代固定只验 2 个） 3 ┤ ●● ●● 2 ┼━━━━━━━━━━━━━━━━━━━━●●●● ← 重载：自动收缩预算，被拒率高的尾部 └──────────────────────────────> token 不再占用 batch 容量 0 50 100 150 200 并发请求数 一句话：轻载时"贪"（多验证多接受），重载时"省"（截前缀保吞吐）—— 这正是 DSpark 能在严格 SLA 下不"塌方"的原因。

🏭 工业框架全面集成

vLLM、SGLang、TensorRT-LLM 都已原生支持投机解码（含 EAGLE / MTP / DFlash 等多种草稿后端）。NVIDIA 报告在 Blackwell 上用 DFlash 给 gpt-oss-120b 加速最高 15×；AMD ROCm、HuggingFace Transformers 也在跟进 DeepSeek-V3 MTP。[11,13]

📚 多篇综述厘清版图

2025 年出现了系统综述，如阿里/清华等的《并行文本生成综述：从并行解码到扩散语言模型》[14]，以及华为云等的《高效 LLM 推理服务综述》[15]，把"自回归 → 自投机 → 并行/块/扩散草稿"的脉络梳理清楚。

🧪 面向真实负载的"系统感知"

AngelSpec（2026.07）指出：没有任何单一草稿结构在所有真实负载下都最优，需要按负载切换；DSpark、SpecSpec、DBLAST、LibraSpec 等一批 2026 年工作，都在研究"如何按系统负载/边际收益动态选草稿长度/结构"。

🤝 从"模仿目标"到"与目标协作"

《Beyond the Target》（2026.05）等提出：草稿不必一味模仿大模型分布，而可以与之"协作"，在保持质量下进一步提升接受率——是范式上的新探索。

7.1 一个有意思的里程碑：MoE 模型反而更受益

Cohere 等的工程实践指出：混合专家（MoE）模型从投机解码中获益更大。原因是 MoE 在单 token 解码时只激活少数专家，带宽受限更严重，正好处于投机解码的"带宽受限甜区"；且草稿与目标的专家路由往往高度相关，验证时复用成本低。

7.2 把"草稿"本身再投机一次

Stanford/Princeton/Together AI 的《Speculative Speculative Decoding》（2026.03，213 票）把投机思想递归——连草稿生成本身也再加速一层，进一步压缩草稿延迟。

8未来发展方向

综合各路线与最新工作，未来几年最值得关注的方向：

① 长上下文投机解码
长 CoT、Agent 场景下，二次方注意力开销 + 跨段上下文丢失成为新瓶颈。TriForce 式分层草稿、SW-SpeedDLM 式滑动窗口正在解决。DFlash 也已展示"4K 训练 + 少量微调适配长上下文"的可行性。[11,16]
② 与 MoE / 稀疏模型协同
为 MoE 专门设计草稿：考虑专家激活模式、路由相关性，做"成本感知"的投机（如 Cost-Aware Speculative Decoding for MoE、DraftExpert）。
③ 扩散 / 并行草稿的成熟
DFlash 已证明扩散草稿可行，下一步是减少去噪步、提升质量、保证分布严格无损（Spiffy 等给出校准式草稿）。"让扩散模型专做轻量草稿"可能成为新范式。
④ 系统级 / 负载感知调度
DSpark 开了头：把"验多少"当成系统调度问题，与 batching、KV 缓存、优先级联合优化。未来推理引擎会内建"投机调度器"。
⑤ 端侧 / 手机部署
Lever（2026.05）等探索手机上的投机解码，把草稿放在闪存、目标放在 DRAM，应对端侧显存极度受限。
⑥ 打破"扩展天花板"
大 batch、大模型下并行验证效率会饱和（"scaling ceiling"）。如何在超大并发下仍保持收益，是开放难题。
⑦ 与其他加速技术正交叠加
量化（FP8/int4）、编译（gpt-fast）、KV 缓存压缩等与投机解码正交，可叠加。EAGLE+gpt-fast 已在单张 RTX 3090 上把 LLaMA2-Chat 7B 推到 160 tokens/s。
