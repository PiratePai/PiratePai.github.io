0.2 大事记

  • 2016–2019前 LLM 时代的推理服务。TensorFlow Serving（2016-02）确立"模型服务器"形态：版本管理、request-level 批处理；Triton Inference Server（2018-10 起）把多框架后端装进一个服务。它们假设的负载是"一次前向几十毫秒"的 CV/推荐模型，为自回归生成式模型服务时先天不足。
  • 2021算子库时代：FasterTransformer。NVIDIA 开源 Transformer 推理算子库，证明"把 Transformer 各步融合成少量大 kernel"本身就能带来数倍加速，但仍是静态 batch（请求级组批），生成式服务吞吐受限。
  • 2022系统调度时代开启：Orca 与 FlashAttention。OSDI'22 的 Orca 提出 iteration-level scheduling（选择性批处理）：批的组装单位从"请求"细化到"迭代步"，论文报告在 2020 年代初期配置下相对 FasterTransformer 最高 36.9× 吞吐[ORCA22]；NeurIPS'22 FlashAttention 把 attention 的 IO 复杂度降到线性，成为之后所有引擎的标配算子[FA22]。DeepSpeed-Inference（2022）面向千亿模型多卡推理。
  • 2023LLM 推理工程大爆发。vLLM（2023-06-20 博客，SOSP'23 论文）以 PagedAttention 把 KV 显存浪费压到 4% 以下：博客口径相对 HF Transformers 14–24×、相对 TGI 2.2–2.5×（LLaMA-7B@A10G / 13B@A100-40GB，ShareGPT 长度）[VLLMBLOG23]，论文口径相对 FasterTransformer/Orca 为 2–4×（OPT 系、A100，normalized latency 曲线）[VLLM23]。两组数字基线与指标不同，不可混引；llama.cpp（2023-03）让消费级 CPU/Mac 跑量化模型成为可能；HuggingFace TGI、LMDeploy、LightLLM 相继发布；NVIDIA 发布 TensorRT-LLM（2023-10 前后）把编译、量化、in-flight batching 打包；Anyscale 博客（2023-06-22）把 continuous batching 一词推广为行业词汇（实测 CB ≈8× over 静态批、CB+PagedAttention 的 vLLM 最高 23×，OPT-13B@A100-40GB、输入 512 tok）[ANYSCALE23]。
  • 2024调度精细化与分离式架构。SGLang（NeurIPS'24）以 RadixAttention 自动复用共享前缀，复杂 prompt 程序任务混合体上最高 6.4×（vs Guidance/vLLM/LMQL，Llama-2-7B@A10G，缓存命中 50–99%）[SGLANG24]；Sarathi-Serve（OSDI'24）chunked prefill 化解"长 prompt 卡住 decode"的尾延迟（P99 TBT SLO 下 vs vLLM 容量 2.6–4.7×，Mistral-7B 到 LLaMA2-70B）[SARATHI24]；DistServe（OSDI'24）与 Splitwise（ISCA'24）论证 prefill/decode 分离的资源解耦收益（DistServe 摘要口径 7.4× 请求率或 12.6× 更紧 SLO；Splitwise 同功率预算 2.35× 吞吐）[DISTSERVE24][SPLITWISE24]；Mooncake（arXiv v1 2024-06-26）把"KVCache 优先"的分离架构做成月之暗面 Kimi 生产系统[MOONCAKE25]。DeepSeek-V2（2024-05）引入 MLA，KV 压缩一个数量级[DSV2]；DeepSeek-V3（2024-12）671B MoE + MTP 投机头上线，KV 占用与投机解码自此成为模型设计的一部分[DSV3]。FlashAttention-3（2024-07）面向 Hopper[FA3]。

本章小结
  1. 推理系统的演进主线是"通用 → 专用"：先有算子库（FasterTransformer），再有调度系统（Orca/vLLM），然后是分离式架构（DistServe/Mooncake），最后是模型厂商自研引擎整体开源（DeepInfer）。
  2. 2023 年的 vLLM + continuous batching + FlashAttention 三件事，定义了之后所有引擎的公共底座；2024–2026 的分化发生在 KV 管理、PD 分离、投机解码与 MoE 并行上。
  3. DeepInfer 的开源证明：当模型结构与服务形态足够收敛，"把引擎做专"可以把吞吐和时延推到通用框架难以企及的位置——代价是放弃宽适配（单模型族、两种加速器）。

1预备知识：一次推理到底在算什么

本章只假设你知道矩阵乘法和"神经网络 = 一堆矩阵乘 + 非线性"这两个事实。所有后文的概念（PagedAttention、TP、投机解码……）都建立在本章的四个直觉上：两阶段计算、KV 缓存、访存瓶颈、批处理两难。

1.1 自回归：模型是一个字一个字往外蹦的

大语言模型生成文本的唯一动作是：给定前面所有 token，预测下一个 token 的概率分布，采样一个，拼回去，再来。你要它写 1000 字的回答，它就要做 1000 次几乎一样的"向前计算"。这个循环叫自回归（autoregressive）。它和传统 CV 模型"一张图进来、一个标签出去"的一次前向完全不同：传统推理服务的全部假设（一次请求 = 一次计算）在这里都不成立，这就是为什么 TensorFlow Serving 时代的"模型服务器"搬不动 LLM。

1.2 两阶段：prefill 与 decode，两种完全不同的计算

把模型想成一个戴着老花镜的抄写员：先把你递进来的 30 页材料通读一遍并做笔记（prefill，预填充），然后开始看着笔记一个字一个字写答案（decode，解码）。通读时他可以一目十行（一次并行处理所有输入 token），写字时却只能一笔一划（每步只产出一个 token）。两种活儿的体力消耗模式完全不同：前者费脑子（计算），后者费眼睛和笔记翻找（访存）。

定量一点：prefill 一步处理 P 个输入 token，attention 与 MLP 都是大矩阵乘（GEMM），能打满 GPU 的算力；decode 一步只处理 batch × 1 个 token，矩阵退化成向量（GEMV），算力大量闲置。同一个模型、同一张卡，两个阶段的瓶颈一个是 FLOPs、一个是显存带宽。所以成熟的引擎会为两个阶段准备不同的 kernel、不同的批策略，甚至不同的机器。

1.3 KV Cache：自回归的"笔记本"

Attention 的公式里，第 i 个 token 的输出要看它和所有前文 token 的关系。如果每生成一个新 token 都重算全部历史，仍需逐 token 前向，但每次重复计算越来越长的前缀；增加的是累计计算量，而非二次数量的前向调用。解决办法：把每个 token 在每层算出的 Key/Value 向量缓存下来，之后每步只需算新 token 自己的 Q/K/V，再拿 Q 去查历史缓存。这块缓存就是 KV Cache。

它的显存占用有一个必须背下来的公式：

KV 显存(bytes) = 2(K与V) × L(层数) × n_kv(KV头数) × d_head(每头维度) × b(每元素字节) × seq_len(token数)

代入一个具体模型感受量级：Llama-2-70B（80 层、GQA 8 个 KV 头、head_dim 128、FP16），每 token 需要 2×80×8×128×2 = 327,680 B ≈ 320 KB。一个 32K 长度的请求就要 10 GB 起，比很多人直觉大一到两个数量级。服务 100 个这样的并发，KV 就要 1 TB，远超单卡。KV Cache 的存、取、放、换，占据了大模型推理系统设计的半壁江山（第 3.5 节、第 4.5 节）。

三个直接推论：① 显存里放不下权重 + 全部 KV，就必须对 KV 做分页/压缩/分层（PagedAttention、MLA、KV 量化）；② 多轮对话/Agent 场景里，历史 KV 是可复用资产，重复 prefill 是巨大浪费（prefix caching）；③ KV 随 token 线性增长，长上下文服务的成本主要在"笔记本身"而不在计算。

1.4 为什么 decode 慢：访存瓶颈与"算术强度"

判断一段计算是算力瓶颈还是带宽瓶颈，用 roofline 模型：算出它的算术强度（每读 1 字节显存做多少次浮点运算，FLOP/Byte），再和 GPU 的"平衡点"（峰值算力 ÷ 峰值带宽）比较。

decode 每步（batch=B）：
  读显存 ≈ 模型权重 W(bytes) + 该步全部 KV              （W 与 B 几乎无关）
  做计算 ≈ 2 × 参数量 × B                              （随 B 线性增长）
  算术强度 ≈ 2 × 参数量 × B / W = 2B / b(每参数字节)    （BF16 时 = B FLOP/Byte）

以 H100（BF16 峰值约 990 TFLOPS、HBM 带宽约 3.35 TB/s，平衡点 ≈ 295 FLOP/Byte）为例：batch=1 的 decode 算术强度是 1，只有平衡点的 1/295。这只是权重主导的 Roofline 上界估算，不能由此认定实测 GPU 有 99% 的时间在等待。把 batch 加到 256，算术强度升到 256，才接近打满。这解释了两件事：

  • decode 天生适合大 batch：并发用户数翻倍，权重只读一遍，吞吐几乎翻倍而单用户速度几乎不掉，直到 KV 读取也成为带宽压力或显存放不下；
  • 一切 decode 优化都在"少读字节"：量化（把每参数 2 字节压到 0.5 字节）、KV 压缩（MLA）、稀疏 attention（只读一部分 KV）、投机解码（一次前向多产出几个 token，摊薄每次访存）。
[PA23] Kwon et al. Efficient Memory Management for Large Language Model Serving with PagedAttention，SOSP 2023，arXiv 首发 2023-09-12。论文区分 KV 空间利用率与系统吞吐；Figure 5 是分页访问示意，不能作为 GPU 计算利用率证据。这里的 Roofline 比值是本文的理想上界推算。论文。

1.6 服务指标：延迟的两张面孔与吞吐

把推理服务想成一家奶茶店：TTFT（Time To First Token，首 token 延迟）是"从下单到吸上第一口"的时间，主要由 prefill 决定；TPOT/ITL（Time Per Output Token，逐 token 延迟/间隔）是"后续每一口之间的间隔"，由 decode 决定；吞吐（tokens/s）是全店每分钟出杯总量；并发数是同时在等餐的客人数。让全店吞吐最大的办法（狂加订单、大锅乱炖）恰恰会毁掉单客体验（TTFT 飙升）。吞吐与延迟的取舍是推理调度永恒的主题。

工程上还要加一个概念：goodput（有效吞吐），只统计满足 SLO（如 TTFT < 2s 且 TPOT < 50ms）的请求吞吐。它把"延迟约束"直接写进优化目标，是 DistServe 等系统提出的核心度量[DISTSERVE24]。

本章小结
  1. LLM 推理 = 一次计算密集的 prefill + N 次访存密集的 decode；前者决定 TTFT、后者决定 TPOT，两者的优化手段几乎相反。
  2. decode 是访存瓶颈：batch=1 时算术强度约 1 FLOP/Byte，离 GPU 平衡点（数百）差两个数量级。所以"加并发"和"少读字节"是 decode 优化的全部秘密。

2发展历程：从通用框架到定制引擎

本章按"题目"而非论文组织：每一代系统都在解决上一代暴露出的特定瓶颈，而每个被解决的问题又会暴露下一个。链条是：算子慢（FT 时代）→ 批处理僵硬（Orca）→ KV 显存浪费（vLLM）→ 前缀重复计算（SGLang）→ 两阶段互相干扰（Sarathi/分离派）→ 通用框架吃不满专属模型（DeepInfer）。

2.1 朴素时代：直接用训练框架跑推理为什么不行（2017–2022）

2022 年之前，"部署一个大模型"的默认姿势是 HuggingFace Transformers 的 generate()，配上一个传统模型服务器。三宗罪：

  1. Python/launch 开销：每个生成 token 跑一遍完整前向，所有算子逐个 eager 启动，小 batch 下 GPU 大部分时间在等 CPU：训练 kernel 本为大 batch 高利用率设计，对小 batch 延迟敏感场景天生次优[DSINF22]。
  2. 无迭代级批处理：批内先完成的请求空转、后到的排队，不同长度输入还要 padding 齐平[ORCA22]。
  3. KV 静态连续分配：按最大长度预留显存。vLLM 论文实测这类系统 KV 显存有效利用率仅 20.4%–38.2%（即六到八成 KV 显存被浪费）[VLLM23]。

传统通用 serving（TF Serving 2016 / TorchServe 2020 / ONNX Runtime 2018）的强项是版本管理、A/B、动态批处理（request 级）与图编译。它们假设"一次请求 = 一次前向"，不理解自回归的多迭代负载，不理解 KV 生命周期，不理解 prefill/decode 差异。结局颇有象征意味：TorchServe 于 2025-08-07 归档只读[TORCHSERVE]；ONNX Runtime 到 2023 年底才以 GenAI 扩展补 LLM 支持。

2.2 算子库时代：FasterTransformer → TensorRT-LLM（2021–2023）

FasterTransformer（NVIDIA，2019 年起服务 BERT，2021 年 v4.0 支持多机 GPT）回答的问题是"Transformer 的算子本身太慢"：kernel 多、launch 开销大、小 batch GEMM 带宽利用率低。答案是纯 C++/CUDA 算子库 + 深度融合（LayerNorm/Attention/采样融合）+ TP/PP 多卡。官方 README 数字（T4/A100，静态定长 batch）：BERT 对 TF XLA ~3×、端到端解码吞吐比 TensorFlow 4–18×[FT21]。它的两个先天缺陷恰好是下一代系统的靶子：自身无调度器（要靠 Triton 做 request 级组批）、KV 按最大长度预分配（Orca 论文实测 13B 模型 batch≥8 即 OOM）。2023-05 官方公告"开发迁移至 TensorRT-LLM"[FT21]。

TensorRT-LLM（2023-09-09 博客发布，10-19 公开可用）是 FT 的继任者，把"编译"补进来：模型编译为 TensorRT engine plan（融合 kernel + 算子调度图）、FlashAttention/XQA kernel、FP8/INT8/AWQ/GPTQ 量化矩阵、in-flight batching（TRT-LLM 对 continuous batching 的命名）。官方口径：GPT-J-6B 在 H100 上比"A100 FP16 PyTorch eager"基线共 8× 吞吐[TRTLLM23]。注意基线是 PyTorch eager 而非 vLLM。代价是部署复杂度：engine 编译构建流程长（第三方教程常引"28 分钟级"构建时间[SPHERON26]）、版本兼容脆弱、绑定 NVIDIA。2025 年它经历了"补课式开源"：2025-03-22 宣布全面开源（C++ 运行时核心进 GitHub）、2025-04 宣布新 PyTorch 架构去 TensorRT 硬依赖、2025-09-25 发布 TRT-LLM 1.0（"Easier. Faster. Open."）[TRTLLM1]。编译型引擎向动态运行时低头，是生态选择的结果。

2.3 系统调度时代：Orca 与 vLLM（2022–2023）

2.3.1 Orca：把调度单位从"请求"改成"迭代"

OSDI'22 的 Orca（首尔大学 + FriendliAI）指出 request 级调度的死穴：批内早完成的请求无法返回、晚到的进不来（论文原话 "early-finished and late-joining requests"）。两个机制：iteration-level scheduling（调度器每次只让引擎跑一个迭代，每步后即可换人）与 selective batching（Linear/Norm 等规则算子按 token 维 flatten 批处理，形状不规则的 attention 拆开算：任意请求集合都能进同一批）[ORCA22]。

[ORCA22] Yu et al. Orca: A Distributed Serving System for Transformer-Based Generative Models. OSDI'22（2022-07；无 arXiv 版本，正式出处为 USENIX 页面）。GPT-3-175B、16×A100-40GB、合成泊松负载：归一化延迟同为 190 ms/token 时 FT+request 级调度 0.185 req/s vs Orca 6.81 req/s = 36.9×。"Orca improves the throughput by up to 36.9×"。注意：引擎微基准里 13B 下 Orca 与 FT 相当甚至略慢。收益几乎全部来自调度层，这正是它成为"系统论文"而非"kernel 论文"的原因。

Orca 的局限：KV 仍按请求 max_tokens 预留连续空间（buddy allocation），这成了 vLLM 论文的直接攻击面。其思想由团队创业公司 FriendliAI 与整个行业继承：TGI 的 "continuous batching"、TRT-LLM 的 "in-flight batching"、vLLM/LightLLM/TurboMind 的调度器全部源于此。

2.3.2 vLLM：把操作系统分页搬进 KV 显存

vLLM（UC Berkeley Sky Lab，2023-06-20 博客、SOSP'23 论文，2025-05 起由 PyTorch Foundation 托管）攻 KV 显存管理：借虚拟内存分页，把 KV 切成 16-token block，逻辑块经 block table 映射到任意物理块。三重收益：消外部碎片（块等大）、内部碎片只剩最后一块（浪费 <4% vs 现有系统 20.4–38.2% 有效率）、天然支持块级共享（并行采样/beam search 的 copy-on-write、前缀共享）。论文数字：对 Orca(Oracle) 1.7–2.7×、对 FT 最高 22×（OPT 系、A100）[VLLM23]；博客口径对 HF 14–24×、对 TGI 2.2–2.5×（LLaMA-7B@A10G/13B@A100，ShareGPT 分布）[VLLMBLOG23]。实现代价（论文 §7.1 自述）：PagedAttention 因 block table 间接寻址，attention kernel 本身比 FT 慢 20–26%。收益在系统层而非 kernel 层，这是"内存管理 vs 算子极致"的第一笔公开账。

谱系铁证（官方原文）：vLLM 论文 §5.1 明言其 attention kernel "adapt the attention kernel in FasterTransformer"（改造自 FT）；2025 年 vLLM V1 博客致谢 "the design of vLLM V1 builds upon and enhances several open-source LLM inference engines, including LightLLM, LMDeploy, SGLang, TGI, and TRT-LLM"[VLLMV1]。开源引擎间的继承与反哺，比"谁抄谁"的叙事健康得多。

vLLM V1（2025-01-27 alpha，年内转正）是单引擎历史上最大规模的一次重写：调度器统一（取消 prefill/decode 二分表示，请求即 {id: num_tokens}）、prefix caching 默认开（0% 命中时损失 <1%）、EngineCore 独立进程、piecewise CUDA graph + torch.compile、FlashAttention-3，相对 V0 最高 1.7× 吞吐[VLLMV1]；2025-12 又交付 DeepSeek Wide-EP 部署（2.2k tok/s/H200）、async scheduling、PD 分离[VLLMLSC25]。

本节小结（记住三句话）
  1. 通用框架的三宗罪：launch 开销、request 级批处理、KV 静态分配，分别由三代技术解决：算子融合/CUDA Graph（FT/TRT-LLM）、iteration-level 调度（Orca，36.9×）、分页 KV（vLLM，浪费 60–80%→<4%）。
  2. 关键分水岭在 2023：Orca+vLLM 证明"系统层收益可以远大于 kernel 层收益"，此后所有引擎都是调度系统而不仅是算子集合。
  3. 这些引擎相互借鉴实现：vLLM 的 kernel 出自 FT，V1 吸收 LightLLM/LMDeploy/SGLang/TGI/TRT-LLM，TRT-LLM 2025 年全面开源并向 PyTorch 动态架构靠拢。静态编译与动态运行时在互相靠近。

2.5 专用化时代：从分离式架构到模型厂商自研引擎（2024–2026）

2.5.1 学术三部曲：PD 分离成为共识

2024 年三篇论文把"prefill 与 decode 干扰"这个矛盾推到台前，给出了同一个方向的解法，即物理分离：

  • DistServe（OSDI'24）：论证两阶段资源画像互斥、混部署注定顾此失彼；提出按 per-GPU goodput（SLO 内请求率）做放置与配比。摘要口径 7.4× 请求率或 12.6× 更紧 SLO（vs vLLM/DeepSpeed-MII，OPT 系、32×A100）；KV 传输在最优放置下占总时延 <0.1%[DISTSERVE24]。
  • Splitwise（ISCA'24，微软）：从数据中心视角看，同功率预算下分离集群 2.35× 吞吐（DGX-A100/H100 集群级模拟+实测 profile，BLOOM-176B）[SPLITWISE24]。
  • Mooncake（月之暗面 Kimi 生产系统，arXiv v1 2024-06-26 / FAST'25 最佳论文）：把分离做到极致：KVCache 为中心的分层池（GPU/CPU/SSD），Conductor 全局调度；真实负载回放多承载 75% 请求且 TBT 达标率 ~100%（vs vLLM 混部署 57%），A800/H800 集群实际多承载 115%/107%[MOONCAKE25]。月活数亿用户的生产规模（数千节点、日处理 100B+ token）使其成为"分离式架构可行"的最强证据。

这一代与前代的本质区别：2023 年的引擎在"通用负载"上优化（谁都能跑，尽量快）；2025–2026 年的定制引擎在收敛后的负载上优化（单一模型族 + 固定集群拓扑 + 已知流量形态），于是可以把 KV 存储做进文件系统、把调度决策搬上 GPU、把验证预算按 token 分配。这些设计的共同前提是"我不需要服务别人家的模型"。与此同时通用引擎也吸收了全部单点技术（vLLM/SGLang 的 Wide-EP、PD 分离、FlashMLA/DeepGEMM/DeepEP 集成均已落地），两条路线在 2026 年形成稳定分工：通用引擎吃宽矩阵，定制引擎打深极限。
本节小结（记住三句话）
  1. 2023–2024 的百家争鸣各攻一个切口：SGLang 攻前缀复用（RadixAttention）、LightLLM 攻 token 级调度、LMDeploy 攻量化落地、DeepSpeed 攻超大模型多卡。它们的最好设计全部被 vLLM V1 / SGLang / TRT-LLM 吸收（官方致谢可查）。
  2. PD 分离三部曲（DistServe/Splitwise/Mooncake）证明了同一个论断：混部署的 goodput 损失可达数倍，分离的代价（KV 传输与系统复杂度）在 RDMA 与分层存储下可承受。
  3. DeepSeek 用两年时间完成了"模型创新（MLA/MTP/DSA）→ 组件开源（FlashMLA/DeepGEMM/DeepEP/3FS）→ 引擎开源（DeepInfer）"的三级跳，把"模型—系统—芯片协同设计"从口号变成可逐行阅读的代码。

3.1 计算图与编译：把"逐算子的解释执行"变成"整图的机器码"

PyTorch 直接跑模型像现场点菜的厨师：每做一道工序（一个算子）都停下来看下一张订单。图编译像中央厨房的预制流水线：提前把整个菜单拆解、合并工序、备好料，开餐时按 SOP 一次走完。

这一层做四件事：

  1. 计算图解析：把 HuggingFace checkpoint（safetensors + config.json）加载进来，在引擎里重建为自家 IR（中间表示）。vLLM 为每个模型族手写 *ForCausalLM 执行类；TensorRT-LLM 走 ONNX/权重转换 + builder 编译为 engine plan；llama.cpp 需要转 GGUF。
  2. 算子替换与图优化：把通用算子序列换成融合/专用版本：LayerNorm+Residual 合并、QKV 三个投影合并为一个大 GEMM、GatedMLP 的两次 GEMM+SiLU 合并；常量折叠、死代码消除。经典结论：Transformer 推理的 kernel 数能从一个前向 ~1500+ 个降到数百个。
  3. Kernel 编译与自动调优：Triton（OpenAI，2019）让 Python 写 GPU kernel、按硬件即时编译；DeepGEMM 为 FP8 GEMM 做 JIT 编译；TensorRT 的 builder 对每层做 tactic 搜索选最快的实现。
  4. CUDA Graph 捕获：decode 每步的算子序列几乎不变，把整步前后向录制成一张 CUDA Graph，之后每步一次 launch 传入不同指针即可。这消除了"每步几百次 kernel launch、每次几微秒 CPU 开销"的致命问题：对单步仅几毫秒的 decode，launch 开销可占 30%+。vLLM 的 piecewise CUDA graph、DeepInfer 的 cuda_graph_runner.py 与 dflash_cuda_graph_runner.py（把 DFlash 草稿路径也捕获进同一张图）都是这个目的。
去掉这一层会怎样？回到 2022 年的 HuggingFace generate()：Python 循环 + 逐算子调度 + 每次 launch 都过一遍框架分发，A100 上 13B 模型单序列 decode 只有每秒几十 token，而且 GPU 利用率常年在个位数。vLLM 论文的对照实验显示，仅"kernel 化 + CUDA graph"一类工程就能带来数倍差距（24× 总差距中与调度、KV 管理并列的第三根支柱）[VLLM23][ANYSCALE23]。

代价：编译型引擎（TRT-LLM 的 plan、MLC 的 .so）换模型/换硬件/换 batch 形状都要重编译（分钟级），且对动态形状（变长序列）处理笨拙。"静态引擎 vs 动态运行时"的取舍正是从这里开始的（3.9 节）。2023 年后主流方向是混合：保留 eager 执行框架做调度，只对 decode 热路径做 graph 捕获（vLLM/DeepInfer 路线），或用 torch.compile 做自动图编译。

3.2 算子层：CUDA / Triton / TileLang 与算子融合

不管上面几层多聪明，最终在 GPU 上跑的是一个个 kernel。定制化引擎在算子层做三类事：

  • 融合（fusion）：相邻小算子合成一个 kernel，省掉中间结果写回显存。RMSNorm、RoPE、残差加、激活这类"访存多、计算少"的算子最该融合：它们是 roofline 上的极致低算术强度操作。DeepInfer 的 tilelang_ops/norm.py、fused_transform.py（1330 行）就是这类。
  • 专用大 kernel：FlashAttention 是范本（3.7 节展开）。同类还有 FlashMLA（MLA decode）、fused MoE kernel（vLLM 的 fused_moe Triton kernel 把路由+gather+GEMM+scatter 融在一起）。
  • DSL 生成：CUDA C++ 性能最高但开发慢、不可移植；Triton 面向 NVIDIA（社区有 AMD 后端）；TileLang（北大-DeepSeek 合作开源，2024–2025）用 Python 声明式写法生成多后端代码，DeepInfer 用它同时生成 CUDA 与昇腾两套算子（tilelang_ops/cuda/ 与 tilelang_ops/asc/ 平行目录）[DI26]。昇腾 NPU 无法直接跑 CUDA，"TileLang 双后端"就是 DeepInfer 支持多厂商加速器的工程底座。
去掉这一层会怎样？FasterTransformer 时代的历史对照最清楚：2021 年在同一张 A100 上，仅靠把 Transformer 各算子融合重写，GPT-3 类模型的推理就能比 PyTorch eager 快 2–5×（NVIDIA 官方博客口径，2021–2022，模型与配置各异）[FT21]。算子层是所有其他优化的"地基收益"。

3.4 请求调度：continuous batching 与 chunked prefill

3.4.1 从 request-level 到 iteration-level

去掉它会怎样？生成长度高度不齐（10 到 1000 token），static batch 的有效利用率被最长请求绑架：vLLM 论文与 Anyscale 博客都给出 10× 量级的浪费场景；这也是 2023 年前所有"模型服务器"跑 LLM 的共同瓶颈[ORCA22][ANYSCALE23]。

3.4.2 Chunked prefill：让长 prompt 不再"卡全场"

continuous batching 混批 prefill 与 decode 后出现新问题：一个 32K prompt 的 prefill 是一次数百毫秒的大计算，期间同批所有 decode 用户的逐 token 延迟瞬间抖动（TBT 毛刺）。Sarathi-Serve 的答案：把长 prompt 切成固定预算的 chunk，每个调度步只混入一个 chunk，让每步计算量平滑（stall-free decoding）。论文报告：P99 TBT 约束（strict = 单次 decode 步时延 ×5）下的服务容量 vs vLLM：Mistral-7B（1×A100）2.6×、Yi-34B（2×A100）最高 3.7×、LLaMA2-70B（8×A40）4.69×、Falcon-180B 4.3×（sharegpt4 与 arxiv 摘要负载，Poisson 到达）[SARATHI24]。TensorRT-LLM 的 chunked context、DeepSpeed-FastGen 的 SplitFuse 同属此族。DeepInfer 更进一步：chunk 大小不固定，而是由每步时间预算反解（4.6 节代码 4-3）。

3.4.3 调度器实现：从 Python 循环到 C++ 与零开销

调度本身是纯 CPU 逻辑，但每步都要做（组批、分配 block、更新状态）。三代演进：vLLM V0 的 Python Scheduler（每步毫秒级）→ vLLM V1 的独立 EngineCore 进程、Python 调度器与持久 batch（2025）；async scheduling 是另一项重叠机制→ SGLang 的 zero-overhead scheduler 与 DeepInfer 的 ZOS（调度与上一步后处理藏进 GPU 前向时间里，QA 明言借鉴 SGLang 与 NanoFlow[DIQA26]）。去掉异步调度会怎样：decode 步长 5–10ms 中 CPU 要占 1–3ms，吞吐直接损失 20–40%（SGLang 论文与 vLLM V1 博客的动机部分均有此口径）[SGLANG24][VLLMV1]。

3.5 KV Cache 管理：布局、分页、复用、压缩、卸载

3.5.1 为什么"连续分配"是灾难，分页是解药

最朴素的 KV 布局：每个请求预留一段连续显存（按 max_len 预留）。三个恶果：① 预留了用不完（内部碎片，max_len 4096 平均用 800 → 80% 浪费）；② 请求长度各异导致显存空洞（外部碎片）；③ 无法共享相同前缀。vLLM 的 PagedAttention 借操作系统虚拟内存的思路：KV 切成固定 block（vLLM 默认 16 token/块，DeepInfer 为 128），每请求持有 block table 指向离散块。论文实测 KV 浪费 <4%（对比连续分配最差 ~80%），论文在其模型/负载、同等延迟下相对 FasterTransformer/Orca 的吞吐提升 2–4×；这不是普遍的并发上限倍数[VLLM23]。

连续预留像酒店只卖整层（按最大团建规模留房间），分页像按间卖：旅游团来多少住多少，退房立刻再卖。去掉分页会怎样：有效 KV 容量可能降低，吞吐变化还依赖长度分布、调度与 kernel；不能从分页开关直接套 2–4×，长尾请求（很短的对话）最吃亏。

3.5.2 前缀复用：RadixAttention 与 prefix cache

多轮对话、few-shot、Agent 循环都会重复发送几乎相同的前缀（系统提示 + 历史）。Prefix caching 把完成请求的 KV block 保留，新请求命中前缀直接复用。SGLang 的 RadixAttention 用基数树组织所有前缀、LRU 淘汰，论文报告高复用场景（复杂 prompt 程序）较 vLLM 最高 5× 加速（GPT/Llama 系、A100×8，2023-12 论文口径）[SGLANG24]；vLLM 的 automatic prefix caching、TensorRT-LLM 的 KV reuse 是同类。生产系统进一步把前缀 KV 挪出 GPU：Mooncake 用 CPU DRAM + SSD 做全局 KV 池（FAST'25）[MOONCAKE25]，DeepInfer 用 3FS 集群存 3–7 天（4.5 节）。前缀复用是 Agent 时代省钱的第一杠杆。

3.5.3 压缩与卸载：让 KV 更小、放得更远

  • 结构压缩（模型侧）：MQA/GQA 把 KV 头数减少（Llama-2-70B 用 GQA 已省 8×）；DeepSeek MLA 把 KV 压到低秩潜变量（DeepSeek-V2 按 60 层、512 维 latent 与 64 维 RoPE、BF16 计算：60×576×2 = 69,120 B/token，约 67.5 KiB/token，属于全模型数十 KB）[DSV2]。
  • 量化（数值侧）：KV cache 是容忍度较高的量化对象，KIVI（2-bit，per-channel K + per-token V）在保持精度的同时把 KV 压 8×（2024-02）[KIVI24]；DeepInfer 生产直接用 FP4 级主 KV + MXFP4 indexer KV[DIQA26]。
  • 稀疏/检索（访问侧）：H2O 重影注意力（保留累积分数高的 token）[H2O23]、Quest 按查询选块[QUEST24]、MInference 长 prefill 稀疏化[MINFER24]：只读"可能重要"的 KV。
  • 分层卸载（容量侧）：GPU→CPU DRAM→SSD 的阶梯；LMCache（vLLM 生态）、InfiniGen（OSDI'24）、Mooncake transfer engine 是代表；DeepInfer 的三层结构（4.5 节）是"存储集群化"的极端形态。
去掉这一层会怎样？并发上限 = 显存 ÷ 每 token KV：以 Llama-2-70B FP16 为例，80GB A100 除去权重（需 TP）后单卡可容纳 KV 约 20 万 token，只够同时服务个位数长上下文用户。KV 压缩 8× 就是并发×8、SSD 池化就是"命中率即利润"。

3.6 并行与通信：TP / PP / DP / EP / CP

单卡装不下大模型，就像一本书要多人一起抄：张量并行（TP）是每页拆成几半各抄一半再拼（切矩阵）；流水线并行（PP）是每人负责几章，传着抄（切层）；数据并行（DP）是每小组领不同的书整套抄（复制整个模型）；专家并行（EP）是百科全书按词条分人（切 MoE 专家）。前两种抄写时大家要不停对暗号（通信），后两种基本各干各的。

去掉并行会怎样？模型物理放不下（70B FP16 = 140GB > 单卡 80GB）一切免谈；但并行过度同样有害：TP 超出 NVLink 域后 all-reduce 走 PCIe/IB，带宽骤降一个数量级，吞吐不升反降。"并行度选择"本质上是在通信成本与容量/带宽收益之间找平衡。

3.7 算法级加速：FlashAttention、量化、稀疏化、投机解码

3.7.1 FlashAttention：从"少算"到"少搬"

标准 attention 先把整个 S=QK^T/√d 写回显存再 softmax 再读回乘 V：S 矩阵 O(n²) 大小，读写三遍。FlashAttention 的洞见：乘法本身不贵，贵在把中间矩阵搬进搬出 HBM。它把 Q/K/V 切块装进 SRAM（片上共享内存），用 online softmax（边累加边归一，数学上精确等价）在片内直接算完，不物化完整 n×n 中间矩阵，使额外存储从 O(n²) 降至 O(nd)；原论文定理 2 的 HBM 访问量为 Θ(n²d²/M)（M 为 SRAM 容量，以元素计），稠密计算仍为二次量级。v1（NeurIPS'22）证明 2–4× 加速且省显存[FA22]；v2（2023-07）优化并行划分与非 matmul FLOPs，decode 场景大幅增强[FA2]；v3（2024-07）用 Hopper 的 warp specialization 与异步流水[FA3]。去掉它会怎样：长上下文 prefill 的中间矩阵显存与访存爆炸：32K 序列的 S 矩阵（FP16）单头就要 2GB×读写三遍；今天所有引擎的全部 attention 路径都建立在其分块思想之上（FlashMLA、FlashDecoding、FlashInfer 均为其变体）。

3.7.2 量化：把每个数字从 2 字节压到 1/0.5 字节

三条路线：权重量化（W4A16：GPTQ[GPTQ22]/AWQ[AWQ23]，只压权重存储，计算时反量化，是 LMDeploy TurboMind 的主打；W8A8：SmoothQuant[SQ22] 权重激活都压）；全链路低精度（FP8：Hopper 起硬件原生支持，DeepSeek-V3 训练推理全 FP8[DSV3]；FP4：Blackwell 起原生，DeepInfer 用 FP4 KV 与 MXFP4 专家权重[DIQA26]）；KV 量化（3.5.3 节）。收益直接换算成 §1.4 的算术强度：decode 的算术强度 ∝ 1/每参数字节，W4 相对 FP16 直接×4。代价：精度损失任务相关（量化研究的评测口径从困惑度走向下游任务），错误累积在长生成下更明显。生产系统普遍"权重可以激进、激活与 KV 保守"。

3.7.3 稀疏化：不读"不重要"的 KV

训练后稀疏（H2O 重影注意力：按累积注意力分数保留 top-k token[H2O23]）、查询感知检索（Quest：每 query 只取相关块[QUEST24]）、预填充稀疏（MInference：长 prompt 的 attention 天然集中在对角/竖条模式，2024-07）[MINFER24]、以及模型原生稀疏（NSA[NSA25]/DSA[DSA25]：训练时就学会稀疏注意，V4.1-Flash 的 indexer 属于这一族）。去掉会怎样：不会"错"，只是长上下文的成本二次增长；稀疏化是"用可控的近似换线性成本"。

3.7.4 投机解码与并行解码：一次前向多产 token

正常 decode 像邮件一封一封寄；投机解码像先把可能要写的回信草稿都打好，一次性拿去盖章：草稿（draft）便宜，盖章（verify）用的是正式模型一次前向，盖过章的部分全部有效。数学上由拒绝采样保证输出分布与原模型完全一致（Leviathan et al. ICML'23；Chen et al. 2023）[SPEC23]。
# 代码 3-1 · 投机解码期望加速（ γ 个草稿、第 i 个被接受概率 αᵢ ）
E[每步产出 token] = (1 − α^(γ+1)) / (1 − α)     # α=0.8, γ=4 时 ≈ 3.36 个/步
成本 = 1 次草稿前向(便宜) + 1 次验证前向(γ+1 个位置并行, compute 更饱满)
假设：逐位置接受率独立同分布，α 为条件接受率；E 含修正/bonus token。
净加速条件：T_draft + T_verify < E × T_AR；一般情形用实测整轮耗时和产出，不只看 α。

3.8 特殊负载：MoE、超长上下文、多模态、异构硬件

3.8.1 MoE 推理：权重全驻留 + 专家不均衡 + all-to-all

MoE（如 Mixtral 46.7B/激活 12.9B[MIXTRAL24]、DeepSeek-V3 671B/激活 37B[DSV3]）推理的三重挑战：① 全部专家权重必须常驻（不激活也要在显存里等着被路由）→ 必须跨卡（EP）或卸载（LRU+投机预取，Mixtral-offloading 思路）；② 每个 token 只访 8/256（V3）的专家，batch 内专家负载天然不均 → EPLB 冗余副本重排；③ EP 的 all-to-all 延迟在小 batch 时占比高 → DeepEP 提供 NVLink/RDMA 两套内核，prefill 用正常内核、decode 用低精度内核压缩流量[DEEPEP25]。SGLang 2025-05 实测 DeepSeek-R1 大规模 EP：EP72 decode 22,282 tok/s/节点，相对 TP16 方案 5.2×（H100/H200，官方博客口径）[SGEP25]。

3.8.2 超长上下文：64K 到 1M

四件事配合：位置外推（YaRN 类 RoPE 缩放，DeepSeek-V3 用 s=40 外推到 128K[DSV3]）、prefill 并行（CP/Ring Attention，可跨 32×A100 算 1M 上下文[RING23]）、KV 侧稀疏（NSA/DSA/MInference/Quest，把 O(L²) 注意力降到 O(L·k)，DSA 技术报告口径 k=2048 仍保精度，2025-09）[DSA25]、以及长上下文评测（RULER：一半模型过不了 32K 线，2024）[RULER24]。DeepInfer 的答案是把模型结构（indexer+SWA+YOCO）与 KV 存储（3FS）一起设计。

3.8.3 多模态（VLM）：两段式前向

VLM = 视觉编码器（ViT/卷积）+ LLM 主干。系统要点：图片变数百 token 插入序列（VL2 动态 tiling 可把 729→196 token，DeepSeek-VL2 论文口径）[VL224]、视觉 token 剪枝（FastV：深层视觉 token 的平均注意力效率较低；system prompt 的注意力效率反而很高，K=2/R=50% 时省 45% 计算，2024-03）[FASTV24]、以及 VE 独立部署（DeepInfer 的 VE 引擎单卡即可、推荐便宜卡）[DIQA26]。

本章小结
  1. 十层栈环环相扣：图编译与算子（L1–L2）决定单步多快，调度与 KV（L4–L5）决定 GPU 多满，并行（L6）决定能装多大、算法加速（L7）决定每 token 多便宜。任何一层缺失都会让其他层的收益打折。
  2. 四大算法杠杆各有公式可算：FlashAttention 降低 HBM 搬运并避免二次中间存储，不能概括成线性 HBM 访问，量化乘的是算术强度，稀疏化换的是线性成本，投机解码的期望产出 = (1−α^(γ+1))/(1−α)。
  3. MoE/长上下文/多模态/异构在 2025 年后已是主战场：专家并行与 all-to-all、KV 稀疏与存储分层、VE 独立部署、TileLang 双后端。定制化引擎的护城河恰恰在这些"通用框架难以同时伺候"的地方。

几个反直觉但关键的架构决定（QA 文档原文口径）[DIQA26]：

  • Prefill 和 Decode 用不同大小的 EP：prefill 尽量小（EP2–8，"HBM 允许的最小值"），decode 尽量大（EP64–128，"GPU 允许的最大值"）。原因：prefill 是算力瓶颈，专家切太碎通信占比高；decode 是访存瓶颈，Wide-EP 让每卡只驻留一小部分专家，每卡驻留专家容量可随分片减少，但每步实际读取量还取决于 batch 的专家覆盖、负载均衡与通信，不能认定随 EP 无条件线性下降（QA："Wide-EP substantially reduces per-step memory traffic in the MoE expert part"）。
  • KV 存储用专用 3FS 集群而非分层卸载：任何 prefill 机器都能命中任意前缀，避免"前缀亲和路由"和负载均衡打架；存储节点故障率比计算节点低一个数量级以上，KV 生命周期与计算节点解耦。
  • 不用 TP/PP："TP and CP are not used for now"（当前不用张量并行；CP 仅在源码中留有 balanced CP 的实现用于超长序列）。通信全部压在 EP 的 all-to-all 上（vendor 里的 DeepEP）。注意力部分用 Attention DP（#DP = #EP），每张卡持有一部分请求的完整注意力。
  • VE/P/D 三段全部独立部署、独立扩缩：prefill 按非缓存 token 数扩、decode 按在途请求数扩；长尾请求在 decode 引擎缩容时有 1 分钟宽限期，未完成请求连同 KV 一次性转发给其他引擎继续解码。

4.4 执行引擎：一次 step 的"四拍"与零开销调度

引擎内核（deepinfer/engine/llm_engine.py，文件头注明 "Derived from vLLM; modified by DeepSeek"）沿用了 vLLM 的 iteration-level 调度骨架，但把调度器本体搬进了 C++（deepinfer/_C/engine：Scheduler / BlockManager / SequenceMetadataPool / RequestOutputPool / process_MTPInfo 都是 C++ 实现），Python 层只做编排。这正是 QA 里"asynchronous scheduling (zero-overhead batch scheduler)"的落地。

4.4.1 四拍执行

Worker.execute_model_step()（worker/worker.py）把每一步收成固定的四拍，docstring 原文："every step goes through this Forward-Post_process-Sample round"：

# 代码 4-1 · DeepInfer 一步执行的"四拍"（据 worker/worker.py:execute_model_step 精简，注释为本文所加）
def execute_model_step(step):          # ZOS=零开销调度 默认开启
    # ① 本步前向：主模型（prefill 或 decode），可走 CUDA Graph
    main_out = model_runner.execute_main_model(seq_metadata, gpu_cache)

    # ② 后处理【上一步】的结果 —— 关键：延迟一拍，与本步前向在时间上重叠
    request_outputs = post_process(prev_step_state)   # 等 sample 完成事件 → 引擎回调

    # ③ 本步采样：拒绝采样(投机验证)/温度/top-k 都在融合 kernel 里
    sampler_out = model_runner.execute_sample(...)    # 同时产出 draft 的置信度

    # ④ 本步后处理：prefill 步或未开 ZOS 时当场做；
    #    ZOS 的 decode 步留到下一步（回到②），GPU 全程不空转
    prev_step_state = curr_step_state

代码 4-1 · 依据 DeepInfer 源码 deepinfer/worker/worker.py L88–189（main 分支 2026-10 快照）改写的伪代码。QA 文档口径："while the GPU runs forward(N) → sample(N), the CPU concurrently runs schedule(N+1) → launch_forward(N+1) → post-process(N−1)"，并注明该思路"following existing implementations (SGLang, NanoFlow)"[DIQA26]。

传统执行像单人家务：洗衣机转完（GPU 前向）→ 人停下来晾衣服（CPU 后处理）→ 再回去按下一桶（调度）。四拍重叠像流水线主妇：洗衣机转着第 N 桶时，人晾第 N−1 桶、顺便把第 N+1 桶衣服塞进盆里，洗衣机（GPU）永远在转。如果去掉这个设计：每步 decode 后 GPU 都要停下来等 CPU 做批调度与后处理（毫秒级），decode 每步本来就只有几毫秒，等于一半时间 GPU 在发呆。QA 与 SGLang 论文都把这类 CPU-GPU 串行化列为 decode 吞吐的头号杀手[SGLANG24]。

4.4.2 ZOS 下"迟到一步"的元数据修正

延迟一拍的后处理带来一个连锁问题：调度第 N+1 步时，第 N 步的采样结果（尤其投机解码实际接受了几个 draft token）还没回来，CPU 侧每个请求的 seqlen_q/seqlen_k 是过期的。DeepInfer 的解法是把修正也搬到 GPU 上：_correct_seqlens_qk() 把上一步采样产物（接受 token 数、置信度）留在显存里，用 kernel 算出修正后的 seqlens 与请求重排表（remap），D2H 回来只用于"更正 CPU 账本"，不阻塞本步前向。DSpark 的变长验证预算也在这条路径上用 TileLang kernel（累积积 → 全局排序 top-k → fused remap scatter）算出，写回 pinned buffer[DIQA26]。

4.5.2 SWA bounded replay：常数代价重建滑窗缓存

滑窗层的 KV 只在最近 W 个 token 内有意义，但严格重建需要重放最后 2,560 个 token 过 20 层 decoder。V4.1 的做法：只重放最后 128 个 token，且重放时注意力窗口也被截断在重放段内，得到一份"近似但自洽"的滑窗 KV，固定模型与重放窗口后，代价对总上下文长度近似为常数；仍随模型层数、窗口大小和核效率变化。QA 给出量化效果：prefill 总计算量"nearly halving"（近乎减半）[DIQA26]。源码开关即 README 中的 DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact + DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140（128 窗口 + 最大回退长度）[DI26]。

4.5.3 KV 的搬运如何不挡路

命中后的取回链路（QA "cache-related overhead" 节）：匹配在 Entrypoint 以 CHECK 角色对本地 kvcache-store 做纯元数据哈希链匹配（必须在路由前完成，无法隐藏）→ 拉取在独立进程异步把 KV 从 3FS 搬进主机共享内存 → 换入由引擎进程内线程执行，"目标是逐层 H2D 与前向计算重叠"，且因 CUDA copy engine 对细粒度块拷贝低效，换入用 GDR（GPUDirect RDMA）：网卡直写显存、打满 PCIe、不占 SM[DIQA26]。

本章小结（4.1–4.5，记住三句话）
  1. DeepInfer = "EPD 三段分离的集群系统"的开源内核：prefill 用小 EP、decode 用 EP64–128 Wide-EP，KV 存独立 3FS 集群（TTL 3–7 天、~100 PiB），这是它与单机引擎的根本差异。
  2. V4.1-Flash 的模型结构（MLA 压缩 KV、indexer 稀疏、SWA+YOCO 跨层复用、FP4 KV、MTP 头）每一项都直接服务于"KV 变小、decode 读得更少"的系统目标——模型是为引擎设计的。
  3. 引擎内核的关键工程：调度器 C++ 化 + 四拍流水把 CPU 工作藏进 GPU 前向里（ZOS），过期的批元数据在 GPU 上用 kernel 修正。删掉任何一条，decode 的毫秒级步长都会被 CPU 开销吃掉一半。

Decode 侧的均衡同时照顾两个维度：请求数（决定每步 batch 大小）与 KV 总长度（决定 attention 成本），启发式地把短请求发给"并发低但 KV 长"的卡、长请求发给"KV 短"的卡。EPLB 则在专家维度均衡：每卡除本职专家外多驻若干冗余热专家副本，按统计窗口（prefill 100 步/decode 1000 步）周期性重排专家，权重经 NVLink symm_mem 在组内洗牌。实测不均衡度 moe_lb（最慢 rank/均值）prefill 1.045–1.074、decode 1.090；整套 LB 让线上达到离线理想基准的约 80%[DIQA26]。

6.1 高吞吐低延迟调度与 SLO 保障

进展：goodput 成为一等目标（DistServe/Sarathi-Serve 之后成为论文标配口径）；Llumnix（OSDI'24）做跨实例动态调度 + KV 迁移（prefill P99 ≤5.5×、成本 −36% vs INFaaS 口径）[LLUMNIX24]；ServerlessLLM（OSDI'24）面向 serverless 冷启动，checkpoint 加载比 Safetensors 快 3.6–8.2×、负载延迟改善 10–200×[SLLM24]；生产栈层出：vLLM Production Stack（UChicago/LMCache，2025-01）、AIBrix（字节，2025-02）把 router/session-aware 调度/K8s 弹性打包[VLLMPS25]；NVIDIA Dynamo（2025-03）以 KV 感知路由 + NIXL 把编排做成标准件[DYNAMO25]。Agent 负载成为新主战场：Autellix（2025-02）把 agent 程序建成动态 DAG 调度，吞吐 4–15× vs vLLM（同延迟）[AUTELLIX25]；vLLM 2025–2026 的 Bi-Directional KV Transfer 把多轮 agent 的 TTFT 改善最高 3.3×[VLLMKVT26]；DeepInfer 的 agent TTL=3 天/chatbot=7 天是生产侧 KV 生命周期管理的直接证据[DIQA26]。

开放问题：agent 请求间 DAG 依赖与连续批调度的联合优化尚无理论；thinking/answer 双相 SLO（推理链长、答案段要快）尚未形式化；多租户多层 SLA 的公平性与抢占代价（2026-08 有首批工作）；过载下的早拒/降级（Mooncake Early Rejection 的推广）。

6.2 KV Cache 管理：全局池、传输层与新存储层

进展：传输抽象层 NIXL（2024-12 开源，插件式 UCX/GDS/S3 后端）成为 Dynamo/vLLM PD 分离的底座[NIXL25]；Mooncake Store 2025-03 开源，vLLM 自 2024-12 官方支持 Mooncake Transfer Engine、2025-12 TRT-LLM/vLLM v1 接入、2026 年演进到跨引擎 KV 复用（FlexKV）[MOONCAKE25]；LMCache 做分层 store（HBM/DRAM/NVMe/Redis + P2P 共享），系统论文 2025-10 发布[LMCACHE25]；硬件侧出现新层：华为 OceanStor M900（HC 2026，原生 KV 语义、单节点 480GB/s）与业界首个量产 CXL KV 服务器（Penguin Solutions，2025–2026）[M90026]；语义/记忆缓存兴起：MemOS（2025-07）用 MemCube 统一明文/激活/KV 三类记忆，宣称 token 节省 35%[MEMOS25]。SGLang×Mooncake PD 实测 KV 传输仅占 TTFT 2.4%（164.3 GB/s，2026）[MOONCAKE25]。

开放问题：跨引擎 KV 格式标准缺失（块大小/量化/哈希链各不相同）；语义缓存命中率不可复现（Mooncake 论文指出公开基准高估实际复用率，线上理论上限 ~55%）；KV 池化后的计费、隔离与一致性；CXL/SSD 新层的统一抽象与基准。

6.3 推测式解码与并行生成

进展：EAGLE-3（2025-03）报告 temp=0 下 4.1–6.5× 加速，vLLM Speculators v0.3（2025-12）支持其训练[EAGLE3]；MTP 成为部署标配（DeepSeek 系、GLM 系）；置信度调度进入生产（DeepInfer DSpark：+1.6%~+11%，验证量 −30%）[DIQA26]；P-EAGLE（AWS，B200）单前向并行出 K 个 draft，再快 1.69×[PEAGLE26]；扩散/并行解码商用：Inception Labs Mercury（2025-02 首发，1000+ tok/s）、Mercury 2.5（1107 tok/s、260K ctx）、Google Gemini Diffusion（I/O 2025 预览，外部实测 ~1000–2000 tok/s）、开源 DiffusionGemma（2026-06，25.2B MoE）[MERCURY25]。负面结果同样重要："Speculative Decoding: Performance or Illusion?"（MLSys 2026）实测 EAGLE 在 Llama3.1-8B/GSM8K 上从 bs=1 的 1.73× 掉到 bs=128 的 1.21×；"Batch Speculative Decoding Done Right"（2025-10）指出公开 batch 实现存在正确性 bug 与"被最差序列拖垮"的截断问题；工程经验法则"bs>32 关投机"流传（第三方）[MLSYS26SD]。

开放问题：batch 与投机的结构性冲突（memory-bound→compute-bound 切换点随模型/硬件漂移，需在线自适应）；temperature>0 时等价性证明的边界；扩散 LLM 与 KV 语义不兼容，需要全新 serving 栈。

6.4 分离式 Prefill/Decode 与算力解耦

进展：学术（DistServe/Splitwise/Mooncake）→ 工业标准件（Dynamo/NIXL，2025-03）→ 引擎内置（vLLM v0.8 起、SGLang、TRT-LLM 2025 主打特性）[DYNAMO25][VLLMLSC25]；vLLM 2025–2026 演进路线：Push-based KV Transfer（prefill 直写 decode 显存）→ Bi-Directional（多轮 agent）→ 混合 SSM 状态迁移[VLLMKVT26]；DeepSeek 生产口径：E/P/D 三分离、P:D≈1:1、最小单元 64P+64D、跨相邻 DC ~400Gbps/GPU[DIQA26]。

开放问题：P:D 配比随负载漂移的自适应；分离后 prefill 侧 HBM 冗余的再利用；跨 DC RTT 抖动下的 SLO 保障；KV 传输与计算重叠已接近极限（layer-wise streaming 后剩余收益小）。

6.5 MoE 推理与超长上下文

进展：NSA（DeepSeek，2025-02，ACL'25 最佳论文）确立"原生可训练稀疏注意力"路线[NSA25]；DSA 随 V3.2-Exp 上生产（2025-09，lightning indexer + top-2048，API −50%+）[DSV32]；超大 EP 实践成熟：DeepSeek 生产 decode EP64–128[DIQA26]、SGLang 96×H100 复刻并扩展至数百卡[SGEP25]；Kimi K2 系列（2025-07 起开源，1T 总参/32B 激活、MLA、256K ctx）延续 MLA+MoE 路线[K2]；DeepSeek-V4.1-Flash（2026-10）以 CED 架构 + indexer + SWA + YOCO 把 1M 上下文做进 763B 模型[DIV4126]。

开放问题：稀疏注意力与前缀缓存的块语义冲突（被选中的 token 跨块复用困难，DSA 类模型的多轮复用比连续 KV 更棘手）；KV 压缩的可逆性验证；超长上下文 TTFT 的用户可感知上限；专家负载突变下 EPLB 的时滞。

6.6 异构硬件与国产栈

进展：昇腾路线图（HC 2025-09）：950PR（2026-Q1，主打 prefill）→ 950DT（2026-Q4，训练+decode）→ 960/970；DeepInfer 支持 Ascend 950（CANN 9.2），TileLang-Ascend/DeepGEMM-Ascend 同步开源[DI26][ASCEND25]；寒武纪 vllm-mlu 2026-04-24 day-0 支持 DeepSeek-V4[MLU26]；摩尔线程 MUSA 后端合入 SGLang 主线；AMD MI300/MI325 在 MLPerf v5.0 与 H200 对位（2025-04）；TPU 侧 JetStream 并入 tpu.vllm.ai（2026-02）。"day-0 支持新模型"已成为国产芯片竞争的核心话术。

开放问题：算子生态碎片化（Triton kernel 四家国产硬件均不直接支持，各持私有 DSL：AscendC/CNRT/MATE）；MLA/MoE/MTP 新结构的跟进速度差距；异构混布集群的调度与 KV 互传缺统一抽象；MLPerf 级中立基准覆盖不足导致"各家自说自话"。

6.7 自动编译与算子 DSL

进展：TileLang（2025-01 开源、ICLR 2026 论文）证明 tile 级 DSL 可同时覆盖 CUDA/AMD MI300X（FlashMLA 移植，2025-04）/昇腾（2025-09）/Metal（2025-10）多后端，DeepInfer 的 DSpark 调度算子即用其编写[TILELANG26]；NVIDIA 开放 CUDA 编译栈（cuda-tile，MLIR 基 tile IR，随 CUDA 13.1 开源，2025-10 起）与 CuTe Python DSL（编译时间比 C++ 路线低最多两个数量级，CUTLASS 4.8，2026-09）[CUTLASS26]；DeepJIT（轻量 xPU kernel JIT，2026-10 出现在 DeepSeek GitHub org）；FlashInfer 成为 vLLM/SGLang 共享 kernel 层，SGLang 2026 年向 TVM-FFI 按需 JIT 体系迁移。

开放问题：DSL 碎片化（Triton/TileLang/CuTe/cuda-tile/MATE/AscendC 并存）与长尾算子维护负担；JIT 冷启动与确定性；"模型结构向系统让步"的边界（稀疏/SWA 损害质量时的回退机制）。

6.8 模型—系统—芯片协同设计

进展：协同已成标配而非口号：MLA（DeepSeek/K2/GLM）、MTP 投机头、GQA、SWA、DSA/indexer 逐个从"论文技巧"变成"模型出厂配置"，引擎则为其反向定制（DeepInfer 的 SWA bounded replay、StateBlock、Engram 全是"模型结构在引擎里的投影"）[DIQA26]；FlashMLA/DeepGEMM/DeepEP 是"模型定义的 kernel"（MLA decode、FP8 GEMM、MoE all-to-all 各自专用）[DSOSW25]；昇腾 950 与 SM100 的硬件特性（HiBL HBM、FP4 单元）直接进入 DeepInfer 的低精度决策。

开放问题：协同的僵化风险：模型绑引擎、引擎绑芯片后，社区复现与第三方创新变难（DeepInfer 单模型单硬件即是显例）；结构创新的评测标准（KV 压缩了，检索质量掉没掉？）滞后于结构迭代。

6.9 服务级目标与成本：能耗、碳与"每 token 成本"

进展：Splitwise 首次把功率写进推理目标（-15%~-25%）[SPLITWISE24]；DeepInfer 公开"每 GPU 小时营收 38 美元（谷电价）"——推理系统第一次把电价写进 KPI[DIQA26]；API 价格战的技术面：DeepSeek V3.2（DSA，−50%+）与 V4.1 的降价曲线背后是"KV 进 SSD + FP4 + Wide-EP"的组合账。

开放问题：主流基准仍无能耗/碳口径；"每 token 成本"缺乏跨厂商可比的公开模型（推理侧碳核算几乎空白）；长尾 P99.9 与成本的联合优化。

本章小结
  1. 2025–2026 的主旋律是三件事落地：PD 分离成为标配（Dynamo/NIXL/Mooncake 系）、KV 从"显存问题"升级为"存储系统问题"（全局池/TTL/跨引擎复用）、投机解码从"能不能"进入"何时值得"（batch 冲突与置信度调度）。
  2. 负面结果与边界同样关键：大 batch 下投机收益衰减（1.73×→1.21×）、公开基准高估前缀复用率、稀疏注意力与前缀缓存互相打架。工程界正在为这些边界设计自适应机制。
  3. 最大的结构性变化在生态：模型—引擎—芯片三方互相"投影"（MLA→FlashMLA→950PR；MTP→DSpark→SM100 FP4），开源组件（DeepSeek 开源周→TileLang→cuda-tile）第一次让外部可以复现和研究这种协同。

7总结与展望：后续方向

7.1 当前引擎的定位

通用引擎（vLLM/SGLang/TRT-LLM）吃宽矩阵：多模型、多硬件、开箱即用，吸收一切可泛化的单点技术；定制引擎（DeepInfer 类）打深极限：单模型族、专属拓扑、贴 SASS 与 SSD，把"专"的红利换算成 $38/GPU·h；编排层（Dynamo/Mooncake/Production Stack）负责把两者组装成集群服务。三层分工在 2026 年已稳定，且互相开源反哺（vLLM V1 致谢五个引擎；DeepInfer 自述基于 vLLM）。

7.2 尚未解决的问题（按紧迫度）

  1. Agent 负载的调度理论缺位：DAG 依赖、超长会话、双相 SLO（thinking 慢答案快）、KV 跨请求生命周期。现有 continuous batching 理论（Orca/Sarathi 一族）没有覆盖"请求之间有依赖"的世界，而这正在成为主要流量。
  2. batch 与投机的结构性冲突：投机解码的收益随并发、草稿成本和验证预算变化；低并发常有计算余量，高并发也可能获益，须与普通解码同条件比较，而低并发恰恰不赚钱；DSpark 式动态预算是补丁不是终局，需要的是"随 batch 在线切换生成策略"的自适应机制与理论。
  3. KV 生态碎片化：块大小、量化格式、哈希链、TTL 语义各引擎互不兼容；跨引擎/跨厂商 KV 复用（迁移模型、混合集群、灾备）没有标准：NIXL/FlexKV 在做传输层，格式层仍是空白。
  4. 稀疏注意力 × 前缀缓存：因果模型在模型、token、位置与适配器相同时可复用前缀 KV 及索引状态；DSA 的 query 相关 top-k 选择不否定此前缀复用。开放问题是压缩、淘汰、块布局和跨实例迁移的兼容性，直接威胁 Agent 场景的成本曲线。
  5. 能耗与碳成本不可见：所有主流基准都不报每 token 焦耳；而电力已是推理成本的一阶项（DeepInfer 的谷电价定价是明证）。
  6. 可复现横评基础设施缺失：版本锁定 + 全条件披露 + 第三方运行的公开基准不存在，导致选型靠信仰与营销。

7.3 短期可落地（0–2 年）

  • PD 分离 + KV 全局池的"商品化"：Dynamo/NIXL/Mooncake/LMCache 的组合会变成云厂商一键产品；中小企业不再自建。
  • 置信度自适应投机解码：DSpark 的思路（接受概率预测 + 预算分配）会被 vLLM/SGLang 吸收为默认开关，配合"大 batch 自动关闭"策略。
  • FP4/MXFP4 全面进生产：Blackwell 与昇腾 950 的 FP4 单元 + DeepInfer 已验证的 KV FP4 路线，会在 2027 年前成为大流量服务的默认精度（权重激进、KV 谨慎的分层策略）。
  • TileLang/Triton 多后端成为算子层的"写一次到处跑"层：国产芯片 day-0 支持新模型的速度竞赛会推动 DSL 统一（cuda-tile 开源是同方向信号）。
  • Agent 专用服务特性：会话亲和路由、KV TTL 策略化、结构化输出编译机、流式工具调用解析（DeepInfer recipe 的防注入与增量 KMP 是模板）成为标准 API。

7.4 长期研究方向（3–5 年）

  • 生成范式的更替：扩散/并行解码 LLM 若证明可在质量上对齐 AR 模型，"逐 token + KV cache"的整套世界观（本文全部内容的地基）将被重写——serving 栈要为"一次产出一段"重新设计内存与调度。这是最大的不确定项。
  • 推理系统进入"存储系统"成熟期：KV 的全局寻址、跨引擎复用、纠删码与 GC、SSD/CXL 分层的统一抽象。类比数据库 buffer pool 的演进史，最终会出现"KV OS"标准。
  • 模型—系统—芯片协同的自动化：给定目标负载与硬件约束，自动搜索模型结构（KV 形态/稀疏模式/MTP 深度）与引擎配置的联合设计空间（把 DeepInfer 工程师做的事变成编译器问题）。
  • SLO 与成本的联合最优理论：goodput、能耗、碳、价格的统一目标函数；过载下的早拒/降级/优先级有了理论根基。
  • 端云一体的推理：3B–30B 端侧模型 + 云端大模型的路由与协同缓存（端侧命中就不上云），把"前缀复用"扩展到设备维度。
本章小结
  1. 三年内最确定的四件事：PD 分离商品化、投机解码自适应化、FP4 生产化、算子 DSL 统一化，全部已有生产级证据（Dynamo、DSpark、DeepInfer、TileLang）。
  2. 并行或扩散式生成可能改变 KV cache 的占用和调度方式；其适用范围仍取决于生成质量与端到端成本。
  3. 选型条件：多模型/多硬件/快速迭代选 vLLM 或 SGLang；单一 DeepSeek 系模型 + 大规模集群 + 有平台工程能力，参考 DeepInfer 路线；评估时同时计入运维成本与模型迭代频率。
