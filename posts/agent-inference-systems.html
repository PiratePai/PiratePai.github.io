0 导读：从一次生成到一项可恢复的任务

本文主线：任务状态 → 上下文装配 → 模型与工具调度 → 持久化恢复 → 最终状态验收。本文回答四个问题：Agent 时间和费用究竟花在哪里？怎样缩短上下文又保住任务事实？工具等待和多分支怎样调度？进程中断后如何继续，并检验没有重复执行动作？

这里的 Agent 指模型根据当前任务状态选择动作、读取外部观察并继续求解的程序。ReAct 将推理与环境动作交替组织，为理解这条循环提供了早期范式。[REACT] 本篇研究上线后的运行系统；训练时如何产生轨迹、更新策略与同步权重，见Agent 与强化学习。

1 预备知识：状态机、上下文与记忆

1.1 状态是事实，提示词是一次读取

任务状态至少包含目标、约束、已确认事实、待办动作、工具结果引用、预算余额和终止原因。一次模型调用的上下文是从这些信息中选出的输入，而非全部状态的唯一副本。模型生成的新结论也应区分“已观察事实”和“待检验假设”。

项目档案记录已经发生的事情；会议材料只选本次讨论需要的部分。删去会议材料中的旧日志，不应该同时删掉档案里可追溯的原始凭据。

本章小结
  1. 任务事实应独立于某一次提示词保存。
  2. 上下文、检查点、长期记忆和 KV 分别解决不同问题。
  3. 压缩与缓存可以优化读取过程，最终状态仍需可追溯。

2 时间与费用：找到任务的关键路径

2.1 用依赖图计算等待

一个任务由模型调用、工具调用、排队、存储和验收等节点组成；依赖边表示后一项必须等待前一项。没有资源争用时，任务时间至少是依赖图中最长路径的时长。真实系统还要加上资源排队与重试。把所有节点耗时相加，会高估已经并行的部分；只看模型时间，又会低估任务等待。

表 2-1 · 人工构造的关键路径例子，不是服务实测
阶段时长依赖
第一次模型调用1 秒任务开始
工具 A / 工具 B8 秒 / 5 秒都依赖第一次调用；相互无依赖
最终模型调用1 秒等待 A、B
验收与保存0.2 秒等待最终输出

串行执行工具时，总耗时为 1+8+5+1+0.2=15.2 秒；允许二者并行且资源足够时是 1+max(8,5)+1+0.2=10.2 秒。此后即使两次模型调用都快一倍，总时间也只从 10.2 降到 9.2 秒。这个算式解释了为何模型加速未必等比例缩短 Agent 任务。

2.2 完整成本账本

任务费用应累加所有模型、验证器、工具、存储和重试成本。以同一任务集为分母，记录成功率和平均任务成本；以成功次数为分母时，用所有尝试总成本/成功任务数，避免把失败花掉的钱丢掉。工具订阅、自部署 GPU 与空闲容量如何摊销，应另写计费假设。

首个用户可见响应、首个有效工具动作、最终产物完成时间分别记录。展示“正在处理”可能改善交互感受，却不会减少完成任务的时间。若用户有明确截止时间，还要统计截止时间内的成功比例。

本章小结
  1. 任务时间由依赖、关键路径和资源排队共同决定。
  2. 并行化只适用于没有数据依赖且资源允许的节点。
  3. 模型、工具、验证和失败重试全部进入任务成本。

3 上下文工程：减少输入而保留任务依据

3.1 装配顺序与数据类型

本文建议把上下文分为稳定指令、当前任务约束、结构化状态、相关证据、最近交互五部分。原始日志与大文件保留在外部，通过路径、版本和摘要引用；只读当前决策需要的片段。检索结果带来源和时间，冲突事实保留冲突标记，不能由摘要悄悄选一个当真。

Anthropic 的工程文章讨论了压缩、结构化笔记和分工；同时指出压缩过度可能丢失后续才显得关键的细节。[CTX] 因此压缩不能只按 token 缩减比例验收，要检查约束、数值、失败尝试、未决问题和证据链接是否仍然可恢复。

3.2 摘要、检索与裁剪的误差

表 3-1 · 本文建议的上下文策略检查
策略主要收益失败模式与检查
裁剪旧工具输出减少重复 token删除了未解决错误；先保留错误码、产物位置与状态
摘要压缩缩短长会话数字或约束丢失；用任务事实清单做前后对照

结构化任务笔记恢复目标和进度状态过期；写入版本并在恢复时核验外部环境

3.3 压缩与前缀缓存的交互

SGLang 的 RadixAttention 研究复用多次模型调用中的公共前缀。[SGL] 缓存命中取决于实际 token 前缀及服务端兼容条件；“文字意思相同”不等于相同 KV。重写较早位置的摘要会缩短最长公共前缀，其后的缓存不能直接复用。稳定内容置前、变化内容置后，是值得验证的布局策略，不能以改变指令语义为代价。

一次压缩的净时间收益，可以按本文账本写成“后续各轮节省的处理时间之和 − 压缩耗时 − 新增检索耗时 − 因前缀变化增加的重算时间”。各项应实测；如果任务即将结束，压缩可能来不及回本。更长窗口也不能消除事实筛选、冲突处理和无关信息干扰。

本章小结
  1. 上下文优化要保住约束、事实与证据引用。
  2. 摘要和检索各有误差，应以完整任务结果验证。
  3. 前缀缓存按实际 token 复用，压缩收益需扣除重算与额外调用。

4 工具与模型调度：并行、限流与背压

4.1 先检查依赖，再决定并发

独立的只读查询可以并行；读取工具 A 的结果再构造工具 B 参数时必须串行。共享文件、同一数据库对象或同一外部资源的写入，应明确冲突处理与提交顺序。多个 Agent 分支共享任务预算，生成候选计划与真正执行计划分开记录。

模型服务善于组批生成；工具可能等待网络、磁盘或外部任务。工具等待期间，运行时可以释放工作线程或计算槽，但是否保留会话 KV 取决于缓存策略。等待期间的缓存占用、重载成本和下一轮延迟，应一起比较。

4.2 背压防止局部加速拖垮下游

背压指下游处理不过来时限制上游产生新工作。本文建议分别设置任务数、模型请求数、每种工具并发数和排队上限，而不是只设一个全局线程数。某个工具持续返回限流时，降低该工具的并发，避免模型继续产生无法执行的动作。

为任务建立统一截止时间；各节点超时不应超过剩余时间。重试只针对明确可重试的暂时故障，使用次数上限和退避；参数错误需要修正，重复相同请求不会自动成功。取消要传播到在途节点，记录哪些已经停止、哪些仍可能完成及产生费用。

4.3 任务级调度与请求级调度

把每条分支都当独立用户，会使大扇出任务占据过多资源。本文建议在任务级分配预算、优先级和并发配额，再在模型服务内部做组批。跨会话的前缀复用仍需满足隔离和授权条件；不能让缓存命中改变工具可访问的数据范围。

本章小结
  1. 并发前先确认数据依赖与资源冲突。
  2. 下游限流应反馈到上游，重试受统一预算约束。
  3. 任务级配额与模型服务组批共同决定体验。

5 持久化与恢复：检查点为何还不够

5.1 保存什么，何时恢复

一个检查点至少保存任务 ID、逻辑步骤 ID、状态版本、已完成动作、结果引用、剩余预算和下一动作。LangGraph 的 checkpointer 保存线程执行状态，持久化存储可以支持中断后的恢复；内存实现则不能跨进程重启保留。[PERSIST] 故障处理还涉及重试、超时和恢复语义，具体支持应按所用版本核对。[FAULT]

[PERSIST] LangChain 项目. LangGraph Persistence，官方滚动文档，首发日期未标注；核验快照 2026-11-04。原文：“resume after an interruption, recover from a failure”（在中断后继续，并从失败中恢复。）原文。

恢复时重新核对工作区版本、外部对象状态和数据有效期。如果文件已被别人修改、订单状态已改变，旧计划可能失效。恢复计算与重新执行外部写操作是两个不同决定；检查点不能单独保证外部副作用恰好发生一次。

幂等指同一个逻辑动作重复提交，不会重复产生业务效果。幂等键必须绑定逻辑动作，不能每次重试生成新键；同一键对应不同参数应报冲突。可靠去重通常需要工具或业务存储在同一事务中提交效果与键记录。若外部服务不支持幂等或结果查询，遇到结果未知应先对账，不能一律盲重试。

  3. 恢复示例覆盖明确故障窗口，真实服务仍需对账和更多故障注入。

6 可观测性：把一项任务拆成可归因的记录

6.1 事件应能还原依赖关系

表 6-1 · 本文建议的最小事件字段
字段用途常见遗漏
task_id、span_id、parent_span_id关联任务与依赖链只有日志文本，无法识别并行节点
logical_step、attempt、action_key区分逻辑动作与物理重试重试被当成新的成功动作
计划、开始、结束时间区分排队与执行只记执行时间，漏掉等待
模型/工具版本、输入摘要哈希、输出引用定位行为变化与复现输入版本随默认值变化
费用、token、状态、终止原因汇总预算与失败取消或超时费用消失

跨进程耗时使用各进程的单调时钟测量，再通过关联 ID 连接；跨机器墙钟可能存在偏差，不能直接拿两个未校准时间戳相减。正文和工具原始输出可以存为独立产物，事件只保留引用；公开复现材料时需清理凭据和不应公开的数据。

6.2 从请求指标汇总到任务指标

至少报告任务成功率、截止时间内成功率、全部尝试费用/成功次数、任务延迟分布、超时率和重复副作用次数。成功任务延迟要与所有终止任务的分布分别展示；超时记录是被截断的观察，不能把超时阈值当成任务本来就会在该时刻完成。

本站账本工具支持相同任务集合上的策略比较，显式记录 completed、failed、timeout、cancelled。它不自动验证任务成功，success 必须来自最终状态评测器；提供的样例标签为人工设定。

本章小结
  1. 事件记录应还原依赖、重试、版本与费用。
  2. 任务时间与请求时间分别统计，超时是截断观察。
  3. 成功标签来自独立验收，日志本身不产生正确性证据。

7 评测：状态验收、消融与故障矩阵

7.1 验收最终状态

τ-bench 比较交互结束后的数据库状态与目标状态，并用 passk 研究重复运行可靠性。[TAU] 这里的 passk 关注多次运行均成功，不能与“多个候选至少一个成功”的 pass@k 混用。自己的任务应定义相应最终判据：代码测试是否通过、产物字段是否满足要求、业务对象是否处在正确状态。

任务环境也要固定版本和初始快照。每次运行从同一状态开始，不能让上次产生的文件、缓存或外部修改使后续任务变简单；如果研究跨会话记忆，则把允许保留的状态作为独立实验条件写清。

7.3 交付材料与负结果

保存任务定义、初始化快照、模型/工具版本、策略配置、事件流、最终状态和验收结果。每项优化至少报告失败案例：摘要删掉约束、并发读取过期数据、重试导致重复效果、长期记忆命中旧事实。把“尚未覆盖的故障”与“已经通过的测试”列开，避免一次本地演示被当成生产可靠性证明。

本章小结
  1. 以环境或产物的最终状态评价成功。
  2. 重复运行可靠性与多候选覆盖率是不同指标。
  3. 消融与故障注入使用固定任务和环境，并归档所有失败。

8 工程选型与研究边界

短任务、工具少且无持久化需要时，可以从简单循环和结构化日志开始。长任务、人工中断、多分支与恢复需求增加后，再引入显式状态图、持久化检查点和任务级预算。选择框架时核对状态序列化、恢复兼容性、工具幂等支持、观测接口和版本升级策略。

后续值得验证的方向包括：上下文压缩与 KV 生命周期的联合决策、工具等待预测与缓存驻留策略、带任务期限的生成调度、可检验的长期记忆更新。每个方向都需要任务级指标，才能与服务评测和预算分配对齐。

本章小结
  1. 从任务持续时间、分支和恢复需求选择运行时复杂度。
  2. 框架提供机制，最终正确性仍取决于工具和业务协议。
  3. 研究收益用任务成功、完成时间和总成本共同衡量。
