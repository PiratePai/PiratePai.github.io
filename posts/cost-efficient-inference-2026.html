0导读与大事记：高性价比是什么、和低时延高吞吐有何不同

这份报告回答四个问题：高性价比推理与低时延、高吞吐到底是不是一回事、什么时候冲突；单位有效产出成本由哪些项构成、自己怎么算；四年降了三个数量级的功劳簿怎么分；推理引擎与服务化团队该盯哪些指标、按什么顺序动手。全文沿一条主线展开——最小化单位有效产出成本：C_unit = C_total ÷ V_valid。分子 C_total 是统计窗口内全部已付费资源（算力忙碌与闲置、状态与搬运、失败与重试都算钱）；分母 V_valid 只计通过质量、SLO 与任务成功过滤的有效产出，单位是任务、有效 token、图像或视频秒数——单位不同不能跨业务直接横比。低时延优化的是"时间"里的等待部分，高吞吐优化的是"产出"里的批量部分；高性价比是它们的上层目标函数，还要多管两项它们不管的事：买什么硬件（时租）与质量是否守得住（哪些产出能进分母）。

为什么是现在？三个变化叠加：

  1. 价格曲线进入"分级定价"时代。DeepSeek 2026-08 起对 V4 系列实行峰谷分时计价、缓存命中价约为未命中的 1/50，OpenAI/Anthropic/Google 把 Priority/Flex/Batch 与缓存读折扣做成常规档位——价格本身成了成本工程的一部分[DSPRICING26][OAIEN]。
  2. 降本手段完成了"全家桶"组装。量化走到 NVFP4（B200 上每 token 成本比 FP8 再降 53–60%[SEMIX-GLM]）、KV 池化跨实例复用进入 vLLM/SGLang/LMDeploy/TRT-LLM 主线[VLLMMK26]、P/D 分离与弹性并行有 Dynamo/llm-d/AIBrix 系统层托底[DYNAMO1][LLMD10]、vLLM-Omni 把语音/视频等多模态全双工会话与跨阶段 KV 传递做成统一服务框架[OMNI]。
  3. 账本公开了。DeepSeek 2025-03 披露了业界第一份推理系统级成本账（545% 理论成本利润率）[DS545]，Epoch AI 把"固定性能价格每季 −47%"做成了可引用的曲线[EPOCH26]——高性价比第一次同时有了目标、手段与刻度。

本章小结
  1. 高性价比是上层目标函数：C_unit = C_total ÷ V_valid，低时延、高吞吐各优化公式的一项，而性价比还要管"时租"（买什么）与"哪些产出能进分母"（值不值）这两件兄弟目标不管的事。
  2. 降本手段已成六层账本：模型级少算、缓存级不重算、调度级填满 GPU、任务链级把多轮任务跑成功、集群级填满日历、商业级设计价格结构——层与层是乘法关系。
  3. 2024 年价格战是"模型级+调度级"的产物，2025–2026 的主线是缓存池化、P/D 分离系统化、任务链级与分级定价；每季 −47% 的价格曲线由软件贡献了大部分。

1预备知识：一条请求、一份账本与三个目标

写给第一次接触推理经济学的读者：本节只需要"除法"和"租东西按时计费"两个常识。先建立四个概念：一条请求的一生（排队、计算、状态）、成本公式、三个目标的三角形、质量调整成本与账本隐藏项。

一条请求的一生：到达后先进排队（等 GPU 席位），然后 prefill（把整个输入算一遍，产出 KV Cache——一份随长度线性增长的状态），再逐 token decode（每步都读写这份状态），最后可能被取消、超时或答错。成本的账就记在这条时间线上：排队时 GPU 在为别人付费，prefill 时算力与写入带宽是主角，decode 时显存带宽与状态容量是主角，失败时已花的钱不会退。第 2 章的账本会把这些逐项列出；本节先把总公式立起来。

1.1 从 GPU 时租到 $/M tokens：一条除法公式

自部署推理的成本起点不是"模型多大"，而是你租（或买）的算力每小时多少钱。云上 H100 的市场合约价 2025-10 约为 $1.70/小时，2026-03 回升到 $2.35；B200 在 2026-09 达 $8.01（三个月 +79%，HBM 短缺驱动）[GPUIDX]。假设租了 N 张卡、系统总输出吞吐为 T（tok/s），那么：

$/百万输出 tokens = (时租 R × 卡数 N × 10⁶) ÷ (T × 3600)

代两个数：单卡 H100（$2.35/h）跑出 2,000 tok/s，则每百万 tokens ≈ $0.33；同样吞吐用 $8 的 B200 反而要 $1.11——贵卡必须跑出与价差相称的吞吐才划算。MLPerf Inference v6.1 里 CoreWeave 的 GB300 NVL72 在 gpt-oss-120b 离线场景做到 16,635 tok/s/卡[MLPERF61]：按 $8/小时算，每百万 tokens 仅 $0.13——吞吐摊薄了时租，这就是"高性能硬件反而更便宜"的全部秘密。反过来，若利用率只有 10%，分母缩小 10 倍，什么卡都贵。

把 GPU 集群想成一支按小时计费的专业施工队：低时延是"一个电话就到"（养着随时待命），高吞吐是"一车尽量装满"（拼车摊薄成本），高性价比是"每运一吨货花的总钱最少"——既要车装满（吞吐），又要少养闲车（利用率），还要货不返工（质量）。施工队的时薪（GPU 时租）你谈不下来多少，能做的是让每一分钟都有货可运、运的每趟货都算数。

1.2 三个目标的三角形：一致与冲突

低时延（TTFT/TPOT）、高吞吐（tok/s）、高性价比（tokens/$ 或 $/M tokens）经常被混为一谈，但它们只在特定区间一致：

手段低时延高吞吐高性价比说明
加大 batch✗ 变差✓ 显著提升✓ 提升（质量不损）decode 是访存受限的，更多人摊薄权重搬运；但 TPOT 随 batch 增大而升高，超过 SLO 的 batch 是"白赚的吞吐、丢掉的承诺"
更小/量化模型✓ 改善✓ 提升✓ 提升，但引入质量折扣FP8/NVFP4 在现代硬件上几乎免费提速；质量损失要过回归（R1-0528 从 FP8 到 NVFP4 主流基准损失 ≤1%[NVFP4]）
P/D 分离✓ TTFT 改善✓ goodput 提升✓ 但有额外成本消干涉收益常大于 KV 传输与双池固定成本，但池配比错了反而更贵（详见 6.2）
投机解码✓ 改善△ batch 大时可能持平或略降△ 视能耗与接受率接受长度高时每成功 token 便宜；batch 大时验证算力挤占主算力，能耗口径可能变差（2.33 vs 2 J/token 的教学账本[SPECENERGY]）
独占低负载机器✓ 最优✗ 空转✗ 最差"为 10 个用户保 p99"是合法业务选择，但要清楚它对单位成本意味着什么

判断标准一句话：低时延与高吞吐是"承诺"，高性价比是"账本"；前两者定义了 goodput 的边界，后者要求在边界内最大化产出÷投入。这也是 DistServe 提出 goodput（SLO 达标吞吐）的初衷——把承诺与吞吐绑成一个可优化的单一指标[DISTSERVE24]（站内推理服务篇 1.4 与评测篇 2.1 给了定义与手算例子，本文不重复）。

1.3 质量调整成本：便宜但答错要重来

$/M tokens 的分子是钱，分母是 token 数；但用户买的从来不是 token，是答对的任务。一次答错触发重试，实际成本翻倍还搭上时延。于是有了质量调整口径：

每成功任务成本 = 全部尝试的总成本 ÷ 成功任务数（失败尝试花的钱全部计入分子）

评测篇 4.2 的教学账本给出方向性结论：更多预算可以买到更高成功率，却同时推高每次成功的成本——同一组四道题上，单次作答总成本 4 积分、成功 2 次，每次成功 2 积分；best-of-4 总成本 20、成功 3 次，每次成功约 6.67；自适应策略总成本 12、成功 3 次，每次成功 4。换小模型、降精度、少采样同样要做这道除法：单价便宜一半而成功率掉三成，账反而是亏的。同理，混合价（如 Artificial Analysis 的 7:2:1 缓存:输入:输出加权）对 reasoning 类 1:5 负载会失真最多 5 倍[TOKENARENA26]——先想清楚自己的负载长什么样，再选口径。

1.4 账本的隐藏项：TCO 不止租金

Epoch AI 的测算：电费只占 GPU TCO 的 10–15%，资本开支（购置/折旧/资金成本）主导长期成本下限[EPOCHTCO]。完整的账本还包括：网络（400G RoCE 集群非小事）、存储（KV 池的 SSD）、机房 PUE、运维人力、以及碎片化时间的浪费——白天为峰值预留的容量在凌晨就是纯折旧。很多"降价 90%"的新闻只算了 GPU 时间，没算这些；自己建集群算账时一项都不能少（第 7 章展开）。

本章小结
  1. 成本公式只有一条除法：$/M tokens = 时租×卡数÷吞吐；GB300 贵 4 倍却更便宜，因为吞吐摊薄了一切。
  2. 低时延/高吞吐是承诺，高性价比是账本；goodput 是它们的交汇点——承诺之内最大化产出÷投入。
  3. 质量是分母上的折扣项：每成功任务成本才对齐用户的真实开销；TCO 里电费只占一两成，资本与碎片时间才是大头。

2单位有效产出成本与可复查账本

一筐里烤了十块饼干，八块烤好了，两块烤焦了。面粉和烤箱时间十块都用了。算每块能吃的饼干花了什么，要把整筐的花费分到那八块上。

"性价比"不是玄学词，它有一个可以写下来的目标函数和一套可计算的指标族。本章先立公式与它的六个陷阱，再按"钱从哪出、货从哪进"给出指标族（价格、产出、能耗、资产、质量调整），最后把分子展开成一份可复查的资源账本。指标选错，优化方向就会错。

2.1 主公式：C_unit = C_total ÷ V_valid

C_unit = C_total ÷ V_valid
  C_total：统计窗口内全部已付费成本（GPU 忙碌与闲置、状态与搬运、失败与重试、冷启动……）
  V_valid：同一窗口内"有效"产出 —— 满足质量要求、任务成功且不违反对应 SLO 的部分
  单位：元/任务 · $/有效 M tokens · $/图像 · $/视频秒 —— 单位不同，不能跨业务直接横比

这个除法看似简单，六类常见"降本"都可能在另一头把账做坏——每一条都对应后文一层手段的失效边界：

  1. 加 GPU 降时延，通常抬高单位成本：分母（产出）未必线性增长，分子（已供给算力时间，含新增的闲置）却实打实增长——为 p99 买冗余是合法业务决策，但要按 C_unit 计价，不能只报时延改善。
  2. 加大 batch 提吞吐，可能使排队或交互响应违约：超 SLO 的产出进不了 V_valid（goodput 口径），"白赚的吞吐"只抬电费不抬分母。
  3. 缓存压缩降存储，可能因解压、临时副本或质量下降把总成本做高：KV 量化/驱逐省的是容量项，重算与精度补偿计入分子（5.4）。
  4. 少步采样、缩小模型、减少输出长度改变质量或任务预算：它们不是无损加速——扩散少两步、模型小一档、max_tokens 砍一半，都要重新过质量回归（4.1/4.5/8.4）。
  5. 平均质量分数不是线性效用：不能机械地把成本除以 FVD、VBench 或平均评分当"性价比"——FVD 是集合级距离、评分不可当倍数用；质量要作为约束（Q ≥ Q₀）或进入 V_valid 的过滤条件（8.4）。
  6. 输出过时、被取消、被丢弃或任务失败时，成本仍在分子：交互场景里被新控制作废的帧、Agent 里失败轮次的 token，都不能计为有效产出。

两种问法，同一架天平："成本最小化且满足服务目标"（min C_unit s.t. SLO/质量约束）适合有承诺指标的服务方；"固定预算下最大化有效产出"（max V_valid s.t. C_total ≤ 预算）适合配额制的内部平台。二者可以互相换算：把第一种的最优 C_unit 当单价、用预算除它，就得到第二种的目标产出——但两种问法下的最优配置通常不同，报告里要写清问的是哪一种。这个框架也能概括全站的研究路径：建模提供账本（本章），约束优化定义可行域（8.3），协同设计调整结构与资源（第 4–7 章的手段），自适应处理负载变化（第 6 章的弹性与任务链）。

2.3 产出类：tokens/s/$ 与 goodput

自部署侧的对称指标是每美元产出多少 token（tokens/s/$），它把 1.1 的公式倒过来。三个常见变体：

  • 聚合吞吐（tok/s/卡 或 tok/s/集群）：MLPerf Inference 的 Server 场景在 p99 TTFT/TPOT 约束下测吞吐，再乘以时租就得到每 token 成本——"基准吞吐 × 租金"是工程侧最硬的口径[MLPERF61]。局限：单租户、无抢占，生产环境"每完成 token 成本"高于基准推算。
  • goodput（SLO 达标吞吐）：只数满足 TTFT/TPOT 承诺的请求。定义见 DistServe（OSDI'24），教学手算见站内评测篇 2.1。用吞吐不达 SLO 的部分是"白赚的数字、丢掉的客户"。
  • 并发敏感性：同一硬件、同一模型，成本随并发剧烈变化——并发感知成本模型（arXiv 2606.11690）实测 H100 上 Mixtral-8x7B FP16：1 请求/秒时 $15.25/M tokens，25 请求/秒时 $0.87/M，同一套硬件差 17.5 倍[CONCOST26]。低并发自部署"看起来免费"，其实是按最贵档付费。

2.4 能耗类：J/token 是被低估的硬通货

每 token 能耗（J/token）把"算力、带宽、利用率"压成一个物理量。NVIDIA 给出的 GPT-MoE-1.8T 代际曲线：Hopper ≈10 J → Blackwell ≈0.4 J → Blackwell Ultra ≈0.2 J（NVFP4 口径，十年 200,000×）[NVFP4]。

但能耗在账本里的位置常被高估：Epoch AI 测算电费只占 GPU TCO 的 10–15%，资本开支主导[EPOCHTCO]——省电的意义更多在散热上限、机柜密度与碳口径，而非直接省钱。

2026 年学术侧开始把能耗当一等指标：SIMPLE 定律用 4 个参数闭式拟合每 token 能耗（13 个稠密模型、H100 上 R²=0.969）[SIMPLE26]；Wilhelm 等直接主张把 Energy/Token 列为基准一等公民并做能耗感知路由[EPT26]。

2.5 资产类：TCO 与租金曲线

SemiAnalysis InferenceMAX 把自部署成本写成一条公式： $/M tokens = TCO($/chip-hr) × 10⁶ ÷ (3600 × tok/s/chip)，其中 TCO 含折旧、电费、机房、网络与运维[INFERMAX]。

芯片小时价本身在波动：H100 合约价从 2025-10 的 $1.70 回升到 2026-03 的 $2.35（+38%），B200 在 2026-09 达 $8.01（三个月 +79%，HBM 短缺）[GPUIDX]。

租金上行与每 token 成本下行并不矛盾——软件与精度优化的降本速度（如 B200 上两个月 $0.11→$0.02/M 的纯软件 5×[NVIDIABLOG]）跑得比租金快，但把"租卡比去年贵"算进 TCO 是诚实账本的前提。

2.6 质量调整类：为"答对"付费

两个口径：

  1. 每成功任务成本（1.3 的公式，评测篇 4.2 有完整账本）。
  2. 固定能力价格——Epoch AI 的"固定性能成本"曲线：找能力相同（如 GPQA 同分）的模型比价格，2023 年以来平均每季 −47%[EPOCH26]。

市场结构数据：同等能力档，开源模型比闭源便宜约 90%（OpenRouter 大规模交易数据研究）[MARKET25]；tiered 定价研究发现"经济档"价格半衰期仅 1.10 年，且降价的主力是软件/架构创新（TFP 残差约 103.7%）而非 GPU 降价[TIERED26]。

2.7 成本账本：把分子展开成可复查的资源项

C_total 不是一个数，而是一张可以逐项对账的清单。按"钱付给什么资源"分组（每项都注明统计窗口与分摊规则，避免双计）：

资源组账本项统计与分摊要点
算力供给已供给的加速器时间——忙碌与闲置都计按节点小时计；预留/待机/扩容余量按占用时长分摊到业务，不能只算"忙碌 GPU 时"
通用资源CPU、主存、存储、网络、缓存层、迁移与数据搬运KV 池的 SSD、400G 网卡、跨实例 RDMA 流量都是钱；迁移按"搬迁字节数 × 单价"或占用端口时间分摊
容量占用模型权重、KV/其他持久状态、临时激活、输出队列的显存/内存占用同卡多模型按峰值占用分摊；碎片与峰值预留要显式一行（vLLM v0.34.0 的共享 RoPE 缓存省 11.5 GiB/卡就是这一行的收益[VLLM34]）
切换成本冷启动、编译、预热、扩缩容与版本切换按事件计；AIBrix 的 ModelWarmup、ServerlessLLM 的快冷启都是在压这一行[AIBRIX][SERVERLESSLLM]
失败与浪费失败重试、过时输出、被取消请求、推测解码未采用部分、降级回退全部计入分子、不得计入 V_valid；投机解码的草稿 token 按接受率折算浪费比例（4.3）
质量补偿精度/近似方法的质量损失所需的补偿计算量化回归、重试、验证器开销；"近似无损"要附回归集证据，否则补偿成本被隐藏

三个口径务必分开：能耗（J/token，物理量）、采购或租赁成本（TCO，含折旧与资金成本）、计费价格与商业售价（价目表，含毛利与折扣结构）。API 售价不是基础设施成本——租金随市场波动（H100 合约价 2025-10 到 2026-03 涨 38%[GPUIDX]），引用时给来源与日期快照；本文不虚构租金与毛利数字，厂商自报毛利一律标注口径（3.3）。统计窗口要与业务对齐（日/月/结算周期），跨窗口的预留资源按时间比例分摊——双计（同一 GPU 时既算给业务又算给平台）和漏计（夜里空转的折旧没人认领）是账本最常见的两种错。

2.8 跨系统比较的纪律

引用任何成本数字前问三句：

  1. 口径——输入/输出/命中哪一格？哪个混合比例？离线吞吐还是 SLO 约束下的 server 吞吐？V_valid 的过滤条件是什么？
  2. 快照日期——价格与租金随月波动，"DeepSeek 输入 $0.28"是 2025-09-29 的 V3.2 牌价，2026-11 的 flash 谷价已是 $0.15。
  3. 谁测的——厂商自提交（MLPerf 的传统警示）优于媒体转述，同行评审优于官方博客，官方博客优于匿名评测。

本站评测篇 5.2 的横评口径纪律同样适用于成本数字。

本章小结
  1. 主公式只有一条除法：C_unit = C_total ÷ V_valid；六个陷阱（加卡、大 batch、压缩、少步/小模型、质量非线性、过时失败）都源于只动一头不看另一头。
  2. 价格必须三分口径（未命中/命中/输出）+ 快照日期；混合价比例要按自家负载校准，错配可失真 5 倍。
  3. 分子要展开成可复查的账本（算力/通用资源/容量/切换/失败/质量补偿/任务链），能耗、TCO 与售价三个口径分开；产出指标用 goodput 而非裸吞吐。

3发展历程：从"按 token 卖钻石"到分级定价的四年

$/M tokens 四年降了两个多数量级。把功劳簿摊开，会发现每一轮降价都对应一层技术的成熟：2022–2023 系统层（批处理与显存）、2024 模型层（MoE 与价格战）、2025 缓存与分离层（545% 账本）、2026 定价结构层（峰谷与分级）。本章按时间复盘，数字均带口径。

3.1 2022–2023：系统层革命，先消灭"浪费"

降本的第一性原理不是让计算更快，而是让已付费的计算不空转。三块基石：

  1. Orca（OSDI'22）的迭代级调度：静态批处理在变长负载下吞吐损失可达一个数量级，连续批处理把它拉回，GPT-3 175B 上较静态批处理/FIFO 吞吐最高 36.9×（SLO 约束口径）[ORCA22]。
  2. vLLM/PagedAttention（SOSP'23）：KV Cache 碎片从 60–80% 浪费降到 <4%，吞吐较当时系统 2–4×[VLLMPA23]。
  3. Sarathi-Serve（OSDI'24）chunked prefill：把 prefill 切块掺进 decode 批，尾延迟约束下服务容量 2.6–5.6×[SARATHI24]。

这些工作的共同点：零质量损失、纯系统收益，是所有后续降本的"免费头寸"。

4模型级降本：每个产出少算一点、少搬一点

模型级手段改变的是每个产出（token、图像、视频秒）要做多少计算（FLOPs）与搬运多少字节（显存带宽）。它们共同的风险是质量折扣——所以每个手段后面都跟着"质量账"。站内量化篇与投机解码篇已把机制讲透，本章只做"性价比视角"的重读、最新数字，并补上此前缺的视觉与多模态一条线。

4.1 量化：精度换吞吐，在 Blackwell 上是"降本第一杠杆"

量化同时省三样东西：显存（装得下）、带宽（搬得快）、Tensor Core 吞吐（算得快）。

代际叠加的量级（MLPerf Llama-2-70B、8 卡离线口径）：以 H100 FP16 为基线，H100 FP8 +29%、H200 FP8 +84%、B200 FP8 +193%、B200 NVFP4 +441%[MLPERFFP4]。

SemiAnalysis InferenceX 在 GLM-5.1/B200 上的口径：FP4 较 FP8 吞吐 +113%~149%，每 token 成本 −53%~−60%（46 tok/s/用户档：$0.16/M vs $0.35/M）[SEMIX-GLM]。

质量侧：DeepSeek-R1-0528 从 FP8 量化到 NVFP4，MMLU-Pro/GPQA/LiveCodeBench 损失 ≤1%（厂商口径）；NVIDIA QAD 报告给的大模型界线——671B 级模型 PTQ 近无损（MATH500 95.4→94.2），小模型需要量化感知蒸馏[NVFP4QAD]。

工程结论：旗舰模型 + NVFP4 目前是 $/token 的最优点之一，但质量回归必须跑自己的评测集。

量化像把货运卡车从"每件货物单独包装"改成"标准托盘"：单件防护弱一点（精度损失），但装车快了几倍、一趟运的货多几倍。货越贵重（模型越小、任务越难），越需要专门定制托盘（QAD）而不是直接套用。

4.2 MoE 与激活稀疏：参数可以贵，激活必须便宜

MoE 把"模型能力（总参数）"与"每 token 成本（激活参数）"解耦：DeepSeek-V3 671B 总参、每 token 仅激活 37B——能力按 671B 计、算力按 37B 付。腾讯混元 Turbo S（2025-02）用 Hybrid-Mamba-Transformer 结构降 KV 占用，牌价打到输入 0.8 元/M、输出 2 元/M，官方称约为 DeepSeek 同期 API 成本的 1/2~1/4（官方发布，媒体转述）[HUNYUANTS]。

部署侧的研究线：Fiddler（ICLR'25）用 CPU 算专家、GPU 算注意力[FIDDLER25]；Pre-gated MoE（ISCA'24）预门控把专家预取与计算重叠，峰值显存降到 GPU-only 的 23%[PREGATED24]；MoE-Infinity（ASPLOS'24）按请求级专家激活矩阵做缓存，个人机器每 token 延迟 3.1–16.7×[MOEINF24]。

2026-11 的 SGLang Paged Experts 把"专家按需进出显存"带进主流引擎：16 GB 卡跑超显存 MoE，比 CPU offload 快 12–30×[SGLPE]——MoE 的性价比红利第一次不需要专用引擎就能吃到。

4.3 投机解码的性价比观：加速 ≠ 省钱

投机解码通常被归入"低时延"工具箱，但它同时改变每 token 成本，方向不定。三个口径：

  1. 小 batch 加速：经典场景，接受长度 2–4 时 decode 加速 2–3×（站内投机解码篇全文）。
  2. 大 batch 仍可能赚：MagicDec 证明长上下文下 batch 32–256 仍有 2.51× 加速（稀疏注意力草稿抵消验证开销）[MAGICDEC24]。
  3. 能耗口径会反转：《Only Accepted Tokens Count》实测接受率低时每 token 能耗反而升高——教学账本：方案 A 10 J 产出 5 个 token（2 J/token）vs 方案 B 14 J 产出 6 个（2.33 J/token），"接受更多 ≠ 更省电"[SPECENERGY]。

带 SLO 目标的调度版：AdaServe 把投机预算按 SLO 定制，违约降 4.3×、goodput 1.9×[ADASERVE25]；TurboSpec 闭环控制草稿长度以 goodput 为目标[TURBOSPEC]。

结论：上投机解码前，先算"每成功 token 成本"而不是"每秒 token 数"。

4.4 路由与级联：90% 的请求用便宜模型就够了

最古老的降本手段：不每次都请最贵的模型。FrugalGPT（2023）查询级联，匹配 GPT-4 效果下成本最高降 98%（API 计费口径）[FRUGALGPT]；RouteLLM（ICLR'25）用偏好数据训练强弱路由器，部分场景成本降 2 倍以上而质量不降[ROUTELLM]。市场给了结构证明：同等能力档，开源模型比闭源便宜约 90%[MARKET25]——路由的意义就是让每个请求落到"能力够用的最便宜档"。这条线与站内推理预算篇（test-time-compute）的"自适应预算"是同一枚硬币的两面：那边管"该花多少思考"，这边管"该花谁的钱"。

4.5 视觉与多模态：VLM 的 token 经济与扩散的步数经济

站内 20 篇里，VLM 与扩散生成的降本此前没有落到"性价比视角"——本节补上。它们的公式与 LLM 同构，但产出单位不同（图像、视频秒），且"质量折扣"更难标定。

  1. VLM 的视觉 token 是第二个"激活参数"。一张高分辨率图可展开数千视觉 token，prefill 成本被图像主导；FastV/VisionZip/ToMe 一类剪枝（站内 ViT 稀疏化篇详述）相当于给视觉通道做"MoE 式稀疏"——砍 token 就是砍分母侧的计算。但 2026-10 的评测批评指出：留存 token 数与聚合准确率都是坏代理——很多样本随机剪枝或只靠文本捷径也能答对，等量 token 预算的端到端成本可以不同；该文提出 Random-Pass@k 与"保持率约束下的真实加速"（Preservation-Constrained Speedup），把评测拉回"每有效产出的成本"口径[VLMPRUNEEVAL]。缓存侧，VisMemo 把视觉 KV 复用做成 GPU/CPU/SSD 分层缓存，生产 trace 命中率 27.78%→61.45%、8K 输入 prefill 时延最多降 48.3%[VISMEMO]；CodecSight 则用视频编解码器信号替代滑动窗全量重算，让"并发视频流"这类稳态负载的每流成本有界[CODECSIGHT]。
  2. 扩散少步不是无损加速。少步蒸馏、ODE 求解器与引导强度调优改变的是每次产出的模型求值次数（站内采样效率篇的同预算算例），质量要按 FVD/VBench 重新验收——少两步省的是分子，掉的是 V_valid 的过滤通过率，与量化一样要过回归，不能因为"都是生成"就当免费午餐。
  3. 多模态服务把两个世界的账本接在一起。vLLM-Omni（vllm-project，2026-10-28 v0.32.0）把语音/视觉/生成的全双工会话做成统一 serving 框架，核心卖点正是"跨阶段 KV 与多模态载荷的原生传递"——让 AR 模型到 DiT 的接力不重算上下文[OMNI]；实时世界模型篇 5 章的流式会话与事件级 KV（Hy-Nomas in SGLang）是同一趋势。扩散服务侧，TileCache 把多轮图像编辑的激活缓存压缩复用做成服务级调度，90% SLO 达标下承载 2× 到达率[TILECACHE]——"缓存级降本"第一次跨进扩散范式。
本章小结
  1. 量化在 Blackwell+NVFP4 上是降本第一杠杆（$/token −53~60%），大模型 PTQ 近无损、小模型要 QAD。
  2. MoE 把能力与算力解耦（671B/37B），Paged Experts 让红利进入通用引擎；激活便宜才算便宜。
  3. 投机解码与路由都要按每成功 token 成本结算：接受率低时投机更贵，90% 的请求配得上便宜模型。
  4. 视觉 token 剪枝、扩散少步与多模态接力同属模型级账本：留存 token 数和步数都不是钱，端到端每有效产出的成本才是；剪枝评测要看质量保持约束下的真实加速。

5缓存级降本：不重算已经算过的

两个人从头读同一版书，前面已经一起读过的那一段，可以接着用留下的记录。读到内容不同的地方，就从那里分别往下读。只有中间某几页一样，还不能直接借用那几页的旧记录。

system prompt、Agent 对话历史和 RAG 文档可能在请求间重复。精确前缀缓存复用已计算的 KV，减少重复 Prefill。它要求 token 前缀及模型、位置、适配器等影响计算的条件兼容；后续生成仍要读取缓存并执行计算。精确复用与本章后述的压缩、语义缓存分别评估质量边界。[APC]

5.1 命中价经济学：价目表已经替你算好了

API 账单应按服务商的实际命中规则和计费项计算。设命中输入、未命中输入和输出的 token 数分别为 Nh、Nu、No，对应每 token 单价为 ph、pu、po，则基础费用为 Nhph + Nupu + Nopo，另计缓存写入、存储等项目。第 2.2 节价格表是其标注日期的快照，具体节省比例需代入实际输入输出量和当期价格。

自部署的资源账本另算：命中可省去复用前缀的大部分 Prefill，但仍有缓存匹配、读取、必要传输、末 token 计算及后续 Decode。即使全部提示词的 KV 已存在，vLLM 的标准 APC 路径仍需得到末 token 的 logits，按块对齐时可能重算末块；完整边界见推理服务篇第 3 章。[APC][APCSRC]

给引擎团队的两个推论：

  1. 把可复用前缀放到 prompt 最前面（缓存按前缀匹配；插入时间戳会使变化位置及其后续前缀失配，之前满足完整块条件的前缀仍可能复用）。
  2. 若用 API，把"我们该不该自建缓存"换成"命中率的每一个百分点值多少钱"——vLLM×Mooncake 的生产数据显示 Agent 负载命中率从 1.7% 提到 92.2%[VLLMMK26]，这就是答案的量级。

5.2 单机前缀缓存：命中收益与管理开销

SGLang 的 RadixAttention 用基数树匹配最长前缀并复用历史 KV。论文按复用输入 token 数与输入 token 总数之比计算命中率；Chatbot Arena 部署中，LLaVA-Next-34B 和 Vicuna-33B 分别为 52.4% 和 74.1%。这些是特定模型与流量的结果，不能作为任意 Agent 负载的预期。[SGLANG24]

vLLM V1 的 2025-01-27 发布博客说明默认开启前缀缓存，并在文中测试条件下报告 0% 命中率时吞吐损失低于 1%。这里的“零开销”是架构目标与该基准下的近似描述，不能理解为缓存匹配、管理和读取完全免费。[VLLMV1]

研究侧的补充：PromptCache（MLSys'24）模块化复用使 TTFT 降 8×（GPU）[PROMPTCACHE]；IC-Cache（SOSP'25）更进一步复用"语义相近"的历史问答，8 个部署吞吐 1.4–5.9×[ICCACHE]——从"精确前缀"走向"语义缓存"，代价是要管好质量边界。

5.3 跨实例 KV 池：把缓存从"单机内存"升级成"机房资源"

单机缓存的问题：请求被调度到别的实例就全miss。解法是把 KV 从引擎里拆出来做成共享池：

  • Mooncake（FAST'25 最佳论文，Moonshot 生产系统）：以 KVCache 为中心的分离架构，真实负载下 Kimi 多承载 75% 请求、模拟场景 SLO 内吞吐最高 +525%；Transfer Engine 在 8×400G RoCE 下 190 GB/s[MOONCAKE25]。2025-07 起 Kimi K2 生产部署（128×H200，P/D 分离 + 大规模 EP）prefill 224k / decode 288k tok/s[MOONCAKE25]。
  • 引擎集成潮：vLLM 官方博客（2026-05-06）给出 KV 池化数字——Agent 负载吞吐 3.8×、P50 TTFT 降 46×、命中率 1.7%→92.2%、近线性扩展至 60×GB200[VLLMMK26]；LMDeploy v0.18.0、TensorRT-LLM（Mooncake Store connector，2026-10）、TRT-LLM 镜像基线的 llm-d 相继接入[MKREPO][LLMD10]。
  • KV 当数据搬运：CacheGen（SIGCOMM'24）把 KV 流式压缩传输，TTFT 缩短 3.7×、字节流压到 1/4.3[CACHEGEN24]；CacheBlend（EuroSys'25 最佳论文）解决"多条预计算 KV 拼接会掉质量"的问题——选择性重算 10% 左右 token，TTFT 2.2–3.3×、吞吐 2.8–5×[CACHEBLEND25]。
  • 反直觉教训：LMCache（UChicago）实测，业界常用的上下文截断会把前缀缓存命中率砍半——为省显存做的截断，反而把缓存的钱亏掉了[LMCACHE]。

有了共享 KV 池，调度器就多了一个自由度：把请求派去"已有它前缀"的实例，还是派去最短的队列？两者的适用负载、否定条件与拟回看日期登记在研究判断登记表第 1 条；KV Cache 篇 5.4 的边界算例（命中收益被传输或排队吃掉）是它的最小反例。

5.4 KV 压缩与卸载：缓存本身变小，命中更便宜

第三条线是让缓存本身更便宜：KIVI（ICML'24）2-bit 非对称 KV 量化，峰值显存省 2.6×、batch 至 4×、真实负载吞吐 2.35–3.47×[KIVI24]；DeepSeek-V2 起的 MLA 把 KV 压缩约一个数量级（站内 KV Cache 篇与注意力篇详述）；Cake（ICML'25）让"计算 KV"与"从盘加载 KV"并行互掩，TTFT 平均再降 2.6×[CAKE25]。压缩与池化是乘法：KV 小 4× 意味着同容量池装 4× 的会话、RDMA 搬运时间缩 4×。

账本侧的两个 2026-11 更新：其一，引擎在"省存放 KV 的每一 GiB"上继续内卷——vLLM v0.34.0（2026-11-16）默认开启可扩展 KV 缓存并以共享 RoPE 缓存每卡省 11.5 GiB，8×B200 上等效 KV 容量 +14.5%[VLLM34]——相当于不动硬件白送缓存容量。其二，卸载介质的磨损与寿命进入成本：Lachesis（2026-10）按数据生命周期把 agent 负载的 KV 分层放到高带宽 Flash，把闪存寿命摊销延长 1.19–3.13×（3.3–12.2 设备年）[LACHESIS]——KV 卸载的账本从"带宽与容量"扩展到"设备折旧"，这是 2.7 账本"容量占用"行的长期版本。

本章小结
  1. 缓存级是唯一零质量损失的降本层：命中价（1/50~1/10）就是它的官方定价。
  2. 2025–26 的主线是跨实例 KV 池化：Mooncake 系（vLLM/SGLang/LMDeploy/TRT-LLM）把命中率推向 90%+，Agent 负载吞吐 3.8×。
  3. 别为省显存截断上下文——命中率减半的代价比显存贵；压缩（KIVI/MLA）与池化叠加是乘法收益。

6调度级与任务链降本：把昂贵的 GPU 时间填满、把多轮任务跑成功

一趟车坐了很多人，也要看有多少人最后到了自己的站。有人半路换车，有人到晚了，这一趟照样用了车和油。把车坐满和把人按时送到，是两件要一起算的事。

调度级手段不改变模型也不改变缓存，它改变的是"已付费的 GPU 时间里有多少在产出有效 token"；任务链级手段再把镜头拉远："一条多轮任务里有多少轮白跑"。核心指标从吞吐升级为 goodput、再到每成功任务成本，核心动作从"批"升级为"分"、"迁"与"适配"。机制细节站内推理服务篇第 2/4/5 章与 Agent 推理系统篇有完整拆解，本章聚焦性价比账。

6.1 批处理与切块：成本视角的两句话重述

Orca 的迭代级调度允许已完成请求及时退出、等待请求加入，减少静态批处理的空闲计算。[ORCA22] Sarathi-Serve 用切块 Prefill 与持续 Decode 组批，在论文的尾延迟约束下，相对 vLLM，Mistral-7B 单张 A100 的服务容量提高 2.6 倍；Falcon-180B 在 8 张 A100、2 路流水线和 4 路张量并行配置下最高为 5.6 倍。两项数字对应不同模型与部署条件。[SARATHI24]

这些机制能改善特定负载下的资源利用率，单位成本收益需要在相同模型、到达率、质量和 SLO 下测量。低负载时可能没有足够请求组成大批次；不能把论文的服务容量倍数直接换成所有部署的费用倍数。

6.2 P/D 分离的账：什么时候值得养两个池

Prefill 计算受限、decode 访存受限，混在一个池里互相干扰。分离的收益证据：DistServe（OSDI'24）在 SLO 达标口径下较 vLLM 可承载 2.0–4.6× 请求速率、较 DeepSpeed-MII 7.4×、更紧 SLO 下 12.6×[DISTSERVE24]；Splitwise（ISCA'24）给出成本口径：同型机集群 1.4× 吞吐且成本 −20%，或同成本同功耗预算下 2.35× 吞吐[SPLITWISE24]；TetriInfer 直接以 perf/$ 为目标：混合负载省 38% 资源[TETRIINFER]。

代价三条（KV 要跨机传、两池配比要调、显存规划更碎）与配套技术（NIXL、Mooncake Transfer Engine、EPLB 负载均衡）见服务篇 5.3。

2026 年的新方向是"分离不再是二选一"：STAR（2025-10）按输入/预测输出长度在 decode 端再调度[STAR25]；DuetServe（2025-11）用单卡 SM 空间复用替代跨卡分离[DUETSERVE]；PPD（ICML'26）发现多轮会话里"部分 prefill 本地做"更划算，Turn2+ 的 TTFT 降约 68%[PPD26]；Cascade（2026-08）给每个请求算"SLO 减去预计剩余服务时间"的时延预算，用它同时驱动调度与 KV 管理，生产 trace 上 goodput 最高 2.4×、SLO 违约 −40%[CASCADE]——goodput 目标从"达标/不达标"细化到"每个请求还剩多少预算"。

决策口径：负载 TTFT 与 TPOT 双敏感、规模够大（双池固定成本摊得开）才上全分离；否则 chunked prefill + 单机 P/D 已够。

6.3 弹性、迁移与抢占：把"空的时间"卖出去

  • 请求迁移：Llumnix（OSDI'24，阿里）跨实例 live migration，同尾延迟下省 36% 成本[LLUMNIX24]。
  • 弹性并行：LoongServe（SOSP'24，北大）按请求长度动态伸缩序列并行度，长上下文最大吞吐较 chunked prefill 3.85×、较 P/D 分离 5.81×[LOONG24]。
  • 抢占实例：SpotServe（ASPLOS'24）让推理跑在可中断的 spot 上，真实中断 trace 下 P99 只劣化 2.4–9.1×，实例费省 54%[SPOTSERVE]——离线/批处理负载的理想选择。异构版本的 2026 续作 ShuntServe：用 roofline 估计器 + 动态规划在 L4/A10G/L40S 等异构 spot 池上做放置与保输出的活迁移，成本效率（吞吐/美元）较按需同构池 +31.9%（离线）/+31.2%（在线）[SHUNT]。
  • 冷启动：ServerlessLLM（OSDI'24）本地存储层级 + live migration，serverless 场景端到端延迟降 10–200×[SERVERLESSLLM]——弹性扩容的"开机型"成本被压到可用区间。
  • 系统层编排：NVIDIA Dynamo 的 Planner 按 SLA 目标自动扩缩，官方引用的 APSARA 2025 实践为 SLA 违约 −80%、TCO 再 −5%[DYNAMO1]；字节系 AIBrix（已捐 vllm-project）与 Red Hat llm-d（v1.0 GA，2026-10-20）把 P/D 分离、多租户 QoS、KEDA 自动扩缩做进 K8s——"调度级降本"正在从论文变成发行版[LLMD10][AIBRIX]。

6.4 多租户与削峰：好价格是调度出来的

公平性也有成本意义：VTC 虚拟 token 计数（OSDI'24）给多租户加了"服务差异 ≤2×"的硬上界，防止大客户挤走小客户造成的隐性违约[FAIRNESS24]。

削峰的两个做法：

  1. 错峰复用：DeepSeek 披露其集群白天全量推理、夜间腾节点给训练/研究[DS545]——同一批卡的日历被排满，摊薄的就是 1.4 节说的"碎片化折旧"。
  2. 价格杠杆：峰谷计价（3.4 节）本质是让需求曲线配合供给曲线。

DynamoLLM（HPCA'25 最佳论文）则证明能耗也能调度：按负载调实例数/并行度/DVFS，满足延迟 SLO 下省 53% 能耗、61% 客户成本[DYNAMOLLM]——调度器顺手把 2.4 节的 J/token 也管了。

6.5 任务链级：Agent 负载把"每成功任务成本"推到台前

Agent 负载与单轮请求的差别是结构性的：多轮串行、上下文随轮次膨胀、工具调用穿插、一步失败全链重来。2026 年下半年的集中发现，几乎每条都改写 C_unit 的分子或分母：

  • 失败与恢复会改变成功任务的成本。Ali 等的预印本用独立失败模型分析 Agent 执行，未开展原始测量。若每步失败概率为 2%，一项 20 步任务一次跑完的概率约为 66.8%。在每次尝试都按完整任务成本计费的简化条件下，平均每次成功需要约 1.50 次尝试。若失败提前结束或启用检查点，实际支出还要按重跑范围和恢复开销核算。[ENTERPRISE]
  • KV 增长是 agent 的头号账本项。Cache Engineering for Agents（清华，2026-10）论证：轨迹超出上下文限制后，KV 的 I/O 与存储成为主导成本，需要主动控制缓存增长[CACHEENG]。配套的归因研究 Total Cost of Agency（2026-09）用两遍精确计数把"记忆注入 token"从普通输入里拆出来：企业级 200 任务基准上记忆注入约占总计费成本的 12%，其中约 28.7% 可在不损精度的前提下去掉[TCA]——观测工具把它们按普通输入计费，账本就看不清。
  • 命中/未命中的成本不对称会放大突发。微软的测量（2026-11）：前缀缓存命中只补约 1K token 的增量 prefill，未命中要重算 10–40K 上下文——这使前缀缓存的 agent 服务亚稳：短暂突发压垮命中率后，吞吐与命中率互相拖累、难以自愈[BURSTS]。缓存级降本（第 5 章）在任务链上有了失效边界。
  • 客户端与服务端的账要一起算。Think or Remember（2026-11）发现：丢弃早期推理内容的上下文策略，在服务端有无缓存复用下，重发成本相差可达 5 倍（1.74× vs 0.34×）——比较上下文策略必须同时说明服务端缓存行为[EXCHANGE]。
  • 排序问题交给登记表。"按 token 单价与按每次成功任务成本给配置排序何时一致"是可回看的研究判断：同一任务集、验收门槛与预算下的对照设计登记在研究判断登记表第 2 条，本节的证据构成它的机制依据。
  • 系统层开始原生适配 agent。Evolving Infra（2026-11）把运行时算力分配与 KV 自适应做进 P/D 分离服务，coding/math/computer-use 负载、GLM-5.2 与 Kimi K2.6、最高 256×GB300 规模上，平均端到端时延较 NVIDIA Dynamo 降 4.1×、P95 TTFT 降 14×[EVOLVINGINFRA]（预印本、厂商侧评测，口径见参考文献）。站内 Agent 推理系统篇的"任务成功成本账本"给的是同一问题的评测视角。
本章小结
  1. 调度级的本质是把分母（goodput）抬到 roofline、把分子（空闲时间）压到零：连续批处理+chunked prefill 是没商量的基础项。
  2. P/D 分离的收益证据充分（goodput 2–7×、成本 −20%），但 2026 的答案是自适应：按长度再调度、SM 复用、部分分离、每请求时延预算。
  3. 任务链级是独立战线：agent 跑在 batch=1、KV 增长主导成本、命中率亚稳、每步失败复利——优化对象从"每 token"移到"每成功任务"。
  4. 弹性三件套（迁移/抢占/快冷启）+ 系统层（Dynamo/llm-d/AIBrix/Evolving Infra）让"填满日历"成为产品功能；削峰既靠调度也靠价格。

7集群与商业级：采购曲线、能耗账与定价设计

前四层都假设"卡已经在那了"。最后两层管更贵的事：买什么卡、怎么付电费、价格怎么定。这一层的决策周期是季度到年度，但一旦做错，上面四层的努力都在给错误的分母打工。

7.1 硬件性价比曲线：贵 4 倍的卡反而便宜

1.1 的公式在采购层面的推论：卡的"每 token 成本"= 时租 ÷ 吞吐，而不是时租本身。

三个快照数字：H100 合约价 2025-10 为 $1.70、2026-03 回升 $2.35（+38%）；B200 2026-09 达 $8.01（三个月 +79%，HBM 短缺驱动）[GPUIDX]；GB300 NVL72 在 MLPerf v6.1 上单卡离线 16,635 tok/s（gpt-oss-120b）[MLPERF61]。

代际吞吐差距更大：NVIDIA 引用 SemiAnalysis InferenceMAX 口径，GB200 NVL72 跑 DeepSeek-R1 较 H200 NVL72 吞吐 15×，叠加 Dynamo 后较"无 Dynamo 的 B200"每卡 7×[NVIDIABLOG]。

采购的另一个方向是异构与"经济型加速器"：2026-11 的 Cluster Efficiency 研究把非 GPU 经济型加速器（Tenstorrent Blackhole）经快互连池化，在 3 年 TCO 口径下 tokens/$ 达到 8 卡 RTX PRO 6000 Blackwell 服务器的 1.07–2.24×；但互连一慢优势即失（吞吐 −23.5%~−67.4%）[CLUSTEREFF]——"买什么"不只是"买哪代 GPU"，还包括互连拓扑与非 GPU 加速器的性价比核算（站内 CPU-GPU 混合推理篇是同一命题的软件版）。

采购纪律：永远按"目标负载下的 tok/s/芯片 ÷ 芯片时租"排序，而不是按卡价排序；同时把 NVLink 域（NVL72 的 72 卡共享显存带宽）当作计价单位——MoE 时代的吞吐是按"域"出来的。

7.2 能耗与碳：电费不是大头，密度和碳是

账本事实：电费仅占 GPU TCO 的 10–15%[EPOCHTCO]。

但能耗仍以三种方式进入成本：

  1. 散热与功率上限决定机柜密度——同样机房塞进更多算力等于摊薄房租（TAPAS，ASPLOS'25 研究功率超额认购的收益[TAPAS]）。
  2. 碳口径开始进采购评估（大客户的 Scope 3）。
  3. 每 token 能耗是跨代际最公平的效率尺：Hopper ≈10 J → Blackwell ≈0.4 J → Blackwell Ultra ≈0.2 J（NVFP4，GPT-MoE-1.8T 口径）[NVFP4]。

软件侧：DGX-H100 特征化显示多数配置可降 ~20% 功率而不损延迟/吞吐[GREENER]；DynamoLLM 在 SLO 内省 53% 能耗[DYNAMOLLM]。

水足迹的科普口径（"每 10–50 条回复一瓶水"）已被修正到现代模型短对话约 5 ml/次——引用时用后者[WATER26]。

7.3 定价设计：价目表是最便宜的成本工程

3.4 节列了分级定价的四种形态。这里补设计视角：定价结构本质是把系统成本的不均匀性翻译成价格信号——峰谷对应集群利用率曲线、命中价对应缓存命中率、长度分档对应 prefill 计算量、SLO 分级对应资源独占程度。TSE 的工作论文从机制设计证明：开发者 API 的线性按 token 计价是"容量约束下影子成本的受限有效定价"，订阅/聚合器/按 token 各自对应不同的最优场景[MENUPRICE]。给自建平台团队的启示：内部计费（chargeback）也该长这样——按命中/未命中分开记账、给离线团队自动"谷价"，成本行为会自己跟着价格信号走。

8视频案例：响应延迟如何改写成本可行域

你按下开关，盯着灯什么时候变亮，这是一段等待。旁边一排灯一秒能亮多少次，是另一个数。想让开关用起来顺手，要记住每次按下到看见变化的时间。

前面所有账本都默认"产出单位是 token 或任务"。当产出变成交互式视频流时，三个时间口径必须再分开，否则"高吞吐优化"会把系统推向错误的方向。本章用一个 2026-11-12 的案例把这件事讲透：PixVid（Roblox 等，arXiv:2611.17336）——把预训练潜空间视频模型（Wan2.1-14B 系）搬到像素空间逐帧生成的工作[PIXVID]。它只作为"吞吐、响应和成本不同"的一个案例，机制细节（Self Forcing 因果蒸馏、世界模型谱系）见站内实时世界模型篇，少步采样与求解器见采样效率篇。

8.1 control-to-screen：第四个时间口径

视频服务里容易混为一谈的四个量：启动时延（TTFC，第一帧出现）、流式间隔（相邻可见帧的时间差，其分布不能由平均吞吐推出）、平均帧率（FPS）与控制到屏幕时延（control-to-screen：从用户输入一个事件，到第一个反映该事件的可见帧出现）。最后一个由论文定义并计量，本文引用的模型侧计时包含两部分——等待同块其余控制到齐 + 块生成时间；它与 TTFC、帧间隔、平均 FPS 都不同，也互相推不出。

[PIXVID] Song, Y., Chen, S., Rockwell, C. et al.（Roblox / UC Merced / UPenn / UT Austin）. Back to Pixels: Lifting Latent Video Diffusion into Pixel Space. arXiv:2611.17336v1，2026-11-12。原文（§1）："Since common latent world models autoregressively generate frames in blocks, the frame corresponding to a control cannot be generated until all controls for the full block are received. This results in a minimum control-to-screen latency proportional to the block size, a barrier that no model-side optimization can remove."（中文译文：常见潜空间世界模型按块自回归生成帧，与某条控制对应的帧必须等到该块全部控制到齐才能生成。这造成一个与块大小成正比的 control-to-screen 延迟下限——任何模型侧优化都移除不了的屏障。）链接：arXiv · 项目页

  2. 结构性等待由架构决定，内核优化移除不了：3D VAE 把 4 帧压成 1 个 latent，块必须等齐全部控制才能开算（SolarWM 每四个帧才收到一次相机位姿，急转自然糊掉，Turn 0.70）。论文明确说这是"no model-side optimization can remove"的屏障；是否等待、等多久，取决于控制采样与生成协议的约定，而非算得快慢。
  3. 缩小块改善响应，但改变算术强度与质量：单 latent 版把延迟 495→164 ms，FVD 却从 53.8 恶化到 118.6、Turn 从 0.70 崩到 0.11——省下的等待换来了质量折扣；PixVid 逐帧生成则把每帧 DiT 计算抬到 3×（16.4 vs 5.6 TFLOPs）、吞吐降 2.4×，去掉 VAE 解码的同时引入 detailer head 的逐帧特征缓存这类新解码状态。响应的每一档改善都在动分子（计算量）与 V_valid 的过滤条件（质量）。
  4. 预生成与更深缓冲能降卡顿，但代价是响应与过时帧（本文推论，论文未测缓冲深度）：把块算在前面、播放吃缓冲，播放平滑度上去了，可缓冲越长，新控制被"埋"在已生成帧里的时间越长，且转向瞬间的旧帧全部变过时产出——成本照记分子，产出不计入 V_valid。
  5. 吞吐越过播放帧率只说明平均供给能力：72.0 与 29.4 fps 都超过 16 fps 原生线，都能"实时播放"；但等待是 0–688 ms 的分布、中位 495 ms——平均 FPS 既不保证尾部不卡顿，也不能证明成本最优。提高吞吐不能消除等齐控制这一等待项，但计算加速仍可能降低响应中的块计算部分。

8.3 把案例写回公式：约束优化视角

视频交互服务的目标可以写成与 2.1 同构的约束形式：

min_x  C_unit(x) = C_total(x) ÷ V_valid(x)
s.t.   Q(x) ≥ Q₀              （质量效用下限；FVD 等越低越好的指标需另设上限）
       R_p99(x) ≤ R₀           （控制到屏幕延迟的尾部分位，ms）
       StallRate(x) ≤ ε        （卡顿率：播放间隔超阈值的帧占比）
       M_peak,g(x) ≤ C_g       （每卡峰值显存：权重 + KV/特征缓存 + 激活）

决策变量 x 包括块大小、蒸馏步数、缓冲深度、分辨率、解码结构与资源分配。论文报告的是中位响应，不能据此断言 p99 ≤ 100 ms，也不能用平均 FPS 判定成本最优。12 帧块的等待支持范围约为 0–688 ms；这是最大等待的量级，不是每次请求都要付出的最小延迟。是否满足尾延迟约束，需要同一负载下的分布测量。

一个教学算例（以下尾延迟与质量门均为假设，不是论文测量）：设时租 $8/h，两个方案分别具有吞吐 72 与 29.4 fps、p99 响应 839 与 50 ms，且都通过同一质量门。若要求 p99 ≤ 120 ms，只有第二个方案可行。在持续满载、所有输出均被消费且有效的假设下，其每有效播放秒成本为 8 ÷ 3600 ÷ (29.4/16) ≈ $0.0012。放宽到 900 ms 后两者才都可行，第一方案按同一假设约为 $0.00049。单会话生成超出播放速率但未被消费的帧不算有效产出；质量门、利用率或消费方式变化时应重算，不能据此宣布实际模型最优。

完整的块等待推导与消融口径见视频案例篇 3.6 节（跳过去会看到：62.5 ms 控制间隔下可动手核对的块等待算例表，以及首帧时间、帧间隔、平均帧率与控制到屏幕时延四个定义）；如何把该问题组织成建模与验证任务，见研究路线篇。"同资源、同质量门下对照同卡与流水线分离"的可回看判断登记在研究判断登记表第 3 条。交互视频投机生成提供了改变等待协议的研究方向，但仍需按接受率、废弃产出与验证成本记账[IVGSPEC]。

这段案例也是全站四阶段研究路径的缩影：建模给出账本（本节表格）、约束优化定义可行域（上面的公式）、协同设计同时动结构与资源（PixVid 改的正是架构而非内核）、自适应处理变化（按负载在块大小/缓冲间切换，尚是开放问题）。

8.4 质量指标不是线性效用

视频侧还有一个容易踩的坑：把 C_unit 除以 FVD 或 VBench 平均分当"性价比"。FVD 是集合级分布距离，不是"质量倍数"——118.6 对 53.8 不是"质量差 2.2 倍"，也换算不回成本；VBench 各维分数加权方式因业务而异。更贴近交互价值的反而是任务相关指标（Turn 相关性、旋转/平移误差）与人的体感（跟手、卡顿）。正确做法：质量作为约束（Q ≥ Q₀）或 V_valid 的过滤条件，而不是除数——这与 1.3"平均质量分数不是线性效用"是同一条纪律的多模态版。

本章小结
  1. control-to-screen 与 TTFC、帧间隔、平均 FPS 是四个不同的量：潜空间时间压缩带来的块等待是结构性下限，内核与吞吐优化都移除不了。
  2. PixVid 案例：72.0 fps 的 12 帧块中位响应 495 ms，29.4 fps 的单帧块 34 ms——吞吐越过播放线只说明平均供给能力，不保证响应与尾部；缩块的代价是算术强度、吞吐与质量同变。
  3. 把响应写成 R_p99 约束后，可行域由业务容限定义：约束不可行时 V_valid→0；质量指标（FVD/VBench）作约束或过滤，不作除数。

9.4 观测与归因：钱花到哪个请求上了

没有归因就没有优化优先级。

  1. 请求级能耗归因：StepSplit（arXiv 2611.13802）把 Shapley 值方法扩到大批量：每请求能耗 = 自身部分 + 共享均摊，静态批 batch 8–256 下 L1 误差 0.4–4.3%（按 token 均分则为 13.4–61.3%）——"按 token 均摊"是常见的错误归因[STEPSPLIT]。
  2. 先仿真后上机：Vidur（MLSys'24）证明配置搜索可用仿真完成——LLaMA2-70B 最优配置 96 核 CPU 约 1 小时（$9.93/时）替代 42K GPU 小时（约 $218K）的实测搜索；配置错配的代价高达 2×[VIDUR24]（站内性能仿真篇有完整方法论）。
  3. 口径统一：并发感知成本模型提醒同一硬件不同并发下 $/M 相差 17.5×——归因报告必须带并发与 SLO 上下文[CONCOST26]。

9.5 反模式清单

  • 用旗舰模型做路由级任务：分类/抽取/改写用小模型或便宜档，市场数据说同能力开源便宜约 90%[MARKET25]。
  • SLO 过度：所有请求都要 p99 快 = 全员 Priority 价。把流量分层（交互/批处理/离线），每层各自的 SLO 与价格。
  • 只看吞吐不看 goodput：不达 SLO 的吞吐是对着镜子举杠铃；报表里两列必须并排。
  • 缓存价目没设计：自建平台不区分命中/未命中 → 内部用户没有动力把 prompt 写成可缓存的前缀结构。
  • 截断上下文省显存：LMCache 实测命中率减半，省了小钱亏了大钱[LMCACHE]。
  • 跨系统直接比数字：不带口径与快照的 "$X/M" 一律不可比（2.8 纪律）。

9.6 动手：三十行算清你的 $/M tokens

把 1.1 与 1.3 的公式放进标准库 Python（无第三方依赖，口径注释即文档）：

#!/usr/bin/env python3
"""单位成本计算器：$/M tokens、命中率收益、质量调整与 goodput。口径见注释。"""
RATE = 2.35          # USD per GPU-hour，集群时租（含分摊的 TCO 加成）
GPUS = 8             # 卡数
TOKS_OUT = 16_000    # 系统输出吞吐 tok/s（SLO 达标部分才计入，即 goodput 口径）
HIT_RATE = 0.80      # 输入 token 的缓存命中率
HIT_DISCOUNT = 0.1   # 命中部分的相对成本（按"命中价≈未命中 1/10"折算）
IN_OUT_RATIO = 3     # 真实负载输入:输出比（先用自家日志算，别抄基准的）
QUALITY = 0.9        # 任务成功率（用于质量调整）

per_m_out = RATE * GPUS * 1e6 / (TOKS_OUT * 3600)        # 输出每 M tokens 成本
per_m_in  = per_m_out / IN_OUT_RATIO                     # 未命中输入的粗估同价折算
per_m_hit = per_m_in * HIT_DISCOUNT
blended   = (IN_OUT_RATIO * ((1-HIT_RATE)*per_m_in + HIT_RATE*per_m_hit) + 1*per_m_out) / (IN_OUT_RATIO + 1)
per_task  = blended / QUALITY                           # 质量调整：答错重试都算钱

print(f"输出 ${per_m_out:.3f}/M | 输入(未命中) ${per_m_in:.3f}/M | 命中 ${per_m_hit:.4f}/M")
print(f"混合价(输入:输出={IN_OUT_RATIO}:1) ${blended:.3f}/M | 每成功任务等效 ${per_task:.3f}/M")
# 例： RATE=2.35, GPUS=8, TOKS_OUT=16000 → 输出 $0.326/M；命中率 0.8 使混合价较全未命中约省 26%

本章小结
  1. 仪表盘 8 个数，先看goodput 达标率与命中率——它们决定其他数字有没有意义。
  2. 决策树按症状下药：贵在 prefill 找缓存、贵在 decode 找精度、贵在空闲找调度、贵在峰值找定价、贵在重试找质量。
  3. 归因要 Shapley 不要均摊、搜索要仿真不要实机、对比要口径不要裸数——算错账的降本比不降本更贵。

10.1 本文结论的边界

  • 证据口径：本文全部性能与价格数字来自所引论文、官方发布与官方价目页（快照日期随文标注），没有一项是本站自测的 GPU 基准或服务实测；跨系统数字不可直接比较。价格与租金随月波动，2026-11-15 之后未重验的数字仍按原快照口径引用。
  • 案例边界：第 8 章 PixVid 为单篇论文的单卡实验（B200、480×864、4 步蒸馏、81 帧），结论刻画的是"块等待"这一类结构性现象，不构成对任何生产视频服务的评测；其质量与延迟数字是论文自报口径（预印本，尚未同行评审），扩散模型代际迭代快，具体数字有效期有限。"缓冲深度换响应"的账为本文推论，非论文数据。
  • 预印本成熟度：2026 年新增引用中，Evolving Infra、Cache Engineering for Agents、Total Cost of Agency、Bursts、Cascade、ShuntServe、Cluster Efficiency、VisMemo、TileCache、Lachesis、VLM 剪枝评测等均为 arXiv 预印本（个别有厂商背景），机制洞见可引，量级数字须待同行评审与独立复现。
  • 覆盖面：推理预算（test-time compute）、Agent 系统机制、仿真与自动调优方法论分别由站内专题承担，本文只保留成本视角；vLLM-Omni、扩散服务等多模态服务栈的成本形态仍以定性为主——公开的多模态服务级成本账本（类似 DeepSeek 545% 那种）尚未出现。

10.2 研究问题

  • 从每 token 到每任务：Agent 多步调用把 token 消耗放大 10–100 倍，"每 token 便宜"与"每任务便宜"开始脱钩——6.5 的 2026 年工作已经把任务链级做成独立战线，下一步是任务级计费与"客户端上下文策略 × 服务端缓存"的联合定价（站内推理预算篇与 Agent 推理系统篇已铺开）。
  • 质量感知定价与路由：tiered 定价研究显示旗舰档因 reasoning 溢价不服从指数降价[TIERED26]；按"能力档"而非"模型名"计价（AA 的 Intelligence per $ 是雏形）会倒逼路由器与级联成为标配。
  • 能耗/碳口径标准化：主流基准（MLPerf）尚无能耗与碳的必报项[MLPERF61]；SIMPLE 定律、Energy/Token 倡议与 Shapley 归因正在把 J/token 变成可审计指标[SIMPLE26][EPT26][STEPSPLIT]。
  • 硬件市场波动 vs 效率赛跑：HBM 短缺把 B200 租金三个月推高 79%[GPUIDX]，而纯软件两个月可降 5×[NVIDIABLOG]——租约结构（短约 vs 长约）本身将成为成本工程题目。
  • 跨厂商成本可比模型：定制引擎篇 6.9 指出的开放问题依然成立——每家"每 token 成本"口径不可比；学术界（并发感知成本、Tiered 定价）正在补这块地基[CONCOST26][TIERED26]。
本章小结
  1. 主口径正从每 token 走向每任务：Agent 时代便宜的是 token，贵的是任务。
  2. 定价、基准与归因方法都在向质量感知与可审计演进；J/token 会成为像 MFU 一样的常识指标。
  3. 租金上行与效率赛跑并行，租约与采购结构本身进入成本工程的射程。
