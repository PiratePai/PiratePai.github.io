1 预备知识：请求的四只时钟

表 1-1 · 本文账本的指标定义
指标公式边界
客户端排队s − a压测机或并发上限造成的等待
TTFT（首 token 延迟）f − a本文包括客户端排队；若使用 f − s 必须另标口径

餐厅中，TTFT 类似从入队到第一道菜上桌；TPOT 类似后续菜品的平均上菜间隔。最后一道菜和结账结束也不是同一时刻。

流式 HTTP 的一个数据块可能包含多个 token。把数据块数量当 token 数，会同时算错吞吐和 TPOT。真实采集应保留服务端 token 计数、客户端接收时间及聚合方式；得不到逐 token 时间戳时，不宣称测到了逐 token ITL。上述时间线是本文的统计约定，不要求不同压测器天然采用同一口径。

1.2 两种负载回答不同问题

闭环负载维持固定数量的在途请求，完成一个再补一个，适合观察并发用户体验。系统变慢时，产生新请求的速度也下降。开环负载按预定时间发送，例如每秒到达若干请求，用来观察排队和过载。限制最大并发会把开环输入变成受限输入，必须记录积压或拒绝，避免隐藏负载。

vLLM 将 --request-rate 与 --max-concurrency 分开控制；文档明确说明，并发限制可能使实际发起速率低于设定速率。无限请求速率则表示一次性提交，不能标为“稳态每秒请求数”。[BENCH]

本章小结
  1. 先说明计时从哪里开始，结束在什么事件。
  2. 平均 TPOT、逐 token ITL 和完整任务耗时是不同指标。
  3. 固定并发与固定到达率应分别实验，过载时仍保留积压和失败。

2 指标：从吞吐走到有效吞吐与质量

2.1 goodput 的单位与分母

在长度为 T 秒的观察窗口内，完成吞吐为成功请求数/T；输出吞吐为成功请求生成的 token 总数/T。本文的 SLO goodput 定义为：同时满足首 token、输出间隔、总延迟上限的成功请求数/T，单位是请求/秒。SLO 是服务目标，例如 TTFT ≤ 300 ms；这些阈值由应用确定，本文教学阈值不构成部署建议。DistServe 研究的核心也是受延迟约束的服务能力。[DIST]

[DIST] Yinmin Zhong 等. DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving，OSDI 2024；arXiv:2401.09670，首次提交 2024-01-18，v3 2024-06-06。原文：“within both TTFT and TPOT constraints”（同时处在 TTFT 和 TPOT 两项约束内。）原文。

另一个量是达标率：达标请求数/全部计划请求数。失败、超时、取消不能从分母消失。只有一个 token 的请求没有 TPOT，本文将该约束记为“不适用”，仍检查 TTFT 和总延迟；必须同时报告单 token 数量或 TPOT 有效样本数。

如果成功响应还有准确性标签，可以再计算“质量与延迟同时合格的请求/秒”。但不能默认 HTTP 成功就是回答正确；质量标签不全时，附带工具会把该指标输出为 null，避免让未知质量冒充已验证质量。

2.2 分位数和不确定性

P95 表示一个分布的 95% 分位位置。本文工具使用 nearest-rank：升序排列 n 个值，取第 ceil(0.95n) 个。插值算法会给出不同答案，所以实验应固定算法。成功请求的延迟分布必须与失败率并列展示；大量超时被排除后，“成功样本 P99 很低”仍可能对应不可用的服务。

六条请求只足以检查算式。小样本的 P99 往往就是最大值，不能据此估算生产尾延迟。正式比较需要独立重复、相同请求集和随机化执行顺序；置信区间的抽样单位也应匹配依赖关系。多轮 Agent 应按整条任务轨迹重采样，不能把同一任务中的 token 当作独立实验。

2.3 费用与显存应怎样记录

报告峰值显存时，区分驱动看到的进程占用、框架预留内存和活跃张量；说明预热、空闲缓存及共卡进程。费用至少包含生成、验证器、草稿、工具和失败重试；自部署服务还要明确 GPU 空闲时间是否计入。单纯降低每 token 费用，未必降低完成一个任务的总费用。

本章小结
  1. 吞吐、有效吞吐和达标率必须标明单位与分母。
  2. 失败率应与成功请求的尾延迟同时展示。
  3. 质量、显存和费用各有独立口径，不能从吞吐推导出来。

随机 token 输入适合控制形状，不代表真实对话内容，尤其不能代表草稿接受率、前缀命中率或准确率。测投机解码至少增加真实文本回放；测前缀缓存则生成并保存确切共享前缀，避免压测脚本无意复制系统提示导致不公平热缓存。

3.2 固定什么，允许改变什么

记录权重和 tokenizer 的 revision、提示模板、引擎提交或镜像 digest、驱动、计算库、GPU 型号与数量、功耗设置、并行配置、采样参数、输出上限、数据哈希和压测机规格。模型量化会改变数值行为；投机方法即使有分布等价保证，也不意味着同一种子下逐字相同。应在相同任务上比较质量分布。

固定种子有助于复现，但不足以消除调度和浮点实现差异。vLLM 文档明确限定其复现条件；跨硬件或跨版本不应承诺逐位一致。性能测试与确定性测试可以分开做，并记录为了确定性开启的配置。[REPRO]

3.3 组合优化需要消融

对两个开关 A、B，至少测基线、A、B、A+B 四组。若 A 使平均时间从 100 降到 80，B 降到 70，不能据此承诺组合后是 56；它们可能在优化相同瓶颈，也可能争用缓存或工作空间。先检查后端支持与数值精度，再对同一负载画质量—延迟曲线。

同一条拥堵道路拓宽两次，收益会互相影响。每项技术单独节省的时间，不能像两笔互不相关的折扣直接相乘。
本章小结
  1. 短长输入、短长输出、冷热点和负载必须分层。
  2. 保存模型、环境、请求集及配置的不可变标识。
  3. 组合实验先查兼容性，再做四格消融，不乘论文加速比。

5.1 从一个可以归档的基线开始

下面使用已安装且记录版本的 vLLM，并指向本地已固定 revision 的模型目录。先在隔离环境检查 vllm serve --help 与 vllm bench serve --help；命令参数按 2026-11-04 官方文档核验，不表示所有旧版本都支持。服务端与客户端各用一个终端。[BENCH]

vllm serve /models/pinned-checkpoint --served-model-name baseline --host 127.0.0.1 --port 8000

# 另一个终端：先确认服务就绪，再执行形状可控的冒烟压测
vllm bench serve --backend vllm --host 127.0.0.1 --port 8000 --model /models/pinned-checkpoint --served-model-name baseline --dataset-name random --input-len 512 --output-len 128 --num-prompts 100 --request-rate 1 --num-warmups 10 --seed 0 --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 --goodput ttft:300 tpot:60 e2el:10000 --save-result --save-detailed --result-dir runs/baseline-r1 --result-filename raw.json
代码 5-1 · 待在目标硬件执行的服务冒烟实验；1 请求/秒、100 请求与延迟阈值是示例设置，不能据此声明容量。参数含义见 [BENCH]；随机输入不能用于质量或投机接受率结论。

归档目录至少包含 environment.txt（硬件、驱动、依赖）、commands.txt（完整启动及压测命令）、manifest.json（模型/数据哈希、负载、缓存状态）、原始结果、服务日志和质量结果。提供的运行清单模板中未填写字段保留 null；有空缺时不把它标为已复现。

官方原始 JSON 与本站标准化 JSONL 是不同格式。转换时必须核对单位、结束时刻和失败记录；不能直接改扩展名，也不能从汇总平均值倒推出逐请求记录。若原始数据缺少计划到达时刻，本文“包含客户端排队的 TTFT”应标为未测，不能补造时间。

5.2 从冒烟到可以支持结论的运行

  1. 锁定配置并预热；冷启动耗时单独测，稳态样本不混入编译和加载。
  2. 扫描到达率并观察积压，确定低负载、临界点和过载三档；检查压测机 CPU、连接数和网络是否先饱和。
  3. 对每档运行基线与单项优化，多次独立重复并交错执行；为每次运行分配独立目录。
  4. 缓存实验明确清空或预热过程，确认实测命中率；量化和投机保持任务、提示模板、采样协议一致。
  5. 在留出集测质量与失败类型，按输入长度、任务类型分组；画质量—延迟—费用曲线，再决定是否保留配置。
负结果也归档：接受率高但吞吐下降、平均延迟改善但 P99 变差、缓存命中高但路由成本吞掉收益，都应留下原始数据。是否启用一项优化由目标负载决定。
本章小结
  1. 先留下一份完整基线，再扩大扫描矩阵。
  2. 官方压测结果必须核对格式与口径后才能进入本站账本。
  3. 真实质量与硬件性能实验尚未执行，命令和清单提供可复现起点。

一份可审阅结论应是：“在模型 revision X、硬件 H、请求分布 W、质量阈值 Q 下，配置 A 相对基线的指标如何变化”。只在采样过的范围内声明结论；不同模型、不同长度或另一种并行拓扑属于外推。容量模型的用途是提出下一次实验，不是替代校准。

6.2 与另外两个新专题形成闭环

推理时计算确定每道题该投入多少生成与验证预算；Agent 在线推理系统把多轮模型调用、工具等待和恢复开销放回完整任务。最终以相同任务集上的成功率、延迟和成本选择方案，并把失败样本送回下一轮优化。

本章小结
  1. 性能现象先转成可验证的瓶颈假设。
  2. 模型、硬件和负载共同限定结论的适用范围。
  3. 用任务成功率与总成本收口，保留原始材料和负结果。
