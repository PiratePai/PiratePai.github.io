1.为什么不动权重也能加速：给本科生的原理课

“Training-free（免训练）推理优化”指的是无需额外训练目标模型；量化仍可改变权重数值表示，草稿或优化 Agent 自身也可能经过训练，只改变模型运行时的“环境”——执行哪个算子、数据存哪、按什么顺序算、用什么精度算——来降低延迟和显存、提高吞吐。为什么这能奏效？因为训练得到的权重只决定了“算什么”，而“怎么算”存在巨大的浪费。

1.1 一分钟硬件经济课：卡在哪

把 GPU 想成一家中央厨房：算力（FLOPS）是灶台数量，显存带宽（GB/s）是传菜电梯。做一道菜（一个算子）既要用灶台（计算）也要电梯送原料（读写显存）。算子的算术强度 AI = FLOPs / 实际搬运字节；硬件峰值算力/带宽则给出 Roofline 的分界值。只有把这两个比值比较，才能判断理想瓶颈。如果一道菜只需要来回运一次料却只炒一勺（比如逐元素加法），电梯先忙不过来——这叫访存受限（memory-bound）；如果像矩阵乘法那样一次进料能炒一大桌，灶台先满载——这叫计算受限（compute-bound）。

关键事实：大模型自回归解码（一个 token 一个 token往外蹦）是极端 memory-bound 的。每生成一个 token，都要把全部权重从显存搬一遍，却只做一点点乘法。所以解码阶段的提速秘诀几乎全在“少搬东西”：权重少搬（量化）、KV 少存（KV cache 压缩）、一次搬多个 token 的活儿（投机解码）、让电梯尽量满载（batching）。而视频生成这类扩散模型的去噪阶段通常是 compute-bound 的，秘诀则是“少算几步/少算几份”（步数削减、缓存复用、注意力量化）。

1.2 六个加速杠杆（无需额外训练目标模型；量化会改变权重表示）

  1. batching（拼单）：电梯一次运 1 份菜和运 16 份菜耗时几乎一样，把 16 个请求拼一起，人均成本骤降。Orca 的 continuous batching（2022）解决了“拼单中途有人下车”的问题。 [Orca: A Distributed Serving System for Transformer-Based Generative Models, OSDI 2022]译要点：提出迭代级调度（iteration-level scheduling），每一步都动态重组 batch，而不是等整批完成。
  2. KV Cache 与分页（记账）：自回归生成时把已算过的 Key/Value 存起来避免重算；vLLM 的 PagedAttention 借操作系统“分页”思想管理这块缓存，把碎片浪费压到几乎为零。 [Efficient Memory Management for LLM Serving with PagedAttention (vLLM), SOSP 2023]译要点：把 KV cache 切成固定大小的块（block）按需分配，显存利用率显著提升、吞吐翻倍级。
  3. 量化（换成小包装）：权重/激活从 16 比特压到 8/4 比特，电梯每次运的“份数”翻倍。GPTQ（2022）/AWQ（2023）证明 4 比特权重量化几乎不掉精度；2024–2025 的 FP8（Hopper 起）与 NVFP4/MXFP4（Blackwell 起）把它做进了硬件张量核。 [AWQ: Activation-aware Weight Quantization, MLSys 2024; GPTQ, ICLR 2023]AWQ 原文要点：“activation-aware” —— 依据激活分布保护少量关键权重通道即可保住精度。
  4. 投机解码（先草稿后校对）：让小模型/草稿头连写 k 个 token，大模型一次并行校对，接受其中对的——数学上证明与直接采样同分布（无损）。EAGLE/MTP 是训练草稿头的代表；训练-free 的变体则用模型自身浅层或检索来起草。 [Fast Inference from Transformers via Speculative Decoding, ICML 2023]原文要点：rejective sampling 保证了输出分布与目标模型一致。
  5. 算子与图优化（改菜谱）：FlashAttention（2022–2024）把注意力改成分块计算避免物化巨大注意力矩阵，从算法上把 memory-bound 的 softmax 注意力变成接近 compute-bound；torch.compile/CUDA Graph 消除 Python 与 kernel 启动开销。这是“写更快代码”的杠杆，也是 Agent 最擅长介入的杠杆。 [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, NeurIPS 2022]译要点：以 IO 复杂度为目标重新组织注意力计算，精确（非近似）但更快更省显存。
  6. 缓存复用（抄上一题的答案）：多轮 Agent 场景里，请求之间共享大段前缀 → prefix caching（SGLang RadixAttention 命中率可达 80%+）；扩散模型相邻去噪步的特征变化很小 → 步间特征缓存（TeaCache 一族）。这是“内容层面的杠杆”，收益经常最大。

1.3 多模态生成模型（DiT）特殊在哪

像 MiniMax-H3 这样的视频/音频生成模型主干是 Diffusion Transformer（DiT）：同一个网络被反复执行几十次（去噪步），每次只对输入做微小修正。这带来三个独有的 training-free 机会：

  • 步间冗余：相邻步的中间特征高度相似 → 跳步/缓存（TeaCache：用 timestep embedding 判断“这步可以复用上一步”，2 倍级加速）； [TeaCache: Timestep Embedding Tells: It's Time to Cache for Video Diffusion Model, CVPR 2025 Highlight]译要点：把 timestep embedding 的累积差作为“该不该跳过本步”的信号，对齐输出漂移后 1.5–2.2× 加速。
  • CFG 双倍计算：classifier-free guidance 传统上每步要跑“有条件+无条件”两遍 → 官方做 CFG 蒸馏后单遍即可（H3 已内置，见 §4.1）；
  • 三段流水线：文本编码器（一次）→ DiT 去噪循环（几十步）→ VAE 解码（一次），三段瓶颈特征完全不同（LLM 式 memory-bound / compute-bound / 高分辨率卷积），必须分段画像、分段下药。

  • KV cache 压缩：老三样（H2O 2023、SnapKV 2024、KIVI 量化 2024）之后，2026 年的新方向是“查询无关”（Google TaskPress：pruning 决策与 query 解耦，2026-08）与“残差锚点”（Technion AnchorKV，2026-08）等更鲁棒的设计；DeepSeek 的 MLA（2024-12，KV 压到 1/10 以下）与 NSA（2025-02，原生稀疏注意力）则是“训练时就把 KV 压进架构”的路线——H3 模型卡也预告了其原生稀疏注意力“训而未放”（见 §4.1）。

3.2 三个教训（决定流程设计）

教训 1：奖励会被钻空子。Sakana AI 事件后，CUDA Agent 论文把“评测脚本文件权限保护、禁止 fallback 调用、多随机输入验证、测量同步与预热、不给联网工具”列为可靠奖励的前提。
对流程的推论：质量门脚本对 Agent 只读；变更必须可回滚。
教训 2：局部加速 ≠ 端到端加速。KernelOPT 的回退分析指出，在部分多 kernel 题目中“单独测更快的子 kernel”拼回整模型后收益消失甚至倒退（拼装开销、隐式 .contiguous() 拷贝、Amdahl 定律），故必须设端到端性能门（γ=1.03）。
对流程的推论：一切以端到端门 + 质量门收口，子项数字只做归因参考。
教训 3：别跟厂商库硬碰。KernelOPT 的 85 个回退案例中 61 个（约 72%）源于对 cuBLAS/cuDNN 已近峰值的算子强行重写。
对流程的推论：先 profile 找“真热点且可优化”的部分（Inductor 生成物、调度、缓存、精度），把重写算子放在最后且只对 Top-3 热点。

4.2 流程是怎么长出来的：四站式闭环

先想清楚三个物理事实，流程的形状就自然浮现了。事实一：H3 服务是系统问题——encoder、DiT 步循环、VAE、传输封装各有各的病，端到端数字根本没法指导下一步，所以第一件事必须是"分段看清基线"。事实二：不同病要用不同的药，吃错药不只是无效，还会浪费数周（官方端到端改动报告降低 30.8% 延迟，其中也含 DiT kernel 与通信优化，不能据此预设单算子优化上限），所以诊断必须产出一纸"按预期收益除以风险排序"的处方清单，纯参数的排前面、有损的排在无损后、自写 kernel 永远垫底。事实三：视频生成的耗时测量噪声在 3% 量级，而 Agent/人都天然想"看见自己想看的提升"（Sakana 事件的教训），所以每副药必须走一个很小的六拍循环——预期→只改一个变量→复测→对比→过门→判决（接受/回滚/噪声），并记入台账。

1
目标与基线：把"更快"翻译成三个数字（RTF 目标、显存上限、精度红线——红线决定有损处方是否入列）；冒烟→钉版本→三次分阶段基线→台账开张。
2
三层诊断：时间轴（设备 busy 覆盖率 / underfeed / 空隙位置）→ 算子四桶（注意力/矩阵乘/逐元素/通信，DiT 与 VAE 分开看）→ 通信暴露比。产出处方清单。
3
处方循环：七张处方笺（并行形态 / 注意力逐级加深 / 在线 FP8 / DLO 卸载 / 缓存标定 / host 侧 / 自写 kernel），每副走六拍循环；每并入两三副药回诊断站快扫一次——时间分布变了，处方要重排。
4
收口：四个停机信号（目标达成 / 连续两副<3% / 病根在驱动或硬件 / 触显存带宽顶）任一命中→终验（全量+双门）→归因报告→归档。

诊断的判读规则直接内建在流程里，不靠经验直觉：

这套流程不是凭空设计的：分层决策的顺序（先场景与框架、后算法与结构、最后才是 kernel 精装修）承自八层推理优化决策框架；闭环的工程细节（warmup 剔除、3% 噪声线、阈值触发表、唯一支持矩阵、产物归档）借鉴 MindIE-SD 的 .agents 技能体系；处方的量级预期则以 vLLM-Omni 官方博客的实测数字为锚。三者在这里被重新组织成一个东西：一个能同时被 Agent 执行和被人照着走的操作规程（配套 zcode-autotune/：AGENTS.md 给 ZCode，RUNBOOK.md 给人，§4.5 详述双模式）。 [Obsidian Vault《Notion/AI Infra/推理优化/推理优化》（八层框架）；MindIE-SD .agents（gitcode.com/Ascend/MindIE-SD/tree/master/.agents, 2025-11）；vLLM Blog: MiniMax H3 on vLLM-Omni, 2026-09-01]八层框架原话（节译）："自上而下定方向，自下而上抠细节，至少走两遍；反模式：跳过上面几层直接抠 kernel。" MindIE-SD 停止条件（节译）："差距 <3% 视为噪声，不宣称有效。"

4.3 GPU 实战（vLLM-Omni @ 8×B300/H100）：四站走一遍是什么样

环境：8×B300（或 H100），uv pip install "vllm-omni"（≥0.26，推荐 0.28+），模型 MiniMaxAI/MiniMax-H3。这里给每一站的关键动作与判读方式；逐条命令、示例输出与勾选清单在配套 zcode-autotune/RUNBOOK.md（人）与 AGENTS.md（ZCode）。

第一站半天：写三个数字（RTF≤1.0、HBM 上限、精度红线）→ 保守配置冒烟（最低步数、1 条 prompt，只验"没坏"）→ 钉版本与权重 revision → 三次分阶段基线。判读三条：最大段即本轮主战场；各段之和与端到端的差是"看不见的损耗"（喂给第三站 host 处方）；三次极差 >3% 可提示继续检查，但三次样本不足以刻画稳定性，应交错 A/B、多次重复并估计置信区间，先修环境。锚点：官方同规模的优化后 vLLM-Omni 结果为 56.917s，对照 Diffusers 为 82.239s；不能把 56.9s 当“无优化”，差数倍先怀疑配置。

第二站两小时，自上而下三层：时间轴回答"设备在忙还是在等"（busy<85% 时空隙成片 = host 病，kernel 处方直接降权）；算子四桶回答"DiT 的时间在哪类操作上"（注意力/矩阵乘/逐元素/通信，按 §4.2 表开出处方）；暴露比回答"通信是否被计算盖住"（>30% 才值得动并行形态）。产出一纸按收益/风险排序的处方清单——清单之外的事，这一轮不做。

第三站是主战场，每副药六拍循环（预期→单变量→复测→对比→过门→判决）。第一副几乎永远是并行形态（无需改算子代码、仍需验证内存与通信风险）：从保守配置逐组加 --usp 8 --ring 1 --ulysses-a2a-permute → --text-encoder-tp-size 8 → --vae-patch-parallel-size 8 --vae-parallel-mode tile --vae-use-tiling → --diffusion-attention-backend TRTLLM_ATTN，四组各自记账，再组合收益最大者。之后按诊断信号走：注意力高→量化注意力逐级加深（每级单独过有损门，损失会叠乘）；矩阵乘高或显存紧→在线 FP8（官方 -5.3%/-38.9%）；显存超线→DLO 换血（用延迟买显存，台账两个数字都记）；步数多且允许有损→缓存三点标定。每并入两三副药回第二站快扫——时间分布变了，处方重排（打地鼠的节奏控制）。

第四站：四个停机信号任一命中即收口——全量终验 + 双质量门 + 诊断复扫（前后两张时间分布表是报告里最有说服力的一页）+ 台账全文 + 每行一句归因（"时间省在了哪"）。两个容易踩的判断：FastH3 四步版（RTF≈0.857）是训练路线且与 DLO/量化/缓存互斥，只作对照；自写 kernel 永远最后，且必须端到端 ≥1.03× 收口——子算子的收益在拼回整模型后消失的比例高得超出直觉（该现象依任务与调度而变，此处不保留未定位分母的 29%）。

4.4 NPU 实战（昇腾）：vLLM-Omni NPU 后端 + MindIE-SD 双路径

v2 事实修正：vLLM-Omni 0.28.0 已官方宣布 H3 在 GPU 与 NPU 上生产就绪（其支持矩阵覆盖 CUDA/ROCm/XPU/NPU/MUSA）。因此 NPU 流程不再是"从零移植"，而是双路径选择：

  • 路径① vLLM-Omni NPU 后端：与 GPU 同一套 vllm serve --omni 命令面，底层经 vllm-ascend/torch_npu/CANN 落到昇腾——四站流程与 §4.3 完全同构，只是诊断站的采集与分析换 msprof/MindIE-SD 脚本、量化换 W8A8、通信换 HCCL；
  • 路径② MindIE-SD 原生引擎：当 vLLM-Omni NPU 后端未覆盖某能力（某 Pattern/量化形态/调度特性）时，MindIE-SD 是昇腾原生的 DiT 引擎（cache_agent / compilation / quantization / eplb 四大模块，2025-12-31 起支持稀疏 Attention；2025-12-25 已实现 vLLM Omni × MindIE-SD 在昇腾上原生跑 Qwen-Image-Edit 系）。

NPU 流程的王牌：MindIE-SD 已把整套闭环开源成 .agents 技能，ZCode（或人）直接复用现成脚本而不必重写：

满足"既能自动跑、也能人照着走"的关键设计是：流程写成一份，角色只改执行者。配套 zcode-autotune/ 里，AGENTS.md 是给 ZCode 的机器风格规约——状态机（S0 目标→S1 基线→S2 诊断→S3 处方循环→S4 收口）、六拍循环、信号→处方映射表、台账 schema、停机规则、必须停下等人的介入点；RUNBOOK.md 是给人看的自然语言手册——同样的四站，每步先讲为什么现在做这件事、再给可复制的命令、然后教你怎么读输出（含示例格式和判读规则），最后以检查点收束。两份文档面向同一套 bench_gen.py/quality_gate.py 裁判脚本：

4.6 每一步"为什么"——方法论的根源

  1. 为什么"系统问题"优先于"DiT 问题"：官方博客的量化答案——官方完整响应 82.239s→56.917s（−30.8%），优化后 DiT 仍耗 51.800s、约占 91%，因此 DiT 仍可能是主战场；不能从整系统收益推出该段优化天花板低（encoder 51.5GB、VAE 与传输通路都是可结构化的延迟源）。
  2. 为什么处方按"收益/风险"排序、自写 kernel 永远垫底：八层框架的反模式警告（"花两周融算子拿 8%，开个结构开关直接 2×，前功尽弃"）+ KernelOPT 的 61/85（约 72%）厂商库主导回退案例（硬碰近峰算子）。无需改算子代码、仍需验证内存与通信风险的并行形态永远第一副。
  3. 为什么诊断第一问是"设备忙还是等"：busy 低可能来自 host、通信、依赖或并行度不足，须结合 CPU/GPU/网络时间轴归因，不能由单一利用率直接开处方；busy 高才往下分桶——用信号代替直觉。
  4. 为什么 3% 噪声线与只读裁判：MindIE-SD 与 KernelOPT 双重背书（<3% 不宣称有效；评测脚本防篡改防 reward hacking）。
  5. 为什么"支持矩阵"要先于动手：框架能力随版本漂移，任何 flag/量化形态先对当版 --help（NPU 侧对 MindIE-SD 的 features 矩阵）验存在性——把"教训 3"制度化。
  6. 为什么 NPU 先 Dummy Run 再下权重：51.5GB 级权重下载昂贵；§A 用 KB 级配置+随机权重即可验证架构兼容（MindIE-SD model-verification 的核心价值）。
  7. 为什么质量门分无损/有损两档、端到端门定 1.03：两类声明两类证据（数值验收→指定测试集与容差下 allclose/PSNR；感知质量验收→CLIP/LPIPS 与抽检；这些有限测试不证明一般数值或语义等价）；3% 仅是待标定的工程阈值；使用交错 A/B、足够重复与置信区间，避免搜索挑中偶然快的配置。
  8. 为什么"每并入两三副药要回诊断快扫"：每副药都改变时间分布，注意力压下去后矩阵乘就是新的头号——打地鼠要有节奏控制，否则处方清单会过期。
