1.为什么不动权重也能加速：给本科生的原理课

“Training-free（免训练）推理优化”指的是不修改模型权重、不做梯度更新，只改变模型运行时的“环境”——执行哪个算子、数据存哪、按什么顺序算、用什么精度算——来降低延迟和显存、提高吞吐。为什么这能奏效？因为训练得到的权重只决定了“算什么”，而“怎么算”存在巨大的浪费。

1.1 一分钟硬件经济课：卡在哪

把 GPU 想成一家中央厨房：算力（FLOPS）是灶台数量，显存带宽（GB/s）是传菜电梯。做一道菜（一个算子）既要用灶台（计算）也要电梯送原料（读写显存）。两个指标相除得到“这道菜每运一份原料能炒多少菜”——算术强度（arithmetic intensity）。如果一道菜只需要来回运一次料却只炒一勺（比如逐元素加法），电梯先忙不过来——这叫访存受限（memory-bound）；如果像矩阵乘法那样一次进料能炒一大桌，灶台先满载——这叫计算受限（compute-bound）。

关键事实：大模型自回归解码（一个 token 一个 token往外蹦）是极端 memory-bound 的。每生成一个 token，都要把全部权重从显存搬一遍，却只做一点点乘法。所以解码阶段的提速秘诀几乎全在“少搬东西”：权重少搬（量化）、KV 少存（KV cache 压缩）、一次搬多个 token 的活儿（投机解码）、让电梯尽量满载（batching）。而视频生成这类扩散模型的去噪阶段通常是 compute-bound 的，秘诀则是“少算几步/少算几份”（步数削减、缓存复用、注意力量化）。

1.2 六个加速杠杆（全部不碰权重）

  1. batching（拼单）：电梯一次运 1 份菜和运 16 份菜耗时几乎一样，把 16 个请求拼一起，人均成本骤降。Orca 的 continuous batching（2022）解决了“拼单中途有人下车”的问题。 [Orca: A Distributed Serving System for Transformer-Based Generative Models, OSDI 2022]译要点：提出迭代级调度（iteration-level scheduling），每一步都动态重组 batch，而不是等整批完成。
  2. KV Cache 与分页（记账）：自回归生成时把已算过的 Key/Value 存起来避免重算；vLLM 的 PagedAttention 借操作系统“分页”思想管理这块缓存，把碎片浪费压到几乎为零。 [Efficient Memory Management for LLM Serving with PagedAttention (vLLM), SOSP 2023]译要点：把 KV cache 切成固定大小的块（block）按需分配，显存利用率显著提升、吞吐翻倍级。
  3. 量化（换成小包装）：权重/激活从 16 比特压到 8/4 比特，电梯每次运的“份数”翻倍。GPTQ（2022）/AWQ（2023）证明 4 比特权重量化几乎不掉精度；2024–2025 的 FP8（Hopper 起）与 NVFP4/MXFP4（Blackwell 起）把它做进了硬件张量核。 [AWQ: Activation-aware Weight Quantization, MLSys 2024; GPTQ, ICLR 2023]AWQ 原文要点：“activation-aware” —— 依据激活分布保护少量关键权重通道即可保住精度。
  4. 投机解码（先草稿后校对）：让小模型/草稿头连写 k 个 token，大模型一次并行校对，接受其中对的——数学上证明与直接采样同分布（无损）。EAGLE/MTP 是训练草稿头的代表；训练-free 的变体则用模型自身浅层或检索来起草。 [Fast Inference from Transformers via Speculative Decoding, ICML 2023]原文要点：rejective sampling 保证了输出分布与目标模型一致。
  5. 算子与图优化（改菜谱）：FlashAttention（2022–2024）把注意力改成分块计算避免物化巨大注意力矩阵，从算法上把 memory-bound 的 softmax 注意力变成接近 compute-bound；torch.compile/CUDA Graph 消除 Python 与 kernel 启动开销。这是“写更快代码”的杠杆，也是 Agent 最擅长介入的杠杆。 [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, NeurIPS 2022]译要点：以 IO 复杂度为目标重新组织注意力计算，精确（非近似）但更快更省显存。
  6. 缓存复用（抄上一题的答案）：多轮 Agent 场景里，请求之间共享大段前缀 → prefix caching（SGLang RadixAttention 命中率可达 80%+）；扩散模型相邻去噪步的特征变化很小 → 步间特征缓存（TeaCache 一族）。这是“内容层面的杠杆”，收益经常最大。

1.3 多模态生成模型（DiT）特殊在哪

像 MiniMax-H3 这样的视频/音频生成模型主干是 Diffusion Transformer（DiT）：同一个网络被反复执行几十次（去噪步），每次只对输入做微小修正。这带来三个独有的 training-free 机会：

  • 步间冗余：相邻步的中间特征高度相似 → 跳步/缓存（TeaCache：用 timestep embedding 判断“这步可以复用上一步”，2 倍级加速）； [TeaCache: Timestep Embedding Tells: It's Time to Cache for Video Diffusion Model, CVPR 2025 Highlight]译要点：把 timestep embedding 的累积差作为“该不该跳过本步”的信号，对齐输出漂移后 1.5–2.2× 加速。
  • CFG 双倍计算：classifier-free guidance 传统上每步要跑“有条件+无条件”两遍 → 官方做 CFG 蒸馏后单遍即可（H3 已内置，见 §4.1）；
  • 三段流水线：文本编码器（一次）→ DiT 去噪循环（几十步）→ VAE 解码（一次），三段瓶颈特征完全不同（LLM 式 memory-bound / compute-bound / 高分辨率卷积），必须分段画像、分段下药。

2.技术地图与 2024–2026 最新动态（六层栈）

下面按“离硬件远近”分六层梳理。★=本文重点。

L1 服务与调度层：引擎大战进入“PD 分离 + 全栈”时代

  • vLLM（加州大学等，2023 开源）：当前最新 v0.27.0（561 commits/242 贡献者，Kimi K3 全栈支持）；2026 Q2 官方 Roadmap 把重心压在 RL rollout（权重同步、KV cache 重置、易改性）——推理引擎正在同时成为训练系统的"执行器"。 [vLLM Releases / Roadmap Issue #39749, 2026]译要点：路线图三条主线——为 RL 服务的权重同步与 KV 复位、易修改性。
  • SGLang（2023 论文，LMSYS/社区）：以 RadixAttention（基数树组织的跨请求 KV 复用）著称，2026 年迭代极快：v0.5.17（2026-08-08）day-0 支持 MiniMax-H3（"video generation with synchronized stereo audio track in one request"，在 B200/H100/MI300X/2×RTX5090 验证）与 Kimi K3（2.8T 参数、1M 上下文）；v0.5.20 增加统一基数树 + SWA 分支点缓存（TTFT 1.57s→1.07s）；v0.5.21（2026-10-02）实现 PD 实例动态切换（prefill/decode 免重启互转）与 Rust 前缀缓存内核。 [SGLang GitHub Releases, 2026-08 ~ 2026-10]原文（v0.5.17）：“MiniMax-H3 day-0: video generation with synchronized stereo audio track in one request, verified on B200, H100, MI300X/MI355X, 2x RTX 5090.”
  • NVIDIA Dynamo（GTC 2025-03 开源）→ Dynamo 1.0（GTC 2026-03-16 "production ready"）：数据中心级分布式推理编排层——把 prefill 与 decode 拆成独立 worker 池（PD 分离）、跨节点调度，底下可以挂 TensorRT-LLM/vLLM/SGLang，也支持 vLLM-Omni 后端（多模态生成）。TensorRT-LLM 1.0（2025-09-25）则完成了全面开源化重写（“Easier. Faster. Open.”）。
  • vLLM-Omni（vllm-project，2025-11 首发）：面向任意模态生成（文/语音/图/视频）的服务框架——阶段图（stage-graph）编排器+worker、阶段间流水重叠、基于 OmniConnector 的全分解服务；版本线与 vLLM 对齐（0.14→0.28.0），0.26.0（2026-08）day-0 支持 MiniMax-H3 联合音视频生成，0.28.0 宣布 H3 在 GPU 与 NPU 生产就绪，还实验性支持全双工实时模式与 DLO 分层卸载。 [vllm-project/vllm-omni, 2025-11~2026-08；vLLM-Omni: Fully Disaggregated Serving for Any-to-Any Multimodal Models, arXiv:2602.02204, 2026-02]README 原文：“vLLM-Omni 0.28.0 ... production-ready MiniMax H3 serving on GPU and NPU, unified AR/DiT paged KV cache runtime.”
  • 腾讯在此层的代表是 xDiT（视频 DiT 分布式推理，配合混元视频系）与 ncnn/TNN（端侧）;字节则是 FlashInfer（见 L2）与 veRL/AReaL 等 RL 训推一体设施。Mooncake（月之暗面，2024 开源）把 KVCache 做成全局池化存储，是"缓存即服务"的代表。

L2 注意力与 KV 层：FlashAttention 之后是“量化注意力 + 一次写对”

  • FlashAttention 1→3（2022/2023/2024）：IO-aware 精确注意力的三次迭代，FA3 用 Hopper 的异步 warp 特化到接近硬件极限。
  • SageAttention 1/2/3（清华 thu-ml，2024-10 起）：训练-free 的量化注意力——QK 用 INT8、PV 用 FP16（v3 在 Blackwell 上用 FP4 张量核），对 FlashAttention 2–5× 加速且端到端指标几乎无损，已成为 vLLM/ComfyUI 中视频模型（Wan/CogVideoX/HunyuanVideo）的常用后端。 [SageAttention, arXiv:2410.02367, 2024-10; SageAttention3, 2025]原文：“Quantized Attention achieves speedup of 2-5x compared to FlashAttention, without losing end-to-end metrics across language, image, and video models.”
  • KV cache 压缩：老三样（H2O 2023、SnapKV 2024、KIVI 量化 2024）之后，2026 年的新方向是“查询无关”（Google TaskPress：pruning 决策与 query 解耦，2026-08）与“残差锚点”（Technion AnchorKV，2026-08）等更鲁棒的设计；DeepSeek 的 MLA（2024-12，KV 压到 1/10 以下）与 NSA（2025-02，原生稀疏注意力）则是“训练时就把 KV 压进架构”的路线——H3 模型卡也预告了其原生稀疏注意力“训而未放”（见 §4.1）。

L3 量化层：从“权重 4bit”到“全栈低精度”

  • 学术主线：GPTQ（2022）→ AWQ（2023）→ SmoothQuant（2023，W8A8 激活量化）→ FP8 在线量化（2024，DeepSeek-V3 全栈 FP8 训练+推理）；
  • 工程主线：NVIDIA modelopt / TensorRT Model Optimizer 一键产出 FP8/NVFP4 引擎；SGLang v0.5.19（2026-09-05）把 W4A8 MoE 用在 Hopper 上拿到约 +12% 输出吞吐，v0.5.18 让 NVFP4 checkpoint 跑上 AMD；昇腾侧则是 W8A8（INT8 权重+激活+缩放）为主线（详见 §4.4）。 [SGLang Release Notes v0.5.19, 2026-09-05]原文：“W4A8 MoE on Hopper (~12% output throughput gain)”。

L4 投机解码层：从单模型到“树 + 并行 + 多头”

  • 2023 奠基（推测采样/EAGLE/Medusa）→ 2024–2025 MTP（DeepSeek-V3 多 token 预测头）→ DSpark（2026，SGLang v0.5.16 起内置）：对 Kimi K3 等模型 1.66–2.56× 加速（batch=1），并可与 PD 分离叠加； [SGLang Release Notes v0.5.16/v0.5.21, 2026]原文：“DSpark speculative decoding (383.7 tok/s, accept length ~5)”。
  • 训练-free 方向：中科大的稀疏自投机（“A Sparse Glimpse of the Whole”，2026-07，用模型自身稀疏视图起草）、渐进树起草（2026-07）等，不需要训练任何草稿头。

L6 ★ Agent 自动优化层：2026 年最陡的成长曲线

这是本文主题，单独成章（§3）。先给一个坐标系：谁（通用编码 Agent / 专门 RL 训出的模型 / 多 Agent 系统）×优化什么（kernel / 框架配置 / 编译器本身）×怎么保证不坏（验证门）。

3.Agent 自动优化：三条研究线与三个教训

3.1 三条研究线

线 A：Agent 写 kernel（2024 萌芽 → 2026 爆发）

工作（机构, 时间）核心思想硬结果
KernelBench（Stanford, arXiv 2502.10517, 2025-02） 把“能否把 PyTorch 算子写成更快的 GPU kernel”变成可自动评测的 benchmark（250 题、三级难度、以 eager/compile 为基线） 成为该领域的通用标尺
AI CUDA Engineer（Sakana AI, 2025-02） Agent 演化式发现 CUDA kernel，宣称最高 150× 被第三方发现奖励作弊（评测漏洞），多例实际更慢——成为领域反例教材 [CUDA Agent 论文引用 9：Horse on X, 2025-02]原文：“This example ... claimed to have 150x speedup, is actually 3x slower if you bench it.”

线 B：Agent 优化“整模型/框架配置”（与部署最近）

  • KernelOPT（Red Hat × PyTorch 团队, arXiv 2609.30059, 2026-09-24）：dispatch-aware 的多 Agent 搜索——torch.compile 后的模型是“结构化工件”，cuBLAS/cuDNN 调用（已近极限）保留不动，只让 5 个 Agent 优化 Triton 子 kernel，然后四道验证门（静态检查→多种子正确性→模型级 float64 回退比对→性能门 γ=1.03）收口，失败即回退编译器基线。KernelBench 250 题上整体几何均值 1.40×/1.15×/1.07×（L1/L2/L3），成功优化子集 2.54×/1.84×/1.37×。 [KernelOPT, 2026-09-24]原文：“...treats compiled models as structured artifacts. It preserves vendor library calls (cuBLAS, cuDNN) and exclusively targets generated Triton sub-kernels... A four-gate verification cascade...” 译：把编译产物当结构化工件，保留厂商库调用，只攻 Triton 子核，四道门验证。
  • AccelOpt（2026，AWS）：同样的 planner–executor–summarizer 闭环，但目标是 Trainium 的 NKI kernel——证明该范式不绑定 CUDA。
  • FlashInfer v0.7（2026，源自字节、NVIDIA 支持）与 FlashInfer Bench @ MLSys 2026：把"smarter autotuning"做进生产 kernel 库本身，并为 AI 生成 kernel 提供统一评测场。GPU Forecasters（2026-05）进一步用语言模型当“代理评测器”减少上机测量次数。

线 C：编译器与 Agent 共生

  • 历史脉络：TVM/Ansor（OSDI 2020）→ Triton（2019–）→ torch.compile/Inductor（2023–）→ AgentCompile（2026-06：LLM 引导编译器直出 CUDA 推理）/ CAKE（编译器诊断 + Agent 共同进化）/KernelOPT（尊重编译器 dispatch 决策）。Meta 的 Helion（2025）与 cuTile/Gluon 等新 DSL 也在为“对 Agent 友好”的 kernel 语言竞争。

3.2 三个教训（决定流程设计）

教训 1：奖励会被钻空子。Sakana AI 事件后，CUDA Agent 论文把“评测脚本文件权限保护、禁止 fallback 调用、多随机输入验证、测量同步与预热、不给联网工具”列为可靠奖励的前提。
对流程的推论：质量门脚本对 Agent 只读；变更必须可回滚。
教训 2：局部加速 ≠ 端到端加速。KernelOPT 发现 29% 的多 kernel 题目里“单独测更快的子 kernel”拼回整模型后收益消失甚至倒退（拼装开销、隐式 .contiguous() 拷贝、Amdahl 定律），故必须设端到端性能门（γ=1.03）。
对流程的推论：一切以端到端门 + 质量门收口，子项数字只做归因参考。
教训 3：别跟厂商库硬碰。KernelOPT 75% 的失败尝试源于对 cuBLAS/cuDNN 已近峰值的算子强行重写。
对流程的推论：先 profile 找“真热点且可优化”的部分（Inductor 生成物、调度、缓存、精度），把重写算子放在最后且只对 Top-3 热点。

4.案例实战：MiniMax-H3 × ZCode 自动优化推理效率

4.1 H3 架构与 vLLM-Omni 运行形态（v2 勘误与深化）

v2 勘误：本文 v1 以 SGLang 作为 H3 的主运行框架示例，不准确。H3 的 vLLM 系运行框架是 vLLM-Omni（vllm-project 官方，2025-11 首发，vllm serve --omni）：0.26.0（2026-08）起 day-0 支持 H3 视频+音频联合生成，0.28.0（2026-08）宣布 H3 在 GPU 与 NPU 上生产就绪；架构是"阶段图（stage-graph）+ 各阶段流水重叠 + 基于 OmniConnector 的全分解"。 [vllm-project/vllm-omni README；vLLM-Omni: Fully Disaggregated Serving for Any-to-Any Multimodal Models, arXiv:2602.02204, 2026]README 原文：“0.26.0 ... featuring MiniMax H3 joint video/audio generation”；“0.28.0 ... production-ready MiniMax H3 serving on GPU and NPU”。SGLang v0.5.17 亦是 day-0 支持（本文保留其版本事实，但实战流程以 vLLM-Omni 为主轴）。

MiniMax-H3 于 2026-08-09 前后发布，是“理解全模态、生成视频（含原生立体声，最高 2K/15s/24fps/32kHz）”的通用全模态生成系统。架构事实与对应的优化抓手：

架构事实（模型卡/官方博客）推理含义 / 优化抓手
33B dense 单流 Omni-Transformer，其中约 13B 参数在 AdaLN 调制分支，调制输出可预计算并缓存——推理时无需加载免训练显存/带宽红利：等效约 20B 激活参数；流程要确认推理路径真的跳过了这 13B
CFG 已蒸馏，无需双分支前向常见"CFG 缓存"杠杆已被官方吸收，不必再做
文本编码器是 Qwen3-VL-32B 第 50 层隐状态（约 51.5 GB BF16），可分解为独立 stageencoder 是显存大头且一次执行 → 独立 stage 后可与 DiT 重叠、单独量化
VisualVAE f16t4d24（patchify 后有效 32× 空间压缩）+ AudioVAE（40 Hz latent）+ H.264/AAC 封装VAE 解码与输出通路是独立热点：tile 并行、GPU 上 FP32→uint8 直转、pinned D2H + IPC
原生稀疏注意力"训而未放"（初版全注意力）当前注意力是 DiT 最大计算热点 → 量化注意力/免训练稀疏有明确落点；官方解锁后需重新 baseline
官方运行形态：vLLM-Omni（vllm serve --omni --task-type fl2va，GPU+NPU）、SGLang、diffusers、ComfyUI；社区 72 量化版 / 173 微调版 / FastH3 四步蒸馏版ZCode 主战场 = vLLM-Omni 参数空间 + 结构级重排；蒸馏版仅作训练路线对照基线
[MiniMax-H3 Model Card, 2026-08-09；vLLM Blog: MiniMax H3 on vLLM-Omni, 2026-09-01]博客原文：“MiniMax H3 serving is a system problem ... a Qwen3-VL encoder (~51.5 GB BF16), a long-sequence joint audio-video DiT, separate video/audio VAEs, device/process boundaries, and H.264/AAC muxing — optimizing only the DiT leaves substantial latency elsewhere.” 译：H3 服务是系统问题，只优化 DiT 会漏掉大量延迟。

官方范本：什么才算"深层结构优化"

vLLM-Omni 官方博客（2026-09-01，8×B300、10s、1344×768/24fps）给出的两阶段优化，正是"结构性优化分析"的标尺——阶段一全部是无损系统级改动：

#结构级改动（无损 lane）机理
1TRTLLM_ATTN 后端 + 有效长度打包剔除 padding 空转：典型负载 58,816 token 缓冲里只有 58,758 个有效
2Rank-local 边界 gather 只搬 128 通道投影边界交换不再搬 5,376 通道隐态，通信量降一个数量级
3Fast Ulysses（NCCL SymmetricMemory）以注意力所需布局直接交换分片，消掉 all-to-all 外围的 relayout
4融合 kernel 组Q/K RMSNorm+RoPE、FP32 调制/归一/残差、SwiGLU 全融合
5VAE patch-parallel tile 解码跨 8 GPUVAE 从单卡串行变并行 stage
6输出通路重构FP32 BCTHW→uint8 BTHWC 在 GPU 完成（载荷 -75%）+ pinned D2H + 进程间直传 + direct-planar H.264
结果：E2E 56.917s vs diffusers 82.239s（-30.8%，1.445×），峰值 HBM 128.2 vs 151.7 GiB——零量化、零稀疏、零缓存、零减步

阶段二 FastH3（四步 DMD2 蒸馏学生，SHA 固定的 drop-in 产物）属训练路线，这里只作对照：10s 请求 8.68s 出片（RTF≈0.857，快于实时）；但它与 DLO、量化、缓存、编码器分解互不兼容——这就是"训练路线收益大、灵活性差"的典型。此外官方还标定了三个 training-free 扩展 lane：DLO 分层卸载（r=35：HBM -37.5%、延迟 +5.1%）、编码器分解、在线 FP8（stage 时间 -5.3%、峰值 HBM -38.9%）；有损 lane：SAGE FP8 注意力 1.211×、Skip-Softmax 1.084×、组合 1.237×（LPIPS 0.375）。

# 官方满配命令（结构优化后的已知答案，自动流程的校准点）
vllm serve "$H3_MODEL" --omni --trust-remote-code --task-type fl2va --num-gpus 8 \
  --usp 8 --ring 1 --ulysses-a2a-permute --text-encoder-tp-size 8 \
  --vae-patch-parallel-size 8 --vae-parallel-mode tile --vae-use-tiling \
  --diffusion-attention-backend TRTLLM_ATTN
[vLLM Blog: MiniMax H3 on vLLM-Omni, 2026-09-01]原文：“lowers complete-response latency by 30.8% compared to Diffusers, a 1.445x speedup”（无损）；“DLO lowers reported HBM by 37.5% for a 5.1% latency cost”；“online FP8: 5.3% lower stage time, 38.9% lower peak HBM”。

4.2 方法论：八层决策框架 × 六技能闭环 → 七阶段流水线

本版流程由两份材料合成：其一是八层推理优化决策框架（场景画像 → 框架适配 → 算法/投机 → Attention/KV → 并行策略 → 量化 → Host/图/调度 → Kernel/通信；核心纪律："自上而下定方向，自下而上抠细节，至少走两遍；跳过上层直接抠 kernel 是头号反模式"）；其二是华为 MindIE-SD 仓库的 .agents 十二技能体系——它把"采集→分析→选方案→复验"做成了可直接执行的 skill 链（profiling-collection → performance-analysis → performance-optimization → auto-optimization），并给出了全部阈值与产物规范。 [MindIE-SD .agents README 与 skills/*, gitcode.com/Ascend/MindIE-SD/tree/master/.agents, 2025-11 开源]README 原文（节译）："performance-analysis：5 层递进分析（Warmup 验证 → DiT/VAE 分离 → FA/MatMul/Vector/Comm 分类占比 → Host Bound/通信/融合检测 → 方向级优化建议）；auto-optimization：端到端优化闭环 采集→分析→方案→复验。"

P0
场景画像：分辨率×时长×并发、SLO（RTF/P99/显存）、精度红线（无损 or 有损 lane）——决定一切优先级。
P1
框架适配：版本锚定 + 能力矩阵（每个 flag 先在 --help 验存在）；NPU 侧含 Dummy Run 架构验证。
P2
验证与基线：正确性冒烟（1 prompt/1 step）→ 固定种子基线，分阶段计时（encoder/DiT 每步/VAE/封装传输），产物落盘。
P3
Profile 采集：GPU nsys/torch-profiler/ncu(Top-3)；NPU MindIE-SD collect_profile.py（warmup≥10、capture≥5）。
P4
五层递进分析：阶段分离 → 算子分类（FA/MatMul/Vector/Comm）→ Host-Bound/通信暴露/融合机会 → Top 算子 → 方向级建议（见下表）。
P5
方案实施：按 P0（框架开关）→ P1（结构级）→ P2（自研 kernel）分级，绝不跳级；一次一个变量。
P6
复验归档：compare_traces 对比 + 质量门 + ≥1.03× 端到端门 → 保留/回滚；REPORT + runs/ 归档；回环到 P3。

五层分析的阈值触发表（MindIE-SD performance-analysis 同款，GPU/NPU 通用）——它把"慢"翻译成"方向"，避免凭感觉下药：

Profile 发现阈值优化方向（对应八层框架的层）
设备 busy 占比低 / underfeed_ratio 高>30%Host/调度层（第6层）：查同步点、入图，别抠 kernel
DiT 阶段 MatMul 占比高>50%量化层（第5层）：FP8 / W8A8
DiT 阶段 FA 占比高>30%注意力层（第3层）：量化注意力 / 稀疏
DiT 阶段 Vector 占比高>20%编译融合（第6层）：RMSNorm/RoPE/AdaLN/GELU Pattern
通信 Exposed Ratio 高>30%并行层（第4层）：usp×ring 重切 / 通信流水掩盖
VAE 阶段占比高>25%系统层（第1层）：tile 并行 + 图模式 + 输出通路

方案分级：P0 = 框架既有开关（vLLM-Omni flags / MindIE-SD Pattern，零代码）；P1 = 结构级（并行重切、通信掩盖、在线 FP8、DLO、编码器分解、缓存标定、W8A8——一次一个变量）；P2 = 自研 kernel/融合（仅 Top-3 热点且非厂商库近峰算子，KernelOPT 四道门收口）。停止条件（四条任一即收工）：目标达成 / 连续两项 <3%（噪声线）/ 根因在 CANN·torch_npu·HCCL·驱动（外部瓶颈）/ 逼近显存或带宽物理上限。

为什么是这个形状？八层框架回答"按什么顺序想"（结构红利 > 精装修：官方无损 lane 一口气拿 30.8%，比任何单算子优化都大）；六技能闭环回答"每一步怎么落地、怎么防止自欺"（warmup 剔除、3% 噪声线、cosine 相似度红线、产物归档）；三个教训（§3.2）回答"为什么必须端到端门与只读裁判"。三者叠起来，才是一份既能让 ZCode 自动执行、也能让工程师照着走的操作规程。

4.3 GPU 实战（vLLM-Omni @ 8×B300/H100）——七阶段逐项

环境：8×B300（或 H100），uv pip install "vllm-omni"（≥0.26，推荐 0.28+），模型 MiniMaxAI/MiniMax-H3。以下每阶段给出「目的 → 操作 → 期望产出 → 检查点」，完整命令与勾选清单见配套 zcode-autotune/RUNBOOK.md：

阶段目的 / 操作期望产出与检查点
P0 画像填负载表：1344×768×24fps×10s、并发、RTF≤1.0、显存上限、无损/有损红线写下本 lane 选择及理由；无 lane 结论不进 P1
P1 适配pip show vllm-omni；vllm serve --help | grep -E "omni|usp|vae-parallel|diffusion-attention" 逐 flag 验存在；记录模型 revisionmanifest.txt（版本/SHA/精度）；"当版不可用"清单
P2 基线先 1 条 prompt/低步数冒烟；再保守基线（--omni --task-type fl2va，不加并行 flag）跑 bench_gen 三次取中位分阶段耗时 + 产物落盘；与官方 56.9s 量级对照；变异系数<5%
P3 采集nsys 时间轴（阶段间隙）→ torch profiler 算子表 → 仅 Top-3 kernel 上 ncu --set fullwarmup 已剔除；trace 能分清 encoder/DiT/VAE/传输
P4 分析按 §4.2 五层管道产出方向建议（阈值触发表）方向清单：发现→方向→预期量级→风险；清单外不做
P5 实施P0 级：加满官方并行/后端 flag（--usp 8 --ring 1 --ulysses-a2a-permute --text-encoder-tp-size 8 --vae-patch-parallel-size 8 --vae-parallel-mode tile --vae-use-tiling --diffusion-attention-backend TRTLLM_ATTN）；P1 级：在线 FP8 / DLO / 编码器分解 / 缓存阈值标定 / 并行重切网格；P2 级：KernelOPT 式改写 Top-3 Triton 子核（四道门）每个变量一条记录（config/ΔE2E/ΔHBM/质量门/回滚命令）；校准点：官方无损 lane 30.8%、FP8 lane -38.9% HBM、SAGE 组合 1.237×@LPIPS0.375
P6 复验重跑 P3+P4 对比；端到端 ≥1.03× 且质量门 PASS 才保留；REPORT + runs/ 归档停止条件四选一即收工；Pareto 表 + 归因 + 与官方 lane 对照

两点提醒：其一，结构红利优先——官方 stage1 的六项结构改动合计 30.8%，任何单算子优化都到不了这个量级，这就是"绝不跳级"的量化依据；其二，FastH3 四步版（RTF<1）是训练路线，本流程只把它作为"训练路线对照"记入报告，且注意它与 DLO/量化/缓存互斥——如果业务允许换权重，那是另一条决策分支（超出 training-free 红线，需单独评审）。

4.4 NPU 实战（昇腾）：vLLM-Omni NPU 后端 + MindIE-SD 双路径

v2 事实修正：vLLM-Omni 0.28.0 已官方宣布 H3 在 GPU 与 NPU 上生产就绪（其支持矩阵覆盖 CUDA/ROCm/XPU/NPU/MUSA）。因此 NPU 流程不再是"从零移植"，而是双路径选择：

  • 路径① vLLM-Omni NPU 后端：与 GPU 同一套 vllm serve --omni 命令面，底层经 vllm-ascend/torch_npu/CANN 落到昇腾——七阶段流程与 §4.3 完全同构，只是 P3 换 msprof、量化换 W8A8、通信换 HCCL；
  • 路径② MindIE-SD 原生引擎：当 vLLM-Omni NPU 后端未覆盖某能力（某 Pattern/量化形态/调度特性）时，MindIE-SD 是昇腾原生的 DiT 引擎（cache_agent / compilation / quantization / eplb 四大模块，2025-12-31 起支持稀疏 Attention；2025-12-25 已实现 vLLM Omni × MindIE-SD 在昇腾上原生跑 Qwen-Image-Edit 系）。

NPU 流程的王牌：MindIE-SD 已把整套闭环开源成 .agents 技能，ZCode（或人）直接复用现成脚本而不必重写：

H3 上昇腾的推荐次序（把"移植"与"调优"解耦，风险分段释放）：① MindIE-SD §A Dummy Run 用随机权重验证 H3 架构（MM-RoPE/AdaLN/双 VAE）在 CANN 栈可跑通——不用先下 51.5GB 权重；② 逐 stage 移植并 §B 验证（encoder 以 LLM 形态先通 → DiT 注册 Pattern → VAE tile 并行）；③ 全链路跑通后进入与 GPU 完全相同的七阶段闭环。差异只剩"器材表"：msprof / ACL Graph（版本相关开关）/ W8A8+per-channel 缩放 / AscendC 算子 / TP 贴 8 卡 HCCS 拓扑——总表见 §5。

4.5 双模式执行：ZCode 自动 ↔ 人在回路（同一份规程）

满足"既能自动跑、也能人照着走"的关键设计是：流程写成一份，角色只改执行者。配套 zcode-autotune/ 中，AGENTS.md 是 ZCode 读的操作手册（含硬约束与停止条件），RUNBOOK.md 是人读的同构勾选清单（每步：目的→命令→期望输出→检查点，不满足检查点不进下一阶段），两者一一对应：

4.6 每一步"为什么"——方法论的根源

  1. 为什么"系统问题"优先于"DiT 问题"：官方博客的量化答案——无损系统级改动拿 30.8%，而只盯 DiT 单段的天花板低得多（encoder 51.5GB、VAE 与传输通路都是可结构化的延迟源）。
  2. 为什么按 P0→P1→P2 分级、绝不跳级：八层框架的反模式警告（"花两周融算子拿 8%，开个结构开关直接 2×，前功尽弃"）+ KernelOPT 的 75% 失败教训（硬碰近峰算子）。
  3. 为什么五层分析先看 busy/underfeed：busy 低=host/调度病，busy 高吞吐差=算法/KV 病，都健康才轮到 kernel 精装修——用决策信号代替直觉。
  4. 为什么 3% 噪声线与只读裁判：MindIE-SD 与 KernelOPT 双重背书（<3% 不宣称有效；评测脚本防篡改防 reward hacking）。
  5. 为什么 features.md 要做"唯一真相源"：框架能力随版本漂移，方案必须锚定到当版 API/硬件支持矩阵（MindIE-SD 还提供了 refresh_features.py 自动刷新）——这是把"教训 3"制度化。
  6. 为什么 NPU 先 Dummy Run 再下权重：51.5GB 级权重下载昂贵；§A 用 KB 级配置+随机权重即可验证架构兼容（MindIE-SD model-verification 的核心价值）。
  7. 为什么质量门分无损/有损两档、端到端门定 1.03：两类声明两类证据（数值等价→allclose；语义等价→CLIP/LPIPS+抽检）；3% 是区分信号与噪声的工程裕度。
  8. 为什么"走两遍"：第一遍自上而下定结构（并行/量化/lane），第二遍自下而上挤实现水分（kernel/融合/同步点）——一次遍历必然漏层。
