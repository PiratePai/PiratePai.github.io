1.为什么不动权重也能加速：给本科生的原理课

“Training-free（免训练）推理优化”指的是不修改模型权重、不做梯度更新，只改变模型运行时的“环境”——执行哪个算子、数据存哪、按什么顺序算、用什么精度算——来降低延迟和显存、提高吞吐。为什么这能奏效？因为训练得到的权重只决定了“算什么”，而“怎么算”存在巨大的浪费。

1.1 一分钟硬件经济课：卡在哪

把 GPU 想成一家中央厨房：算力（FLOPS）是灶台数量，显存带宽（GB/s）是传菜电梯。做一道菜（一个算子）既要用灶台（计算）也要电梯送原料（读写显存）。两个指标相除得到“这道菜每运一份原料能炒多少菜”——算术强度（arithmetic intensity）。如果一道菜只需要来回运一次料却只炒一勺（比如逐元素加法），电梯先忙不过来——这叫访存受限（memory-bound）；如果像矩阵乘法那样一次进料能炒一大桌，灶台先满载——这叫计算受限（compute-bound）。

关键事实：大模型自回归解码（一个 token 一个 token往外蹦）是极端 memory-bound 的。每生成一个 token，都要把全部权重从显存搬一遍，却只做一点点乘法。所以解码阶段的提速秘诀几乎全在“少搬东西”：权重少搬（量化）、KV 少存（KV cache 压缩）、一次搬多个 token 的活儿（投机解码）、让电梯尽量满载（batching）。而视频生成这类扩散模型的去噪阶段通常是 compute-bound 的，秘诀则是“少算几步/少算几份”（步数削减、缓存复用、注意力量化）。

1.2 六个加速杠杆（全部不碰权重）

  1. batching（拼单）：电梯一次运 1 份菜和运 16 份菜耗时几乎一样，把 16 个请求拼一起，人均成本骤降。Orca 的 continuous batching（2022）解决了“拼单中途有人下车”的问题。 [Orca: A Distributed Serving System for Transformer-Based Generative Models, OSDI 2022]译要点：提出迭代级调度（iteration-level scheduling），每一步都动态重组 batch，而不是等整批完成。
  2. KV Cache 与分页（记账）：自回归生成时把已算过的 Key/Value 存起来避免重算；vLLM 的 PagedAttention 借操作系统“分页”思想管理这块缓存，把碎片浪费压到几乎为零。 [Efficient Memory Management for LLM Serving with PagedAttention (vLLM), SOSP 2023]译要点：把 KV cache 切成固定大小的块（block）按需分配，显存利用率显著提升、吞吐翻倍级。
  3. 量化（换成小包装）：权重/激活从 16 比特压到 8/4 比特，电梯每次运的“份数”翻倍。GPTQ（2022）/AWQ（2023）证明 4 比特权重量化几乎不掉精度；2024–2025 的 FP8（Hopper 起）与 NVFP4/MXFP4（Blackwell 起）把它做进了硬件张量核。 [AWQ: Activation-aware Weight Quantization, MLSys 2024; GPTQ, ICLR 2023]AWQ 原文要点：“activation-aware” —— 依据激活分布保护少量关键权重通道即可保住精度。
  4. 投机解码（先草稿后校对）：让小模型/草稿头连写 k 个 token，大模型一次并行校对，接受其中对的——数学上证明与直接采样同分布（无损）。EAGLE/MTP 是训练草稿头的代表；训练-free 的变体则用模型自身浅层或检索来起草。 [Fast Inference from Transformers via Speculative Decoding, ICML 2023]原文要点：rejective sampling 保证了输出分布与目标模型一致。
  5. 算子与图优化（改菜谱）：FlashAttention（2022–2024）把注意力改成分块计算避免物化巨大注意力矩阵，从算法上把 memory-bound 的 softmax 注意力变成接近 compute-bound；torch.compile/CUDA Graph 消除 Python 与 kernel 启动开销。这是“写更快代码”的杠杆，也是 Agent 最擅长介入的杠杆。 [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, NeurIPS 2022]译要点：以 IO 复杂度为目标重新组织注意力计算，精确（非近似）但更快更省显存。
  6. 缓存复用（抄上一题的答案）：多轮 Agent 场景里，请求之间共享大段前缀 → prefix caching（SGLang RadixAttention 命中率可达 80%+）；扩散模型相邻去噪步的特征变化很小 → 步间特征缓存（TeaCache 一族）。这是“内容层面的杠杆”，收益经常最大。

1.3 多模态生成模型（DiT）特殊在哪

像 MiniMax-H3 这样的视频/音频生成模型主干是 Diffusion Transformer（DiT）：同一个网络被反复执行几十次（去噪步），每次只对输入做微小修正。这带来三个独有的 training-free 机会：

  • 步间冗余：相邻步的中间特征高度相似 → 跳步/缓存（TeaCache：用 timestep embedding 判断“这步可以复用上一步”，2 倍级加速）； [TeaCache: Timestep Embedding Tells: It's Time to Cache for Video Diffusion Model, CVPR 2025 Highlight]译要点：把 timestep embedding 的累积差作为“该不该跳过本步”的信号，对齐输出漂移后 1.5–2.2× 加速。
  • CFG 双倍计算：classifier-free guidance 传统上每步要跑“有条件+无条件”两遍 → 官方做 CFG 蒸馏后单遍即可（H3 已内置，见 §4.1）；
  • 三段流水线：文本编码器（一次）→ DiT 去噪循环（几十步）→ VAE 解码（一次），三段瓶颈特征完全不同（LLM 式 memory-bound / compute-bound / 高分辨率卷积），必须分段画像、分段下药。

2.技术地图与 2024–2026 最新动态（六层栈）

下面按“离硬件远近”分六层梳理。★=本文重点。

L1 服务与调度层：引擎大战进入“PD 分离 + 全栈”时代

  • vLLM（加州大学等，2023 开源）：当前最新 v0.27.0（561 commits/242 贡献者，Kimi K3 全栈支持）；2026 Q2 官方 Roadmap 把重心压在 RL rollout（权重同步、KV cache 重置、易改性）——推理引擎正在同时成为训练系统的"执行器"。 [vLLM Releases / Roadmap Issue #39749, 2026]译要点：路线图三条主线——为 RL 服务的权重同步与 KV 复位、易修改性。
  • SGLang（2023 论文，LMSYS/社区）：以 RadixAttention（基数树组织的跨请求 KV 复用）著称，2026 年迭代极快：v0.5.17（2026-08-08）day-0 支持 MiniMax-H3（"video generation with synchronized stereo audio track in one request"，在 B200/H100/MI300X/2×RTX5090 验证）与 Kimi K3（2.8T 参数、1M 上下文）；v0.5.20 增加统一基数树 + SWA 分支点缓存（TTFT 1.57s→1.07s）；v0.5.21（2026-10-02）实现 PD 实例动态切换（prefill/decode 免重启互转）与 Rust 前缀缓存内核。 [SGLang GitHub Releases, 2026-08 ~ 2026-10]原文（v0.5.17）：“MiniMax-H3 day-0: video generation with synchronized stereo audio track in one request, verified on B200, H100, MI300X/MI355X, 2x RTX 5090.”
  • NVIDIA Dynamo（GTC 2025-03 开源）→ Dynamo 1.0（GTC 2026-03-16 "production ready"）：数据中心级分布式推理编排层——把 prefill 与 decode 拆成独立 worker 池（PD 分离）、跨节点调度，底下可以挂 TensorRT-LLM/vLLM/SGLang。TensorRT-LLM 1.0（2025-09-25）则完成了全面开源化重写（“Easier. Faster. Open.”）。 [NVIDIA Newsroom/Developer Blog, 2025-03/2025-09/2026-03]译要点：Dynamo 定位为"AI 工厂"的分布式推理服务框架，1.0 标志生产就绪。
  • 腾讯在此层的代表是 xDiT（视频 DiT 分布式推理，配合混元视频系）与 ncnn/TNN（端侧）;字节则是 FlashInfer（见 L2）与 veRL/AReaL 等 RL 训推一体设施。Mooncake（月之暗面，2024 开源）把 KVCache 做成全局池化存储，是"缓存即服务"的代表。

L2 注意力与 KV 层：FlashAttention 之后是“量化注意力 + 一次写对”

  • FlashAttention 1→3（2022/2023/2024）：IO-aware 精确注意力的三次迭代，FA3 用 Hopper 的异步 warp 特化到接近硬件极限。
  • SageAttention 1/2/3（清华 thu-ml，2024-10 起）：训练-free 的量化注意力——QK 用 INT8、PV 用 FP16（v3 在 Blackwell 上用 FP4 张量核），对 FlashAttention 2–5× 加速且端到端指标几乎无损，已成为 vLLM/ComfyUI 中视频模型（Wan/CogVideoX/HunyuanVideo）的常用后端。 [SageAttention, arXiv:2410.02367, 2024-10; SageAttention3, 2025]原文：“Quantized Attention achieves speedup of 2-5x compared to FlashAttention, without losing end-to-end metrics across language, image, and video models.”
  • KV cache 压缩：老三样（H2O 2023、SnapKV 2024、KIVI 量化 2024）之后，2026 年的新方向是“查询无关”（Google TaskPress：pruning 决策与 query 解耦，2026-08）与“残差锚点”（Technion AnchorKV，2026-08）等更鲁棒的设计；DeepSeek 的 MLA（2024-12，KV 压到 1/10 以下）与 NSA（2025-02，原生稀疏注意力）则是“训练时就把 KV 压进架构”的路线——H3 模型卡也预告了其原生稀疏注意力“训而未放”（见 §4.1）。

L3 量化层：从“权重 4bit”到“全栈低精度”

  • 学术主线：GPTQ（2022）→ AWQ（2023）→ SmoothQuant（2023，W8A8 激活量化）→ FP8 在线量化（2024，DeepSeek-V3 全栈 FP8 训练+推理）；
  • 工程主线：NVIDIA modelopt / TensorRT Model Optimizer 一键产出 FP8/NVFP4 引擎；SGLang v0.5.19（2026-09-05）把 W4A8 MoE 用在 Hopper 上拿到约 +12% 输出吞吐，v0.5.18 让 NVFP4 checkpoint 跑上 AMD；昇腾侧则是 W8A8（INT8 权重+激活+缩放）为主线（详见 §4.4）。 [SGLang Release Notes v0.5.19, 2026-09-05]原文：“W4A8 MoE on Hopper (~12% output throughput gain)”。

L4 投机解码层：从单模型到“树 + 并行 + 多头”

  • 2023 奠基（推测采样/EAGLE/Medusa）→ 2024–2025 MTP（DeepSeek-V3 多 token 预测头）→ DSpark（2026，SGLang v0.5.16 起内置）：对 Kimi K3 等模型 1.66–2.56× 加速（batch=1），并可与 PD 分离叠加； [SGLang Release Notes v0.5.16/v0.5.21, 2026]原文：“DSpark speculative decoding (383.7 tok/s, accept length ~5)”。
  • 训练-free 方向：中科大的稀疏自投机（“A Sparse Glimpse of the Whole”，2026-07，用模型自身稀疏视图起草）、渐进树起草（2026-07）等，不需要训练任何草稿头。

3.Agent 自动优化：三条研究线与三个教训

3.1 三条研究线

线 A：Agent 写 kernel（2024 萌芽 → 2026 爆发）

Hawkeye（Harvard × Stanford × Together AI × Caltech, 2026-08） “硬件感知”的最小监督：每个架构只写 10 个单元测试（每行一个优化策略：MMA/异步流水线/共享内存 swizzle/…，每列一个架构），Agent 以其为上下文堆叠优化；KernelBench 作者团队出品 Ampere→Blackwell→AMD MI350 跨厂商、BF16→FP8→NVFP4/MXFP4 跨精度可用；新兴注意力上对 torch.compile 几何均值最高 18.9×，接近/超过专家 Triton（FLA 库） [Hawkeye, arXiv 2608.xxxx, 2026-08-20]译要点：前沿模型在新架构上几乎写不出对的 kernel（Blackwell 单元测试 pass@1 仅 0-3），10 个单元测试即可扭转。
CAKENVIDIA（NVIDIA × CMU, arXiv 2608.12629, 2026-08-12；作者含 FlashInfer 创建者叶致钢等） 编译器-Agent 共设计：Agent 写类型化的 Cake IR（显式 warp 角色/屏障/流水线），编译器返回“定位到具体违规”的结构化诊断而非 pass/fail；编译器本身也由 Agent 演进 agent 生成的 Kimi Delta Attention kernel 达官方 FlashKDA 2.05× 并端到端进入 SGLang 服务验证、以 PR 合入 FlashInfer（#4262/#4274/#4279/#4287）；11 项已知 kernel 复现中 10 项≥参考实现 [CAKE, 2026-08-12]原文：“A FlashKDA-compatible prefill ... reaches a 2.05× geometric-mean speedup over that baseline ... verified in end-to-end Kimi-K3 serving under SGLang.”
KernelZero / HIERA / KernelArc / CUDA-Harness / EGG / KernelPro（中科院/上交/IMEC/北航/AWS 等, 2026-06~09） 提议器-编码器共进化 / 跨实现空间规划 / 多 Agent 并行 / 专家引导等 月度级密度产出——该方向 2026 年已成显学

线 B：Agent 优化“整模型/框架配置”（与部署最近）

  • KernelOPT（Red Hat × PyTorch 团队, arXiv 2609.30059, 2026-09-24）：dispatch-aware 的多 Agent 搜索——torch.compile 后的模型是“结构化工件”，cuBLAS/cuDNN 调用（已近极限）保留不动，只让 5 个 Agent 优化 Triton 子 kernel，然后四道验证门（静态检查→多种子正确性→模型级 float64 回退比对→性能门 γ=1.03）收口，失败即回退编译器基线。KernelBench 250 题上整体几何均值 1.40×/1.15×/1.07×（L1/L2/L3），成功优化子集 2.54×/1.84×/1.37×。 [KernelOPT, 2026-09-24]原文：“...treats compiled models as structured artifacts. It preserves vendor library calls (cuBLAS, cuDNN) and exclusively targets generated Triton sub-kernels... A four-gate verification cascade...” 译：把编译产物当结构化工件，保留厂商库调用，只攻 Triton 子核，四道门验证。
  • AccelOpt（2026，AWS）：同样的 planner–executor–summarizer 闭环，但目标是 Trainium 的 NKI kernel——证明该范式不绑定 CUDA。
  • FlashInfer v0.7（2026，源自字节、NVIDIA 支持）与 FlashInfer Bench @ MLSys 2026：把"smarter autotuning"做进生产 kernel 库本身，并为 AI 生成 kernel 提供统一评测场。GPU Forecasters（2026-05）进一步用语言模型当“代理评测器”减少上机测量次数。

线 C：编译器与 Agent 共生

  • 历史脉络：TVM/Ansor（OSDI 2020）→ Triton（2019–）→ torch.compile/Inductor（2023–）→ AgentCompile（2026-06：LLM 引导编译器直出 CUDA 推理）/ CAKE（编译器诊断 + Agent 共同进化）/KernelOPT（尊重编译器 dispatch 决策）。Meta 的 Helion（2025）与 cuTile/Gluon 等新 DSL 也在为“对 Agent 友好”的 kernel 语言竞争。

3.2 三个教训（决定流程设计）

教训 1：奖励会被钻空子。Sakana AI 事件后，CUDA Agent 论文把“评测脚本文件权限保护、禁止 fallback 调用、多随机输入验证、测量同步与预热、不给联网工具”列为可靠奖励的前提。
对流程的推论：质量门脚本对 Agent 只读；变更必须可回滚。
教训 2：局部加速 ≠ 端到端加速。KernelOPT 发现 29% 的多 kernel 题目里“单独测更快的子 kernel”拼回整模型后收益消失甚至倒退（拼装开销、隐式 .contiguous() 拷贝、Amdahl 定律），故必须设端到端性能门（γ=1.03）。
对流程的推论：一切以端到端门 + 质量门收口，子项数字只做归因参考。
教训 3：别跟厂商库硬碰。KernelOPT 75% 的失败尝试源于对 cuBLAS/cuDNN 已近峰值的算子强行重写。
对流程的推论：先 profile 找“真热点且可优化”的部分（Inductor 生成物、调度、缓存、精度），把重写算子放在最后且只对 Top-3 热点。

4.案例实战：MiniMax-H3 × ZCode 自动优化推理效率

4.1 H3 架构速览（决定优化抓手）

MiniMax-H3 于 2026-08-09 前后发布，是“理解全模态、生成视频（含原生立体声，最高 2K/15s/24fps/32kHz）”的通用全模态生成系统，开源部分为核心生成模块 H3-Base（另有托管预处理 H3-Context-IR 与未开源的 H3-Regenerate-2K）。关键事实与对应的优化抓手：

架构事实（模型卡）推理含义 / 优化抓手
33B dense 单流 Omni-Transformer，其中约 13B 参数在 AdaLN 调制分支，且“调制输出可预计算并缓存”——推理时无需加载这部分权重免训练的显存/带宽红利：预计算 AdaLN 调制 → 等效约 20B 激活参数；ZCode 应检查所用推理路径是否真的跳过了这 13B
CFG 已蒸馏（提供 CFG-distilled checkpoints），无需双分支“CFG 加速”这一常见杠杆已被官方吸收；流程中不再需要 CFG 缓存类技巧
文本编码器是 Qwen3-VL-32B 第 50 层隐状态（H3-Encoder，托管），开源侧可替换/本地化分段画像时把 encoder 与 DiT 分开对待；本地部署时可对 encoder 单独做量化/batching
VisualVAE 为 f16t4d24（16× 空间/4× 时间压缩、24 通道 latent，patchify 1×2×2 后有效 32× 空间压缩），解码器用 ViT 降低解码成本；AudioVAE 40Hz latentVAE 解码是独立热点（高分辨率卷积/ViT），可单独量化/批处理；视频 latent 序列长度 = 决定 DiT 注意力成本的主变量
原生稀疏注意力“已训练但初版未启用”（初版仅全注意力，后续解锁）当前版本的注意力是最大计算热点之一 → 量化注意力（SageAttention 系）/ 免训练稀疏（SVG/LoSA 系）有明确落点；官方解锁后应重新 baseline
官方推荐推理：SGLang（day-0，sglang serve --num-gpus 4 --ulysses-degree 4 --performance-mode speed --model-variant fl2va）、vLLM、diffusers、ComfyUIZCode 的主战场=SGLang 启动参数空间 + diffusers 级别的模型改写（缓存/量化挂载点）
社区生态：72 个量化版、173 个微调版、FastH3/VDN-H3 蒸馏版（SGLang v0.5.20 起支持）可作为“训练路线基线”对照——本文流程恪守 training-free，但报告里应引用其数字作上限参考
[MiniMax-H3 Model Card, HuggingFace MiniMaxAI/MiniMax-H3, 2026-08-09；SGLang v0.5.17 Release Notes, 2026-08-08]模型卡原文（节译）：“AdaLN 调制输出可预计算并缓存，推理无需加载该分支权重（~13B）”；“原生稀疏注意力已训练，初始版本先启用全注意力”。

4.2 通用闭环协议（GPU/NPU 共用）

1
固定评测：≥10 条 prompt 固定种子 → baseline 三次取中位（延迟分阶段/显存/吞吐 + 产物落盘）。
2
画像：nsys/ncu（GPU）或 msprof（NPU）定位热点在哪一段（encoder/DiT 步循环/VAE）与哪类瓶颈（计算/带宽/启动）。
3
假设：按 §2 的层次与画像证据列候选动作（参数→缓存→量化→算子），先低风险后高风险。
4
A/B 验证：一次只动一个变量，重跑同一基准；记录 run_id。
5
端到端门：加速 ≥1.03× 且质量门 PASS（视频 PSNR≥28/SSIM≥0.90 或有损通道 CLIP≥0.92+抽检）才保留，否则回滚。
6
沉淀：Pareto 表 + 归因（时间省在哪）+ 回滚方法写入 REPORT.md；连续两项 <3% 收益即停（Amdahl）。
为什么是这个形状？教训 1→裁判只读与固定种子；教训 2→端到端门；教训 3→动作按风险排序、算子放最后；“画像先行”则来自 Roofline 直觉——不同段瓶颈类型不同，药方不同。整个闭环正是 CUDA Agent 的 SKILL.md（“profile → 写 kernel → 验证 → 达标 5% 才收”）在部署层的投影：把领域专家的工作流显式写成 Agent 可执行的协议。

4.3 GPU 流程（B200/H100×4, SGLang）——ZCode 的执行脚本

假设环境：4×B200/H100，CUDA 12.8+，已 uv pip install "sglang[all]"，模型 MiniMaxAI/MiniMax-H3（fl2va 变体）。对 ZCode 的指令就一句：“按 zcode-autotune/AGENTS.md 执行”。它的实际动作序列：

Step 0 · 版本锚定

pip show sglang vllm flashinfer | grep -E "Name|Version"   # 记入 REPORT.md
python -c "import torch; print(torch.__version__, torch.cuda.get_device_name(0))"

把每个 knob 对照当版 sglang serve --help 验证存在后再用。为什么：SGLang 半年 5 个 minor 版本，flag 集合变动大（如 v0.5.15 起 breakable CUDA graph 默认开）；盲用旧参数会静默失效。

Step 1 · Baseline（官方推荐配置）

sglang serve --model-path MiniMaxAI/MiniMax-H3 --model-variant fl2va \
  --num-gpus 4 --ulysses-degree 4 --performance-mode speed --port 30000
python bench_gen.py --mode video --endpoint http://127.0.0.1:30000/v1/video \
  --prompts bench/prompts.txt --seed 42 --run-id baseline

产出分阶段延迟：encoder / 每步 DiT（共 N 步）/ VAE+音频解码。为什么：三段瓶颈性质不同，端到端数字无法指导下一步。

Step 2 · 画像（对 baseline 进程）

nsys profile -o h3_base --trace=cuda,nvtx python bench_gen.py ...   # 时间轴：谁在等谁
ncu --set full -k "regex:.*flash.*|.*attn.*" -o h3_kernels python ...  # 单 kernel 指标
# 或框架自带：SGLANG_TORCH_PROFILER_DIR=./prof 打开 torch profiler

典型结论形态：“DiT 段占 78%，其中注意力 41%、MLP 33%、launch 开销 4%；VAE 段 12%”。为什么：教训 3——避免在 cuBLAS 级近峰算子上浪费时间，直接锁定“可优化面”。

Step 3 · 框架参数搜索（低风险高杠杆）

python knob_search.py --device gpu --model MiniMaxAI/MiniMax-H3 --ngpus 4 --dry-run
python knob_search.py --device gpu --model MiniMaxAI/MiniMax-H3 --ngpus 4

搜索空间（脚本内置，可按画像增删）：ulysses-degree（序列并行度，H3 官方 4）、performance-mode（speed/quality）、attention backend、FP8 权重量化、cuda-graph-max-bs。每配置 = 拉起→健康检查→bench→杀掉→记 JSON。为什么：这类“旋钮”组合数约 10²，Agent 用网格/贪心就能覆盖，且零代码风险——KernelOPT 的第一课（先尊重现有系统的 dispatch 决策）在这里最便宜地兑现。

Step 4 · 模型级 training-free 加速挂载（diffusers 路径）

对 Step 2 证实的 DiT 热点，在 diffusers/ComfyUI 路径上挂载三类免训练加速（这也是 TeaCache/SVG 仓库的用法）：

# (a) 步间缓存：TeaCache 式（本地仓库 D:/Github/spec/TeaCache 的 H3 移植点）
pipe.transformer.enable_teacache(rel_l1_thresh=0.08)   # 阈值=质量-速度旋钮
# (b) 量化注意力：SageAttention 后端（需验证 H3 注意力形态兼容）
pipe.transformer.set_attn_backend("sage2")
# (c) AdaLN 预计算检查：确认未加载 13B 调制分支（H3 特有红利）

为什么阈值要“标定”而不是抄论文：TeaCache 系方法的 rel-L1 阈值对模型/分辨率/步数敏感，Agent 应在 3~4 个阈值点各跑质量门，取“过门的最高加速点”——这正是“缓存革命”论文族（ACID/MORCA 等）想自动化的那一步，ZCode 在部署层用 4 次 A/B 就能手工等价。

Step 5 · 量化校准（若 Step 3 的 FP8 有收益且过门）

用 modelopt/llm-compressor 对 transformer 做权重 FP8（Hopper+ 原生）或对 encoder 单独 INT8；每个精度档跑全量质量门。为什么 encoder 单独对待：文本编码一次执行、占比小但对语义敏感，低收益高风险——按画像裁剪动作是流程的核心纪律。

Step 6 · 算子级代理优化（可选，高风险高上限）

仅当 Step 2 的 Top-3 热点 kernel 是框架生成的 Triton/逐元素融合核（而非 cuBLAS 类）时：让 ZCode 按 KernelOPT 模式工作——保留厂商库调用，只改写热点 Triton 子核，四道门收口（quality_gate.py --mode operator 承担 allclose 门，端到端 γ=1.03 由 REPORT 自动判）。生成 H3 注意力的自定义 kernel 时参考 CAKE/Hawkeye 的结论：给 Agent 提供目标架构的“优化模式单元测试/样例”比堆文档有效。为什么：教训 2+3 的制度化。

Step 7 · 服务层（上生产前）

并发≥8 时评估：PD 分离（Dynamo/SGLang PD 动态切换）、prefix cache（多轮编辑场景）、批调度。为什么：单流延迟优化与服务吞吐优化的交叉点常在 batch 维——vLLM 2026 Roadmap 与 SGLang v0.5.21 都把资源编排当主线。

Step 8 · 报告

REPORT.md：Pareto 表（延迟/吞吐/显存/质量四列）、每项归因、回滚命令、与社区训练路线（FastH3 蒸馏版）的对照。ZCode 停止条件：连续两项端到端 <3%。

4.4 NPU 流程（昇腾 910B/CANN, vLLM-Ascend + MindIE-SD）

现状事实：H3 官方推理栈（SGLang/vLLM/diffusers）目前面向 NVIDIA/AMD GPU；昇腾侧的等价生态是 vLLM-Ascend（vLLM 的硬件适配插件：NPU worker/模型运行器/注意力后端/ACL Graph 适配）+ MindIE（推理使能套件，其中 MindIE-SD 是面向 SD/DiT 系的端到端视频/图像生成套件，2025-11-30 开源，含 cache_agent（缓存加速）/ compilation（fx graph 自动改图）/ quantization / eplb 四大能力，2025-12-31 又加了稀疏注意力）。

[MindIE-SD README（本地仓库 D:/Github/MindIE-SD）, 2025-11~12]；[vLLM-Ascend docs & 昇腾社区调优指南, 2026]MindIE-SD 目录注释原文（节译）：“cache_agent 提供高阶 cache 能力；compilation 基于 fx graph 实现自动改图；quantization 提供量化能力；eplb 提供专家并行负载均衡。”
因此 NPU 流程的第一原则：目标模型没有官方 NPU 支持时，先做“协议移植”而不是硬调参。对 H3 的现实路径是分层迁移：① 先把本协议在已支持模型上跑通验证（LLM：Qwen3 系 on vLLM-Ascend；DiT/视频：Wan2.x / Qwen-Image on MindIE-SD——本地 D:/Github/Wan2.2、D:/Github/MindIE-SD 可直接对照），② 评估 H3 三段（Qwen3-VL encoder / DiT / VAE）各自在 CANN 栈上的落点与缺口，③ 缺算子的部分走 AscendC 定制（等价于 GPU 流程 Step 6）。

GPU 版脚本（对照）

# SGLang + H3
sglang serve --model-path MiniMaxAI/MiniMax-H3 \
  --model-variant fl2va --num-gpus 4 \
  --ulysses-degree 4 --performance-mode speed

# 画像
nsys profile / ncu --set full

# 缓存/量化挂载
enable_teacache(0.08); FP8 via modelopt

NPU 版脚本（昇腾）

# vLLM-Ascend + LLM（协议验证载体）
vllm serve Qwen/Qwen3-32B --tensor-parallel-size 8 \
  --quantization w8a8 \
  --quantization-param-path quant/w8a8.json

# MindIE-SD + 视频 DiT（H3 DiT 部分的迁移目标形态）
python run_wan.py --cache-enabled --cache-threshold 0.08 \
  --compilation-enabled --quant-config w8a8

# 画像
msprof --application=... --output=prof_out
# 图模式：ACL Graph（随 vllm-ascend 版本启用，先查当版文档）

NPU 流程与 GPU 的本质差异不在协议而在“器材表”（同一闭环，换工具与参数语义）：

  • 画像：nsys/ncu → msprof/Ascend Profiler（结论形态相同：算子耗时、带宽利用率）；
  • 图捕获：CUDA Graph → ACL Graph（vllm-ascend 通过环境变量/配置启用，版本间开关名有变化——ZCode 必须先读当版 README 再动）；
  • 量化：FP8/NVFP4（硬件代次决定）→ W8A8/INT8 + per-channel 缩放为主线（CANN/MindIE 校准工具链），FP8 仅最新硬件；
  • 自定义算子：Triton/CUTLASS → AscendC + CANN 算子仓（Hawkeye 已证明“每架构 10 个单元测试”式的最小专家输入可让 Agent 跨到非 NVIDIA 硬件——这套思路对昇腾同样成立）；
  • 并行拓扑：NVLink/NCCL → HCCS/HCCL，TP 度要贴 8 卡一机的物理拓扑（社区实战记录：Llama2-70B 在昇腾上 SGLang/vLLM-Ascend 调优“性能翻倍”的核心是 TP 与调度而非奇技淫巧 [CSDN 昇腾调优实战, 2026-02；hikunpeng MindIE Turbo 调优指南, 2026-06]译要点：W8A8 量化、TP 匹配拓扑、MindIE Turbo 插件、ACL Graph 为昇腾四大通用抓手。）；
  • DiT 侧对应物：TeaCache 挂载 → MindIE-SD cache_agent；torch.compile → MindIE-SD compilation（fx graph 改图）；量化 → quantization 模块。即：GPU 流程的每个模型级动作在 NPU 栈上都有命名好的入口，ZCode 的工作是把它们纳入同一 knob 搜索与质量门。

4.5 每一步“为什么”——方法论的根源

  1. 为什么先固定种子与输入集：视频生成对种子极其敏感，不固定则质量门无从谈起；这也是所有缓存加速论文的实验纪律。
  2. 为什么分阶段度量：三段流水线瓶颈性质不同（§1.3）；端到端数字无法归因，无法归因就无法决定下一个假设。
  3. 为什么参数搜索先于代码改动：风险/收益比最好；且尊重框架调度者的既有决策（KernelOPT 教训）。
  4. 为什么质量门分“无损/有损”两档：量化注意力、激进缓存本质有损，用 CLIP/人工抽检语义保真即可放行；而算子替换声称数值等价就必须 allclose——两类声明两类证据。
  5. 为什么端到端门定 1.03：直接采纳 KernelOPT 的工程取值（3% 噪声裕度），低于此无法区分真实收益与测量噪声。
  6. 为什么把“写 kernel”放最后且限量 Top-3：Amdahl + 厂商库已近峰（75% 失败教训）；而 AI 写 kernel 的真实上界已很高（CUDA Agent 2.11×、CAKE 已进生产库），值得但要门控。
  7. 为什么 NPU 上先跑“协议移植”：把不确定的“模型移植”与确定的“调优协议”解耦，风险分阶段释放。
