推理研究路线：性能建模、约束优化、协同设计与自适应系统（2009–2026）

把站内 既有专题放回一条可操作的研究主线上——先解释"请求为什么慢、状态为什么占内存"（性能建模），再在质量与服务目标下求"单位有效产出成本"最小（约束优化），然后让模型结构、执行粒度与资源放置一起被选择（协同设计），最后在条件变化时靠反馈调整而不抵消收益（自适应系统）。四阶段不是历史进化链，也不必逐级通关：每个阶段独立产出证据，可以并行进入。本文补上专题之间缺的那层"如何组织研究问题"，并把响应延迟（control-to-screen）作为一类一等公民约束讲清楚——高吞吐不等于低响应，PixVid 用 29.4 fps 换 34 ms 的实测就是证明。

0导读与大事记：一条主线、四个阶段、不要进化链

这份报告回答四个问题：推理研究的问题空间怎么组织成一条可执行的路线；四个阶段各自吃什么输入、产出什么证据、在哪里失效；响应延迟为什么不是吞吐的倒数、该怎么定义和约束；站内 既有专题与 16 章教程分别服务哪个阶段。全文主线一句话——推理系统研究 = 在质量与服务约束下最小化单位有效产出成本，手段沿"建模 → 优化 → 协同设计 → 自适应"逐层获得能力。

本文是方法入口：它说明怎么组织问题。落到具体技术取舍上，本站另维护一份研究判断登记表——每条判断带登记日期与拟回看日期，记录问题、适用负载、最强基线、固定变量、否定条件与当前证据状态，可直接跳到既有正文的证据与实验方案。方法是地图，判断是带日期的赌注，两者互不替代。

先把一个容易误读的关系说清楚。本站已有的四条线索——推理 infra（基础能力）、高性价比推理（优化目标）、定制推理引擎（实现载体）、自演进/自适应推理（反馈闭环）——是同一个体系的四个侧面，不是前后相继的历史阶段：

侧面它回答的问题对应研究阶段站内对应
推理 infra系统有哪些可控制手段（算子、缓存、调度、并行、部署）四个阶段共同的基础能力推理服务 · 并行 · 引擎
高性价比推理工程目标函数是什么（$/M tokens、goodput、单位有效产出成本）阶段二约束优化的目标高性价比推理
定制推理引擎系统手段在哪里落地（编译、算子、运行时、分离边界）阶段三协同设计的载体定制引擎 · 混合部署
自适应推理研究条件变了怎么办（观测、预测、策略、切换成本）阶段四反馈闭环自动调优 · Agent 在线系统

同样，四个研究阶段也不构成"所有项目必须逐级通关"的流程。阶段一是"慢在哪"的证据，阶段二是"在合法配置里选最省"的证据，阶段三是"把模型与系统一起改"的证据，阶段四是"条件变化时守得住"的证据。一个具体项目可以只做一个阶段（例如只做算子融合，属于阶段三的一个点），也可以从阶段四的问题倒着进入（例如先发现自适应策略抖动，再回头补阶段一的模型）。路线的价值在于让每个工作说清楚自己在哪一层、依赖哪些下层的证据、给哪些上层供货，而不是规定先后。

  • 2022-05FlashAttention（NeurIPS 2022）：把注意力的 IO 复杂度从二次降到线性（精确计算），证明"建模说清了 HBM 流量，优化才知道搬什么"——阶段一→阶段三的经典通道[FLASHATTN22]。

1预备知识：四个阶段在做什么、指标怎么读

写给第一次组织研究问题的本科生：本节只需要"账本"和"带约束的除法"两个常识。先把四个阶段各用一句人话+一个类比立住，再给一张指标词典。

1.1 四个阶段，四句人话

性能建模：在跑任何实验之前，用纸笔算出时间与显存去了哪里。输入是模型结构（层数、注意力形态、KV 每层多少字节）、硬件参数（算力峰值、HBM 带宽与容量、互连带宽）与负载描述（到达率、长度分布）；输出是一张瓶颈归因表——某一步慢，是因为算不动（compute-bound）、搬不动（memory-bound）、装不下（capacity）、传不快（communication）、排不上队（queueing）还是必须等前一步（串行依赖）。

性能建模像体检报告而不是药方：它只回答"堵塞在哪根血管"，不负责疏通。Roofline 就是第一张标准体检单——横轴"每字节算多少次"（运算强度），纵轴可达性能，屋顶是算力峰值、屋檐是带宽×运算强度，一个点落在哪，瓶颈就在哪[ROOFLINE09]。

约束优化：把"越快越好/越大越好"换成"在边界内最省"。质量下限（Q ≥ Q₀）、响应上界（R_p99 ≤ R₀）、显存上界（M ≤ C）圈出可行域；目标函数是单位有效产出的成本；优化的全部内容就是在可行域里找最优点，并画出"再要快 10% 要多花多少钱"的边界。

约束优化像在预算内点菜：钱（成本）、时间（上菜时限）、忌口（质量红线）都定死了，要的是"每一块钱买到的满足感"最大——而不是把最贵的菜全上一遍。可行域外再诱人的配置（比如把 batch 拉到吞吐峰值）都是"白赚的吞吐、丢掉的承诺"。

协同设计：承认模型结构、执行粒度、资源放置是一组要一起解的变量。KV 的语义（MHA/GQA/MLA 决定每 token 状态多少字节）改变缓存与通信的行为；生成的块大小（视频模型一次生成几帧）决定响应延迟的硬下限；分离边界（prefill/decode/解码器各占多少卡）改变成本曲线。任何一层单独"最优"，拼起来可能整体次优。

协同设计像装修前先一起看户型：不能先买好沙发（模型结构）再发现门进不去（运行时放不下），也不能只改水电（运行时）却不管房间用途（模型语义）。PixVid 干的就是"把墙拆了"——改掉 VAE 的时间压缩，让每帧独立成块，系统的响应延迟才有 34 ms 的可能[PIXVID26]。

自适应系统：负载、硬件状态、模型质量都会漂移，静态最优解会过期。自适应系统 = 观测（测什么）→ 预测（用什么模型外推）→ 策略（切换到哪个配置）→ 执行（切换本身花多少）的闭环，外加迟滞（hysteresis，防止在阈值附近反复横跳）与回退路径。它不是无条件更优：策略切换、状态迁移、权重重载都占资源，错判时还会放大损失。

自适应系统像恒温器而不是空调遥控器：遥控器只响应你的设定（静态配置），恒温器持续测温（观测）、预测趋势（预测）、决定启停（策略）、并容忍 ±0.5°C 的死区以免压缩机频繁启停（迟滞与切换成本）。TurboServe 的会话迁移就带这个特征：只有"预期延迟下降大于迁移成本"才动[TURBOSERVE26]。

2阶段一 性能建模：请求为什么慢、状态为什么占内存

输入条件：模型结构（层数 L、隐维 d、KV 每层字节数）、硬件（峰值算力、HBM 带宽/容量、互连）、负载（到达过程、长度分布、并发上界）。核心问题：延迟的时间去了哪、显存被什么占满。输出证据：瓶颈归因——任意一步被标成计算/访存/容量/通信/排队/串行依赖之一（或其组合），且数字对得上。

2.2 三种建模路径：解析、排队、离散事件仿真

解析模型（closed-form）：把每步延迟写成参数公式，最快但最粗。SIMPLE 能耗定律（4 参数解析模型）是 2026 年的代表，站内仿真篇已综述。排队论：把服务台-到达过程抽象成队列，直接回答"多小的并发才稳定"与"SLO 违约率"——2026 年出现两篇直接面向 SLO 的模型：把 KV 容量约束纳入稳定性分析[QUEUEKV26]，以及用于 SLO 驱动自动扩缩的近似排队模型[IBMQ26]。离散事件仿真：逐请求逐 token 推进事件时钟，Vidur 证明它能准确到"先仿真搜配置再上机"（论文评测的推理时延误差低于 9%，站内仿真篇专述）[VIDUR24]；2026 年的 GAUSS 把解析与蒙特卡洛混合，按 SLO 口径输出舰队容量与账单[GAUSS26]，Frontier 与 SLIM 分别扩展到分离部署与饱和区建模[FRONTIER26][SLIM26]，KernelSight-LM 则下沉到 kernel 级[KERNELSIGHT26]。

2.3 小算例：同一模型，三个"每块耗时"

建模阶段最容易犯的错是口径混用。以 PixVid 论文里的 SolarWM（12 帧一块、16 fps、单卡 B200）为例，"生成一个块要多久"有三个截然不同的数[PIXVID26]：

口径怎么算数值含义与陷阱
稳态吞吐的倒数12 帧 ÷ 72.0 fps≈166.7 ms不是单块响应耗时：72 fps 含块间流水重叠，逐块执行并不串行地花 166.7 ms
自定义栈实测块计算论文 B.5 直接计时（优化 CuTeDSL 内核）151 ms集齐控制后 GPU 真正算一个块的时间；与吞吐倒数的差就是流水重叠

2.4 失效边界：模型什么时候骗你

性能模型的四类系统性失效，每类都有文献反例：

  • 未校准——解析模型的常数（kernel 效率、通信利用率）必须用少量实测锚定，Vidur 的校准协议就是为此设计[VIDUR24]
  • 稳态假设——真实负载有突发与长尾会话，TurboServe 的生产 trace 显示活跃会话数在 30 分钟内剧烈起伏，静态模型会系统性低估尾部[TURBOSERVE26]
  • 尾部事件——Runway 每 42 步一次的位置重置步耗时 263 ms（超预算 96 ms），稳态均值完全掩盖它，只有分布建模可见[RUNWAY26]
  • 跨层耦合——单算子最优不等于端到端最优，Ansor 已经证明搜索必须带着上下文代价模型做[ANSOR20]。

下一阶段为何需要它：约束优化的可行域边界（最大并发、最坏延迟）全部由阶段一的模型给出；没有可信的模型，"优化"只是试错。

本章小结
  1. 性能建模 = 六本账（计算/访存/容量/通信/排队/串行依赖），任何"慢"与"占内存"都要能落到具体一本。
  2. 三种路径各司其职：解析快而粗、排队管 SLO、离散事件仿真支撑配置搜索；2026 年的代表（GAUSS）把输出统一到 SLO 口径的容量与成本。
  3. 口径纪律：稳态吞吐倒数 ≠ 单块响应耗时（SolarWM 三口径 151/166.7/748 ms 的例子）；未校准、稳态假设、尾部事件、跨层耦合是模型骗你的四种方式。

3阶段二 约束优化：质量与服务目标下的单位成本

买午饭时，要在下课前拿到，也得是自己能吃的。先把来不及送到或不能吃的去掉，再在剩下的里面比价。最便宜的一家，可能早就被划掉了。

输入条件：阶段一的模型（预测不同配置的延迟/显存/吞吐）、质量评估器（能对输出打分）、成本结构（时租、能耗、摊销）。核心问题：在质量与服务目标都满足的前提下，单位有效产出的成本最小是多少。可控变量：批大小、并行度、量化档位、投机参数、分离配比、路由策略等。输出证据：可行域内的最优点、Pareto 前沿、以及对"每个约束值多少成本"的灵敏度。

3.1 把目标写成带约束的除法

约束优化阶段的第一件事是把目标函数写下来。一个适用于文本与视频的抽象形式（各符号含义随后展开）：

min_x   C_total(x) / V_valid(x)          # 单位有效产出成本（目标）
s.t.    Q_k(x) ≥ Q0,k   对每个质量维度 k  # 质量：多维向量，逐维约束
        R_p99(x) ≤ R0                    # 响应延迟：按输入事件口径（见 §4）
        StallRate(x) ≤ ε                 # 播放连续性：卡顿率（流式媒体）
        M_peak,g(x) ≤ C_g                # 每台设备 g 的峰值显存

这个形式有四个要点。第一，目标在分子分母各占一项：降成本（分子）与提升有效产出（分母）都是优化，压价不等于优化。第二，质量是约束不是权重——把质量乘进目标函数（比如除以 VBench 分数）隐含"质量线性折算成钱"的假设，通常不成立（3.3）。第三，约束彼此可能冲突：R_p99 收紧可能压缩可行 batch、推高成本；约束未激活时最优解也可能不变——这条"约束-成本"曲线本身就是阶段二的核心产出。第四，它不是性能预测：在未经校准的模型上解这个式子得到的数字只用于比较配置，不能当作部署后的延迟承诺（这是与阶段一的分工）。

V_valid（有效产出）必须写清单位与通过条件，否则整个目标函数无意义。两种典型定义：

负载V_valid 的单位通过条件（示例）常见错误
文本任务个/小时（通过的完整回答）单元测试通过 / 可解析 JSON / 评审通过；且在 R_p99 内交付把生成 token 数当 V_valid——答错的 token 不是产出

为什么质量只能当约束（Q_k ≥ Q0,k 逐维）而不能折进分母？PixVid 与 SolarWM 的对比给了直接证据——同一个系统对，两个质量指标给出相反的排序[PIXVID26]：

比较两个系统时必须先固定一件事，有三种合法口径，回答三个不同问题：

3.5 失效边界与对下一阶段的供货

约束优化的三类失效：

  • 约束口径错——用吞吐 SLO 代替响应 SLO，会把交互体验失败的系统判为优（§4 整章展开）
  • 可行域时变——负载漂移让今天的解明天违约，这正是阶段四存在的理由
  • 离散跳跃——许多变量（并行度、分离配比）不连续，解析最优解落在不可实现的点上，需要搜索或整数规划。

对阶段三供货：当可行域内所有配置都无法满足约束（或成本仍太高），说明"在现有模型结构下无解"，必须改模型本身——这就进入协同设计。

  1. 目标函数是一条带约束的除法：min C_total/V_valid，s.t. 质量（逐维）、响应 p99、卡顿率、峰值显存；质量是约束不是折扣系数。
  2. V_valid 必须写清单位与通过条件；只约束吞吐的 goodput 对交互负载是错口径。
  3. 比较前先定口径（固定资源/固定时延/固定成本），三口径结论不可互换；2026 年主线是把约束精细化到延迟预算、deadline 与尾部抖动。

4响应延迟：从吞吐到 control-to-screen

别人不停地递给你一叠画，递得很快。你告诉他现在想换成另一种画，要等你真的看到新画才算有响应。旧画送得再多，也没有让那张新画更早到。

本章是四个阶段共享的一块地基：把"响应延迟"从吞吐的阴影里拉出来，作为一等约束。所有数字来自 2026 年两篇一手论文（PixVid、Runway Characters），口径逐项核对原文。

4.1 为什么吞吐不等于响应：结构性等待

自回归视频模型按块生成：一个块必须等齐块内所有帧的控制信号（按键、视角）才能开始推理。潜空间模型用 3D VAE 把 4 帧压成 1 个 latent，SolarWM 的标准配置一个块 3 个 latent = 12 帧——新按键最多要等 11 帧的时间控制才集齐。PixVid 论文 §3.5 的原话把这件事的性质说死了：

[PIXVID26] Song, Y. et al.（Roblox/UC Merced 等）. Back to Pixels: Lifting Latent Video Diffusion into Pixel Space. arXiv:2611.17336，2026-11-12（预印本）。原文："a new control waits for the rest of its block, a delay that no throughput-side optimization can remove… SolarWM's extra throughput cannot shorten its control-to-screen latency."（中文译文：新控制必须等齐它所在块的其余控制，这一延迟任何吞吐侧优化都无法消除……SolarWM 多出来的吞吐缩短不了它的 control-to-screen 延迟。）链接：arXiv · 项目页。

论文 §4.5 的实测（单卡 B200、同样 4 步因果蒸馏、同样内核）：SolarWM 吞吐 72.0 fps、中位 control-to-screen 495 ms；PixVid 每帧计算量约为其 3 倍（16.4 vs 5.6 TFLOPs/帧）、吞吐 29.4 fps、中位 34 ms。两者都超过 Wan 基座的 16 fps 播放线——都"实时"，只有一个"跟手"。

4.2 指标对照与五条关系

把 1.2 的词典展开成"谁决定谁"的关系网：

五条必须记住的关系，每条配一手证据：

（i）平均 FPS 够，不保证尾部不卡。Runway Characters 稳态产能 24.8 fps（超过 24 fps 播放线），但每 42 步一次的位置重置步耗时 263 ms——超预算 96 ms；这些 2.4% 的异常步在均值里几乎看不见，却足以冻结画面（音频随帧一起停）[RUNWAY26]。播放连续性取决于间隔分布的尾部、缓冲深度与并发，不是平均吞吐。

（ii）播放缓冲买连续性，卖交互响应。Runway 附录 B 的模拟：生成领先播放 1 步（s=1）时，每个重置步让播放卡约 100 ms（约 10 次/分钟）；领先 2 步（排一个 166.7 ms 的 chunk）后，重置的超支被缓冲吸收，零卡顿——代价是在途 chunk 变多：连同排队音频、去噪、解码与播放缓冲，3–5 个 chunk 同时在途，这直接决定了对话回合与打断（barge-in）的延迟[RUNWAY26]。缓冲是拿交互延迟换连续性，两头都要的企业只能买更多算力。

（iii）首块快，不等于控制生效快。服务侧 TTFC（请求到第一个流式 chunk）可以很小——流水线上已经在出块；但用户新按的一个键要等包含它的块才能上屏。SlackServe 把 TTFC 当服务指标优化（降 1.61–9.65×），同时用 playout slack 管连续播放比[SLACKSERVE26]；PixVid 论文则把 control-to-screen 定义为"等待同块控制 + 生成时间"两部分之和——服务 TTFC 与 control-to-screen 是两个指标，不可互相顶替。

（iv）低延迟、高吞吐、高性价比是三个目标。PixVid 用 2.4× 的吞吐损失换 14.6× 的响应提升（用户价值判断）；Runway 用 batch=1（吞吐最差）满足每用户死线（产品约束）；TurboServe 在两者之间按最坏 chunk 延迟与 GPU 成本联合优化[TURBOSERVE26]。它们可能相互促进（更好的内核同时提升三者），也可能冲突（本节全部例子）——先声明目标空间，再谈优化。

（v）响应时间必须定义"输入事件"与"第一个反映该事件的输出"。PixVid 的定义是 control-to-screen：从按键到包含该动作的第一帧上屏，含块等待与生成[PIXVID26]。用"任意下一帧"代替会高估跟手性：SolarWM 每 4 帧才收到一个相机位姿，急转弯被摊到邻帧上，Turn 相关性只有 0.70，而逐帧接收控制的 PixVid 是 0.95——响应口径错了，质量账也会跟着错。

4.3 小算例：块等待下界及其条件依赖

块等待下界取决于控制采样、等齐协议、覆盖/取消与推测策略。PixVid 附录 B.5 的 SolarWM 对照在单卡 B200、480×864、4 步去噪下报告中位 495 ms（约 344 ms 等待 + 151 ms 块计算），属于论文模型侧口径，不包含完整公网链路。逐项拆分、one-latent 消融与适用边界统一见视频案例篇 3.6 节[PIXVID26]。本篇只用它说明：结构约束与执行加速需要分开建模。

4.4 Runway 算例：一条死线的全账

Runway Characters 给了罕见的"实时约束全账"：24 fps ⇒ 每 4 帧 chunk 166.7 ms 死线、batch=1（单用户独占）、3 步在途流水（去噪 i ‖ 解码 i−1 ‖ 播放 i−2）、99.5% 会话平均 >23.5 fps（7 周生产遥测）、回合中位 2.13 s（语音代理占 1.42 s、管线占 0.49 s）[RUNWAY26]。三条工程经验值得抄：一是找到"每次读取都重复的整块工作"——240 次注意力调用每次都重做全缓存的 RoPE/量化/移位，占每步 29%，移到写入时做一次后砍掉 91% 缓存整备（69.7→6.2 ms）；二是给每个优化留回退开关——fused 内核上线数周后在生产输入上翻车被一键回滚，之后才重新启用（6.3 再谈）；三是测量自己的测量——GPU 事件时钟漂移 58–65 ms、浏览器"音频结束"标记跟声音不对齐，两处仪器误差都靠交叉核对才揪出来。

本章小结
  1. 论文模型侧 control-to-screen = 块等待 + 块生成；公网端到端还需计入排队、传输、缓冲与显示。块等待是结构性的（等齐控制），吞吐优化消除不了；SolarWM 495 ms = 中位等待 ≈344 + 计算 151（论文 B.5）。
  2. 五条关系：均值够≠尾部不卡；缓冲买连续性卖交互；首块快≠控制生效；三目标可冲突；响应必须按"事件→首个反映事件的输出"定义。
  3. 块等待下界依赖四个前提（控制采样/等齐/覆盖取消/推测），不是普适定律；PixVid 证明块结构是模型语义、服务侧改不动，one-latent 消融（164 ms、FVD 118.6）说明改一半更糟。

5阶段三 协同设计：模型、运行时与硬件一起选

做个书架，要一起量墙的宽度、想好书怎么放、找得到什么木板。光挑最大的板子，可能放不进屋里。把三件事一起改，才有机会做出正好能用的书架。

输入条件：阶段二判定"现有结构下无解"（约束不可满足或成本过高）。核心问题：模型结构、执行粒度、资源放置作为联合变量一起选择时，解空间长什么样。输出证据：联合设计点及其在阶段二目标下的位置（比"单层最优拼接"好多少）。

5.2 案例：PixVid 的墙是怎么拆的

PixVid 展示了一次完整的跨层重新议价：模型侧放弃 3D VAE 的时间压缩，每个 token 绑定单帧 1×p×p 像素块，输出头换成时间因果卷积 detailer（解码开销逐帧恒定）；训练侧用 x-prediction + 更大噪声 shift + Self Forcing 因果蒸馏，把双向模型改造成 4 步逐帧生成的因果学生；运行时侧逐帧块意味着块等待归零、KV 每帧写入；代价侧每帧 DiT 计算量 ×3.0、吞吐 ÷2.4、81 帧长滚出相机漂移更高（旋转误差 5.44° vs 4.24°，作者明确留作 future work）[PIXVID26]。这就是协同设计的典型形状：没有一层是免费的，收益与代价都跨层结转——如果只看吞吐（阶段二的单一口径）会否决它，只看响应会高估它。

5.3 案例：Runway 的"写入时"原则

Runway Characters 的核心优化一句话可以带走：把"每次读取都重复的整块工作"移到写入时做一次。KV 缓存 5,788 槽、每步 240 次注意力调用、每次只新写 757 token——旧实现每次读都对全缓存重做 RoPE、重量化 FP8、移位窗口，占每步 29%（69.7 ms）；改成环形缓存 + 写入时一次性 RoPE/量化 + 位置重置时的增量旋转（Δ=−42 的仿射结构使"重旋转"可加性成立）后只剩 6.2 ms[RUNWAY26]。这个原则与 PagedAttention（把管理成本从"搬内容"降到"改页表"）、Mooncake（把 KV 从实例资源变成可寻址的全局对象）同源：状态被谁写、被谁读、多久读一次，决定了运行时的正确设计。

5.4 失效边界

协同设计的三类失效：

  • 搜索空间爆炸——层间变量组合是乘法关系，Ansor 一层就要分层搜索空间 + 进化算法 + 预剪枝才可解[ANSOR20]，跨层联合只能靠结构化假设（比如固定 KV 语义搜放置）
  • 跨层假设失效——为旧块结构调优的缓存策略在单帧块下前提消失；反过来 PixVid 的 detailer 依赖"DiT 已捕获全局结构"的分工假设，换小模型未必成立
  • 迁移成本——联合设计点越深，锁进特定模型/硬件组合越深（Runway 的整套栈绑定 TP-3 + 独立解码 GPU 的拓扑）。

对阶段四供货：协同设计产出的是静态最优点；负载与硬件状态漂移时守住它的任务交给自适应系统。

本章小结
  1. 协同设计把 KV 语义、块大小、解码器/流水、分离边界、算子数值五层当一组联合变量；任何单层最优拼接都可能整体次优。
  2. PixVid：拆掉 VAE 时间压缩换来 34 ms 响应，代价跨层结转（计算 ×3、吞吐 ÷2.4、长滚出漂移）；Runway：写入时原则砍掉 91% 缓存整备。
  3. 失效方式：搜索空间爆炸、跨层假设失效、深设计点强锁定；产出的静态最优交给阶段四去守住。

6阶段四 自适应系统：反馈闭环与切换成本

饭快凉了，可以把保温灯打开。每次一凉一点就开、一暖一点就关，切换本身也费力。先看温度变了多久、这一次切换能省下多少，再决定要不要动。

输入条件：静态最优解存在但环境漂移（负载、硬件状态、模型质量、价格）。核心问题：如何调整而不抵消收益。输出证据：闭环策略在漂移 trace 上的表现 + 切换成本账 + 失效时的回退路径。

6.1 闭环的五个环节

观测：测什么、多快测一次（TurboServe 用滑动窗口提取需求与波动信号；Runway 的 worker 自测 fps 并逐 10 s 上报）。预测：从外推（简单的负载趋势）到仿真（GAUSS 直接按 SLO 口径模拟扩缩后果）[GAUSS26]。策略：规则（min-max 再平衡）、优化（在线调度问题）、学习（策略训练）。执行：扩缩容、迁移、降级、重路由——每个都有真实成本。反馈：执行后的延迟/成本回流观测，闭环闭合。

6.2 三条实现路径：离线搜索、在线控制、自动生成

三条路径不是互斥的选项，而是闭环的不同环节可以各选一条：离线搜索给策略一个良好初值，在线控制负责跟踪漂移，自动生成补足长尾算子。组织一个自适应系统时的有用分工是把语义理解（这个请求/会话需要什么质量与状态）、策略决策（在该状态下选哪个配置）与运行时执行（切换、迁移、恢复）拆成三个明确接口——TurboServe 的 workload detector / 两个 controller / session manager 正是这个三分法[TURBOSERVE26]。没有必要为此引入 Agent 协作框架或额外依赖：闭环的每个环节都有更简单的确定性实现。

6.3 切换成本、迟滞与回退：闭环的三道保险

自适应不是无条件更优，2026 年的三篇一手工作恰好各给一道保险的证据：

保险一：切换成本要记账。TurboServe 的会话 GPU 间迁移（NCCL 传状态 + 所有权更新）实测 23–30 ms，占每 chunk 2–3%；论文明确"只有预期延迟下降大于迁移成本才触发"——迁移本身占资源，把这条规则去掉就会为了微小收益反复搬状态。消融也印证：去掉迁移 GPU 成本 +15%、去掉自动扩缩 +42.9%（固定时延口径）[TURBOSERVE26]。LLM 侧还要多一层考虑：视频生成是计算受限的，TurboServe 选择不用重算做状态恢复（与 LLM 服务里常见的 prefill 重算相反）——切换成本的形态取决于哪一侧受限。

保险二：状态不能廉价迁移时，弹性要换形式。交互世界模型的 KV 状态每步几乎全部重写、多 GB 常驻，哈佛的 exact-state serving 分析指出这种状态无法像 LLM 请求那样中断-迁移-恢复，弹性必须以"无状态控制面 + 有状态工作面"的形式设计[EXACTSTATE26]；TurboServe 的 suspend/resume（GPU→CPU 卸载）与 DHSched 的做法同属这一族。迟滞（hysteresis）是同原理的时间版：扩容阈值与缩容阈值留出死区，防止负载在阈值附近抖动导致集群反复加减机器。

保险三：每个优化都要有回退路径。Runway 的 fused FP8 GEMM+all-reduce 内核在基准里表现良好、上线数周后在生产输入多样性下失败，被一键回滚（配置开关切回朴素路径），修复后才重新启用[RUNWAY26]。他们把"每个优化保留 plain path 的开关"写进工程守则，并把"策略替换连续两次慢会话的 worker"实现了但关闭，直到其决策被生产日志验证——闭环里最贵的环节是策略本身出错的时候。

6.4 失效边界与质量约束

自适应系统的失效清单：观测滞后（等指标恶化才动作，错过突发）、策略震荡（无迟滞时在两个配置间横跳，TurboServe 论文的时间线快照显示扩缩容与再平衡在两个时间尺度上各自动作，正是为了避免互相打架）、降级失控（SlackServe 的按 chunk 降保真度必须带质量下限——Bi-Modal Pareto Routing 只在质量地板之上选配置，否则连续播放是保住了、画质跌穿产品红线[SLACKSERVE26]）、反馈污染（Runway 发现测量仪器自身漂移 58–65 ms，污染反馈回路）。质量约束在阶段四的角色与阶段二一致：自适应调整的是成本与时延的分配，永远不许越质量红线。

本章小结
  1. 自适应闭环 = 观测→预测→策略→执行→反馈，三条实现路径（离线搜索/在线控制/自动生成）按环节组合，不必引入 Agent 框架。
  2. 三道保险各有 2026 年一手证据：切换成本记账（TurboServe 迁移 23–30 ms 只占 2–3% 才值得做）、状态不可廉价迁移时换弹性形式（exact-state + 迟滞）、每个优化留回退开关（Runway fused 内核回滚）。
  3. 降级必须带质量地板（SlackServe），反馈回路要先验证自己的仪器（Runway 时钟漂移）；自适应调整分配，不越质量红线。

8局限、方法纪律与未来方向

8.1 本文自身的边界

  • 本文不运行任何模型或硬件实验，所有数字转引自所引论文的正文与附录，代码阅读与论文核验不等于运行验证
  • 视频/流式服务文献非常年轻——TurboServe、SlackServe、DisagFusion、Runway、PixVid、GAUSS 等截至 2026-11-18 均为预印本（PipeDiT 除外，AAAI-26 已收录），数字未经同行复现，引用时保留版本号
  • 跨系统数字（如 TurboServe 的 chunk 延迟与 Runway 的 step 延迟）口径不同不可直接比：前者是多会话共卡的最坏 chunk，后者是单用户独占的死线达成。

8.2 方法纪律清单（给开始研究的人）

  1. 先写口径再跑实验：响应延迟按"输入事件→首个反映事件的输出"定义；比较前固定资源/时延/成本三者之一。
  2. 质量逐维约束，不当线性折扣；每个质量维度单独定阈值与测量协议。
  3. 报分布不报均值：至少 p50/p99 + 异常事件率（Runway 的 reset 步是教学案例）。
  4. 切换成本入账：自适应系统的收益表必须减去迁移/重载/降级成本，并给回退路径。
  5. 测量自己的测量：时钟漂移、标记错位、遥测口径都曾误导过一线团队[RUNWAY26]。

8.3 开放问题

  • 块结构的自适应议价：PixVid 证明块大小是模型语义、服务侧改不动；能否在训练时就让块大小可变（或推测式先行生成+迟到控制校验），把 4.3 的四个前提变成运行时可选项？
  • exact-state 服务的弹性理论：状态不可廉价迁移时，容量规划与迟滞设计还缺少一套像排队论那样可算的框架[EXACTSTATE26]
  • 仿真闭环化：GAUSS 类 SLO 仿真器与在线控制器的直接对接（仿真器当预测环节）的校准、漂移与开销是本文建议进一步核查的研究方向；本文未完成足以证明空白的系统查新
  • 响应延迟的标准化基准：control-to-screen 已有单篇论文级测量，缺跨系统的公开基准与统一 trace。
本章小结
  1. 本文边界：不做实验、预印本占多数、跨口径数字不可比；引用保留版本与日期。
  2. 五条方法纪律：先口径、质量逐维、报分布、切换入账、验证仪器。
  3. 四个开放问题：可变块结构、exact-state 弹性理论、仿真-控制闭环、响应延迟基准。
