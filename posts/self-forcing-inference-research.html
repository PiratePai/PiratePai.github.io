一个贯穿全文的比喻：把 Self Forcing 流式推理想成一条视频包子铺流水线：历史蒸笼（KV 缓存）越摞越高、占的案板（显存）越来越大；每笼包子（12 帧的块）要经过同一个师傅（DiT）反复揉四遍再去一次火（4 次去噪 + 1 次 KV 提交），再交给另一个师傅（VAE）揭笼出包子；顾客的临时点单（控制输入）必须等这一笼凑齐才开始做——等凑笼的时间（最长 688 ms）和做笼子的时间是两笔账，六个维度就是这条流水线的六张不同视角的监控摄像头。

0导读与大事记：一条执行链上的六个问题

这份报告回答四个问题：Self Forcing 的官方实现在每一步到底执行什么、花掉什么（机制与成本）；六个常被分开讨论的量——存算比、宽容比、异构分离、KV 缓存、VAE 显存、响应延迟——如何放进同一条执行链、互相怎么约束（建模）；一条严肃的研究线应该怎么设计对照组才能回答"哪个优化真的有效"（研究设计）；在这个已经很挤的领域里，还剩哪几块真正属于新贡献（创新边界）。全文沿一条主线展开——把流式视频推理看成一条由"历史状态 + 块计算 + 链路传输 + 输出缓冲"组成的执行链，六个维度是这条链的六个截面，最终都汇入"单位成本的有效产出"这一个目标函数。

为什么单独写 Self Forcing？三个理由：

  1. 它是公共底座。官方实现把 Wan2.1-T2V-1.3B 改造成 chunk-wise 因果生成器并配好 KV cache 与流式解码，2025-06 以来多项"自回归视频扩散 × 推理系统"研究（UnStep、MonarchRT、Forcing-KV、PixVid 的蒸馏部分）都在它或其变体上做——把这一份代码的结构数字一次核对清楚，后面所有论文的量纲都有了锚点[SFGIT][SF26]。
  2. 它是"视频版 LLM decode"的完美教学标本：块内数千 token、块间严格因果、KV 随会话线性增长——LLM 推理的每一面都在，但每个结论都要重新检验（3.1 节会看到：单 token decode 的"访存受限"在视频块上直接翻转为"算力受限"）。
  3. 响应延迟正在变成第一公民。PixVid 用 495 ms → 34 ms 的对照说明：吞吐越过播放帧率之后，块等待才是交互体验的结构性下限[PIXVID]——但它也带来了目前流传最广的一组误读（见 3.6 节纠错框），需要一份把口径写清楚的正面文档。

本章小结
  1. Self Forcing 官方实现 = Wan2.1-T2V-1.3B 衍生的 chunk-wise 因果生成器（每块 3 latent、4 次去噪 + 1 次 KV 提交），是流式视频推理研究的公共底座与本文唯一主线案例。
  2. 六个维度不是六个独立话题，而是同一条十步执行链的六个截面：存算比管每步、宽容比管设备、KV/VAE 管两侧状态、分离管链路、响应管整链总账。
  3. 本文是研究方案而非实验报告：数字全部可由源码形状复算，实测、质量回归与控制扩展都是后续研究的待办而非结论。

两个最容易混淆的量：N（像素帧）与 b（latent）。Wan2.1 VAE 时间压缩 4×，换算关系是 T 个像素帧 → 1+(T−1)/4 个 latent：独立片段 9 帧对应 3 latent；有因果解码缓存时，后续每新增 3 latent 输出 12 帧，不是新增 4 latent，也不需要重复一个 latent。官方实现按 latent 分块（b=3），所以"每块 12 帧"的稳态说法在像素侧。

1.2 块生成：视频版的"自回归 + 扩散"合体

普通文生视频扩散模型（如 Wan2.1 原版）是双向的：81 帧一起加噪、一起去噪，第 1 帧能看见第 81 帧。这在离线没问题，但没法流式——你必须等全片算完。自回归视频扩散把它切成块：先生成第一块，再以第一块为条件生成第二块……像 LLM 逐 token 生成一样，只是"token"换成了"一块 12 帧"。块内的帧互相可见（双向），块间严格因果（后面的块只能看前面的块）——这就是 Diffusion Forcing 确立的表示[DIFORCE]。

块内怎么"生成"？仍然走扩散：给当前块的 latent 加噪声，用 DiT 预测去噪方向，迭代若干步。Self Forcing 用 DMD 蒸馏把步数压到 4 步（详见 2.1）。于是每块的完整生命周期是：

取历史 KV之前所有块的 clean KV 已在缓存
→
去噪 ×4当前块噪声 latent 迭代 4 次前向；每步"预测 x0 → 重新加噪到下一档"
→
KV 提交 ×1t=0、输入 clean latent 再前向一次，把本块 KV 定稿写入缓存
→
VAE 解码因果缓存解码，输出 12 像素帧
→

1.3 三面墙：算力、带宽、容量

任何一步计算的时间下界由两面墙的较大者给出——这就是经典的 roofline 模型[ROOFLINE]：

tLB = max( F / Peff , D / BWeff )墙 = max(算力墙, 带宽墙)

F 是这一步的浮点运算量，P_eff 是有效算力（峰值 × 实测效率）；D 是必须从 HBM 搬进计算单元的字节数，BW_eff 是有效带宽。两者的比 I = F/D 叫算术强度：强度高于"屋脊点"（P/BW）就吃算力墙，低于就吃带宽墙。第三面墙是容量：状态（KV、VAE 缓存、输出）放不进显存时，要么换更大的卡、要么切分、要么跨设备——这就是 3.5 节异构分离的动机。H100 SXM 的屋脊点 ≈ 989.5 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/B（FP16 dense 口径）；记住这个数，3.1 节马上要用。

三面墙 = 一家餐厅的三种排队：算力墙是后厨灶眼不够（厨师忙不过来）；带宽墙是传菜电梯太慢（菜做好了送不出去）；容量墙是冷库太小（食材没地方放，只能频繁往返采购）。优化之前必须先搞清排在哪一队——在视频块上，这个答案和 LLM 单 token decode 完全不同（3.1 节）。
本章小结
  1. 符号一次定死：N 是像素帧（12），b 是 latent（3），q=4,680 是每块 token，S=4+1 是前向次数——分清像素侧与 latent 侧是全文数字不混账的前提。
  2. 每块生命周期 = 读历史 KV → 4 次去噪 → 1 次 KV 提交 → VAE 解码；去噪期间当前块 KV 被带噪输入反复覆写，commit 才定稿。
  3. 时间下界 = max(算力墙, 带宽墙)，第三面是容量墙；H100 FP16 的屋脊 ≈ 295 FLOP/B——视频块的强度会远高于它（下章核算）。

2.1 机制：自生成历史为什么能桥接训练与推理

因果视频蒸馏（CausVid 一系）的老问题是曝光偏差：训练时模型看的是真实视频的干净历史（teacher forcing），推理时看的是自己生成的、带误差的历史——分布对不上，误差越滚越大[CAUSVID]。Self Forcing 的答案简单直接：训练时就让模型看自己生成的历史。做法是 rollout 式训练：维护一个 KV cache，用模型自己上一块的去噪结果作为下一块的条件，采用随机截断梯度：抽取去噪退出步保留梯度，其余去噪步骤与 clean KV 更新在 no_grad 下执行（pipeline/self_forcing_training.py）；再叠 DMD 蒸馏把每块步数压到 4 步[SF26]。副作用是训练贵（一条轨迹串行展开），好处是减少由历史条件来源不同造成的训练—推理分布偏差，但不保证消除全部分布差异，流式质量随长度衰减得更慢。

[SF26] Xun Huang, Zhengqi Li, Guande He, Mingyuan Zhou, Eli Shechtman（Adobe Research + UT Austin）. Self Forcing: Bridging the Train-Test Gap in Autoregressive Video Diffusion. NeurIPS 2025 Spotlight，arXiv:2506.08009，v1 2025-06-09。要点：next-chunk prediction 的 rollout 训练 + DMD 少步蒸馏；官方 demo 在单张 RTX 4090 上实时流式生成（16 fps、832×480）。（机制转述，非逐字原文。）

蒸馏配置（configs/self_forcing_dmd.yaml）里有两个值得记的数：denoising_step_list: [1000, 750, 500, 250]（4 步，配 warp_denoising_step: true 经 shift 变换映射到实际 timestep）与 guidance_scale: 3.0（用在训练期的分数模型上；推理的 4 步生成器无 CFG，每步只有一次条件前向——这一点算成本时很关键，别替它多算一倍）。

2.3 三个执行细节，后面三节都要用

细节一：去噪不是欧拉积分，是"预测 x0 + 重加新噪声"。causal_inference.py Step 3.1 中，非最后一步的处理是 noisy_input = scheduler.add_noise(denoised_pred, torch.randn_like(...), next_timestep)——每步用预测的干净 latent 加全新随机噪声重加噪到下一档 timestep。含义：每次重加的噪声独立，但下一步仍依赖上一步的预测结果，4 次前向并不统计独立；跨步缓存是否有效需要实际误差与质量验证。

细节二：KV 的"覆写-定稿"两阶段。4 次去噪前向也会把当前块的（带噪输入的）KV 写进槽位——同一块多次前向反复覆写同一区间；commit 前向（t=0、clean latent）最后一次覆写完成定稿；每次 attention 前向都会更新缓存索引，同块重复前向的 current_end 相同，不额外推进槽位。因此：①块内任何时刻读到的"当前块 KV"是中间量，只有块结束后才是 clean 的；②缓存注释明确写着 always store the clean cache。3.3 节讨论"换条件后缓存是否仍有效"时，这个两阶段是判定基准。

细节三：默认全量窗口，滑窗是可选分支。默认 local_attn_size=-1：注意力窗口 = 32760 token = 整段 21 latent，无任何驱逐（81 帧任务恰好不溢出）。显式设置 local_attn_size 且超容量时，才走"左移驱逐最老 + attention sink 保留前 sink_size 帧"的滑窗分支（causal_model.py 注释「Shift existing cache content left to discard oldest tokens」）。RoPE 用 causal_rope_apply(..., start_frame=current_start_frame) 保证滑窗后帧号连续。

3.1 存算比与执行成本：视频块的算术强度与瓶颈假设

"存算比"在文献里其实混着两个配比：容量/算力配比（这块卡一秒能算多少、能存多少——静态属性，3.2 节的宽容比是它的对偶）和搬运/计算配比（这一步要搬多少字节才算这些数——动态属性）。统一用两个可检验的量：

Ij = Fj / DHBM,j      tjLB = max( Fj / Peff,j , DHBM,j / BWeff,j )算术强度与时间下界

F_j 是第 j 步的 FLOPs，D_HBM,j 是它必须从 HBM 搬运的逻辑字节。先推每层前向的 FLOPs。普通 MHA（无 GQA）+ 两层 FFN，暂不含交叉注意力：

Flayer ≈ Bq·( 8d² + 4d·df ) + 4Bq·( m + q )·d每层前向 FLOPs（简化式）

逐项说明（乘加计数口径：1 MAC = 2 FLOPs）：第一项是投影与 FFN——Q/K/V/O 四个 d×d 投影（4 × 2d² = 8d²）加 FFN 升降维（2 × 2d·d_f = 4d·d_f）；第二项是注意力打分与加权求和——q 个 query 对 (m+q) 个 key 的相似度（2q(m+q)d）再加权 value（2q(m+q)d），合计 4q(m+q)d。代入 d=1,536、d_f=8,960：每 token 每层约 73.9 MFLOPs（不含注意力项）。

再补上源码里存在、简化式省略的项：①交叉注意力（文本 512 token，pad 后定长）：打分+求和总计 ≈ 4·L·q·512·d ≈ 0.442 TFLOPs/前向（L=30，合计全部层），此外每层仍有 Q/O 投影；文本 K/V 可缓存，但不能省略 Q/O；②patch 嵌入（Conv3d 16→1,536 通道）与时间/位置嵌入、输出头，合计 <1%。交叉注意力 Q/O 另需 4Lqd² ≈ 1.325 TFLOPs，加上打分与求和约 1.77 TFLOPs，在 hist=5 时约为简化式的 5.1%；尚未包含嵌入与输出头，本文表格按"简化式 + 标注"处理。

逻辑字节 ≠ 真实 HBM 流量

  • 不良布局（KV 非连续、头维切分错位）会把 θ 推到 >1

定义带宽/容量比（本文简称宽容比）：

ρ = BW / C ,  [ρ] = s⁻¹宽容比 = 带宽 ÷ 容量

ρ 的直观含义：每字节驻留状态每秒能被搬动多少次。它把"这一卡放不放得下、搬不搬得动"合并成一个数，用于回答状态放置问题。把一次访问的时间写成三因子分解：

tHBM = ( D / Mresident ) · ( Mresident / C ) · ( 1 / ρ )访问放大 × 容量占用 × 单位带宽时间

三个因子分别是：访问放大（D 字节流量摊到 M_resident 字节驻留状态上，重复读多少遍——3.1 的 5 次前向读同一份 KV 就是放大 5）、容量占用（驻留状态占掉容量的比例）、单位带宽时间（1/ρ = C/BW，把整个容量搬一遍的秒数）。乘出来就是 t = D/BW——分解的价值不在改数，而在把三个可独立优化的杠杆摆在一起：压流量（KV 压缩、复用）、压驻留以满足容量约束、换设备（ρ）。固定 D 与 BW 时，减少驻留量本身不会改变 D/BW；三个因子并非独立的延迟收益。

3.3 KV 缓存：一个 5.62 GiB 的"只增不减"账本

KV 缓存的容量公式（每层 K、V 各一份）：

MKV = 2 · B · L · nstored · hkv · dh · skvKV 显存

四个口径必须分开，否则必错：分配槽位（源码预分配 32,760 token：K/V 各 [B, 32760, 12, 128]，30 层，bf16 → B=1 时 5.6236 GiB，这是形状推算）；有效历史（第 k 块后 m = 4,680k token，对应 0.2678 GiB/latent 递增）；当前块（去噪期间被反复覆写的 4,680 token 中间量，不额外占槽）；实际读取长度（注意力窗口 = min(max_attention_size, 已写入量)）。另有 cross-KV 每层 [B, 512, 12, 128]、整段只算一次：30 层合计 0.0879 GiB——它小到常被忽略，但 3.3 末尾会看到它是换文本条件时必须失效的缓存之一；还需重新做文本编码，并判断历史状态语义是否有效。

三个常犯的乘法错误
  • 持久容量不乘去噪次数：S=4 次去噪读的是同一份 KV，不复制 4 份——乘的是"读取流量"（3.1 的访问放大），不是显存。
  • 槽位不乘块数：预分配 32,760 是上限（恰好等于 81 帧整段），7 块写满即止。
  • 不乘层数之外又乘注意力头：h_kv·d_h = 1,536 = d，12 头×128 已经是全部维度。

布局：官方"覆写追加"与语义相同的 ring/paged。官方实现的写入是：当前块 KV 直接写进槽位 [local_start:local_end]（块内多次前向覆写、commit 定稿），块指针只前进——等价于连续追加。超容量的滑窗分支用的是 shift/clone：把 [sink+evicted, ...] 克隆左移、尾部插入新 KV——语义正确，但每次驱逐拷贝几乎整个窗口（O(window) 字节）。LLM 服务里的 ring/paged 布局在语义上完全等价（同样的"最老先出 + sink 保留"），可避免整窗搬移；元数据更新、非连续 attention 寻址与 kernel 支持仍有成本。第 4 章 E2 组把这个差距列为独立对照：预测收益 = 每块省下的窗口拷贝字节 ÷ BW（若搬移接近 5.6236 GiB 的默认容量，按一次读取加一次写入约 12.08 GB，在 3.35 TB/s 峰值下理想传输下界约 3.6 ms；实际窗口及测量值需另报，长会话高频驱逐时非可忽略）。

压缩与它的隐藏成本。KV 压缩（量化/剪枝/合并）是当前最热的方向：Forcing-KV 按注意力头分工做混合压缩（静态头剪枝 + 动态头相似度驱逐）[FORCINGKV]；FlowCache 做 chunk 级缓存 + 定上界 KV 压缩[FLOWCACHE]；UCSD 的 33 方法实证在 Wan2.1 基 Self Forcing 栈上给出目前最完整的地图——最佳实用点是 FlowCache 式 soft-prune INT4（5.42–5.49× 压缩、峰值显存 19.28 → 约 11.7 GB、质量与 bf16 持平），并给出两个反直觉结论：名义压缩比 ≠ 显存下降（attention/refresh 期间保留的 bf16 缓冲占主导）、若干"高保真"方法运行时反而慢 2–3 倗[KVQ33]。计入压缩后状态 = 压缩 KV + 压缩元数据 + 解压工作区（反量化临时缓冲）——E5 组要求三者一起报。

语义有效性：换条件后缓存还"对"吗？这是比容量更根本的问题。设用户中途换 prompt：技术上需要重新编码新 prompt 并使 text cross-KV 失效；额外开销取决于文本编码器与缓存策略，本文没有测量——但这只更新了"未来的条件"。历史 self-KV 是模型在旧 prompt 下自生成轨迹的记录（Self Forcing 的训练语义恰恰如此）：画面内容由旧条件塑造，换条件后历史仍保持"物理连续"，但"prompt 说过什么"与新条件不一致。系统是否该重置/微调历史，取决于产品语义（切镜头 vs 改画风），不能假设"只刷 cross-KV 就万事大吉"——E0/E6 组把这一点列为控制语义实验的前提。

3.4 VAE 显存与输出状态：解码侧的峰值账本

DiT 之外，解码侧显存经常是被低估的峰值来源。统一写成峰值形式：

MVAE,peak = MW + maxt[ Σa∈live(t) Ma + Mworkspace(t) + Mfeature-cache(t) + Moutput(t) ] ,   Ma = B·Ca·Ta·Ha·Wa·sa解码侧峰值

各项：M_W 是 Wan2.1 VAE 解码器权重（127M 参数[WAN21]，fp32 权重约 0.51 GB，推理常驻）；feature-cache 是因果 3D 卷积的历史特征缓存（cached_decode，缓存深度 CACHE_T=2，只留最近特征——这正是"因果缓存"的意义：时间上只依赖过去，所以过去的特征可以被最近 k 帧替代而非全保留）；workspace 是反卷积中间激活；output 是已解码未发送的帧缓冲。逐项量级（832×480，标注假设）：81 帧 uint8 输出 ≈ 97 MB；fp32 中间表示 ×4 ≈ 388 MB；因果缓存每层保留最近 2 帧 feature，1/2 分辨率、128 通道 fp32 约 50 MB/帧量级——上述单项不能推出 VAE 总峰值；完整峰值须按具体解码路径测量（fp32 累积口径），相对 5.62 GiB 的 KV 不是主导项，但叠加权重与输出后足以在 24 GB 卡上改变余量。

四个工程语义：

  • 累积 vs 及时释放——离线 decode_to_pixel(use_cache=False) 一次性解 21 latent、输出全部驻留；流式路径逐块解码、块内输出发送后即可释放，峰值差一个"累积输出"项。
  • FP32 转换——VLM 习惯里 VAE 常以 fp32 跑（数值敏感），权重+激活口径都要按 4 字节算，与 DiT 的 bf16 不同。
  • 反压——输出队列有界且消费端（网络/客户端）变慢时，生成端必须暂停或丢弃：这是"慢消费端"负载（E6）要测的形态。
  • 空间 tiling 可以、时间 tiling 受限——因果时间卷积的输出依赖历史特征，时间维不能随意切块；空间 tiling 也需处理卷积感受野、重叠与接缝，是高分辨率下的省显存手段。
区分三种"显存"

allocated（张量实际申请）/ reserved（分配器缓存池，≥ allocated）/ nvidia-smi 的设备占用（≥ reserved，含上下文与碎片）。比较方案时必须同口径——E1/E3 组的报表统一用 allocated 峰值 + reserved 峰值两列。

PixVid 的对照意义：去掉 VAE 换因果 detailer head（1.3B 档 44M 参数），每层卷积只缓存最近 2 帧、逐帧常数开销解码[PIXVID]——无 VAE ≠ 无解码开销 ≠ 无状态：detailer 仍有计算（每帧一次）与历史特征缓存（有界但非零），只是把"块解码"变成"帧解码"、把峰值从块边界搬到帧边界。3.6 节会看到这个差别在延迟维度的含义。

3.5 异构分离：链路切在哪、传多少、亲和谁

单卡放不下（B>1、长会话、高分辨率）或想混用算力档位时，链路要切开。分离边界上引入传输项：

txfer = α + Mboundary / BWlink,eff跨边界传输

在 Self Forcing 832×480 的数字下，DiT→VAE 边界每块传 3 个 latent（16×1×60×104 bf16）≈ 0.6 MB：PCIe 4.0 ×16（≈25 GB/s）上数据项 ≈0.02 ms，α（启动/同步开销）反而是主导（典型 0.1–0.5 ms 量级）。latent 很小、传输几乎免费——这决定了 DiT/VAE 分离在带宽上代价极低；真正贵的是状态迁移（见下）。分离后的稳态吞吐节拍：

Rblock ≤ min( nD/tD , nV/tV , BWlink,eff / Mlatent,block )流水节拍上界

n_D/n_V 是两侧实例数，t_D/t_V 是单实例服务时间（假设实例独立、服务时间可预报——排队与抢占另算）。四种放置对照：

三条纪律：

  • 独立实例假设——R_block 公式假设各实例服务时间独立稳定，突发与抢占会打破它（E4 要测）。
  • 首块、稳态、交互关键路径是三条不同的账——分离改善稳态吞吐（重叠），但把传输与对齐放进每块路径；对"首个可见帧"它通常更慢。
  • 更低的流水间隔 ≠ 更低的单次控制响应——节拍是均值概念，响应是分位数概念（3.6）。

状态迁移：实例调度/故障切换要搬 KV（5.62 GiB 量级）+ VAE 缓存，迁移期间新旧两份并存，峰值翻倍——TurboServe 报告 GPU 间状态迁移可压到 23–30 ms（NCCL 直传）[TURBOSERVE]，但那是工程优化后的结果，不是免费能力。相关工作：DisagFusion 把 Encoder/DiT/Decoder 拆三段并做实例比例弹性[DISAGFUSION]；PipeDiT 的 DeDiVAE 把去噪组与解码组解耦[PIPDIT]；DDiT 在单系统内就地调整各阶段并行度[DDIT]——第 5 章按相关度归队。

本章小结（前四维）
  1. 存算比：I ≈ 4,700–5,100 FLOP/B ≫ 屋脊 295，简化模型预测 Self Forcing 块计算偏向算力受限——与单 token LLM decode 的访存受限结论方向相反；逻辑字节需乘布局因子才是真实流量。
  2. 宽容比 ρ=BW/C 把"放不放得下、搬不搬得动"合成一个刻度（H100/B200/4090 都 ≈42 s⁻¹），但 ρ 不决定优劣：24 GB 与 192 GB 一样"快"，容量差 8 倍——可行域问题再推给异构分离。
  3. KV：满槽 5.6236 GiB（+cross 0.0879 GiB）只随会话增长、不随去噪次数复制；布局（覆写追加 vs shift/clone vs ring/paged）与压缩（元数据+解压区）都要计入；换条件后历史 self-KV 的语义有效性是独立研究问题。
  4. VAE/输出：峰值 = 权重+存活激活+工作区+因果缓存+输出的最大值（须按实际 dtype、解码路径与队列长度测量）；无 VAE 的 PixVid 仍有 detailer 计算与帧级缓存——"无 VAE"省的是块解码语义，不是状态本身。

3.6 响应延迟：从一次控制到一帧画面

前五维都是"钱"（成本、容量、带宽、放置），这一维是"时间"。定义响应延迟：

Ru = t首个反映控制 u 的可视帧 − t输入 u控制到画面

展开成执行链的全项：R_u = 控制采样/聚合 + 块等待 + 排队 + 关键路径计算（部分去噪步）+ KV 提交* + latent 传输* + 解码* + 编码发送 + 网络 + 客户端缓冲 + 显示（带 * 的项是否在关键路径取决于控制语义与放置，下面逐一判定）。与 3.1 的 t_block 相呼应：t_block 是成本分解，R_u 是关键路径分解——KV 提交不无条件加在每个可见响应上，流水重叠也不能重复求和（例如 VAE 解码与下一块去噪重叠时，解码时间只计入一次）。

3.6.1 块等待：W_j 的推导与 344 ms 的核算

在"每帧控制按 1/f 到达、块必须等齐 N 帧控制、控制落在块内第 j 个位置（j=0..N−1，均匀分布）"的协议下，第 j 帧的控制要等块内其余帧到齐：

Wj = (N − 1 − j) / f ,  j = 0,…,N−1;   Wmax = (N−1)/f ,   E[W] = (N−1)/(2f)块等待分布

W_j 是 0 到 W_max 之间的等差序列（对称分布），所以常见中位数约定下中位等待 = E[W]。代入 N=12、f=16：W_max = 11/16 = 687.5 ms，E[W] = 11/32 = 343.75 ≈ 344 ms。PixVid 论文附录 B.5 的分解与此吻合：SolarWM 的延迟 = 等待（0–688 ms）+ 块计算 151 ms → 151–839 ms，中位 495 ms——即 495 = 151 + 344（344 是 495−151 的隐含值，与公式一致）[PIXVID]。单 latent 块（N=4）：W_max = 187.5 ms、E[W] = 93.75 ms——论文实测单 latent SolarWM 中位 164 ms ≈ 94 + 70（其块计算）量级一致。

公式的适用边界

上述推导对应"等齐块内条件"协议。连续随机到达、块头采样后保持（S&H）、允许取消/覆盖/重算等协议的等待分布各不相同（例如块头锁定语义下，块头之后到达的控制只能进下一块，等待分布右偏），须另行推导，不能混用 (N−1)/(2f)。另一个易错点：一般分位数不能相加——"中位等待 + 中位计算 ≠ 联合中位"只有在两项独立且其一为常数时才近似成立；报分位数要报联合分布的实测/模拟分位。

#纪律依据（论文原文口径）
1两种分解口径不能混用：不要用吞吐反推块计算（12/72≈167 ms）再倒算等待（495−167≈328 ms）；论文 B.5 的口径是块计算 151 ms（直接计时）+ 中位控制等待 ≈344 ms（0–688 的一半）= 495 ms。"its wait (0–688 ms) plus its block compute time (151 ms), giving 151–839 ms (median 495 ms)"。167 ms 反推值把"官方实现 16.1 fps"与"优化后 72 fps"两套数字搅在了一起。
2比较条件要整句抄：单张 B200、480×864（不是 832×480）、4 步、局部注意力窗口填满后计时、双方同为自建 CuTeDSL 优化内核栈。"We time both students on one B200 at 480×864 with 4 denoising steps, after the local attention window has filled, on our custom inference stack built with optimized CuTeDSL kernels."
3吞吐与延迟是两个维度：SolarWM 72.0 fps > PixVid 29.4 fps（PixVid 每帧 DiT FLOPs ≈3.0×：16.4 vs 5.6 TFLOPs，吞吐低 2.4×），但延迟 495 ms ≫ 34 ms。更低吞吐不等于更慢响应，也不自动等于更高成本。Tab. 3 / Tab. 10；"SolarWM's extra throughput cannot shorten its control-to-screen latency."
4单 latent SolarWM 是重训（微调+蒸馏）出来的配置，不是现有模型上的"块大小开关"；且它延迟 164 ms 仍是 PixVid 的 4.8×，质量与控制精度大幅崩塌（FVD 53.8→118.6、Turn 0.70→0.11）。"finetuning the teacher-forced AnyFlow Stage 1 checkpoint with one-latent blocks … followed by Stage 2 DMD distillation"（4K+400 迭代）。
5吞吐超过播放帧率 ≠ 无卡顿；更强硬件 ≠ 线性加速。均值 fps 只约束均值供给；抖动、排队与缓冲策略决定卡顿（E6 的负载设计专门覆盖）。"both models exceed their base Wan model's native 16 fps, so both stream in real time"（这只是均值口径的实时）。
6论文计时边界是 model-side：control-to-screen = 块内等待 + 模型生成时间，不含公网传输与真实显示设备；且数字属于 SolarWM-5B/Wan2.2 衍生模型，不能移植成 Self Forcing 1.3B（Wan2.1 VAE、832×480）的结果。"includes both the wait for controls from the same block and the model's generation time"；交互模型为 lift 自 SolarWM-5B（Wan2.2 5B backbone、Wan2.2 VAE）。

最后一条正面结论同样要保留：PixVid 论文诚实给出了权衡的另一面——单帧生成让每帧 DiT 计算量 ≈3×、吞吐降为 0.41×，81 帧长滚出的相机误差更高（Rot 5.44° vs 4.24°，作者归因于更长位姿序列上的漂移累积），FVD 则各长度都更低（51.1 vs 53.8）[PIXVID]。"延迟改善"与"吞吐/长序列精度"是同一枚硬币的两面，引用时不能只挑延迟。

首块 9 帧、稳态 12 帧，与"不要由首块推断控制协议"

官方 1.3B 配置（independent_first_frame: false、b=3）下：首块 3 latent 解码 12 帧丢前 3 帧输出 9 帧、稳态块 12 帧（demo.py 的 pixels[:, 3:] 丢帧逻辑），9+6×12=81。这个首块/稳态差异是 VAE 时间压缩的重建对齐造成的，不是控制协议的一部分——不能从"首块 9 帧"反推出任何控制等待结论；做控制扩展时，等待结构由你自己选择的控制语义（3.6.2）决定。

本章小结（后两维）
  1. 异构分离：latent 边界每块仅 ≈0.6 MB、传输近乎免费，贵的是状态迁移（双份峰值）；流水节拍 R_block ≤ min(n_D/t_D, n_V/t_V, BW/M)，但更低的流水间隔改善稳态吞吐、不自动降低单次控制响应——首块、稳态、交互关键路径是三条账。
  2. 响应延迟：R_u 是关键路径分解，不是成本分解的照抄；等齐协议下 W_max=(N−1)/f=688 ms、E[W]=344 ms，495=151+344 是论文口径的隐含分解；分位数不能相加、协议不能混用公式。
  3. PixVid 六条口径纪律（3.6.3 的对照表）是把"495→34 ms"用对的前提：151+344 不混 167+328；480×864/B200/CuTeDSL 的条件整句抄；吞吐与延迟分开；单 latent 是重训；fps 均值≠无卡顿；model-side 计时≠公网端到端，且数字属于 SolarWM-5B 衍生模型。

4研究设计：目标函数与 E0–E7 对照组

第 3 章给了模型，本章把它变成可以执行、可以证伪的研究方案。先立目标函数，再排对照组，最后定负载与固定变量。本文只设计不执行：所有组都停在"假设、变量、基线、证据、否定条件"的层面。

4.1 目标函数：单位成本的有效产出

minx  Ctotal(x) / Vvalid(x)单位有效产出的成本

决策变量 x 是全套系统旋钮：窗口长度、并发 B、块粒度、NFE、放置方案、KV 布局与压缩、缓冲深度、控制协议、调度策略。约束集合：质量（VBench/人类评测不低于基线阈值）、响应延迟分位数（如 P50 ≤ 500 ms、P95 ≤ 800 ms，按控制语义定义）、首块时间、播放连续性（卡顿率/丢帧率）、容量（allocated/reserved 峰值）与控制有效性（Turn 相关类指标不低于阈值）。

V_valid 的定义是本方案的核心创新点之一：只计满足全部约束的视频秒数——过时（被新控制作废）、被丢弃（缓冲溢出、取消重算的残块）、质量不达标的帧不算有效产出，但它们的成本全部计入分子。这直接惩罚"高吞吐但大量作废"的策略（比如激进取消重算把算力烧在没用的块上）。同时两条红线：质量不能简化为"除以 FVD 或 VBench 分数"——FVD 是集合级指标，不能逐块判定有效性；质量应作为约束（阈值）而非线性折算进目标函数。成本要报资源清单口径（同卡数比吞吐）与预算口径（同预算比有效产出）两遍（见 4.4）。

E6 响应块粒度、输入相位、控制频率、缓冲深度、取消策略对 R_u 分位数的影响基线：等齐协议 + 固定缓冲；变量：块粒度（1/3 latent）×控制到达相位 ×控制频率（1f/2f/4f）×缓冲深度（0/1/2/4 块）×取消/重算与队列策略缓冲加深而 P50 响应不恶化 → R_u 判定实现有错（缓冲必在关键路径）
E7 自适应策略把 slack 与新鲜度联合进调度有没有增量基线：最佳静态配置（E1–E6 扫出的最优定点）+ EDF；变量：slack 策略、响应约束联合策略及其消融（去新鲜度项/去取消成本项）联合策略相对最佳静态提升 <10%（V_valid 口径）→ 自适应在该负载规模不值得复杂度
E0 的门槛地位

官方仓库没有库级流式接口与控制输入（2.4 节），所以 E0 的"最小正确流式接口"是一切响应实验的工程前置；"控制条件扩展"（把动作/中途换条件接进 cross-attention 或新增控制分支）是模型侧改动，单列一组、不与其余组混跑——避免把"接口没写对"误判成"架构不行"。

5.2 三项候选贡献（经查新的增量声明）

候选 1：状态与有效产出的联合账本

主张：把 KV、VAE/detailer 缓存、输出缓冲与过时帧统一进一个"存活状态 × 有效性"模型（3.3/3.4 + V_valid 定义），给出可复算的峰值与单位有效产出成本公式。
与已有工作的重叠：SlackServe 管资源与质量旋钮但按 chunk 吞吐计产出；TurboServe 管迁移成本但状态模型以 KV 为主；KVQ33 实证了压缩但产出按"跑完整个 benchmark"计。
独立机制：过时/作废帧进入分母惩罚（V_valid），状态项含输出缓冲与 detailer 缓存（不只是 KV）。
强基线：最佳静态 + SlackServe 式 slack 调度 + TurboServe 式迁移。
必要消融：去掉过时惩罚、去掉输出缓冲项、KV-only 记账三档。
否定条件：在六种负载下 V_valid 口径与普通吞吐口径的排名一致（无差异）→ 账本复杂度不值得。

候选 2：响应与播放双约束下的分离边界判定

主张：给出"何时异构分离的吞吐收益会被响应关键路径抵消"的可检验判据（3.5 的 R_block 与 R_u 分位数之差）。
重叠：DisagFusion/PipeDiT 优化离线或批式吞吐；TurboServe 讨论迁移代价；但均未把控制响应分位数作为分离决策变量。
独立机制：首块/稳态/交互三条账的解析分解 + 分离边界扫描（E4）。
强基线：同卡、双副本、同构分离。
必要消融：去掉传输项、去掉状态迁移双份、去掉排队波动。
否定条件：所有分离配置的 P95 响应都优于同卡 → 判据无区分度（可能因为该负载响应本来就不受限）。

候选 3：播放余量与控制新鲜度分离建模的联合控制

主张：slack（播放余量）与 freshness（控制新鲜度）是两个不同的时钟——前者对齐消费速率、后者对齐输入语义；联合调度显式计入取消/迁移/重算成本（3.6.2 三种控制语义的调度化）。
重叠：SlackServe 的 Bi-Modal Pareto 路由已经用 slack 选质量旋钮；PixVid 分析了块等待；"控制新鲜度"作为独立调度信号在流式视频 serving 里未见系统化。
独立机制：新鲜度信号 + 取消/重算成本项 + 版本化"首个有效响应"判定。
强基线：EDF、最佳静态、SlackServe 复现。
必要消融：去新鲜度项、去取消成本项、去版本判定（退回时间戳判定）。
否定条件：在 E6 负载上联合策略对 P95 响应或 V_valid 无 ≥10% 增量 → 承认是工程整合而非机制创新。
