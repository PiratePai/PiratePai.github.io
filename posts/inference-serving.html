1预备知识：一次推理到底发生了什么

1.1 自回归：模型是一个字一个字往外蹦的

大语言模型（LLM）生成文本的方式叫自回归（autoregressive）：把前文（prompt + 已生成的部分）喂给模型，模型输出一个关于"下一个 token 是什么"的概率分布，从中选一个 token 拼到末尾，再重复整个过程，直到输出结束符或达到长度上限。所以"生成 1000 个字"并不是一次计算，而是1000 次前向传播。

这一个 token 一个 token 的特性，决定了推理服务的一切矛盾：单次计算又小又快（相对训练），但串行依赖无法压缩——你不知道第 100 个字，就没法算第 101 个字。

1.2 Prefill 与 Decode：性格迥异的两个阶段

工程上把一次请求拆成两个阶段：

用户输入 prompt
（如 8000 个 token）
→
Prefill（预填充）
一次性并行处理整个 prompt
算出所有位置的 KV Cache
输出第 1 个新 token
→
Decode（解码）
每步只算 1 个新 token
每步都要读全部 KV Cache
串行重复几百~几千步
→
输出结束

这两个阶段的资源画像完全相反：

PrefillDecode
每步处理的 token 数整条 prompt（几百~几万）每请求 1 个
瓶颈类型计算受限（compute-bound）：矩阵都很大，GPU 算力打满访存受限（memory-bound）：每生成 1 个 token 都要把模型权重和 KV Cache 从显存搬一遍，计算只是"顺带"

加大 batch 的效果几乎无效（本来就饱和）极其显著：更多人摊薄权重搬运成本，吞吐近线性提升
把 GPU 想象成一家只做两种菜的餐厅：Prefill 是一桌 200 人的大型宴会（厨房火力全开），Decode 是每个客人每分钟点一根薯条（厨师大部分时间在走来走去，锅只热一下）。把很多份薯条拼在同一口锅里炸（批处理）是唯一省钱的方法——这就是后面所有批处理技术的出发点。

1.3 KV Cache：空间换时间的发明

Transformer 的自注意力层在计算第 n 个 token 时，需要用到前 1..n 个 token 的 Key/Value 向量。如果每步都重算全部历史，复杂度是 O(n²) 且重复劳动。因此推理引擎会把每层的 K、V 缓存下来，这就是 KV Cache——用显存换计算。此后每生成一个 token，只需计算新 token 的 K/V 追加进去。

KV Cache 有多大？一个经验公式（GQA/MQA 之前的经典 MHA 模型）：

KV 显存 = 2 × 层数 L × KV头数 h_kv × 头维 d × 序列长 s × batch B × 精度字节数

以 Llama-2-70B（80 层、8 个 KV 头、头维 128、FP16）为例，每 token 的 KV 约 0.33 MB——一条 4K 上下文的请求约 1.3 GB，32K 约 10 GB，batch 一大，KV Cache 轻松超过模型权重本身（140 GB）。所以推理服务的显存管理，本质是 KV Cache 的管理——这是 PagedAttention、前缀缓存、P/D 分离等技术共同的主角。（DeepSeek-V2 起的 MLA 把 KV 压缩到每层一个低秩 latent 向量，KV 体积骤降一个数量级，见第 9 节。）

1.4 服务质量的三个数字

  • TTFT：首 token 延迟 = 排队 + prefill 时间。搜索、代码补全场景极其敏感（用户盯着屏幕等第一个字）。
  • TPOT/ITL：稳定生成后的字间延迟。聊天一般要求 <50 ms 才"打字机感"流畅。
  • Goodput（有效吞吐）：不是"每秒吐了多少 token"，而是"在满足 TTFT 和 TPOT 双重承诺的前提下，每秒能稳定服务多少请求"。这个指标由 DistServe 提出，把"吞吐"与"用户体验"绑在了一起[DISTSERVE24]。

本章小结（记住三句话）

  1. Decode 是访存受限的，批处理是它的命；Prefill 是计算受限的，切块与隔离是它的命。
  2. KV Cache 是推理系统里最重要的"动态数据结构"，谁管好它谁就赢。
  3. 一切调度都是在 吞吐（GPU 利用率） 与 TTFT/TPOT 承诺 之间找平衡点。

2批处理与调度：Continuous Batching

2.1 起点：静态批处理为什么糟糕

2022 年之前的推理服务（如早期 HuggingFace Transformers pipeline、FasterTransformer）使用请求级批处理（request-level / static batching）：攒够 N 条请求凑成一个 batch，一起进模型，一起结束。

图 2-1 静态批处理：短请求被长请求"绑架"，GPU 大量时间在为已完成的请求空转。

问题有三：(a) 早完成的请求空占算力陪跑；(b) 新请求必须等整个 batch 结束才能进队，TTFT 很差；(c) batch 大小固定，无法随负载伸缩。Orca 论文测得这类系统在真实变长负载下吞吐损失可达一个数量级[ORCA22]。

2.2 Orca（OSDI 2022）：把调度粒度从"请求"降到"迭代"

首尔国立大学（SNU）的 Orca 团队提出了两个此后成为所有引擎标配的概念[ORCA22]：

① 迭代级调度（iteration-level scheduling）：调度的最小单位不再是"一整条请求"，而是一次解码迭代（一层前向传播）。每次迭代结束后重新组批：完成的请求立刻退出、释放显存，等待的请求立刻插入。这就是后来广泛流传的名字——Continuous Batching（NVIDIA 称 in-flight batching）。

② 选择性批处理（selective batching）：迭代级组批后，batch 里各请求长度不同。有些算子（注意力）必须按各自长度单独算，有些算子（MLP、LayerNorm）可以拼起来算。Orca 对"能拼的拼、不能拼的循环"，避免了统一 padding 造成的浪费。

请求A:     A  A  A  A  ✔                 ← 第4步完成，立刻换 B 顶上
请求B:                            B  B  B  B
请求C:        C  C  C  C  C  C  ✔
                                  ↑ C 完成的空位马上被 B 填补

2.3 现代引擎里的调度器：以 vLLM V1 为例

Continuous Batching 落到代码里，就是引擎每一步调用的 schedule() 函数。vLLM 在 2025 年 1 月的 V1 重构中给出了一个非常清晰的注释——调度器里根本不存在"prefill 阶段"和"decode 阶段"，每个请求只有一个"已算多少 token / 还欠多少 token"的账本：

# repos/vllm/vllm/v1/core/sched/scheduler.py  (main @ 2026-08-23)

def schedule(self, throttle_prefills: bool = False) -> SchedulerOutput:
    ...
    # NOTE(woosuk) on the scheduling algorithm:
    # There's no "decoding phase" nor "prefill phase" in the scheduler.
    # Each request just has the num_computed_tokens and num_tokens_with_spec.
    # At each step, the scheduler tries to assign tokens to the requests
    # so that each request's num_computed_tokens can catch up its
    # num_tokens_with_spec. This is general enough to cover
    # chunked prefills, prefix caching, speculative decoding, ...
    token_budget = self.max_num_scheduled_tokens   # 每步最多算多少 token（token budget）

调度顺序与抢占

组批策略之外，还有"先服务谁"的问题。工程与学术上出现过三代策略：

策略思想代表
FCFS（先来先服务）公平、简单；vLLM 默认对 running 队列按到达序调度所有引擎的默认值
优先级 / 抢占式KV Cache 不够时，把运行中的请求抢占（preempt）：释放其全部 KV 块，请求回到等待队列，之后重算恢复。vLLM 支持按 priority 抢占最低优先级者vLLM（recompute 式抢占）[VLLM23]
缓存感知 / 最长前缀优先优先调度与 radix 树中缓存前缀匹配最长的请求，提高 KV 复用率SGLang lpm/dfs-weight[SGLANG24]

vLLM V1 的抢占代码就在 allocate_slots() 失败路径上——分配不到新块就踢人：

while True:
    new_blocks = self.kv_cache_manager.allocate_slots(...)
    if new_blocks is not None:
        break                      # 分配成功，可以调度

调度与计算的 CPU/GPU 重叠

调度本身是 CPU 代码（组批、查前缀树、分配块表）。batch 越大调度越重，GPU 可能"等 CPU 想清楚再开工"。SGLang v0.4（2024-12）引入零开销重叠调度器：CPU 提前一步准备好下一个 batch 的全部元数据，与当前 batch 的 GPU 计算并行[SGLANGV04]；vLLM 亦在 V1 后期加入异步调度（async scheduler）。到 2026 年，"调度不挡 GPU"已是所有引擎的默认形态。

The scheduler runs one batch ahead and prepares all the metadata required for the next batch."（译文：把 CPU 调度与 GPU 计算重叠——调度器提前跑一个 batch，把下一步所需的全部元数据先准备好。）链接：lmsys.org/blog/2024-12-04-sglang-v0-4

从单机调度到集群调度

当服务规模到几十上百个实例，调度问题升维成路由问题：这条请求发给哪个实例？核心洞察是——把请求发给已经持有它前缀 KV Cache 的实例最划算。代表工作：SGLang 的 cache-aware 负载均衡（v0.4，缓存命中率提升 3.8×[SGLANGV04]）；Llumnix（OSDI 2024）支持请求在实例间在线迁移（连 KV Cache 一起搬）以平衡负载[LLUMNIX24]；NVIDIA Dynamo（2025）的 KV 感知路由器用 radix 树追踪全集群 KV 位置[DYNAMO25]；llm-d 与 vLLM 语义路由器（2026）进一步按"语义相似度"聚合同类请求。详见第 9 节。

3显存管理：PagedAttention 与前缀缓存

Continuous Batching 解决了"算力空转"，但 2023 年的 vLLM 团队发现另一个瓶颈：KV Cache 的显存管理糟蹋了多达 60–80% 的可用显存，直接限制了 batch 大小（也就是限制了 Decode 吞吐）[VLLM23]。

3.1 问题的根源：连续分配 + 静态预留

早期系统（包括原始 Orca）为每条请求按其最大可能长度预留一段连续显存放 KV Cache。两个后果：

  • 内部碎片：预留 2048 个位置，实际只用了 200 个——剩下的显存谁也用不了。实测预留浪费通常占总显存的 40%+；
  • 外部碎片：连续大块反复申请释放，显存被切割成碎片，明明总量够却分配不出新的连续段。

3.3 前缀缓存（Prefix Caching）与 RadixAttention

分页共享解决"同时在场"的请求，那先后到达的请求呢？真实负载里前缀重复极多：系统提示词、few-shot 示例、多轮对话历史、Agent 的固定工具描述……每条新请求把同样几万 token 的前缀重算一遍是纯粹的浪费。

自动前缀缓存（Automatic Prefix Caching, APC）：请求完成后不销毁它的 KV 块，而是按前缀哈希留在池中；新请求到达时先查前缀哈希表，命中的块直接挂到自己的块表上（引用计数 +1），只有未命中的部分需要计算。淘汰用 LRU。vLLM 自 2023 年底支持，V1 起默认开启[VLLMV1]。

SGLang 把这个思想做到极致，起名 RadixAttention（2023-12）：用一个基数树（radix tree）组织所有历史 KV——从根到叶的每条路径就是一段真实出现过的前缀[SGLANG24]。基数树共享公共前缀节点，所以"多轮对话历史逐轮延长"这种场景可以精确增量复用；配合前述 LPM 缓存感知调度，缓存收益进一步放大。

4Chunked Prefill：把长 Prefill 切成块

4.1 问题：一条 32K 的 prompt 能让所有人卡顿

Continuous Batching 里，prefill 和 decode 混在同一个引擎。当一条超长 prompt 进来，它的一次 prefill 是一个巨大的计算尖刺——比如 32K token 的一次前向，在 A100 上要几百毫秒。而 decode 每步只要 10–20 ms。灾难场景：

                    ↑ 正在生成的 50 条请求集体停顿 450ms
                      用户打字机突然"卡死"半秒，TPOT SLO 破防
图 4-1 prefill 计算尖刺对解码的干扰（interference）：这也是 P/D 分离（第 5 节）要根治的同一病灶的"单机版"。

反过来，如果为了保 TPOT 而限制 batch 里 prefill 的进入，长 prompt 请求就会在队列里堆积，TTFT 崩掉——吞吐与时延的两难。此外还有一个纯算力动机：现代 GPU（如 A100/A100+）在 prefill 矩阵规模偏小时根本喂不饱，把 prefill 切小、与 decode 拼批反而能提高整体利用率（这是 Sarathi 最初的出发点：填满 GPU 的 tensor core 空洞）。

4.2 Sarathi / Sarathi-Serve（2023-08 / OSDI 2024）

印度理工 + Microsoft Research + Georgia Tech 的 Sarathi 系列给出方案[SARATHI23][SARATHISERVE24]：

① Chunked prefill：把一条长 prompt 切成近似等大的块（如每块 512/2048 token），每步只算一块。一条 32K 的请求分 16 步消化，每步的耗时就与 decode 相当。

② Piggybacking / 混合批（stall-free batching）：每一步的 batch = 一个 prefill 块 + 尽量多的 decode 请求。decode 每步都照常进行，不再有长停顿；prefill 块则把 decode 喂不饱的算力填满。Sarathi-Serve 又加入准入控制（admission control），用 token budget 平衡 TTFT 与 TPOT。

chunked prefill（每步 token budget = 2048）：
step:  [decode×2000 + prefill块1(48)]  [decode×2000 + prefill块2(48)] ...
       ↑ 每步耗时恒定 ≈ decode-only batch，打字机丝滑不卡
       ↑ prefill 用剩余预算慢慢"分期付款"付清
图 4-2 token budget 下的混合批：解码永不饥饿，prefill 分期推进。

效果：Sarathi（2023）在单模型场景靠"piggyback"提升 decode 吞吐最高 10×、端到端 1.33×；Sarathi-Serve（OSDI 2024）在多请求负载下同时守住 TTFT 与 TPOT，显著抬高满足 SLO 的吞吐上限[SARATHISERVE24]。该技术随后进入所有主流引擎（vLLM 2024 年默认开启、TensorRT-LLM、SGLang、TGI…），今天你用任何 vLLM 部署，--max-num-batched-tokens 这个参数就是 token budget 的化身。

Sarathi-Serve 论文还讨论了一个重要的后续问题：chunk 边界处的注意力——第 k 块 prefill 的注意力需要前面 k-1 块的 KV，因此必须与"块内 causal mask"配合（只允许本块 query 看全部历史）。FlashAttention 类 kernel 天然支持变长 query/变长 KV，使这一切成为可能[DAO22]。

小结：PagedAttention 管理"KV 放在哪"，前缀缓存管理"KV 能不能再用一次"，chunked prefill 管理"每次算多少"——三者叠加，构成了 colocated（混部）引擎的完整形态。但混部终究是"一锅烩"，下一节我们走出单机。

5P/D 分离：Prefill 与 Decode 各回各家

5.1 动机：混部的天花板

Chunked prefill 是"缓解"干扰，不是"消除"干扰：prefill 块仍然与 decode 抢同一块 GPU 的时间片、同一份 L2 cache、同一个 batch 名额。DistServe 论文（北大 + 阿里，OSDI 2024）把这个矛盾表述得非常清楚[DISTSERVE24]：

  • 资源画像冲突：prefill 想要大算力小显存（可配大 TP 切分计算），decode 想要大显存带宽高并发（更适合小 TP / 复制多份）。混部时二者被迫共用一套并行策略与机器配置，两头不讨好。
  • SLO 耦合：想压 TTFT 就多排 prefill，TPOT 立刻抖；想保 TPOT 就压制 prefill，TTFT 排队爆。两个指标在混部下无法同时逼近极限。

Prefill/Decode 分离（P/D Disaggregation，也称 disaggregated serving）干脆把两个阶段放到不同的 GPU/机器池：请求先到 prefill 实例算完 prompt，产生的 KV Cache 通过高速网络（RDMA/IB/RoCE）传给 decode 实例，decode 从第一个 token 开始接力，边生成边流式吐给用户。

5.3 代价与配套技术

P/D 分离不是免费的午餐，它带来三个新的系统问题，也催生了配套技术：

  1. KV 传输：一条 32K 上下文的 KV Cache 可达数 GB，必须在百 ms 级完成传输，否则 TTFT 反而恶化。手段：RDMA（零拷贝直写对端显存）、层间流水（prefill 算完一层就传一层，与计算重叠）、KV 压缩/量化（FP8 KV）。开源生态：NVIDIA NIXL 统一传输库（RDMA/UCX/TCP/NVMe-oF/S3 多后端，GTC 2025 随 Dynamo 发布）[DYNAMO25]；Mooncake Transfer Engine；AMD MORI-IO（vLLM 2026 年单机 P/D 博客使用）。
  2. 负载均衡与路由：两池配比多少？请求发给哪个 decode 实例（希望它正好空闲且缓存友好）？前缀感知路由、实例间 KV 迁移（Llumnix[LLUMNIX24]）、Dynamo 的 KV 感知调度器都为此而生。负载突变时还希望两池角色可快速互换（如阿里 AMPD，2026）[AMPD26]。
  3. 显存碎片化：decode 池要给"所有在途请求"留 KV 空间，容量规划更复杂；业界用 KV 池化（Mooncake/FlexKV/LMCache）与 decode 实例间的 KV 卸载来缓解。

有趣的是，分离并不需要两个集群才成立。2025–2026 年出现单机 P/D：一台 8 卡机内，不同 GPU 分饰 prefill/decode，KV 经 NVLink/内存通道（如 AMD MI300X 的 MORI-IO）搬运，用于中小规模部署获得稳定的 ITL 与更高 goodput[VLLMSINGLEPD]。思想一旦确立，形态随规模伸缩——这正是它成为"架构"而非"技巧"的标志。

7采样与结构化输出

前六节都在"算得快"，本节处理"生成什么"：模型每步输出的是一个覆盖整个词表（如 15 万 token）的概率分布，从这个分布里怎么挑出下一个 token，既影响文本质量，也直接是服务系统的热路径代码。

7.3 投机采样：让"一步一个词"变成"一步一串词"

Decode 每 step 只算 1 个 token 是 GPU 利用率低的根源，但串行依赖又没法绕过。2022–2023 年的两篇论文给出了一个天才的折中：用小而快的模型猜，用大模型一次验证多个[LEVIATHAN23][CHEN23]。

投机采样一轮：
draft(小模型): 快速连猜 γ=5 个 token     →  [t1 t2 t3 t4 t5]
target(大模型): 一次前向并行算 5 个位置的分布，逐个校验：
   t1 ✓  t2 ✓  t3 ✓  t4 ✗(拒绝，按修正分布重采出 t4')  t5 作废
输出 4 个 token！轮次结束，从 t4' 继续
图 7-1 投机采样：草拟-验证-修正。接受几个，这步就白赚几个 token；拒绝处的重采样保证输出分布与只用大模型完全相同（无损）。

关键性质是无损：验证阶段对"小模型猜的每个 token"按两个分布的比值做接受/拒绝采样，数学上保证最终序列分布严格等于大模型自顾自生成的分布[LEVIATHAN23]。加速比取决于接受率：猜得越准，越接近 γ 倍；猜不准则浪费 draft 与多算的验证（验证比串行算 5 步仍便宜得多，因为它们是并行的一次前向）。

7.4 结构化输出：把语法编进解码循环

让 LLM 输出严格合法的 JSON、正则匹配文本、SQL、函数调用参数——这不是 prompt 工程能保证的（模型总会在第 512 个 token 多写一个引号），而是要在解码的每一步强制合规。方法叫约束解码（constrained decoding）：把目标结构（JSON Schema / 正则 / CFG）编译成一个状态机，每生成一个 token，状态机告诉你"当前状态下哪些 token 是合法的"，把非法 token 的概率置零，再交给采样器。

约束解码一步（以 JSON 为例）：
已生成:  {"name": "A           状态机(自动机)当前状态: 字符串内部
合法下一个 token: 'lice', 'my', 'Z' ...   非法: '}', ':', ',' ...
采样前: logit["}"] = -inf,  logit[","] = -inf, ...   ← token bitmask

8图编译与执行优化

前面所有技术决定了"算什么"，本节讲"怎么算得快"：从算子（kernel）到计算图（graph）两个层面压榨硬件。理解本节只需一个事实：Decode 阶段一次前向包含几百~几千个小 GPU kernel 调用，每个只算几微秒，而"从 CPU 发射一个 kernel 到 GPU"本身就要几微秒——发射开销与计算同量级，GPU 大量时间在"等下一个指令"。

8.1 算子层：融合与 IO 感知

  • 算子融合（fusion）：把 LayerNorm+量化、MatMul+激活等相邻小算子合成一个 kernel，省去中间结果写回显存。FasterTransformer（2021）是手工融合的代表；Triton（OpenAI，2021 起普及）让融合 kernel 可以用 Python 写。
  • FlashAttention（2022，NeurIPS）：不近似、只重排计算顺序——把 attention 分块在 SRAM 里算完，避免 HBM 上的 N×N 注意力矩阵读写。它使长上下文 prefill 可行、也支持变长 KV（PagedAttention 的 kernel 底座、chunked prefill 的块内掩码都靠它）[DAO22]。后续 FlashAttention-2/3（2023/2024）持续优化 decode 与 Hopper 特性（TMA、WGMMA）。
  • DeepGEMM（DeepSeek 开源，2025-02）：面向 MoE 的 FP8 GEMM，JIT 编译按当前 m/n/k 形状即时生成 kernel——"编译"下沉到算子内部。

8.2 图捕获：CUDA Graphs

消除发射开销的直接办法：把整个前向的所有 kernel 调用录制成一张 CUDA Graph，之后每步一次重放（replay）——CPU 只发一条指令。NVIDIA 自 CUDA 10（2018-09）提供该机制，TensorRT 用了多年；难点在于录制时形状必须固定，而推理引擎的 batch 与序列长度每步都在变。

通用解法是"形状分桶 + padding"：把 batch 归一到若干档位（如 1,2,4,8,…,256），每档录一张图，执行时 padding 到档位。decode 阶段计算量小、kernel 数又多，收益最大——vLLM/SGLang 对 decode 默认开 CUDA Graph，端到端可提速约 1.2–2×（小 batch 时更明显）。

10未来发展方向

综合上述脉络，给出六个可判断的方向（带依据，非占卜）：

10.1 分离粒度继续下沉：从"按阶段"到"按算子"

E/P/D 已把"阶段"拆开，AFD（注意力-FFN 分离，2026-07）已开始拆"算子类别"。终点形态是组件化的推理云：注意力、FFN/专家、采样、结构化约束都成为可独立伸缩、独立选硬件的"微服务"，KV Cache 是它们之间流动的"通用货币"。Mooncake 的"存储换计算"哲学（FAST 2025）会从 KV 扩展到中间激活等更多状态的池化[MOONCAKE25][VLLMAFD]。

10.2 以 KV / 会话为中心的服务架构

Agent 时代的请求不再是独立的一次调用，而是长会话中的第 N 轮。KV 会话保持、跨实例会话迁移、会话亲和路由（llm-d/Dynamo 已落地）将从优化项变成架构基石；集群级 radix 索引、跨请求 KV 共享（多用户共用同一段"世界知识"前缀）是活跃的研究与工程方向。

10.3 SLO 优先的智能调度与自治系统

goodput 指标（DistServe，OSDI 2024）把"体验"纳入目标函数；下一步是让系统自动寻找配置：并行度、P/D 配比、batch 上限、投机长度都由在线规划器根据 SLO 与负载实时调整，并在负载变化时快速重配置（分离架构研究者明确把 fast reconfiguration 列为首要开放问题[DISAGGLECTURE]）。语义路由/模型混合（9.3 节）则把"调度哪个模型"也纳入决策。

10.4 训推一体的"为服务而设计"

MLA、MTP、NSA/DSA 证明了模型结构对服务成本的杠杆率最高。可以预期：训练侧会继续内置推理友好特性（更多压缩 KV 的注意力、原生投机头、可编译友好的结构），"训练时多花 1% 算力换推理时省 30%"会成为标配设计原则[DSV3][LMSYSEP]。

10.5 投机采样全面默认化与混合化

EAGLE-3/MTP 让加速 2–4× 成为"免费午餐"，n-gram 草稿在 Agent 负载上意外有效；未来的引擎会把"草稿来源"做成运行时策略（小模型/自身头/n-gram 按上下文切换），并与批处理、EP、分离架构深度耦合（vLLM 2026-07 博客《Parallel All the Way Down》讨论的正是批处理×投机解码的联合设计）[EAGLE][LINKEDIN26]。

10.6 图编译走向"全自动、全动态"

从分段 CUDA Graph 到"可断图"，编译系统正学会与动态形状共存。方向：符号形状编译（一次编译、任意 batch 复用）、按硬件自动调参（DeepGEMM 式 JIT 常态化）、以及把 P/D 传输与计算也纳入统一图调度——让"跨机分离流水线"获得今天单机 CUDA Graph 同量级的确定性开销[VLLMRFC]。

结语

回看 2022→2026：Orca 重新定义了调度粒度，vLLM 重新定义了显存管理，Sarathi 与 DistServe/Splitwise/Mooncake 把"干扰"问题从缓解走向根治，XGrammar 系把"生成可控性"做到近零开销，图编译把"执行开销"逼近物理极限，而 DeepSeek 系模型证明模型本身可以是最大的系统优化。下一步的故事大概率发生在"集群即计算机"的层面：KV 为中心的数据面、SLO 为中心的控制面、Agent 为中心的负载面。这是操作系统、体系结构与机器学习三门课在工业界最热的交汇点——欢迎上车。
