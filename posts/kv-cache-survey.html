大模型（LLM）生成文字的方式是"一次写一个词"。为了让第 1000 个词能"回看"前 999 个词，Transformer 的注意力机制必须保留每个历史 token 的两份小向量：Key（键）与 Value（值）。这些向量随上下文线性增长、随模型规模急剧膨胀，被统称为 KV Cache。它既是长上下文能力的基石，也是显存、带宽和成本的头号瓶颈：今天几乎所有推理系统的核心设计，本质上都在回答一个问题："这份缓存，我们能不能少存一点、管好一点、直接别重算、存粗一点、扔掉一点、分层放、或者干脆不用？" 本文按这七条路线梳理二十余项代表性工作，讲解原理到可以动手复现的程度，并盘点 2025–2026 年的最新动态与未来方向。

1预备知识：KV Cache 是什么，为什么它既是救星又是瓶颈

1.1 从注意力的计算说起

Transformer 解码器每一层都有自注意力。对第 t 个 token，模型用它的隐状态 h_t 生成三个向量：查询 q_t、键 k_t、值 v_t。输出是把"当前的问题 q_t"和历史所有 token 的"索引 k_i"逐一比对（做点积、softmax 归一化），再按比对结果加权求和"内容 v_i"：

# 单头注意力的极简版本（省略缩放因子与多头）
score_i = dot(q_t, k_i)                 # 当前问题 vs 每条历史索引
a_i     = softmax(score)[i]             # 归一化成权重，和为 1
out_t   = sum_i(a_i * v_i)              # 按权重混合历史内容

关键在"历史所有 token"这六个字。语言模型逐词生成（自回归），写第 1000 个词时，需要用 q_1000 去比对 k_1 … k_999。如果没有缓存，每写一个词都要把前文 999 个词重新过一遍整个网络算出各自的 k、v。生成一个 1000 词的回答，就要重复上千次 O(N) 甚至 O(N²) 的计算，代价无法接受。

KV Cache 的定义：把已经算好的历史 token 的 k、v 向量存起来（不存 q，因为 q 只在当前步用到），下一步直接读取。这就是典型的"空间换时间"：显存开销线性增长，换来每步解码只需 O(N) 的注意力计算而不必重算整个前缀。

一个直观比喻 把生成过程想象成开卷考试：上下文是一本书，K 是每页书脊上的索引标签（"这页讲什么"），V 是页内的实际内容。每写一个字，你都要拿着当前的问题（q）扫一遍所有标签（算注意力分数），再去翻相关页（加权取内容）。KV Cache 就是你边读边做的笔记：标签和摘录都抄下来，之后不需要回头重读原书。代价：这本书越长，你的笔记本越厚。本文讲的七条路线分别是：换更小的笔记本（压缩/量化）、给笔记本做活页索引（分页）、别人抄过的直接借来用（前缀复用）、只抄重点（稀疏驱逐）、把旧笔记放进书包和储物柜（分层卸载）、以及训练自己"过目不忘"少记笔记（混合架构）。

1.2 两个阶段：Prefill 算力受限，Decode 带宽受限

推理分为两个阶段，两者的瓶颈差异是理解后续所有技术的前提：

  • Prefill（预填充）：读入整段 prompt，所有 token 并行计算。矩阵很大、算术强度（计算量/访存量）高，GPU 算力是瓶颈（compute-bound）。KV cache 在此阶段被一次性写入。
  • Decode（解码）：每次只生成一个 token。每一步都要把整份 KV cache 从显存搬到计算单元，数据搬运远多于计算，显存带宽是瓶颈（memory-bound）。Quest 论文给出实测：Llama-7B 在 32K 上下文下 KV cache 达 16GB，仅读取就 ≥11ms，占单步解码延迟的 50% 以上[35]。
"LLM inference... for relatively small batch sizes, the computation is memory bound... KV cache loading is therefore always memory-bandwidth bound." （在小批量下，LLM 推理是访存受限的……KV cache 的加载始终受限于显存带宽。 —— KVQuant, NeurIPS 2024 · arXiv:2401.18079 · 2024-01[26]

由此得到本文的两条主线：省显存（容量决定能塞多少并发、多长上下文）与省带宽（每步要搬的 KV 字节数决定解码速度）。所有技术都能映射到其中一条或两条上。

1.3 它到底有多大？一本"显存账"

对标准的多头注意力（MHA）模型，KV cache 大小的经典公式（PagedAttention 论文中亦给出）为：

KV_bytes = 2 × batch × seq_len × n_layers × n_kv_heads × head_dim × dtype_bytes
           └K,V┘   └── 每条请求 ──┘ └────── 每 token 每层 ──────┘

代入第 0 节表格中的三个模型即可感受到量级差异：70B 级 MHA 模型每 token 约 2.6MB，128K 上下文单请求约 340GB。这意味着不经任何优化，长上下文服务在物理上不可能。而每 token 70KB 的 MLA 模型，只看 KV 字节数可容纳多条 128K 的缓存；能否实际部署还须扣除全量权重、工作区与运行时显存，不能据此声称 671B MoE 单卡可部署。七条技术路线，就是从公式中的每一个因子下手：n_kv_heads（结构压缩）、dtype_bytes（量化）、有效 seq_len（稀疏/驱逐）、被同时保留的 batch × seq_len（分页/复用/卸载）、乃至"还要不要这个公式"（混合架构）。

最后补一个系统视角：vLLM 论文实测，服务 13B 模型时显存里权重占约 65%，KV cache 可占 30% 以上，且随批大小增长。KV cache 的管理方式直接决定最大批大小，从而决定吞吐[12]。

3结构压缩：让每个 token 少存一点

这条路线直接修改注意力结构，从公式 n_kv_heads × head_dim 入手。它需要（重新）训练模型，但收益是一次性的、永久性的，且对上层系统完全透明，所以它是"性价比最高的第一步"。

3.1 MHA → MQA → GQA：共享 KV 头

问题：标准 MHA 中每个注意力头都有自己的一套 K/V。假设 64 个头，KV cache 就有 64 份。但 K、V 的作用只是"索引"和"内容"，不同头之间真的需要 64 套完全不同的索引吗？

MQA（Multi-Query Attention，2019）：Shazeer 提出让所有查询头共享唯一一组 K/V 头，KV cache 直接缩小 64 倍（头数倍）。代价是质量略降、训练不稳定。

"We propose a variant called multi-query attention, where the keys and values are shared across all of the different attention 'heads', greatly reducing the size of these tensors and hence the memory bandwidth requirements of incremental decoding." 我们提出一种称为多查询注意力的变体：键和值在所有注意力"头"之间共享，大幅缩小这两个张量，从而降低增量解码的显存带宽需求。 —— Shazeer, "Fast Transformer Decoding: One Write-Head is All You Need" · arXiv:1911.02150 · 2019-11[3]

GQA（Grouped-Query Attention，2023）：谷歌发现 MQA 走得太远，于是把 64 头分成 G 组（例如 8 组），组内共享一套 K/V。GQA-1 等价于 MQA，GQA-H 等价于 MHA，中间任意档位可调。更有工程价值的是升级配方：把已有 MHA 检查点每组的 K/V 权重做平均池化合并，再只用原预训练 5% 的算力继续训练，就能得到一个几乎不掉点的 GQA 模型。

"We (1) propose a recipe for uptraining existing multi-head language model checkpoints into models with MQA using 5% of original pre-training compute, and (2) introduce grouped-query attention (GQA)... We show that uptrained GQA achieves quality close to multi-head attention with comparable speed to MQA." 我们（1）提出一种只用原预训练 5% 算力、将现有多头检查点升级为 MQA 的再训练配方，并（2）提出分组查询注意力（GQA）……升级后的 GQA 质量接近多头注意力，速度接近 MQA。 —— Ainslie et al., GQA · EMNLP 2023 · arXiv:2305.13245 · 2023-05[4]

GQA 随后被 Llama-3、Qwen2/3、Mistral、MiniMax-M2 等几乎所有主流开源模型采纳，是当前全注意力模型的事实默认结构。直觉上它把"64 份笔记"压缩到"8 份笔记"，每个 token 的缓存缩小 8 倍，解码时需要搬运的数据同步缩小 8 倍。

3.2 MLA（Multi-head Latent Attention）：把 KV 压进"潜在向量"

DeepSeek-V2（2024-05）给出另一种压缩思路：不共享头，而是低秩压缩。注意力的 K、V 都由同一个输入 h_t 经过两个大矩阵 W^K、W^V 投影而来。模型通过训练学习受低秩约束的联合投影，不能仅由输入相同推出投影结果天然低秩。MLA 干脆先算一个低维的"潜在向量" c_t，把 c_t 存进缓存；概念上可上投影为各头 K/V；高效 decode 将 K 的上投影吸收到 query，将 V 的上投影合并进输出投影，从而避免显式展开所有历史 K/V。

# MLA 简化伪代码（依据 DeepSeek-V2/V3 论文与开源实现整理）
c_kv = W_dkv @ h_t          # 下投影：d_model → kv_lora_rank(=512)，所有头共享！
k_rope = W_kr @ h_t         # 位置相关部分单独算：→ qk_rope_head_dim(=64)
# —— 以上两项（576 维）才是需要缓存的东西，与头数无关 ——

# 解码时从 latent 还原 K、V（矩阵可预先合并，见下）
k_C = W_uk @ c_kv           # 还原出各头的“无位置”部分
v   = W_uv @ c_kv           # 还原出各头的 V
k   = concat(k_C, k_rope)   # 与 RoPE 部分拼接得到完整 K
# 注意力照常：q @ kᵀ → softmax → @ v

DeepSeek-V3 实际配置：61 层 × (512 + 64) 维 × 2 字节(bf16) ≈ 70 KB/token。作为对比，Llama-3-70B（GQA）约 320 KB/token，而 Llama-1-65B 这类 MHA 老模型约 2.6 MB/token（Llama-2-70B 本身已用 GQA）。

这里有个绕不开的细节：为什么位置编码部分要单独拎出来？主流模型用 RoPE（旋转位置编码），它把位置信息乘进 K 向量。如果对带 RoPE 的 K 做低秩压缩，还原时的矩阵乘法会与旋转操作"打架"（旋转依赖 token 位置，而缓存的对端是任意位置的 query）。DeepSeek 的解法是解耦：无位置信息的部分走低秩 latent（512 维），带 RoPE 的键单独小份缓存（64 维），两头拼接后参与注意力。这就是论文中"Decoupled RoPE"一节的内容。

收益与代价：DeepSeek-V2 相对其前代 67B 模型，KV cache 减少 93.3%、最大生成吞吐提升 5.76×，这是整模型比较，包含 MoE 等设计变化；MLA 的质量和吞吐独立贡献需看受控消融[5]。代价在系统侧：显式重建和矩阵吸收是不同执行路径，后者避免完整历史 K/V 展开；瓶颈由实际形状、batch、核与并行布局决定，不能从"必须还原"推导。另外，KV 头只有"1 个 latent"，张量并行（TP）无法像 GQA 那样沿 KV 头切分，这对多卡部署是个长期痛点（2025–2026 年出现 FastDecode、MLA-TP 等专门优化）。即便如此，MLA 已被 DeepSeek-V2/V3/R1/K2、Kimi K2、Kimi Linear 等旗舰模型采用，是结构压缩路线目前的天花板。

机制与结果转述（非原文直引）：MLA 缓存压缩 latent 与解耦位置键；DeepSeek-V2 摘要的模型级比较还包含 MoE 等变化。 42.5% / 93.3% / 5.76× 是 DeepSeek-V2 整模型相对 DeepSeek 67B 的报告结果，不作为 MLA 的独立贡献。 —— DeepSeek-AI, DeepSeek-V2 · arXiv:2405.04434 · 2024-05（V3 技术报告 arXiv:2412.19437 · 2024-12 延续该设计[6]）

3.3 跨层共享与滑动窗口：另外两个"结构因子"

跨层共享（depth 方向）。既然相邻层语义相近，KV 能不能隔层存一份？两条 2024-05 的工作给出肯定答案：YOCO（You Only Cache Once，微软）由 self-decoder 输出构造全局 KV，供上层 cross-decoder 通过 cross-attention 共享；self-decoder 使用固定窗口或递归状态，缓存复杂度 O(N+CL)，而标准 Transformer 为 O(NL)（N 为长度、L 为层数、C 为固定状态/窗口常数），并非固定减半。CLA（Cross-Layer Attention）让相邻层共享 KV，在 T5/LLaMA 上换得近半压缩且基本不掉点[7][8]。免训练的版本是 NeurIPS 2024 的 MiniCache：推理时把相邻层高度相似的 KV 状态合并，沿"深度维"压缩最高 8×[9]。这条线的工业化程度不及 GQA/MLA（调度复杂），但可与部分压缩路线组合，但需验证训练目标、位置编码及实现布局是否兼容。

滑动窗口（序列方向）。Mistral 7B（2023-10）把滑动窗口注意力（SWA）带入主流：每个 token 只看最近 W 个 token（如 4096），于是 KV 也只需保留最近 W 个，缓存不再随长度无限增长，变成 O(W)[10]。窗口注意力的隐患在 2023 年被 StreamingLLM 揭示：把开头几个 token 驱逐后会"雪崩"（详见第 7.2 节的 attention sink）。2025 年起，工业界把 SWA 与全局注意力交替使用来兼得两边好处：Gemma 3（2025-03）按 5:1 混合局部滑窗（窗口 1024）与全局层[11]；OpenAI 的 gpt-oss（2025-08）同样采用"滑窗层 + 全局层交替"，只是把"保住开头的 sink token"改成了更优雅的"每个头学一个加在 softmax 分母上的偏置"，等价于把 sink 内建进了模型[55]。Llama 4（2025-04）则用 iRoPE（部分层去掉 RoPE）配合注意力层交替来支撑超长上下文[56]。注意：交替滑窗模型的 KV 管理更复杂，全局层要全量缓存、滑窗层只需窗口内的，vLLM V1 为此专门引入了"混合 KV 组"调度（见 4.2 节源码）。

结构压缩小结 压缩因子从何而来？共享 KV 头（GQA，8×）、低秩 latent（MLA，~10–90× 视基线）、跨层共享（CLA 按组共享；YOCO 为 O(N+CL)，收益随层数和序列长变化）、限窗（SWA，封顶 W）。原生 GQA/MLA/YOCO/CLA 通常需要训练或适配；MiniCache 则是推理时压缩，不能归为全部需要再训练，因此演进节奏由预训练周期决定。这也是为什么 2023 年的系统技术（分页/复用）能立刻部署，而结构红利要到 2024–2025 年的模型换代才兑现。

3.4 低秩缓存也改变通信账本

11-02 的 BasisKV 把 V 缓存宽度与 TP 通信量联系起来。低秩 V 表示可与输出投影结合，跨 GPU 分区联合拟合完整注意力输出；同一表示还能辅助选择 K 页。选中页取原始 K 计算精确 QK，并不意味着整个稀疏注意力与全量注意力完全相同。它提示缓存压缩的比较表应同时列字节数、通信量、质量与端到端延迟，不能只看压缩比。[R26:BASIS]

4分页管理：把操作系统搬进 GPU 显存

结构决定"存多少"，系统决定"怎么存"。2023 年之前，推理框架为每条请求预分配一段连续显存存放 KV，问题与早期操作系统遇到的内存碎片一模一样，vLLM 的贡献就是把"虚拟内存 + 分页"这套 60 年前的方案完整搬进了 LLM 推理。

4.1 PagedAttention / vLLM（SOSP 2023）

旧方案的两种浪费：① 内部碎片：输出长度事先未知，只能按最大长度预留（按 2048 预留、实际生成 200，浪费 90%）；② 外部碎片：各请求预留长度不一，反复分配释放后显存被切碎。vLLM 实测当时主流系统（FasterTransformer/Orca）中，真正存着 token 状态的显存只占 20.4%–38.2%；此外 beam search 等多条序列共享前缀时只能各存一份（冗余复制）[12]。

"We propose PagedAttention, an attention algorithm inspired by the classical virtual memory and paging techniques in operating systems. On top of it, we build vLLM... achieves (1) near-zero waste in KV cache memory and (2) flexible sharing of KV cache within and across requests... vLLM improves the throughput of popular LLMs by 2-4× with the same level of latency." 我们提出 PagedAttention——一种受操作系统经典虚拟内存与分页技术启发的注意力算法，并在此基础上构建 vLLM……实现（1）KV cache 显存近零浪费，（2）请求内与跨请求的灵活 KV 共享……在论文 2023 年评测、同等延迟下相对 FasterTransformer/Orca 的吞吐提升 2–4 倍。 —— Kwon et al., SOSP 2023 · arXiv:2309.06180 · 2023-09[12]

做法（与 OS 分页一一对应，可以直接类比的术语用括号标注）：

  • 把每条请求的逻辑 KV 序列切成固定大小的 block（页，vLLM 默认 16 token/块），按需分配（ demand paging）；
  • 每个请求维护一张 block table（页表）：逻辑块号 → 物理块号。逻辑连续、物理可以不连续；
  • 注意力内核按块取数计算，块内连续、块间跳转，这正是 FlashAttention 的分块计算天然支持的形状；
  • 块粒度的引用计数与 copy-on-write（写时复制）：并行采样/beam search 的多条序列先共享同一物理块，真要写时才复制，解决冗余；
  • 显存不足时按请求粒度换出（swap）或重算（recompute）作为"抢占式调度"的恢复手段。

        self.block_pool = self.coordinator.block_pool      # 统一物理块池

    def get_computed_blocks(self, request):
        """前缀缓存查找：返回与该请求 prompt 前缀相同的已缓存块。"""
        if not self.prefix_cache_lookup_enabled(request):
            return EMPTY, 0, 0
        # 注意 -1：全命中时也要重算最后一个 token 以拿 logits
        max_cache_hit_length = request.num_tokens - 1
        computed_blocks, n_hit, n_uncached = (
            self.coordinator.find_longest_cache_hit(
                request.block_hashes, max_cache_hit_length))
        return computed_blocks, n_hit, ...

    def allocate_slots(self, request, num_new_tokens, ...):
        """三步分配：①释放滑窗已滑出的块 ②接上前缀命中块 ③为新城分配块。

            return None                               # —— 这就是批大小的天花板
        self.coordinator.allocate_new_blocks(request.request_id, ...)
        self.coordinator.cache_blocks(request, num_tokens_to_cache)  # 写哈希进缓存

几个工程细节：① 前缀缓存以块哈希为单位（token 序列 + 模型/LoRA 等命名空间信息一起哈希），命中即免 prefill；② 滑窗模型中"滑出窗口"的块会被立即回收（remove_skipped_blocks），这就是 3.3 节说的交替滑窗模型的 KV 管理方式；③ 2025 年后的 vLLM 已原生支持 Mamba/混合层：RNN 状态作为一种新的"块类型"参与同一套池子，这为第 9 节的混合架构铺平了系统侧道路。

5前缀复用：能不算，就不算

因果注意力有个美妙性质：第 t 个 token 的 K/V 只取决于它前面的 token（前缀），与后面的内容无关。因此两条请求只要开头相同，且在相同模型权重、token、位置、适配器和执行语义下，前缀 KV 就可以直接借用；换了浮点 kernel 或 batch，逐比特一致并不保证。这条路线不省单条请求的显存，而是省掉重复的预填充计算，并大幅降低首 token 延迟（TTFT）。

5.1 RadixAttention 与 vLLM 的自动前缀缓存

哪里来的重复？处处都是：系统提示词（几 KB 的固定开头）、few-shot 示例、多轮对话的历史、Agent 每轮带上的完整轨迹、RAG 检索到的同一批文档……SGLang 论文在 Chatbot Arena 生产环境实测：Vicuna-33B 的请求前缀缓存命中率 74.1%，多模态 LLaVA-Next-34B 为 52.4%，命中使 TTFT 平均改善 1.7×[16]。

SGLang / RadixAttention（2023-12）的核心是把"哪些前缀被缓存了"组织成一棵基数树（radix tree：压缩版前缀树，一条边上可以存一段 token 而不是单个 token）。每条请求结束时，把它的 token 序列和对应 KV 物理块索引插入树中；新请求到来时沿树匹配最长前缀，命中的块直接引用（免 prefill），未命中的尾部才计算。整棵树按 LRU 从叶子向上驱逐，正被运行中请求引用的节点加引用计数保护。

"The first technique, RadixAttention, enables the automatic reuse of the KV cache across multiple generation calls... our system maintains an LRU cache of the KV cache for all requests within a radix tree... Experiments show that SGLang achieves up to 6.4× higher throughput compared to state-of-the-art inference systems." 第一项技术 RadixAttention 实现跨多次生成调用的 KV cache 自动复用……我们的系统在一棵基数树中维护所有请求 KV cache 的 LRU 缓存……实验显示 SGLang 相比当时最优系统最高取得 6.4× 吞吐。 —— Zheng et al., SGLang（RadixAttention 论文亦见 NeurIPS 2024 ENLSP Workshop）· arXiv:2312.07104 · 2023-12[16]

6量化：把 16 比特的笔记抄成 2 比特的速记

结构压缩要动模型，量化不用：保持结构不变，把每个 K/V 元素从 FP16（16 bit）压到 INT8/FP8（8 bit）、INT4（4 bit）甚至 INT2（2 bit），显存与带宽线性下降。难点在于 KV 是推理时动态生成的激活值（不像权重可以离线慢慢校准），且分布相当"刁钻"。

6.1 一个关键观察：K 和 V 的分布长得很不一样

KIVI（ICML 2024）对主流模型 KV 逐元素分析后发现两个事实，成为超低比特量化的理论地基[25]：

  • Key 沿"通道"（每个维度）出现固定离群值：少数几个维度的数值长期巨大。若按 token 量化（每个 token 内 128 维共用一组 scale），这些大值会把整个量程撑爆，其余维度全部"糊掉"。→ K 应按通道量化：同一维度跨所有 token 用一组参数。
  • Value 没有明显的通道离群，但必须按 token 量化：因为注意力输出是对 V 按注意力权重加权求和，且注意力高度稀疏（少数重要 token 主导输出）。按 token 量化能把每个 token 的误差锁在自己身上，不污染"重要 token"；按通道量化误差会跨 token 串扰，实测注意力输出误差大近 15×。
"Our findings indicate that the key cache should be quantized per-channel... In contrast, the value cache should be quantized per-token. From this analysis, we developed a tuning-free 2bit KV cache quantization algorithm named KIVI." 我们的发现表明，Key cache 应按通道量化……相反，Value cache 应按 token 量化。基于该分析，我们提出了免调参的 2 bit KV cache 量化算法 KIVI。 —— Liu et al., KIVI · ICML 2024 · arXiv:2402.02750 · 2024-02[25]

流式难题与解法：按通道量化要求"跨 token 聚合统计"，但解码时 token 是一个一个来的。KIVI 的方案是把缓存切成两段：凑满一组的旧 token 做通道量化存储；最近 R 个 token（R≤128）保留 FP16 作为"残差窗口"，读写都按块对齐的矩阵分块完成。效果：Llama/Falcon/Mistral 上 2 bit 几乎不掉点，含权重的峰值显存降 2.6×，批大小最大 4×，吞吐提升 2.35–3.47×。量化伪代码：

# KIVI 风格的量化/反量化（示意）
def quantize_group(x, scale, zero_point, bits=2):        # 非对称量化
    return min(2**bits - 1, max(0, round(x / scale) + zero_point))  # 标量示意；scale>0，无符号 b-bit 裁剪
def dequant(q, scale, zero_point):
    return (q - zero_point) * scale

6.2 KVQuant：向着 1000 万 token 上下文

同一时期的 KVQuant（NeurIPS 2024）来自 UC Berkeley，目标是极致压缩比下的长上下文服务，方法上是 KIVI 观察的"系统化加强版"[26]：

  • Pre-RoPE 量化：RoPE 会打乱通道离群值的稳定性，所以对旋转之前的 Key 量化（与 MLA 的"RoPE 解耦"思想殊途同归）；
  • 非均匀码本（NUQ）：用敏感度加权的 k-means 在校准集上离线学出每层的量化"刻度"分布，而不是均匀网格；
  • 稠密+稀疏分解：每个向量挑出约 1% 的离群值单独以 FP16 稀疏存储，其余用低比特码本（per-vector 阈值，离线/在线分工）；
  • Sink 感知：第 1 个 token（attention sink，见 7.2）保持全精度，2 bit 下困惑度改善显著。
"By removing only 1% of outliers... Our method enables serving LLaMA-7B with a context length of up to 1 million on a single A100-80GB GPU and up to 10 million on an 8-GPU system." 只需分离 1% 的离群值……我们的方法可在单张 A100-80GB 上以最高 100 万上下文服务 LLaMA-7B，在 8 卡系统上最高 1000 万。 —— Hooper et al., KVQuant · NeurIPS 2024 · arXiv:2401.18079 · 2024-01[26]

6.3 工程现状（FP8 的支持与默认值依实现而定）与 2026 前沿（自适应比特）

生产环境的第一个落点是 8 bit：vLLM 的一条命令 --kv-cache-dtype fp8 即可将 KV 减半，显存翻倍地装 token，数据载荷约减半；实际质量取决于 scale 校准、模型、任务和敏感层，不能普遍称无损[27]；TensorRT-LLM 同期支持 INT8/FP8。NVIDIA 进一步在 Blackwell 上推出 NVFP4（4 bit 浮点）KV cache，面向长上下文与大批量场景[28]。到 2025 年，"FP8 KV + GQA/MLA + 分页 + 前缀缓存"是部分引擎支持的可选组合，是否默认与可兼容须按具体版本/模型核对。

2026 年学界方向：从"统一比特"走向"按重要性分配比特"。"Don't Waste Bits!"（arXiv:2604.04722，2026-04）按注意力显著性给不同 token 自适应分配比特数：重要 token 高精度、次要 token 激进压缩[29]；同期的变换编码视角（arXiv:2608.14191，2026-08）把 KV 量化统一到信号压缩的变换编码框架下重新设计[70]；多模态 KV（视频 token 爆炸）的量化也开始出现专门工作。另一个现实问题被 NVIDIA Research 点破：实验室压缩率与生产系统之间存在鸿沟，量化 KV 与分页、驱逐、重排、稀疏内核的组合工程才是量产瓶颈[74]。

量化的边界 超低比特（≤2 bit）下长上下文检索类任务的精度衰减仍是公开难题；离群通道/sink token 必须特殊照顾；与驱逐策略叠加时"重要 token 高精度"与"驱逐不重要 token"需要联合设计。这正是 2026 年自适应比特与"分辨率-覆盖度联合分配"（arXiv:2608.07001）等工作的出发点[66]。

6.4 扩散语言模型：量化前，缓存就可能已经过时

7稀疏与驱逐：注意力本来就"偏心"

量化改"存多粗"，本节改"存多少"：既然注意力的概率质量高度集中在少数 token 上，那么大部分 KV 也许根本不用留。这条线分两档：训练无关（拿现成模型直接扔）与训练时原生稀疏（让模型从预训练起就学会稀疏地看）。

7.1 两个奠基性观察

观察一：注意力矩阵在推理时超过 95% 是稀疏的（H2O 的实测）。少数"重击者"（Heavy Hitter）token 累积了大部分注意力分数，且它们的出现与文本中的高频共现词高度相关。H2O 的驱逐策略因此极其简单：每一步保留"累积注意力分数最高的 k 个 token + 最近的若干 token"，其余扔掉。20% 预算即可保持与全量 KV 相当的精度，KV 显存降 5×，在 FlexGen 之上吞吐最高 3×（对比当时的 DeepSpeed/HF Accelerate 达 29×）[30]。

"Our approach is based on the noteworthy observation that a small portion of tokens contributes most of the value when computing attention scores. We call these tokens Heavy Hitters (H2)." 我们的方法基于一个值得注意的观察：计算注意力分数时，一小部分 token 贡献了大部分价值。我们称这些 token 为"重击者"（H2）。 —— Zhang et al., H2O · NeurIPS 2023 · arXiv:2306.14048 · 2023-06[30]

观察二：attention sink，开头的几个 token 会"吸走"海量注意力。StreamingLLM（ICLR 2024）发现朴素滑窗注意力（只留最近 L 个 token）会在文本超过窗口长度时突然崩溃（困惑度从 5 飙到 5000+），而把最初 4 个 token 的 KV 加回来就恢复正常，哪怕把这 4 个 token 换成无意义的换行符也一样。解释：softmax 要求权重和为 1，当 query 与谁都"不搭"时，模型需要有个地方"倾倒"多余注意力；开头的 token 因为被所有后续 token 看到过，最容易被训练成这种"排水口"。据此 StreamingLLM = 4 个 sink token + 滑动窗口，让 Llama-2/MPT/Falcon 稳定处理 400 万+ token 流式输入，比"滑窗重算"方案快 22.2×[32]。

"We observe an interesting phenomenon, namely attention sink, that keeping the KV of initial tokens will largely recover the performance of window attention... StreamingLLM can enable Llama-2, MPT, Falcon, and Pythia to perform stable and efficient language modeling with up to 4 million tokens and more." 我们观察到一个有趣的现象——attention sink：保留最初几个 token 的 KV 能大幅恢复窗口注意力的性能……StreamingLLM 可使 Llama-2、MPT、Falcon、Pythia 稳定高效地建模高达 400 万甚至更长的 token。 —— Xiao et al., StreamingLLM · ICLR 2024 · arXiv:2309.17453 · 2023-09[32]
为什么 sink 现象如此重要？ 它解释了此后一整串工程与结构选择：KVQuant 把第 1 个 token 保留 FP16（6.2 节）；H2O 发现重要 token 大量出现在句首；gpt-oss 把 sink 做成每头可学习的 softmax 偏置（3.3 节）；2026 年对"massive activation 与 sink 形成机制"的研究仍在继续。可以说 sink 是 KV cache 领域被引用最多的"反直觉事实"。

7.2 训练无关的驱逐策略谱系

在 H2O 与 StreamingLLM 之后，2024 年出现一批精细化改进，核心分歧在于"用什么信号判断重要性"与"什么时候做决定"：

H2O[30]2023-06历史累积注意力分数每步解码时在线驱逐开山之作；需记录累积分数

7.3 Quest：不驱逐，改成"按 query 按需取用"

驱逐类方法有个致命弱点：扔掉的是不可逆的，而"哪个 token 重要"其实取决于未来要问什么。Quest（ICML 2024）改成"全部保留、按需取用"：KV 照常分页存储在显存（或更大存储）中，每页维护一个极小的元数据：Key 每个维度的 min/max。解码时用当前 query 与每页的 min/max 做一次保守估计（区间上界），只把得分 Top-K 的页真正读进注意力计算。页大小 16 时访存约为全量的 1/16 + K/页数；32K 上下文自注意力提速 7.03×，配合 4 bit 权重端到端 2.23×，且在 passkey 检索等长依赖任务上几乎无损。反观 H2O/TOVA/StreamingLLM，在"先给材料后提问题"的设定下接近全错，因为答案 token 早被扔了[35]。

"However, we observe the criticality of a token highly depends on the query. To this end, we propose Quest, a query-aware KV cache selection algorithm. Quest keeps track of the minimal and maximal Key values in KV cache pages and estimates the criticality of a given page using Query vectors." 然而我们观察到，一个 token 是否关键高度依赖于当前 query。为此我们提出 Quest——一种 query 感知的 KV cache 选取算法：为每页维护 Key 的最小/最大值元数据，用 Query 向量估计每页的关键程度。 —— Tang et al., Quest · ICML 2024 · arXiv:2406.10774 · 2024-06[35]

这条"页级元数据 + query 感知选取"的思路后来被 NSA/MoBA 的原生稀疏设计吸收（见下节），也是 2026 年稀疏注意力索引化的雏形。另一支 MInference（2024-07）专注 prefill 稀疏：长 prompt 预填充时注意力呈"星形/竖线"等固定稀疏模式，按模式跳过计算即可给 1M 上下文的首 token 提速数倍[36]。

7.4 训练时就稀疏：NSA、MoBA 与 DeepSeek DSA

以上方法都作用于"训练好的全注意力模型"，NSA（DeepSeek，2025-02）批评这种"事后稀疏"：理论计算降了、墙上时钟没降（不连续访存、prefill 与 decode 只稀疏了一半、与 GQA 组合时各头选块的并集使访存并不省），且模型没有学过怎么稀疏地看。NSA 把稀疏做进预训练，注意力分成三条并联支路：压缩支路（把历史 KV 块粗粒度压缩成代表 token，捕捉全局）、选取支路（块级 Top-n 精细选取）、滑窗支路（局部细节），门控加权求和。27B 骨干 + 260B token 预训练后，通用/长文/推理基准不掉点甚至更好，64K 序列上解码、前向、反向分别提速 11.6×、9×、6×[37]。

"NSA employs a dynamic hierarchical sparse strategy, combining coarse-grained token compression with fine-grained token selection... (1) We achieve substantial speedups through arithmetic intensity-balanced algorithm design... (2) We enable end-to-end training, reducing pretraining computation without sacrificing model performance." NSA 采用动态分层稀疏策略，把粗粒度 token 压缩与细粒度 token 选取相结合……（1）通过算术强度均衡的算法设计获得实质加速；（2）支持端到端训练，在不牺牲模型性能的前提下降低预训练计算量。 —— Yuan et al., Native Sparse Attention · arXiv:2502.11089 · 2025-02[37]

几乎同时，Moonshot 的 MoBA（2025-02）把 MoE 的门控思想搬进注意力：上下文切块，每个 query 用门控网络选取最相关的少数块参与注意力。滑窗、sink 等静态稀疏都是它的特例。MoBA 已在 Kimi 线上服务长上下文请求，10M token 预填充下注意力比 FlashAttention 快 16×[38]。

"We introduce Mixture of Block Attention (MoBA), an innovative approach that applies the principles of Mixture of Experts (MoE) to the attention mechanism... MoBA has already been deployed to support Kimi's long-context requests." 我们提出块注意力混合（MoBA），把混合专家（MoE）的原理应用于注意力机制……MoBA 已部署用于支撑 Kimi 的长上下文请求。 —— Lu et al., MoBA · arXiv:2502.13189 · 2025-02[38]

2025-09，DeepSeek 把这条线推进到产品：DeepSeek-V3.2-Exp 引入 DSA（DeepSeek Sparse Attention）：一种算子级支持的"闪电式"稀疏索引，以极低成本为每个 query 动态选定少量重要 token 做注意力，官方称在长上下文上兼顾训练与推理效率，上线同时 API 价格下调 50% 以上，vLLM 提供 day-0 支持[39]。DSA 与 NSA/MoBA 一起，标志着"稀疏注意力"从推理 trick 变成了被预训练内化的模型能力，KV cache 问题的解法重心开始从系统侧移回模型结构侧。

驱逐/稀疏的适用边界（2026 年的再评价） RULER 等长上下文基准（arXiv:2404.06654）反复表明：免训练驱逐在预算激进时会伤及多跳检索与长推理[40]。2026 年出现一批"反思"工作：RestoreKV（2026-08）研究查询无关驱逐在紧预算下的性能塌陷与修复[66]；"准确率=证据吗"（2026-08）发现压缩后即使答对了、支撑答案的推理链也可能已受损[68]；DistillCache（2026-08）用 KL 引导的自适应驱逐缓解长推理轨迹下的退化[69]。结论倾向于：对"长推理/Agent"负载，优先用原生稀疏或按需取用（Quest/DSA 类），慎用激进免训练驱逐。

8分层卸载：书桌放不下，就放书架和仓库

GPU 显存（HBM）贵而小，CPU 内存（DRAM）便宜一个数量级，SSD 再便宜一个数量级。KV cache 的一个独特性质是它可以从权重算出来（重算）、也可以存下来（缓存）——何时存、存哪里、何时算，是一道经济学题。分层卸载就是把显存、内存、SSD、远端节点组成金字塔，按"热度"摆放。

8.1 从单机卸载到多级缓存

InfiniGen（OSDI 2024）把完整 KV 放在 CPU，通过轻量预演提前预取下一层需要的 KV：利用当前层输入、下一层部分 query 权重和 key cache 估计注意力重要性。它的重点是跨层预演与传输重叠，不是历史 query 外推，也不是 Quest 的页级 min/max 筛选。预测失误、预取预算、PCIe 带宽与质量之间仍有取舍。[41]

随后系统开始把 KV 当作有生命周期的缓存对象管理：AttentionStore（2024-12）构建 CPU/SSD 两级全局 KV 存储，支撑跨请求复用与 P/D 分离[42]；HCache（EuroSys 2025）研究状态恢复时的数据布局：以 KV 张量原格式（而非 token 重算）高效换入，恢复延迟比"卸载 token、重新 prefill"低数倍[43]；Strata（OSDI 2025）给出缓存感知的层级管理与预取调度，面向企业级多租户复用[44]。这些工作的共同洞察：同一份上下文，"算一次到处存"远比"到处算"便宜，尤其是 Agent/多轮场景里同一前缀会被访问几十次。

8.2 Mooncake：以 KVCache 为中心的分离式架构（FAST 2025 最佳论文）

Moonshot AI 的 Kimi 是长上下文重负载的典型（大量 128K+ 请求、经常过载）。其服务系统 Mooncake 的设计哲学是"一切调度围绕 KVCache 展开"：

  • 预填充/解码集群分离（P/D 分离），各自独立扩缩；
  • 全局 KVCache 池：把 GPU 集群里闲置的 CPU DRAM/SSD 聚合成分布式缓存，分页存储、按块索引；
  • Conductor 全局调度器：请求到来时先看 KV 分布，把请求调度到"已有其前缀缓存"的预填充节点（而非反过来），热块复制多份防拥塞，冷块换出；预填充按层流式产出 KV，边算边通过 RDMA 传给解码节点，与计算重叠；
  • 面向过载的早拒绝：预测解码侧将无配额时提前拒绝请求，避免白白预填充。
"Mooncake... features a KVCache-centric disaggregated architecture that separates the prefill and decoding clusters. It also leverages the underutilized CPU, DRAM, and SSD resources of the GPU cluster to implement a disaggregated cache of KVCache... Under real workloads, Mooncake's innovative architecture enables Kimi to handle 75% more requests." Mooncake 采用以 KVCache 为中心的分离式架构，将预填充与解码集群解耦，并利用 GPU 集群中闲置的 CPU、DRAM 与 SSD 资源实现分布式 KVCache 缓存……在真实负载下，该架构使 Kimi 多承接 75% 的请求。 —— Qin et al., Mooncake · FAST 2025（最佳论文）· arXiv:2407.00079 · 2024-06[45]

模拟场景下吞吐最高提升 525%；论文同时披露前文提过的真实复用率数据（一般负载上限 ~50%，特定场景 ~90%）。2025 年起，Mooncake 的 Transfer Engine（RDMA/多协议 KV 搬运库）与 Mooncake Store 开源，成为多个开源引擎的 KV 后端[45]。

8.3 开源生态：LMCache、NVIDIA Dynamo 与标准化接口

LMCache（UCSD 等团队，arXiv:2510.09665，2025-10）把自己定位为"推理引擎外挂的 KV 缓存层"：以 vLLM V1 的 KVConnector 接口为切入点，提供 CPU 内存/本地盘/分布式存储的分层缓存与跨引擎 KV 传输（P/D 分离），内置 CacheGen 式编码压缩与 CacheBlend 式选择性重算，论文报告企业负载下约 3× 的无损吞吐提升[46]。时间线：2025-04 成为 vLLM V1 首个官方 KV 层集成（含 NIXL P/D 分离），2025-05 与 Mooncake 生态宣布合作互通，2025-07 支持多模态 KV 复用[46][48]。

NVIDIA Dynamo（GTC 2025-03 开源）是数据中心级的推理编排层：在 vLLM/SGLang/TensorRT-LLM 等引擎之上做智能路由、P/D 分离与 KVBM（KV cache 管理器）：把 GPU HBM、主机内存、二级存储统一成跨引擎的 KV 地址空间，2026-03 的 Dynamo 1.0 加入缓存钉扎（pinned cache 抗驱逐）等生产特性；官方报告在 GB200 NVL72 上对 DeepSeek-R1 类推理负载取得最高 30× 吞吐提升[47]。加上 vLLM 的 OffloadingConnector/KVConnector API、Kubernetes 原生的 llm-d 等项目，"KV 缓存层"正在成为独立的基础设施软件品类，地位就像数据库之下的存储引擎。

DeepSeek 的"硬盘缓存"（5.3 节）可以视为这条路线在商业 API 上的最简形态：KV 落盘、命中计费 1/10 价格。从 vLLM 的块池，到 Mooncake 的全局池，再到 Dynamo 的跨引擎池：缓存的作用域在一步步扩大，而每一次扩大都要求更强的哈希、传输与一致性设计。

9混合架构：大部分层干脆不要 KV Cache

前面六条路线都在"优化 KV cache"，最后这条问的是：能不能让大部分层根本不产生随长度增长的缓存？答案来自被 Transformer 打败多年的老朋友——RNN。

9.1 线性注意力 = 固定大小的"记忆"

回忆注意力公式 softmax(qKᵀ)V。将 softmax attention 替换为核化算子（并非与原 softmax 数学等价）；使用特征映射 φ，把 φ(q)(φ(k)ᵀv) 括起来看，会发现它等价于维护一个固定大小的外积记忆矩阵 S，每个 token 到来时做一次递归更新。这就是线性注意力（Katharopoulos et al., 2020）：

# 未归一化内积累积的教学示意；完整核化形式还维护 z=sum(phi(k))，输出除以 phi(q)^T z
# 可运行完整例子见 ../scripts/verify-mechanisms.py；S 维度固定但数值/关联干扰可增长
S_t = S_{t-1} + k_t ⊗ v_t      # 写入：新 token 的 (k,v) 外积累加进记忆
o_t = S_tᵀ @ q_t              # 读出：用当前 q 查询记忆
# 训练时可并行展开（chunkwise），推理时每 token O(d²)，缓存恒为 S ∈ R^{d×d}

裸的累加记忆会把所有历史无差别混在一起，检索能力差。近年的两大改进撑起了这条路线的复兴：门控（给 S 乘衰减因子 α，允许遗忘，Mamba/RetNet/GLA）与 delta 规则（写入前先减去旧关联，"先擦后写"，DeltaNet）。Mamba（2023-12）以选择性状态空间模型的形式证明这类结构可以规模化到 LLM 且吞吐数倍于 Transformer[49]；Griffin（DeepMind，ICML 2024）直接给出了"门控线性循环 + 局部注意力"混合配方的系统研究[50]；Gated DeltaNet（2024-12）则把门控与 delta 规则结合，成为 2025 年混合模型最常用的线性层积木[52]。

但纯线性模型有个理论天花板：S 的大小固定，能记住的 (key→value) 关联数量有限，精确检索（"把第 3 页那个电话号码报出来"）天然吃亏。于是工业界收敛到混合：大部分层用线性注意力（省 KV、解码快），穿插少量全注意力层（负责精确检索）。

直观解释"为什么 3:1 有效"：线性层解决"吞吐与显存"（占 75% 的层没有增长型缓存），全注意力层解决"精确回忆"（每 4 层一次的检索机会足够模型把关键事实锚定住，研究表明只需少数"检索头"就能承载长程回忆）。系统侧也要跟上：vLLM/SGLang 已把 Mamba/线性层状态作为新的"块类型"纳入分页管理（见 4.2 节），2026 年的 Gated DeltaNet-2（arXiv:2605.22791）等继续改进"擦除/写入"的解耦，让固定记忆更聪明[60]。

9.3 一个重要反例：MiniMax-M2 为什么退回全注意力

混合路线并非共识。MiniMax 曾是最激进的推手（MiniMax-01 的 7:1 线性混合），但 2025-10 的 MiniMax-M2 回归了纯全注意力（GQA），并公开复盘原因[57]：

"Hybrid attention performed well on public leaderboards but broke down on higher-order, multi-hop reasoning at scale... Linear attention is currently far more sensitive to numerical precision than full attention..." （要点归纳）混合注意力在公开榜单上表现良好，但规模化后在高阶多跳推理上出现退化；线性注意力目前对数值精度远比全注意力敏感；此外线性状态给前缀缓存带来了实现上的麻烦（缓存复用需要保存/恢复 RNN 状态，与成熟的 KV 前缀树生态不兼容）。 —— MiniMax-AI, "Why Did MiniMax M2 End Up as a Full Attention Model?" · Hugging Face Blog · 2025-11[57]（英文字句为博客原文节选，中文为归纳译文）

这场"3:1 vs 全注意力"的路线之争是 2025–2026 年模型架构最大的分歧点：Kimi Linear 与 Qwen 系押注混合，MiniMax 与部分前沿闭源模型押注全注意力 + 原生稀疏（DSA 方向）。两条路线共享同一个判断：朴素的"每层全量 KV"正在退出历史舞台；分歧只在于用"固定记忆"还是"稀疏索引"来替代它。2026 年的 DeepSeek-V4 据公开技术报告描述走得更远：128:1 的高压缩注意力（HCA）层 + 可训练稀疏索引（CSA/Lightning Indexer），并催生了 Lookahead Sparse Attention 一类"按需取块"的后续研究（arXiv:2606.09079，2026-06）[61]。

11未来发展方向

  1. 近期进展 · 2026-10 下旬
  2. 算法-系统协同设计（co-design）成为默认方法论。NSA 的教训（理论加速 ≠ 墙上时钟加速）已被广泛接受：未来的稀疏/压缩算法必须带着内存对齐、Tensor Core 友好、与 GQA/MLA 兼容的约束去设计；反过来，调度器要理解模型的稀疏模式（如 DSA 的索引）来做预取。2026 年的系统感知综述已把这条列为首要方向[63]。
  3. 稀疏注意力 + 外部索引：KV 变成"注意力专用数据库"。Quest 的页元数据、DSA 的闪电索引、LSA 的前瞻记忆索引器（2026-06）[61]、SeKV 的语义层级[71]指向同一个终局：KV cache 不再是被动的张量堆，而是带索引、可检索、可分级存储的存储系统。学习式索引（哪个 query 需要哪块 KV）是核心开放问题。
  4. 混合线性架构的"容量墙"攻坚。固定大小状态的精确检索上限是理论约束（associative recall 容量 ∝ 状态维度）。GDN-2 的擦写解耦、稀疏状态扩展（Sparse Delta Memory）、核化线性注意力等都在扩容"固定记忆"；另一条路是 3:1 比例的再优化与蒸馏（把全注意力模型"蒸馏"成混合模型以复用存量算力）。
  5. 面向 Agent 与 RL 的缓存语义升级。多轮 rollout 的命中率极高（90%+），但分支/回滚/权重更新（RL 训练时权重在变，缓存必须失效）提出了新语义：CommitKV 的事务化、vLLM 的 reset_prefix_cache、按"轨迹树"组织的 KV 都是早期答案。KV 调度将深度耦合 RL 训练框架（rollout 引擎即缓存引擎）。
  6. 长上下文的经济学：百万到千万 token。KVQuant 的 10M 愿景、Llama-4 的 10M 宣称、Kimi Linear 的 1M 实测吞吐优势，都指向"上下文长度成为定价维度"。多模态（视频 token 动辄数十万）会进一步放大需求；多模态 KV 的压缩与量化刚起步。
  7. 存储与网络硬件的入场。Mooncake 未来工作点名：带宽/美元与带宽/瓦特上，GDDR/LPDDR/存算一体/混合键合内存可能比旗舰 GPU 高一个数量级，解码这类访存受限阶段值得搬到"内存导向"的专用设备；CXL、NVL 互联、以太网 RDMA 上的 KV 传输正在成为新基准测试对象。
  8. 量化与驱逐的联合理论。"分辨率（每 token 比特）× 覆盖度（保留多少 token）"的二维联合优化刚被形式化（arXiv:2608.07001，2026-08）[66]；离群值、sink、检索头的联合保护策略，以及与调度器水位联动的动态预算，都缺统一理论。
  9. 安全与正确性：缓存污染、侧信道与"忠实性"。跨租户共享前缀缓存引入新的攻击面（缓存侧信道、提示注入的持久化）；压缩后"答案对但推理链断"的忠实性问题需要新的评测与修复手段[68]。10-26 的 SGLang×Cloudflare 安全披露让这一条从理论风险变成公开事件：P/D 分离部署下 KV 池容量小于上下文长度、失败请求的 KV 又被提前释放，残留 KV 随后被别的请求读走，155 条响应泄漏了他人 prompt 内容；修复分两步落在 v0.5.21（Mooncake/NIXL 默认隔离）与 v0.5.22（MORI 标记 ack），其余 #43719（deferred release，吞吐代价约 −0.38%）将随 v0.5.23 发布（截至 2026-10-30 未发 tag）[95]。随着缓存成为计费与合规对象，这一支会越来越重要。

  • Agent 场景成为主战场：CommitKV（2026-08）的多轮事务语义[67]、"Learning Agent Execution for KV-Cache Management"（2026-07）学习 Agent 执行流来预测缓存价值[73]。RL 训练与 Agent 服务的 rollout 复用把前缀缓存命中率推到 90%+ 的量级，KV 管理成为 RL 基础设施的核心成本项。
  • 可靠性反思：RestoreKV（2026-08，激进驱逐下的恢复）[66]、KV-Rescue（2026-08，长推理链驱逐损失的步进修复）、推理忠实性检验（2026-08）[68]、KL 引导驱逐 DistillCache（2026-08）[69]。"压缩后答对了但推理坏了"成为新的研究对象。

10.3 2026 年秋（9–10 月）：负结果、统一理论与新交互范式

这一波新工作的共同气质是反思与收敛：有人证明"随机驱逐就能打平 SOTA"，有人用 roofline 模型统一了全部五个技术家族，也有人让模型自己"声明"要读哪段缓存。

① Random Attention：一场"负结果"冲击（Salesforce+UIUC，2026.09）

动机：所有驱逐方法共享同一范式：给每个缓存 token 估计"将来重要性"再保 top。但推理负载下这个信号可能根本没用。

做法与结论：完全不打分，保留 prompt、对每头已生成部分做均匀随机驱逐。结果：4 个模型 × 6 项推理任务上与最强已有驱逐器打平，vLLM 部署吞吐反而高 32–43%（因为省掉了打分开销）。更重要的发现：prompt 才是脆弱部分，选择器之间的差距大多来自 prompt 处理而非历史 token 选择，这对整个"重要性度量军备竞赛"（§7）构成方法论挑战。

"Existing KV cache compression methods share one paradigm: score each cached token by some estimate of how much it will matter later, and keep the top-scoring ones." 现有 KV 缓存压缩方法共享同一范式：用某种对"将来重要性"的估计给每个缓存 token 打分，然后保留得分最高的一批。 —— Wang et al., Salesforce AI Research & UIUC, "Random Attention" · arXiv:2609.03430 · 2026-09-03[79]

② The KV Cache Is the New Memory Wall：统一理论（2026.09）

这篇 28 页立场文用 roofline 模型统一量化五大家族（量化、驱逐、分页、前缀共享、分层卸载），给出可检验的结论：低于特定上下文长度时压缩 KV 几乎没有端到端收益；分页/前缀共享无损但只解决"容量"，量化/驱逐才真正降带宽；并提出统一 KV 表示（单一分页布局同时携带 per-block 精度与保留掩码）与拓扑感知放置（B200 上最高 2×、MI300X 上 8× 的恢复空间），把本文 §11"量化与驱逐的联合理论"方向形式化了[78]。

③ xKV：跨层共享低秩子空间（ICML 2026）

各层 KV 的主奇异向量高度对齐（CKA 验证）→ prefill 时对分组层做联合 SVD，共享一套 token 基 + 每层小重构矩阵；免训练、兼容 MLA。收益：最高 8× KV 压缩；叠加 4-bit 量化达 25.6×；端到端最高 4.23× 加速[80]。与 CLA（§3.3"层间共享"）同一思想的后训练版本。同期 OSCAR（2026.05）用离线谱协方差旋转让 INT2 KV 在长上下文可用[81]；QuantMLA（2026.09）沿 SnapMLA 指出的"MLA×低位量化不兼容"问题做函数对齐的双路量化[84]。

④ PulseInfer：I/O 中心的稀疏 KV 卸载（2026.09）

稀疏 KV 卸载把瓶颈从"GPU 显存容量"转移到"CPU–GPU 召回 I/O"：头级稀疏把召回打碎成大量小 PCIe 传输，同步系统 GPU 利用率仅 ~35%。PulseInfer（华中科大等）按召回量的层间/请求间波动动态组织传输、聚合碎片化召回，让"按需取块"（Quest 式）与"分层卸载"（§8）真正吃到容量收益[82]。

⑤ Declarative Attention：让模型自己声明读哪段 KV（2026.09）

零训练、纯提示协议：模型在思维链里用 <global>/<focus>/<local> 标签声明自己的注意力范围，推理引擎（vLLM）像解析工具调用一样解析标签、重写 KV 块表，让 FlashAttention 内核直接跳过被掩块，把"KV 是数据库，模型来发查询"变成了现实；由此提出可逆上下文压缩（只掩不删、可恢复）。收益：Gemma-4-31B 平均注意 token −52.0%，精度仅降 1.27 点；roofline 估计 B200 解码墙钟降到 0.71×[83]。

2026 秋的三个信号① 重要性打分可能被高估（Random Attention），驱逐研究的评测方法需要重新设计；② KV 研究从"各自为战"走向统一理论（Memory Wall 的 roofline 框架 + 联合优化目标）；③ 模型与缓存的交互成为新界面（Declarative Attention、CommitKV 的事务语义），"面向 Agent 的缓存语义"正在成型。
2026 年的一条主线判断如果 2023 年的关键词是"分页"，2024 年是"复用与压缩"，2025 年是"分层与混合"，那么 2026 年的关键词是"以 KV 为中心的算力经济学"：模型结构（MLA/稀疏/混合）决定 KV 的"产量"，缓存系统（Mooncake/LMCache/Dynamo）决定 KV 的"周转率"，而 API 计费（写贵读廉）把这一切翻译成价格信号反馈给应用开发者。学界与业界的努力正在这三层之间打通接口。

① Dynamo 会话感知推理（NVIDIA，2026-10-08）：KV 策略的"大脑"上移到路由器

动机：Agent 会话在工具调用间隙让 KV 长驻显存，请求级路由只看单轮、无视会话工作集，缓存反复抖动。

贡献：以统一 Session ID 为核心原语（开箱识别 Claude Code / Codex / OpenCode 的会话头），把请求级基础设施升级为"程序感知"系统：会话感知准入控制（工具边界背压）；与 Mooncake 团队合作的 shared-pool indexer（跨引擎共享池计入路由成本函数）；"程序化 KV 缓存" KvHint 接口（Share / Prefetch / Demote / Pin / Retain 五类软提示）。

收益：SWE-bench 双 MiniMax-M2 副本吞吐 +12–16%；agentic RL rollout 高并发下 +11.0–14.6%，前缀命中率全程 >94.5%[85]。

"The Dynamo router provides the 'brain' that calculates smart, session/load/cache-aware KV movement policies, while the engine 'executes' the movements that Dynamo mandates." Dynamo 路由器充当"大脑"，计算会话/负载/缓存感知的 KV 迁移策略；引擎则"执行"Dynamo 下达的迁移。 —— NVIDIA, Session-Aware Agentic Inference, pytorch.org Blog · 2026-10-08[85]

② Lachesis（SNU/KAIST/UIUC，2026-10-06）：按"数据活多久"决定放哪层

高带宽闪存（HBF）容量约为 HBM 一个数量级、读带宽同级，但写入寿命有限。Lachesis 指出 Agent KV 的生命周期由 harness 决定且大多可在写入前知晓（reasoning 段 66–83% 的写入只活一轮；lead-agent 段寿命为 sub-agent 的 4.0–6.1×），于是沿时间/结构/worker 三条轴预测寿命、在写入前决定 HBM 或 HBF。收益：HBF 寿命较 HBM-first 延长 1.19–3.13×（紧 SLO 24×7 满载仍超 5 年保修），HBM 吸收 8.2–19.5× 写入量[86]。同期的 HBF 系统表征（UC Berkeley + FuriosaAI）给出 HBM–HBF–host 三级层级与缓冲式缓存感知调度：相对纯 HBM 完成时间 −36.1–87.7%，调度使 HBF 预估写入寿命从 1.21 年延至 14.82 年[87]。§11 方向六"存储硬件入场"落到了具体介质。

③ LORE-KV（2026-10-06）：驱逐该用"未来的 query"打分

对 Random Attention（§10.3①）的正面回应：驱逐发生在未来 query 未知时。与其问"读 prompt 时什么重要"，不如采样 M 条短自回归续写作为"未来轨迹"，按投影 leave-one-out 注意力输出删除代价打分、按轨迹可靠性加权。等精度下缓存效率 1.50–1.63×（128K 领先 AnDPro 达 +11.65 点）；代价是一次性压缩开销 1.46–2.77× 墙钟[88]。问题不在"要不要打分"，而在"用哪组 query 打分"。

④ 商业化：Tensormesh Platform（LMCache 母公司，2026-10-14）

LMCache 团队（CEO 为共同作者 Junchen Jiang，累计融资 $28.5M，投资方含 NVentures / AMD Ventures / CoreWeave）推出首个企业级 KV 缓存管理平台：多级缓存（HBM/CPU/存储）、前缀与非前缀缓存（CacheBlend）、P2P KV 传输、缓存全生命周期控制，vLLM 与 NVIDIA Dynamo 已验证，"KV 是数据"完成了开源 → 商业化闭环[89]。窗口内另见 Kioxia 的 KV-Repurpose 非前缀复用测试床（arXiv:2610.13060）与 Apple 的 KV-Kaizen（arXiv:2609.37988）：存储厂商与端侧厂商相继入场。

① 前缀缓存上互联网：KVCompass（10-16，UC Santa Cruz）

当 provider 在多个地理集群部署同一模型时，KV 复用收益此前被锁死在单集群内。KVCompass 提出发现平面（discovery plane）：跨地理集群共享前缀缓存（arXiv:2610.24179），前缀复用从"跨机器"升级到"互联网尺度"，也为 §5.3 的缓存定价提供了跨区域基础。

② Agent 负载的 KV 常驻实测（10-16，IISc + Microsoft M365 Research）与缓存工程（10-20，清华）

首个生产级 Agent 负载的 KV 常驻（residency）行为刻画（arXiv:2610.22863）：多轮长轨迹下哪些前缀真正被复用、常驻多久，为 Dynamo 的"会话感知"路线补上实证地基。同期清华提出 Cache Engineering for Agents（arXiv:2610.28577）：把 Agent 长轨迹的 KV I/O 与存储当作独立的缓存工程问题系统化。两者共同指向本节判断的落点：面向 Agent 的缓存语义（会话、工具调用、多轮复用）正成为一等研究对象。

③ 低比特 KV 成为出厂默认（10-18/19，vLLM / SGLang）

vLLM v0.32.0：NVFP4 KV cache 从 Blackwell 铺满到 SM8x/SM12x/SM90（含 XQA decode），并覆盖 MiniMax-M3 稀疏注意力；GLM-5.x 在 SM100 默认 FP8 KV（每 rank KV 减半、吞吐 +2.3–5.5%，TTFT 代价 7–11%）；ROCm 新增 4-bit ultraquant KV（密度约 FP8 两倍）。SGLang v0.5.22：FP8 KV 融合进 prefix-valid commit kernel（B200 上该 kernel 2.99×）。§6.3 的"自适应比特"愿景之前，工程界先把统一低比特做成了默认值。

④ 存储/传输生态与多模态（10-11 – 10-21）

Mooncake 主线合入 KV 跨 TP/PP/host 布局的 reshard 重用规划（#4762，跨并行度布局直接复用而不重算）、自适应 RDMA 拥塞控制（#4197）、Intel XPU GPUDirect dma-buf RDMA（#4378）与 Store 多租户配额（#4809），KV 池正朝"跨并行度、跨硬件、多租户"演进。LMCache v0.5.6（10-14）：修复 MP 模式 pickle IPC 的 RCE（安全编号待复核）、admin 端口收敛，新增 SGLang MP 统一 radix cache、原生 NIXL、3FS L2、Kafka 缓存事件流与 Multi-L1。TempoKV（上交+阿里，arXiv:2610.15324，19 票）面向自回归视频扩散做预测式 KV 量化，是 §6.3"多模态 KV 量化刚起步"的最新例证。另：SGLang 修复了混合线性模型在"投机解码 + 结构化输出"同开时 Mamba 状态恢复错误（Baseten 发现）。混合架构的 KV/状态管理仍是大意不得的深水区。

⚡ 10 月下旬快讯（增补 2026-10-30）

  • KVStream（Argonne+RIT+IIT，10-22）：分层 KV 聚合的带宽调度，检索达到带宽界 95%，比 LMCache 高 1.49×、突发负载 TTFT −6.1×[93]。
  • GLM-5.3 破 1M KV 墙（vLLM×Z.ai，10-23）：1M 上下文的 FP8 KV 需 53.4GiB，而单张 H200 权重外仅剩 15GiB；组合 PCP/DCP 上下文并行（DCP 把 KV 轮转切到 8 卡、每卡 6.7GiB）与 Hybrid HiSparse 稀疏注意力后，16×H200 吞吐 1.7–3.2×、TTFT 1.5–5.2s→0.8–0.9s[90]。
  • RAQ-MLA（中科院自动化所+腾讯，10-24）：把 MLA 缓存（含 RoPE 键）整体量化到 ~2.5bit：latent 供 value、RoPE 键主导打分，按"角色"分别变换；推理/代码汇总指标损失 <0.5pp，理论 KV 容量约 6.5×；128K RULER-NIAH 为 79.13 vs BF16 87.22，不能据此说所有长文任务都无损，H20 上 decode kernel 1.38×[91]。
  • ZipFusion（10-24）：无损 KV 解压不再单走一遍 kernel，而是以寄存器位运算融进注意力计算重建 value；H100 decode 比 FlashInfer 快 1.25×，同显存 8K 上下文吞吐 +26.3%[92]。
  • KV 跨请求泄露披露（Cloudflare×SGLang，10-26）：P/D 分离下 KV 池容量小于上下文长度、失败请求的 KV 又被提前释放，残留 KV 被后续请求读出，155 条响应泄漏他人 prompt 内容；修复落在 v0.5.21（Mooncake/NIXL 默认防护）与 v0.5.22（MORI 标记 ack），官方建议运营方升级 v0.5.22+[95]。
  • 偏置折进 Keys（Kanwat，10-27）：把注意力偏置折进 K，不改 FlashAttention/vLLM 内核即可直接服务压缩缓存，14 组对照中 13 组与注意力矩阵方案无差[94]。
